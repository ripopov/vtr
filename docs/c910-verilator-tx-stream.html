Pipeline traces from Verilator, proven on the C910

A small SystemVerilog tracer, attached to an unchanged design, records every instruction as a VTR transaction with its stages, identifiers and flushes. The Verilator fork writes those transactions into the file that already holds the waveforms and the simulation log. Volna's Pipeline and Waves panels then read one run on one timeline.

Proposed 23 September 2026, implemented 26 September 2026. The keyed tracker, the tracker part of the vtr_trace package, the Verilator fork's installation, a demo design with its exact check, the C910 tracer with a differential checker and cost gates, the Volna palette and a standalone sink for other simulators are in the repository. The C910 tracer goes from fetch to retire with member-level stages, dependencies, flushes and the store queue and bus reads behind it; the plan lists the one piece left out. It builds on vtr_clocks.html, which started the vtr_trace package, ships it with the fork together with its sink, adds the signal-free open and the harness time fix, records the C910 clock and makes Volna count pipelines in cycles of a stream's clock. This work extends that package with a tracker for pipeline items and builds on the VTR transaction writer (stages on lanes, status, relations) and Volna's Pipeline panel. Related: pipeline-view.html, tx-detail.html, VDB_APPNOTE.md §2, integrations/verilator.

Try it

There are 282 rows: 137 instructions retire, 104 are wrong-path instructions killed by branch mispredictions, and 41 are still in flight at the right edge. The wave rows at the bottom are the recorded flush and retire signals of the same cycles.

The mock draws in the style of Volna's Pipeline panel so the result is easy to picture; Volna itself opens the same recording. The data is what matters. Every stage boundary comes from a register load the tracer saw at a clock edge, IIDs come from the ROB create ports, and a differential checker replays the tracer's rules over the recorded probe signals and finds the same transactions. The remaining shortcuts are listed under the C910 proof of concept.

What a user does

For the proof of concept, one extra switch on the existing capture script builds the C910 model with the tracer and runs one CoreMark iteration. The recording gains a root tree TX of its own beside the design's signals, with the streams grouped per core:

bench/workloads/c910/capture.sh --pipeline
# volna/volna/examples/c910_coremark.vtr: waves and simulation log under TOP, and
# TX.core0.clk          (kind CLOCK, the core clock)
# TX.core0.pipeline     (kind PIPELINE, generator "instruction")
# TX.core0.store_queue  (kind LSU, generator "store")
# TX.core0.lsu_bus      (kind AXI, generator "read")

A tracer places its streams with a scope path: "^" puts them beside the unit it is bound to, "/TX.core0" in a scope of the file's own that is not part of the instance tree. The C910 tracer takes the group as a parameter (GROUP, default "/TX.core0"), so each core of a cluster gets its own.

In Volna, the stream appears in the scope tree with the pipeline icon and under View ▸ Pipeline. Opening it shows the panel above, linked to the Waves panel's time axis. Clicking an instruction selects it for the Transaction panel. The C910 iteration's stream is 699 MiB once loaded, so raise the object size limit to 1 GiB first, in the memory meter's menu or with memory.objectMiB; with the default 256 MiB Volna refuses the load and offers a retry. vtr tx and the Rust and C readers see ordinary transactions.

Another project using the fork does three things. It writes a tracer module for its core; the API section shows a complete one for a five-stage pipeline. It adds one bind line. And it lists both files on its Verilator command line. The vtr_trace package ships with the fork, and --trace-vtr makes it available without a path:

verilator --cc --exe --trace-vtr \
    my_core_tracer.sv my_core_bind.sv  <design files>  main.cpp

The C++ harness does not change beyond what the clocks proposal already did. The usual VerilatedVtrC open() attaches the tracer's calls to the same file. A run that only needs the pipeline uses the clocks proposal's signal-free open, and is fastest from a model with no signal traced (the C910 build does this with a Verilator configuration file, make model MODE=vtr PIPELINE=1 SIGNALS=0, and runs it with --no-signals). The file then holds only transactions, clocks and log records, which suits runs of millions of cycles. Leaving the tracer files off the command line removes every trace of the feature from the model. Keys are the hardware's own identifiers, narrower than the 64-bit key type, so a tracer module turns off Verilator's WIDTHEXPAND lint around itself.

Other simulators compile core/vtr-capi/include/vtr_trace.sv and integrations/systemverilog/vtr_trace_standalone.cpp with the design, link libvtr and run with +vtr_trace=run.vtr. The same tracer then writes its own file.

Design in seven rules

  1. One run, one file, one timeline. Transactions go through the vtr_writer that already holds the waveforms and the $display log. Their times are simulation times in the file's unit, the same numbers the waves use, so linking the panels needs no conversion.
  2. The design stays untouched. A tracer is an ordinary SystemVerilog module whose inputs are probe signals. It is attached with bind to a module name, or instantiated from the testbench with hierarchical port expressions. Nothing in the RTL changes, and nothing is compiled unless the tracer files are listed.
  3. Tracers describe hardware events; the library owns identity. SystemVerilog code never sees a transaction id. It names instructions by the identifiers the hardware already has: a sequence number the tracer counts, a ROB index, a queue slot, a physical register. A keyed tracker in C++ maps those keys to open transactions and handles re-naming, folding, ordered flushes and reuse.
  4. A call at a clock edge describes what that edge loads. The tracer runs in always @(posedge clk) and sees pre-edge values, which are the load conditions of the pipeline registers. A stage therefore begins at the edge where its register is loaded, and a cell lines up exactly with the waveform of that register.
  5. Record the wrong path. Flushed instructions end with status aborted at the flush edge rather than disappearing. Anything still in flight when the file closes keeps status open. Wrong-path work is much of what a pipeline view is for.
  6. Names in VTR, meaning in VDB. The trace carries a PIPELINE stream, an instruction generator, the stage names of the core's own manual, and identifiers as attributes. Colours, stage roles, dependency anchors and hiding rules belong to a VDB profile. No format change is needed: every item already exists in SPEC §7.
  7. Portable by construction, fastest on the fork. The fork already ships the package and its runtime for clocks, so --trace-vtr is all a Verilator user needs. The package uses only standard DPI-C, so the same tracer also compiles in any other simulator. There, the user lists vtr_trace.sv from the VTR repository and links a small standalone library that writes its own VTR file. With the fork, the calls join the waveform file and cost a few direct function calls per instruction.

Four layers separate the core-specific part from the reusable part. Only the tracer module knows the C910. The package and the tracker know pipelines but no particular core. The sink is the only simulator-specific part.

The SystemVerilog API

A tracer has one job: report, at each clock edge, what happened to the instructions in the pipeline. Examples are "a new instruction was fetched", "the instruction with ROB index 12 entered execute", and "everything younger than this branch was squashed". The vtr_trace package turns such reports into VTR transactions. This section first explains the handful of ideas behind the API, then follows one instruction call by call, then lists every function.

Key concepts

Item
One thing whose life is recorded, here one instruction. Every item becomes one VTR transaction: a begin time, an end time, a status, a list of stages and a set of attributes. The tracer never sees the transaction id; it always refers to an item through a key, described below.
Tracker vtr_tracker_t
The destination for a family of items: one stream and one generator in the file, for example the stream pipeline (kind PIPELINE) with the generator instruction under the core's scope. vtr_pipeline() or vtr_tracker() creates it once, in an initial block, and names the clock its stages are counted in. A tracer can own several trackers, for example one for instructions and one for bus requests. After setup a tracker is needed in only two places: to create its key spaces and to abort everything at once.
Key space vtr_keyspace_t
One kind of hardware identifier within one tracker, for example "sequence number", "ROB index (IID)" or "physical register". Each space is a separate dictionary from key to item. vtr_keyspace(tracker, name) creates it. Spaces exist because instructions change names on the way through a core: the front end knows them by order, the back end by IID. A space belongs to exactly one tracker, so every call that addresses an item takes just the space and the key; the tracker is implied.
Key vtr_key_t
A 64-bit value in a key space, for example IID 57. The pair (space, key) is the complete address of an item, as in "the instruction whose IID is 57". Keys are the hardware's own values, so they repeat. A key is released when its item ends, or when it is moved to another space, and the hardware may then reuse it.
Open, bind, close
vtr_item_open creates an item under a first key and starts its first stage. vtr_item_bind gives an existing item one more key in another space, which is how rename attaches a ROB index to an instruction the front end opened. vtr_item_close ends the item with a status and releases all of its keys.
Stage and lane
A stage is a named interval of an item's life, such as ID, EX or RT. Entering a stage ends the previous stage on the same lane at the same moment, so a tracer reports only entries. A lane is a parallel track of stages in the same item: the default lane holds the main pipeline, and lanes such as stall or mem hold overlapping activity. Entering the stage an item is already in, on the same lane, continues that stage, so a tracer may report a valid bit that stays high for several cycles on every cycle.
Group
One key can name several items. The C910 puts up to three instructions in one ROB entry, and vtr_item_bind_oldest files them all under that entry's IID. Every call made with a group's key applies to each member: a stage, an attribute, or a close.
Status
VTR_TX_OK for a normal end such as retirement, VTR_TX_ERROR for an end that reports a failure, and VTR_TX_ABORTED for a squash. The abort functions end many items at once. Items still running when the simulation stops are written with status open.
Time
Every call takes effect at the current simulation time. No call has a time argument, except the _at forms. These back-date a begin or a stage to a time the tracer saved earlier with vtr_now(), from the package's common part. vtr_now() returns the file's time unit only while a file is open (before that it returns the simulator's precision), so an _at time saved before the file opened is not meaningful.

One instruction, call by call

Here is the life of one instruction in a small out-of-order core, with the call the tracer makes at each clock edge and what the library does in response:

// setup, once
p   = vtr_pipeline("^", "pipeline", "clk"); // stream "pipeline" + generator "instruction"
                                           // in the bound core's scope, counted in its clk
sn  = vtr_keyspace(p, "sn");               // space 1: a fetch sequence number the tracer counts
rob = vtr_keyspace(p, "rob");              // space 2: the ROB index the hardware assigns

// edge 100: fetch accepts the 7th instruction
vtr_item_open(sn, 7, "F");                 // new item; sn 7 names it; stage F starts at 100
vtr_item_attr_u64(sn, 7, "pc", 'h80001f0c);

// edge 101: it is decoded
vtr_item_stage(sn, 7, "D");                // F ends at 101, D starts at 101

// edge 102: rename gives it ROB entry 12
vtr_item_bind(sn, 7, rob, 12);             // the same item now also answers to rob 12
vtr_item_stage(rob, 12, "Q");              // D ends, Q (waiting in the issue queue) starts

// edge 105: issued to execute
vtr_item_stage(rob, 12, "X");              // addressed by its ROB index from now on

// edge 106: result written back
vtr_item_stage(rob, 12, "C");              // complete, waiting to retire

// edge 109: it retires
vtr_item_close(rob, 12, VTR_TX_OK);           // transaction [100, 109], status ok, stages F D Q X C;
                                           // sn 7 and rob 12 are released for reuse

Had a branch mispredicted at edge 104, the tracer would instead call vtr_item_abort_younger(rob, branch_rob). This instruction and every other item opened after the branch would end at 104 with status aborted, and their keys would be released.

The package

The package already exists when this work starts. The clocks proposal created it with a common part (vtr_now and the time units), and the clock part (vtr_clock, vtr_clock_run, vtr_clock_stop), and those stay unchanged. It also set the package rules, which the tracker part below follows. Handles are tagged integers and names are prefixed by the handle they act on: vtr_tracker_*, vtr_keyspace_*, and vtr_item_* for an item addressed by (key space, key). Scope and clock paths follow the package's scope rule. Constructors are called once from an initial block, and the two that place a stream are context imports. Every other function is a plain import taking integers and strings, which Verilator compiles into a direct C call. Calls are safe without a recording, and misuse is counted and reported in the simulation log, as for every part of the package. The tracker part adds the following:

package vtr_trace;
  // … common part and clock part from the clocks proposal …

  // ---- Trackers --------------------------------------------------------------------------------

  typedef int unsigned     vtr_tracker_t;   // a stream + generator that items are written to; 0 = none
  typedef int unsigned     vtr_keyspace_t;  // a key space of one tracker; 0 = none
  typedef longint unsigned vtr_key_t;       // a hardware identifier: sequence number, ROB index, queue slot…
  // How an item ended: the C API's VTR_TX_STATUS_* codes. (vtr.h's VTR_OK = 0 is a call's
  // success, not a status, hence the TX in these names.)
  localparam byte VTR_TX_OK = 1, VTR_TX_ERROR = 2, VTR_TX_ABORTED = 3;

  // ---- Setup (call once, from an initial block) --------------------------------------------

  // Create a tracker: a stream named `stream` of kind `kind` with one generator `generator`.
  // `scope` follows the package's scope rule: "^" for a tracer bound into the unit it traces.
  // `clock` names a clock created with vtr_clock, as a path from the stream's scope or $root;
  // it is stored as the stream's vtr.clock. "" records no clock.
  import "DPI-C" context function vtr_tracker_t vtr_tracker(string scope, string stream, string kind, string generator,
                                                        string clock);

  // Shorthand for a pipeline: vtr_tracker(scope, stream, "PIPELINE", "instruction", clock).
  import "DPI-C" context function vtr_tracker_t vtr_pipeline(string scope, string stream, string clock);

  // Create a key space `name` in tracker `trk`: one more dictionary from key to item.
  // Every item call below names its item by (space, key); the space implies the tracker.
  import "DPI-C" function vtr_keyspace_t vtr_keyspace(vtr_tracker_t trk, string name);

  // ---- Items: create, rename, advance ------------------------------------------------------

  // Create an item named (sp, k) and start its first stage, now. If (sp, k) still names an
  // older item, that item is aborted first and a diagnostic is counted (a missed retirement).
  import "DPI-C" function void vtr_item_open    (vtr_keyspace_t sp, vtr_key_t k, string stage);

  // The same, but the item and its first stage begin at an earlier time t from vtr_now().
  import "DPI-C" function void vtr_item_open_at (vtr_keyspace_t sp, vtr_key_t k, string stage, longint unsigned t);

  // Give the item named (sp, k) one more name (to_sp, to_k), replacing its to_sp name if it
  // has one. Both names stay valid until it ends. to_sp must belong to the same tracker as sp.
  import "DPI-C" function void vtr_item_bind    (vtr_keyspace_t sp, vtr_key_t k, vtr_keyspace_t to_sp, vtr_key_t to_k);

  // Take the n items of space sp that were opened first, remove their sp names, and name them
  // all (to_sp, to_k), as one group. For an in-order stage handing instructions to a ROB entry.
  // Returns how many items moved (fewer than n if sp holds fewer; that is counted).
  import "DPI-C" function int  vtr_item_bind_oldest(vtr_keyspace_t sp, int n, vtr_keyspace_t to_sp, vtr_key_t to_k);

  // Enter stage `stage` on the main lane now; the previous main-lane stage ends now.
  // Entering the stage the item is already in continues it (a valid held for several cycles).
  import "DPI-C" function void vtr_item_stage   (vtr_keyspace_t sp, vtr_key_t k, string stage);

  // The same, but the stage begins at an earlier time t from vtr_now().
  import "DPI-C" function void vtr_item_stage_at(vtr_keyspace_t sp, vtr_key_t k, string stage, longint unsigned t);

  // Enter stage `stage` on the named lane (for example "stall" or "mem"); other lanes are untouched.
  // An empty stage name ends the lane's current stage without starting another.
  import "DPI-C" function void vtr_item_lane    (vtr_keyspace_t sp, vtr_key_t k, string lane, string stage);

  // ---- Items: describe -----------------------------------------------------------------------

  // Record a point event `name` now, for example "replay" or "mispredict".
  import "DPI-C" function void vtr_item_event   (vtr_keyspace_t sp, vtr_key_t k, string name);

  // Set attribute `key` to an integer or a string. A later call with the same key replaces
  // the value; attributes are written when the item ends. Strings are interned.
  import "DPI-C" function void vtr_item_attr_u64(vtr_keyspace_t sp, vtr_key_t k, string key, longint unsigned v);
  import "DPI-C" function void vtr_item_attr_str(vtr_keyspace_t sp, vtr_key_t k, string key, string v);

  // Set the item's caption (the reserved vtr.label attribute), for example "0x2c04 lh a6,0(t1)".
  import "DPI-C" function void vtr_item_label   (vtr_keyspace_t sp, vtr_key_t k, string text);

  // ---- Items: end ----------------------------------------------------------------------------

  // End the item (or every member of the group) named (sp, k) now with `status`, closing its
  // open stages and releasing all of its names.
  import "DPI-C" function void vtr_item_close   (vtr_keyspace_t sp, vtr_key_t k, byte status);

  // Squashes. Each ends the chosen items now with VTR_TX_ABORTED and returns how many it ended.
  // Items opened after the item named (sp, k); that item itself survives. Open order is
  // program order when the tracer opens instructions in program order, as front ends do.
  import "DPI-C" function int  vtr_item_abort_younger(vtr_keyspace_t sp, vtr_key_t k);
  // Every item that still has a name in space sp, for example "everything not yet dispatched".
  import "DPI-C" function int  vtr_keyspace_abort    (vtr_keyspace_t sp);
  // Every open item of the tracker.
  import "DPI-C" function int  vtr_tracker_abort     (vtr_tracker_t trk);

  // ---- Links between items (also across trackers) --------------------------------------------

  // Record a relation of kind `kind` from item A to item B, for example "wakeup" from a producer
  // to a consumer. Both items must still be named when the call is made.
  import "DPI-C" function void vtr_item_relate(string kind, vtr_keyspace_t sa, vtr_key_t ka,
                                               vtr_keyspace_t sb, vtr_key_t kb);

  // Make item B the parent of item A, for example an instruction as the parent of its bus request.
  import "DPI-C" function void vtr_item_parent(vtr_keyspace_t sa, vtr_key_t ka, vtr_keyspace_t sb, vtr_key_t kb);
endpackage

What the library guarantees

  1. Every call is safe without a recording. Trackers and key spaces created before the file opens are replayed at open, like every package declaration. Other calls return at once while no file is open, so a tracer needs no enable flag of its own.
  2. Unknown keys are counted, not fatal. This is the package's misuse rule applied to keys. A stage or close on a key that names nothing is skipped and counted. Opening on a key that still names an item aborts that item first and is counted too. At close, the counts per object go into the file's simulation log as warnings, so a tracer bug shows up in vtr log and in Volna.
  3. Attributes follow "last value wins". The library buffers them and writes them when the item ends, or at the file's close for items still open. A partial PC seen at decode can therefore be replaced by the full PC at retire.
  4. The file keeps its usual meaning. An item is an ordinary transaction, a stage is an ordinary stage, and lanes, events, relations and statuses are those of SPEC §7. Readers need nothing new.
  5. Order within one edge is the tracer's. Calls take effect in the order they are made. Tracers therefore handle the oldest pipeline position first, retire before squash before issue before fetch, as the examples do. An instruction then leaves a key before a younger one takes it. Order is only defined within one always block: with --threads above one, Verilator may run two blocks of the same edge on different threads in either order, so all calls of one tracker belong in a single block, as in both examples.

A complete tracer for a five-stage core

This is the whole reusable story in one screen. The ports are the core's pipeline register load enables. The tracer keeps a shadow of "which instruction is in which stage" as keys, and the hardware's squash rule becomes one call:

module rv5_vtr_tracer (
  input logic        clk,
  input logic        if_fire,  input logic [31:0] if_pc,  // fetch accepts a PC
  input logic        id_load, ex_load, mem_load, wb_load,  // pipeline registers load an instruction
  input logic        retire,   input logic [31:0] wb_insn,
  input logic        squash                                // taken branch in EX kills IF and ID
);
  import vtr_trace::*;
  vtr_tracker_t  p;
  vtr_keyspace_t sn;
  vtr_key_t      n = 0, k_f, k_d, k_x, k_m, k_w;          // identity of each stage's occupant

  initial begin
    p  = vtr_pipeline("^", "pipeline", "$root.tb.clk");   // in rv5_core; the testbench declares tb.clk
    sn = vtr_keyspace(p, "sn");
  end

  always @(posedge clk) begin                              // oldest first
    if (retire)   begin vtr_item_attr_u64(sn, k_w, "insn", wb_insn); vtr_item_close(sn, k_w, VTR_TX_OK); end
    if (wb_load)  begin vtr_item_stage(sn, k_m, "W"); k_w = k_m; end
    if (mem_load) begin vtr_item_stage(sn, k_x, "M"); k_m = k_x; end
    if (squash)   void'(vtr_item_abort_younger(sn, k_x));    // the branch itself survives
    else begin
      if (ex_load) begin vtr_item_stage(sn, k_d, "X"); k_x = k_d; end
      if (id_load) begin vtr_item_stage(sn, k_f, "D"); k_d = k_f; end
      if (if_fire) begin k_f = ++n; vtr_item_open(sn, k_f, "F"); vtr_item_attr_u64(sn, k_f, "pc", if_pc); end
    end
  end
endmodule

// rv5_bind.sv: port expressions resolve inside rv5_core, so the core is not edited.
bind rv5_core rv5_vtr_tracer u_vtr (.clk, .if_fire(if_req && if_gnt), .if_pc(if_addr),
    .id_load(ifid_en && ifid_vld_d), .ex_load(idex_en && idex_vld_d), .mem_load(exmem_en && exmem_vld_d),
    .wb_load(memwb_en && memwb_vld_d), .retire(wb_vld), .wb_insn(wb_insn), .squash(ex_taken));

Reading it with the concepts above:

  • Keys. There is one key space, sn, and the keys are a counter n that increments at every fetch. An in-order core needs no other identifier.
  • Shadow registers. k_f … k_w are the tracer's copy of "which sequence number sits in each stage". They advance with the same load enables as the real pipeline registers.
  • Stage reports. Each vtr_item_stage reports only that an instruction entered a stage. The library ends the previous stage.
  • Squash. vtr_item_abort_younger(sn, k_x) ends everything fetched after the branch in EX, whichever stage those instructions were in, and keeps the branch.
  • Retire. vtr_item_close ends the oldest instruction as ok. The shadow registers of squashed stages are simply overwritten by the next loads.

Verilator binds by module name, not by instance path, and resolves the port expressions in the target's scope. That is enough for a single core or for every instance of one core. A tracer that needs signals from several units, like the C910 one, is bound to the module that contains them all, or is instantiated from the testbench with absolute paths. The existing C910 testbench already reads core internals by hierarchical path for its retire counter.

The C910 proof of concept

The C910 is a hard first customer, which is why it is a good one. It decodes three instructions per cycle, renames and dispatches four, folds up to three instructions into one ROB entry, and runs eight execution pipes. It retires three ROB entries per cycle and flushes in two steps. Its identifiers change on the way. The front end is strictly in order and carries only bits 15:1 of the PC. The 7-bit IID (six index bits and a wrap bit) is assigned at dispatch. All IIDs restart from zero after every ROB flush (ct_rtu_rob.v:4318). The full PC only reappears at retire.

The tracer (bench/workloads/c910/tb/c910_tracer.sv, bound to ct_core by c910_bind.sv) follows that chain with three key spaces. Split instructions add uops between decode and rename, so program order is only final in IR: the tracer numbers instructions in space fe as they enter IR, uops included, and opens each one there, back-dating its ID stage to the edge that loaded it. Instructions a flush catches in ID are opened and aborted at the flush. Issue moves the oldest instructions along. At dispatch each instruction gets a member name in mem (IID × 4 + its position in the entry), then ROB create port k calls vtr_item_bind_oldest(fe, inst_num, iid, iid_k), so a folded entry becomes a group. Retire sets full PCs through the member names and closes the group. A branch cancel aborts the fe space; the ROB flush that follows when the branch retires aborts the iid space. On the flush edge itself the ROB resets its create pointer instead of accepting what the create ports show, so instructions dispatched then are aborted with the rest. IID reuse after a flush is therefore harmless, because every key is released first.

Folded members execute separately, so the entry's stages are not theirs. Dispatch reports each instruction's destination physical register in program order (the PST slots), and the tracer remembers it as that register's producer. When a pipe reads registers, its destination register names the member (ALU and load pipes); other pipes take the entry's first waiting member without a destination. That member's name in mem then receives register read, execute, LSU stages and completion. At its first register read an instruction gets a wakeup relation from the in-flight producer of each source register.

Fetch works per 16-byte block, not per instruction. The tracer follows each block through IF, IP and the IB register, and gives each instruction entering ID the times of the oldest block that holds its PC; IB then includes the wait in the instruction buffer. Instructions the loop buffer supplies get a one-cycle LB stage instead. Two more trackers follow memory. store_queue has one transaction per store queue entry, parented to its store: SQ until commit, CMT until it moves to the write merge buffer, WMB until it pops. Uncommitted entries are aborted by the flush. lsu_bus has the LSU's reads on the core bus, keyed by AXI id and the order of reads with that id. It parents a read-buffer read to the load or store that missed, or to its store queue entry once that store has retired: AR until the first beat, then R.

The heart of the C910 tracer is short, because the tracker does the bookkeeping:

always @(posedge clk) begin
  // … first the previous cycle's registers: LSU and RF valids, IR and ID (see Time) …
  // Retire, oldest slot first. Each slot is one ROB entry of one to three instructions.
  for (int k = 0; k < 3; k++) if (rt_vld[k]) begin
    vtr_item_stage_at(iid, rt_iid[k], "RT", t_prev);
    vtr_item_close   (iid, rt_iid[k], VTR_TX_OK);
  end
  // The ROB flush after a mispredicted branch has retired.
  if (rob_flush) void'(vtr_keyspace_abort(iid));
  // Dispatch: create port k names the oldest instructions in IS by one IID.
  for (int k = 0; k < 4; k++) if (create_en[k] && !rob_flush) begin
    for (int j = 0; j < num[k]; j++) vtr_item_bind(fe, n_disp + 1 + j, mem, create_iid[k] * 4 + j);
    void'(vtr_item_bind_oldest(fe, num[k], iid, create_iid[k]));
    vtr_item_stage(iid, create_iid[k], "IQ");
    n_disp += num[k];
  end
  // A branch cancel or front-end flush: everything not dispatched.
  if (cancel || flush_fe) void'(vtr_keyspace_abort(fe));
  // … completion, launch and IS follow the same pattern …
  t_prev = vtr_now();
end

What the differential check proves

The offline replay that checked the probe map before any simulator work is now the tracer's differential checker. bench/workloads/c910/pipeline_replay.py reads only the 96 probe signals of a capture that also dumped the design, through vtr value and vtr changes, runs the tracer's rules from the start of the run over a Python model of the tracker, and compares the result with the stream the tracer recorded. On one CoreMark iteration (254,773 cycles, capture.sh --pipeline --check):

  • Transactions: the three streams hold 430,816 (411,339 instructions, 18,480 store queue entries, 997 bus reads); the 430,801 that ended before the file closed are identical in times, status, stages, events, attributes and parents, and all 314,177 relations (313,010 wakeup, 1,167 uop_of) match, with none extra.
  • Instructions: 330,196 retired from 230,446 ROB entries, of which 70,485 were folded groups (1.30 instructions per cycle); 81,128 ended aborted on the wrong path and 15 were still open at the end.
  • PCs: decode's PC of the first instruction of every entry matches the core's own retire_inst{k}_cur_pc in 230,446 of 230,446 cases.
  • Program order: in retirement order, each PC follows the previous one sequentially 300,415 times and after a control-flow instruction 29,779 times. It breaks 0 times; one step, the core's first retire after reset, lies outside the program. This is the strongest check that fold groups and the front-end order are right.
  • Members: 281,620 register reads found their instruction by destination register and 90,757 by position; 109 of the 330,196 retired instructions (0.03%) show no execute stage of their own.
  • Fetch: all but 15 instructions (at boot) have IF, IP and IB times, or LB from the loop buffer (468); IF and IP take one cycle at the median, IB seven.
  • Memory: 15,872 stores drain SQ, CMT, WMB and 2,608 wrong-path stores are aborted; 96% of store queue entries find their store. Of the 997 bus reads, 62 come from the read buffer (58 with a parent) and 935 from the prefetcher, 843 of which get a decode error: the prefetcher runs past this SoC's memory.
  • Events: 430 launch replays and 5,104 mispredicted branches or jumps; 36,878 dispatch stalls.
  • Diagnostics: none. No key was reused before its item ended and no call addressed a key that names nothing.
  • Speed: the checker takes about 40 s in Python for the whole run.

The check found one tracer bug on the way: on an edge where the ROB flushes, the create ports still show a dispatch that the ROB never makes, and the orphaned entries later collided with the IIDs issued after the flush. Two more came up while extending it: the prefetcher issues several reads with one AXI id, so bus reads are keyed by id and order, and a pipe cancel stops the block leaving IP rather than the one in IB. The remaining shortcuts are known. Multiply and divide report ROB completion when they are selected, so their execute stage is one cycle; the real result time comes from the write-back ports keyed by physical register. The store-data pipe carries no IID and is not shown, floating-point sources give no wakeup, and fetch blocks are matched to instructions by their 16-byte chunk, in order.

Hard cases and how they map

Split instructions. AMOs, jal/jalr with a link register and some T-Head loads and stores become several uops. They appear as IR slots sharing one PC. Each uop is its own row with a uop attribute and a uop_of relation to the instruction, 1,167 of them in one CoreMark iteration. Because uops are inserted after decode, the tracer opens instructions in IR, where the order is final.

Stores after retire. Stores commit at retire but drain later through the store queue and the write-merge buffer, which are keyed by entry index, not IID. They are store transactions on the store_queue stream, with the instruction as parent, and a read the write-allocate needs on the lsu_bus stream names that entry as its parent once the store has retired. That gives the instruction → memory request → bus transfer chain the README asks for. The LSU's bus writes (victim write-backs; CoreMark's stores hit the data cache) are not traced.

PCs. Decode carries PC[15:1], which the tracer records as pc. At retire it computes every member's full PC, the entry PC plus the lengths of the members before it, and replaces pc and the caption only where the full PC has more bits than decode's; CoreMark fits in 64 KB, so only the core's first retire after reset needs it. Wrong-path rows keep decode's value. Captions such as 0x28ca lhu t6,0(t5) come from the program's objdump listing through a C++ hook (tb/c910_label.cpp, +vtr_dis=). Each caption is built and interned once per static instruction, so the string table grows with code size rather than run length.

Time, edges and cycles

Verilator's DPI calls for time t run inside eval(), and dump(t) follows it. A tracer in always @(posedge clk) therefore sees the values that held during the cycle ending at t, the same values the waveform shows just before the edge. Those are the load enables of the next pipeline registers, so "stage begins now" is exact. When a tracer can only observe a registered valid, it records the stage with vtr_item_stage_at(…, t_prev). The C910 retire slot is an example: it knows at edge t that the entry sat in the retire stage during the previous cycle. The C910's register-read and LSU stage valids work the same way.

Decode and rename need more: which IR slot is a further uop depends on the PCs the IR register holds after its load. The tracer therefore applies the whole front end one edge late, from the load conditions it saved at the loading edge and the register contents it sees now, with _at times. Those late steps run first in the block, before this edge's retire, flushes and dispatch, so the order of events is the hardware's; the checker applies exactly the same order.

DPI time and waveform time agree because the clocks proposal changed the C910 harness to advance time before eval(). In that harness one clock period is two time units of 100 ps. The testbench already declares clk with vtr_clock_run, as the clock TX.core0.clk beside the core's streams. The tracer names it, "/TX.core0.clk", in vtr_pipeline, so each stream carries vtr.clock. A clock declared away from its net's scope is no longer paired with the net's waveform by path; the waveform TOP.top.clk is still in the file. Volna's Pipeline panel then snaps the cursor, labels the ruler and counts stage lengths in cycles of that clock. A design with several clocks gives each tracker its own clock.

Transaction times are independent of signal time in the writer (SPEC §7). A back-dated stage costs nothing, and transactions reach the file when they end, in end order, as VTR already specifies.

Verification

Every check is headless, scripted and fails on a missing prerequisite, as AGENTS.md requires. The tracker unit tests, the standalone sink, the Volna tests and this page run in CI. The demo design needs the fork and runs locally through its script, like the other Verilator integration suites. The C910 is a local demonstration, not a test.

  1. Tracker unit tests. cargo test -p vtr-capi --test track builds a C++ program (core/vtr-capi/tests/track_test.cpp), reads its files back with the Rust reader and runs in the core CI job. It covers folding, bind_oldest order, ordered aborts, stale-key diagnostics, attribute replacement, stage continuation, groups beyond the inline size and key-table growth, and open items at close. Through a stub svdpi.h it drives the package's DPI functions over a test sink: declarations replayed at open, calls ignored while no file is open, _at times, misuse warnings, and the key tables dropped at the close notice.
  2. Demo design. integrations/verilator/pipeline/run.py builds a small design (the fork's own test_regress has no VTR library to run a model against, as for the clocks suite) in one and two thread modes. Its tracer produces fourteen transactions: instructions that open, advance through stages and a stall lane, move to a second key space with vtr_item_bind, share one key as a group through vtr_item_bind_oldest, retire, are squashed by vtr_item_abort_younger and vtr_keyspace_abort, carry attributes, a label, an event, a relation and a parent, and one that is still open at close. The script compares every transaction, stage, status, attribute and time with an exact expected list, checks that stage boundaries fall on edges of the declared clock and that the recording's waveforms are unchanged, checks the misuse warning of a deliberate stale key, and requires the same transactions from a signal-free open. --update-example writes the recording to volna/volna/examples/pipeline_demo.vtr.
  3. Standalone sink. integrations/systemverilog/run.py builds the same design with an upstream Verilator and --vpi, lists vtr_trace.sv like any package and links the standalone sink and libvtr. In one and two threads the file named by +vtr_trace= must hold exactly the fork's transactions, the declared clock and the warning, and without the plusarg no file is written. The pipeline-tracing workflow runs it with Ubuntu's Verilator.
  4. Volna. A headless test opens the committed pipeline_demo.vtr, then checks that the stream is recognised, that stages are counted in cycles of its clock, and that selection feeds the Transaction panel; unit tests cover the palette's order and contrast. The same workflow runs them. An ignored test measures load, layout and paint at half a million rows.
  5. C910. capture.sh --pipeline --check runs the clock check and the differential checker, which also requires that c910.pipeline.vdb.json describes every recorded stage; pipeline_cost.py measures the gates. Both need the RISC-V toolchain and a few minutes of model build, so they run locally.
  6. This page. node --test docs/tests/c910-verilator-tx-stream.test.mjs drives the demo in headless Chrome, and a workflow runs it when the page changes.

Cost

The gates are ratios, so they hold on any host: a pipeline-only run within 1.10× of the untraced model's wall time, and the full dump plus the pipeline within 1.03× of the full dump alone. bench/workloads/c910/pipeline_cost.py measures them on one CoreMark iteration (254,753 cycles), interleaving the four models in one session and keeping the best of five runs. On an Apple M5:

  • Pipeline only: 7.75 s against 7.15 s for the untraced model, 1.084×. The model traces no signal (SIGNALS=0) and runs with --no-signals. The waveform-capable model costs about 0.7 s more even when it records no signal; that is --trace-vtr's instrumentation, not the tracer.
  • Full dump plus pipeline: 30.28 s against 30.22 s for the full dump alone, 1.002×; runs differ by about 1%, and between sessions this host's baseline moved by 5%.
  • Size: the three streams alone are a 1.99 MiB file for 430,816 transactions and 314,177 relations, about five bytes per instruction with its eighteen possible stages, attributes, caption and dependencies; in the full dump they add 2.23 MiB (0.83%) to 267.5 MiB. The estimate before measurement was 10 to 15 MiB.
  • Read: vtr tx decodes all 411,339 instructions of the stream in 0.16 s.

The tracer makes about twenty DPI calls per instruction, each a direct, non-context import. The first build measured 1.23× and 1.045×, its pipeline-only run still on the waveform-capable model. Interning every stage name and attribute key through the C API, allocating per item and per name, two mutexes on the way to the context's runtime, and attributes nobody needed dominated its cost. A string cache in the tracker, recycled items, flat key tables, a per-thread runtime cache in the fork's sink, dropping two derivable attributes and binding only the probe bits the tracer reads brought the decode-to-retire tracer to 1.05× and 1.00×, and the pipeline-only build without signal instrumentation did the rest. Fetch stages, member stages, dependencies and the memory trackers added about 30% more calls; a spin lock instead of the runtime's mutex, exponents cached at open and allocation-free relations kept the gates. docs/BENCHMARK_RESULTS.md keeps the measurements.

Alternatives considered

Native system tasks in the fork ($vtr_begin and similar), lowered like $display. These could shave call overhead. But they need parser and AST work, produce Verilator-only source, and gain little, because a non-context DPI import with scalar arguments already compiles to a direct call. They were to be reconsidered only if the cost gate failed; it holds with DPI.

Extracting pipelines from waveforms after the run. CVA6Flow rebuilds CVA6 pipelines from a VCD this way, and this proposal's replay does the same. It needs no rebuild and works on any simulator's FST. But it needs a full dump of every probe signal (243 MiB for one iteration), it cannot serve long pipeline-only runs, and every core still needs hand-written identity logic. It stays as a research tool and as the tracer's differential checker.

Opening instructions at decode, as first designed. The C910 inserts uops between decode and rename, so the open order of decode-opened items would not be program order and vtr_item_bind_oldest would group an instruction with its successor instead of its own uop. The tracer opens instructions in IR and back-dates the decode stage instead; no API was added for it.

Host C++ sampling of public signals. RSD and NaxRiscv do this. It needs no SystemVerilog, but public signals limit Verilator's optimisation, the code is Verilator-only, and it lives in each harness rather than beside the design.

A text log as an intermediate. RSD, BOOM and gem5 use Kanata or O3PipeView text. That adds a conversion pass and loses typed attributes and alignment with the waves. VTR already imports both formats for existing tools.

A debug sequence number carried in the RTL. BOOM's fetch_seq, XiangShan's seqNum and RSD's sid are the simplest identity, but they change the design. Key chaining reaches the same result from identifiers the hardware already has. A design that does carry such a number simply uses one key space.

Recording only retired instructions. XiangShan's PerfCCT, NaxRiscv and CVA6 do this. It is cheaper, but it hides the wrong path, which is what a pipeline view is mostly for.

Questa's transaction tasks as the API. $create_transaction_stream, $begin_transaction and $add_relation match VTR's stream, transaction and relation model, and the package mirrors it. They have no keys, stages or ordered aborts, however, which are exactly what pipeline tracers need.

  4. Deeper C910. The LSU's bus writes are not traced: CoreMark issues none, so nothing could check them.
  5. Volna and VDB. Done. The palette orders a stream's stage names by their mean position within a row, so hues run from decode to retire, and alternates two lightnesses between neighbours when there are more than eight. At half a million C910-shaped rows the stream loads in 0.36 s and paints in 0.15 ms per frame over a 5,000-cycle window; zoomed out to the whole run a frame takes 14 ms (28 ms before the window's activity was computed once per frame). Such a stream is 541 MiB in Volna's loaded representation, above the default 256 MiB object limit, so Volna refuses it with its retry until memory.objectMiB is raised; the C910 iteration's 411,339 rows, with fetch stages, are 699 MiB and load in 0.39 s. A compact loaded form for large pipelines is future work.   6. Other simulators. Done. The standalone sink with VPI time, integrations/systemverilog/. Its CI job runs through upstream Verilator with --vpi, so the portable path is tested without a commercial simulator.
