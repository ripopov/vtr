Design proposal · volna-core · waveform panel

Transaction lanes as rows in the waveform panel

VTR traces carry transactions next to signals, and the hierarchy browser already lists their generators. Today the only way to see them is a separate Pipeline panel — stage cells, one row per transaction. This proposal adds the missing view: a transaction's lifetime, drawn as a lane beside the signals it correlates with, by making the generator one more row kind in the wave panel. The page carries a working demo over an AXI read scenario, the row, hit-test and loading design, and the comparison with the linked panels it complements.

Summary

The design: a generator is just another wave row

Debugging a handshake stall or an error response is a correlation task: which transaction owns this rvalid plateau, and what was its address phase? That question is awkward today because the two artifacts that answer it — the transaction's lifetime and the channel's signals — live in different panels at different row scales. The Pipeline panel answers stage-level questions (where inside the transaction did time go) better than any lane could; it is the wrong tool for which bar lines up with this signal edge.

A transaction lane is a new row kind in the wave panel's existing row list: a generator sits next to signal rows, at any position, dragged there by its name cell like any row reorder. Zoomed in, the lane draws each transaction as a rounded bar over its lifetime, stacking overlapping transactions into sub-rows; zoomed out past the density threshold it collapses to an aggregate strip; the row's × removes the lane and releases the track. Because the lane lives inside the wave panel, it shares the panel's viewport, cursor, markers and gestures for free — synchronization is not a feature that had to be built. And it is the smallest shape that answers the correlation question: a row enum arm, a lane painter and a move_row primitive, with loading, interval queries, selection and persistence reusing machinery the Pipeline panel already exercises.

Two materially different shapes were prototyped and rejected during the investigation that produced this design: an attached overlay lane pinned beneath a signal group, and a transaction shelf splitting the panel's bottom. Both pay structural costs the row does not — row groups and per-row heights for the overlay, a second in-panel region with a sash for the shelf — while their one genuinely valuable idea, selection cross-highlight on the related signal rows, is a selection overlay this design can grow later. The comparison records the verdicts so they are not re-litigated without new evidence, and experiments lists the measurements that could still change the plan.

The example

One AXI read episode, one demo

generated demo data The demo renders a hand-written event script (embedded in this file, ~40 events), chosen to exercise every interaction the design must answer: overlapping lifetimes, an address stall, data backpressure and an error response. The scenario is a manager issuing four overlapping AXI read bursts on one channel, 1 ns resolution, clock period 2 ns. The recorded trace is taken to span 0–1200 ns with the episode occupying 0–46 ns, so that zooming all the way out is a meaningful gesture that reaches the density regime — in a real trace the interesting episode is likewise a sliver of the total.

Signals: clk, the AR group (arvalid arready araddr arid), the R group (rvalid rready rdata rid rresp), and the idle write-channel pair awvalid/awready dimmed for context. Transactions carry the attributes above plus stage annotations (ADDR, WAIT, DATA) precisely so the prose can discuss reusing Pipeline panel machinery — a lane bar is the same Transaction record the Pipeline panel draws as stage cells. The deepest overlap is three transactions (T0/T1/T2 at 18–20 ns), which is what drives the lane's sub-row stacking.

Zoomed out past ~0.8 px/ns, individual bars stop being distinguishable and the lane switches to a density strip: one aggregate per pixel column. What is retained per column: how many transactions overlap it (drawn as opacity), the peak concurrency (drawn as fill height), and whether any of them ended in an error (drawn as a red cap). What is dropped: individual identities, attributes and stage boundaries — the strip answers where is there activity, and is any of it bad, and zooming in restores full detail. The demo data has only four transactions, so columns rarely aggregate more than three; with a real generator of thousands, each column may summarize dozens.

The existing alternative

existing Time-linked Waves and Pipeline panels

The repository's current answer is two panel kinds over one document. A wave panel shows the signals; a Pipeline panel (PanelKind::Pipeline(PipelineModel), implemented in volna-core/src/pipeline/ per pipeline-view.html) shows the transactions of a stream or generator as Konata-style rows of stage cells. The panels synchronize for free: both embed a nav::NavState, so the Link { viewport, cursor } flags tie them to the document's shared Viewport tween, cursor and markers. A click in either moves the one cursor; zooming one zooms the other while linked.

This is genuinely good for stage-level questions — flushes, per-stage occupancy, long instruction windows — and it cost no changes to the wave panel. It is weak exactly where this design starts:

  • No spatial adjacency. The transaction and the signals it must be compared with are in different panels, separated by chrome; the eye must carry a time position across a panel boundary. A shared cursor helps, but scanning shape (a bar plateau against a handshake plateau) across panels is markedly harder than across adjacent rows.
  • Different row semantics. Pipeline rows are one per transaction in (begin, end, id) order at a panel-wide row pitch; wave rows are signals. There is no way to pin axi_rd directly under arid and keep it there while scrolling.
  • Granularity mismatch. For a four-burst AXI episode the Pipeline panel's stage cells are more detail than the correlation question needs; the user wants lifetimes.

The design below keeps this two-panel workflow intact — the Pipeline panel remains the right tool for stage analysis, and the lane deliberately reuses its loader path, its palette idea and its overlay painting. It adds one capability: the wave panel can also host a generator as a row, next to the signals it correlates with.

Row and lane layout

WaveModel.items is today a Vec<DisplayedSignal>. The minimal change is a row enum, WaveRow { Signal(DisplayedSignal), TxLane(TxLane) }, where TxLane holds a TrackSource-style locator (resolved TrackRef + path, or an unresolved saved path), the prepared sub-row assignment, and transient hover/selection. Everything row-shaped the panel already does — the name and value columns, hover highlight, selection, remove_selected, workspace save of row locators — works over the enum with a signal-only fallback arm. A lane has no value column; its cell shows the transaction under the cursor, if any.

One honest complication: wave/layout.rs assumes a uniform row height (row_at is a division by the theme's row_height). A lane that grows with its overlap depth breaks that invariant. The v1 answer is to cap a lane at four sub-rows (5 × row_height with padding, still fixed multiples of the unit) and scroll deeper stacks inside the lane; generalizing layout to per-row heights is measured first (see experiments) and is only needed if the cap proves annoying. In density mode the lane is exactly one row tall.

Hit testing

The painter already enumerates the visible transactions to draw them, so the hit test reuses that enumeration rather than querying again: pointer y picks the row and sub-row, pointer x becomes a time, and the topmost bar whose [begin, end] contains it wins, with a ±2 px edge tolerance for one-pixel bars. Cost is bounded by painted bars, never by generator size. In density mode there is nothing to hit below column granularity: a click sets the cursor and the status line reports the column's aggregate (count, any-error).

Interval queries

Visible transactions come from LoadedGenerator::visit_window(vp.start, vp.end, …), the balanced max-end interval tree that already exists for exactly this query — inclusive overlap, results in canonical (begin, end, id) order, and it retains long transactions that a begin-time binary search would miss. Paint and hit test share one visitor. The tree is not consulted for sub-row assignment (that is a property of the whole generator, computed once) nor in density mode below the aggregation threshold, where the same visitor feeds the per-column bins with an early exit once every column is saturated.

Asynchronous preparation

Opening the lane retains the track through Document::retain_track — the same LoadRequest::Track path the Pipeline panel uses, with its generation checks and remote memory reservations — and the lane row shows the existing loading/failed row states until delivery. On Delivered::Track the model computes the sub-row assignment: one greedy pass in begin order, O(n) in the generator's transaction count, producing one u16 lane index per transaction plus the depth. For the generators seen so far this is trivially fast enough to run on delivery; if a measurement ever says otherwise, the pass moves into the same cancellable background-job seam the table proposal uses, and the lane draws flat until it lands. No part of preparation touches the paint path.

Memory costs

Zero copies of trace data: the lane reads the resident immutable Transaction records shared with any Pipeline panel on the same track (consumer counting makes the second consumer free). Added state per lane: the locator and view state (tens of bytes), the lane-index vector (2 bytes per transaction), and the shared text-shaping cache entries for labels actually drawn. Density bins are computed per frame into a reused column buffer (O(width)); no persistent pyramid in v1.

Bounded rendering work

Per frame: visible rows are bounded by panel height ÷ row height; per lane, painted bars are bounded by visit_window results clipped to the viewport, with bars narrower than a pixel widened to one and text gated on shaped-width like the wave painter's bus segments. In density mode work is O(visible transactions + width) with the early exit above. Worst case is therefore proportional to pixels, not to generator size — the same contract the wave painter already keeps (O(pixels), ARCHITECTURE.md). This is a bound on work, not a measured frame time; the numbers are owed by experiment E2.

Boundaries that do not move

  • VTR/VDB. The lane reads lifetimes, stages, attributes and status — all raw trace facts. Colours, the decision that rresp = SLVERR means TxStatus::Error (a producer choice recorded as status), grouping heuristics and leader-line routing are viewer concerns; a VDB profile may later recolour bars exactly as it would recolour pipeline stages. Nothing is added to the format.
  • Client/server. The query library and protocol keep carrying raw trace data only. Lane assignment, density aggregation, tints and selection run on the client over the resident immutable objects; a remote lane loads through the existing LoadRequest::Track with its explicit size failure, and a native lane shares the buffers without serialization.
  • volna-core, not the frontends. Row model, lane assignment, density bins, hit testing and selection live in volna-core and are headless-testable; the GPUI element gains lane hitboxes the way it gained pipeline hitboxes. volna-egui builds against the new row enum and otherwise does not grow, per AGENTS.md.
Interaction

Existing wave gestures stay predictable

The first rule of the design: a user who never opens a lane cannot tell the feature exists. Lane interactions live in places wave gestures do not — the name cell (drag to reorder, × to remove), the bars themselves (click to select) — while the wave area's contract is unchanged.

Shapes considered and rejected

Attached overlay lane. A strip pinned beneath the signal group the generator was derived from, expanding accordion-style on click, with stage tints and dashed leader lines tying a selected transaction to its channel rows. The correlation cues are real, but they are a selection overlay this design can grow later, while the entry price is not deferrable: a row-group model with a durable anchor identity, plus per-row heights — changes to wave/layout.rs's uniform-height core invariant rather than a new arm of a row enum. Rejected as the first version; any revival is gated on the same per-row-heights measurement (E4) as removing the sub-row cap.

Transaction shelf. A horizontally split region at the bottom of the wave panel, one row per open generator — the SimVision/Verdi arrangement. Comfortable and familiar, but it grows a second panel inside the first: a new region layout, a sash, per-generator rows with their own scrolling, focus and persistence — most of a panel's machinery without a panel's reuse of Panels, docking and persistence, which already produce this arrangement (with stage cells instead of lifetime bars) by docking a Pipeline panel below a wave panel. Its distinctive feature, cross-highlight on selection, is likewise a selection overlay. Rejected; revisit only with evidence that survives this argument.

Proposed first version

Build the lane, scoped tight

  1. Row enum and lane model. WaveRow { Signal, TxLane } in wave/model.rs; TxLane holds the track locator, prepared lanes and selection; sidebar activation gains an "add as lane" outcome (drop target or modifier; double-click still opens the Pipeline panel). move_row(from, to) lands here as the reorder primitive.
  2. Lane painter. Stacked bars from visit_window over the viewport, stage ticks, status palette, sub-row cap of four with inner scroll, density strip below 0.8 px/ns equivalent; emits Scene quads/text via wave::overlay conventions. Headless tests assert on the scene.
  3. Hit testing and selection. Paint-enumeration hit test, per-panel transaction selection, Escape order, status-line detail; GPUI hitboxes in the wave element.
  4. Persistence. Workspace row entries for lanes with durable track locators; unresolved lanes restore as empty rows, mirroring unresolved signal rows.
  5. Validate, then measure. Run experiment E1 — the task-based comparison against the linked panels — before writing row-enum code; then run the remaining experiments below before any cost claim is written into docs, recording numbers in docs/RATIONALE.md style alongside the change.

The rejected shapes' stage tints, leader lines and cross-highlight are kept as this design's later selection overlay rather than a second lane mechanism; the verdicts are recorded in the comparison above so they are not re-litigated without new evidence.

Deferred features

Named seams, not forgotten ideas

  • later Selection cross-highlight, stage tints and leader lines as an overlay on the lane's selection; needs a "related rows" mapping, which is VDB-attachable metadata, not a format change.
  • later VDB colour profiles for lanes — fill the status/stage palette from a profile, same seam as StagePalette.
  • later Multiple generators per lane, lane filtering, and attribute-driven bar labels — a lane-row index between the generator and the painter, mirroring the Pipeline panel's deferred RowIndex.
  • later Relation arrows between bars — the resident relations() already support the Pipeline panel's deferred arrows; same second pass here.
  • later Per-row heights — a prefix-heights layout that removes the four-sub-row cap, gated on experiment E4; also the prerequisite for any attached-overlay revival.
  • later Density pyramid — a persistent per-generator aggregation for million-transaction generators, only if E3 shows per-frame binning insufficient.
  • later Tooltips, search-into-lane, cursor-follow — same shapes as the Pipeline panel's deferred list.
Open uncertainties

Experiments, the validation gate first

  • E1 · Does the lane actually beat the linked panels? A small task-based comparison (find the stalled burst's address; find which transaction errored) between linked Waves+Pipeline and the lane, on a realistic trace. This runs before any implementation: if the linked panels tie, the honest outcome is to ship nothing.
  • E2 · Paint and preparation cost at scale. Lane-assignment time and per-frame paint time on the largest real generators available (the checked-in pipeline_showcase.vtr, and a Verilator AXI trace with 10⁴–10⁶ transactions), A/B against a build without the lane, best-of-N on pinned cores per AGENTS.md. Claims in this document are bounds, not measurements, until this runs.
  • E3 · Density aggregation strategy. Per-frame per-column binning via visit_window versus a persistent pyramid, at 10⁶ transactions: frame time and memory for both. Decides whether the pyramid stays deferred.
  • E4 · Uniform-height assumption. Audit and measure wave/layout.rs for a prefix-heights variant; if the capped lane (4 sub-rows) proves limiting in use, this decides the cost of removing the cap — and is also the prerequisite for revisiting an attached-overlay lane.
  • E5 · Hit-test enumeration threshold. At what visible-transaction count does re-walking visit_window for the hit test beat reusing the paint enumeration? Sets whether the two share a visitor cache.
  • E6 · Activation UX. Drop target versus modifier-click versus sidebar button for "add as lane", tried on the wave panel's real sidebar; the mock's sidebar button is a placeholder, not a decision.
