Design · Hierarchy browser

Every scope's size, on hierarchies of any size.

A scope row should say how many distinct signals live below it. Ports alias the nets they connect, so the size is a distinct count, not a sum. A gate-level trace makes every cell a scope and every pin an alias, which means millions of scopes and tens of millions of variables. The count itself turns out to be cheap: one streaming pass, 0.22 s for 53 million variables. The expensive part is holding the hierarchy at all. So this design counts in one pass, holds the hierarchy compactly, and for the largest traces keeps a paged scope index next to the trace, so the browser can open without reading every scope.

Measured on C910 and on gate-level expansions of it up to 9,222,096 scopes and 53,148,624 variables · the streaming count agrees with a brute-force walk on every scope of every trace

Problem

A size is a distinct count, and gate-level traces are huge.

Sums are wrong. A net that enters a unit through a port is one signal with two names. Summing variables counts it twice. In C910's RTL trace, x_ct_ifu_top has 16,261 variables but 6,779 distinct signals, and the whole design has 204,905 variables for 67,144 signals. The number a designer wants is the second.

Gate-level traces multiply everything. After synthesis every bit is a net, every standard cell is a scope, and every pin of every cell aliases a net. We expanded C910's real hierarchy this way: one-bit nets, and one driving two-input gate or flop per net, whose three pins alias nets of its module. One core becomes 576,380 scopes and 3.3 million variables; sixteen cores become 9.2 million scopes and 53 million variables. A single module then holds up to 18,637 cells as direct children. Real netlists have more cells per net, so these are lower bounds.

The browser needs sizes before anything else. They appear on the first rows the user sees, the roots, whose subtrees are the whole design. Activity meters then divide by them on every frame. Any scheme must therefore count the whole hierarchy up front, or read counts made ahead of time.

The stamp walk sends every variable up the tree until it meets a scope already stamped with its signal. The streaming count is the colour-set-size method in one preorder pass with Tarjan's offline lowest common ancestors. The per-signal lists keep that method's +1 and −1 entries, so a frame of activity meters adds only the entries of its active signals, here a random 30% of them. All three agree with each other on every scope. The FST files are the same hierarchies written by vcd2fst; the sixteen-core VCD was not converted. The remote rows ran with limits raised to 16 GiB. With VS Code's defaults, a 512 MiB budget and a 256 MiB object cap, one gate-level core is refused for its budget and four cores also for the cap. The sixteen-core remote open was not run: its server alone would hold the 12.6 GiB model and a copy of it.

Findings

Five things the numbers decide.

  1. Count in one streaming pass.The streaming count takes 0.22 s for 53 million variables, about 4 ns per variable, and is 2.2 times faster than the stamp walk. It keeps 12 bytes per scope and 4 per signal and nothing per variable, and it needs only scopes and variables in preorder. That is the order of an FST or VCD hierarchy stream, so it runs while the stream is read. Its cost stays linear however deep the tree gets.
  2. Hold the hierarchy compactly.Volna copies every scope and variable into owned strings and vectors: about 217 bytes per node, 12.6 GiB and 9.6 s for sixteen cores. The VTR reader's own columns hold the same hierarchy in about 34 bytes per node, names included. The count is a rounding error next to this; the model is the problem.
  3. The largest traces need an index made ahead of time.Even the compact form is linear in the whole hierarchy: 2.6 s and 2 GiB to open sixteen cores. A full chip ten times larger would need about half a minute and 20 GiB before a row appears. Opening without reading every scope needs a random-access copy of the hierarchy, and sizes must be in it, because a browser that reads only the visible scopes cannot count what it has not read.
  4. VS Code copies the hierarchy twice more.There the trace is read by a native volna-server child, and Volna runs as single-threaded wasm in the webview, with at most 4 GiB of address space. The server builds Volna's model, clones it into one metadata object and sends it whole; the webview decodes it back into the same model. One gate-level core costs 1.5 GiB on the server, 987 MiB of client budget and 4.4 s before a row. A compact model helps only if the protocol carries it too.
  5. Flat scopes need their own rows.A synthesized module lists thousands of cells as direct children: 18,637 in the largest here. A tree that renders every child, or a filter that scans them on every frame, stalls; Surfer's issue tracker records both. Children must be virtualized, and leaf cells group by cell type, so a module reads as its submodules plus "4,881 NAND2_X1".

Architecture

One count, three ways to hold the tree.

  1. A format-neutral counter.vtr::census takes scopes and variables in preorder: scope(parent), then var(signal) for each of its variables, then finish(), which returns a distinct count per scope. It keeps a union-find, an ancestor and a weight per scope, the scope stack, and the last scope of each signal. Nothing else. The VTR front end walks the reader's columns in preorder; FST and VCD front ends feed their hierarchy streams as they are read; Volna feeds its model.
  2. Lists only for meters.vtr::census::Lists keeps each signal's scopes in preorder with the ancestor of each consecutive pair. A frame of activity meters adds the entries of its active signals and takes one prefix pass over the scopes. The lists cost 8 bytes per entry, so they are built only when a trace has meters.
  3. A compact model in Volna, local and remote.Hierarchy in volna-core becomes columns of ids with an interned name table, like the reader's. The VTR session shares the reader's columns and strings instead of copying them. The FST session builds the same columns while it streams. Callers read names through the table and never own a String per node. The remote protocol carries these columns as they are, in preorder pages, so the VS Code webview holds exactly what a local session holds, and the server sends pages from its own columns without a copy.
  4. A paged scope index for the largest traces.VTR stores its hierarchy in declaration order and FST in one compressed stream, so neither can be read one scope at a time. The <trace>.index sidecar of the activity design gains a scope index: every scope in preorder with its parent, the end of its subtree, its first variable, its variable and distinct-signal counts, its cell type and its name, and every variable in the same order, in pages of 65,536 entries with front-coded names. It is built with the same streaming pass, bound to the trace by the same identity, and needs no change to the trace formats or their writers.
  5. The session hides the difference.The Session hierarchy becomes a small trait: roots, children of a scope as a range, variables of a scope as a range, size of a scope, name of a node. A loaded model answers from memory; a paged one answers from pages it loads through a LoadRequest, and a child range not yet loaded comes back as pending. The sidebar models draw what the trait returns and never ask which kind they have.
  6. Flat scopes in rows.The scope tree renders only visible rows. When a scope has more than a few hundred leaf children of one cell type, they fold into a group row, "NAND2_X1 · 4,881 cells", which opens into a virtualized list. Submodules stay as rows.
  7. Search is the one full scan.Filtering by name must look at every name. On a loaded model it runs off the UI thread, once per edit. On a paged one it streams the name pages and shows results as they arrive. A name index would make it instant; it is left until measured.
  8. Not undoable.Sizes, pages and group rows are derived view state and stay out of the journal. Expanding a group is navigation, like expanding a scope.
  9. Tested headlessly.core/vtr/tests checks the counter against a brute-force walk on random trees with aliases, including aliases in unrelated subtrees and roots. vtr-bench scopes asserts the three methods agree on real and generated traces, and the benchmark report tracks open time and peak memory for the generated gate-level traces. volna-core tests check sizes, pending pages, group rows and a paged model against a loaded one.

Plan

Six commits, each useful on its own.

Every commit builds, passes cargo test for the crates it touches, cargo test -p volna-core and volna/volna/check.sh, and updates the tests and documentation it touches. No commit adds a feature flag or code that only a later commit calls. Where a stage adds something to the screen, its picture shows that stage and the ones before, and red rings number the new elements as its list does. The pictures use rows measured with vtr-bench scopes --children.

Why this order. Sizes help every trace, so they come first. The compact model and cell groups then make gate-level traces usable in memory, natively and in VS Code, where the webview is tighter than any desktop. The paged index comes last, for traces that do not fit even then, and it reuses the counter, the session trait and the remote pages already in place. The activity meters of the activity plan need stage 1 here.

Stage 1 Landed

Scope sizes

Before this stage a scope row showed only its name, so nothing told a two-signal wrapper from a unit of thousands. Now every row says how many distinct signals it holds, subscopes included, as soon as the count finishes after open. Over Volna's hierarchy model the count takes 2.7 ms for C910, 69 ms for one gate-level core and 0.28 s for four. Over the reader's columns it takes 0.9 ms for C910, and stage 2 brings those columns to Volna.

  1. A signal count on every scope row, right-aligned in a muted column. An aliased signal counts once in each scope that holds it.
  2. The tooltip adds variables and scopes, which differ from the signal count when ports and aliases name one signal several times.

Not in the picture: until the count finishes, the column is empty rather than wrong.

Stage 2

A compact hierarchy, local and remote

The hierarchy stops being copied, on both sides of the VS Code extension. Natively, a sixteen-core gate-level trace no longer needs 12.6 GiB before its first row; the target is the reader's own 2 GiB. In VS Code, the server stops cloning its model into one metadata object, and the webview stops rebuilding a String per node. At the reader's 34 bytes per node, one gate-level core would take about 130 MB of client budget instead of 987 MiB and fit the 512 MiB default, and four cores about 530 MB. Those are estimates until this stage measures them. Sixteen cores, about 2 GB, stay out of a webview's reach until stage 6. Nothing changes on screen.

Committed

Core
Hierarchy becomes columns behind the session's hierarchy trait: parents, child and variable ranges, signal references and kind codes as 32-bit ids, and one name table of bytes and offsets, with scope kinds, variable types and cell types interned. The VTR session shares the reader's columns; the FST session builds the same columns while it streams. Every caller of scopes[i].name and vars[i].name moves to the trait.
Protocol
Version 5. The hierarchy leaves the metadata object and travels as its own objects: pages of 65,536 scopes or variables in preorder, the unit of stage 4's index. Each page is a few flat little-endian arrays and a slice of the name table, well under the object cap, so no single object grows with the design. The client charges a page to the memory budget, copies its arrays into the columns and checks their ids, with no allocation per node, in steps short enough for the single-threaded webview. The server sends every page at open, reading them from its shared columns, not from a clone. Stage 6 sends only the pages asked for.
Sizes
The server runs stage 1's counter over its columns, 0.9 ms for C910 on the reader's, and sends the sizes column with the pages. The webview then never runs the count on its UI thread. LoadRequest::Sizes stays for local sessions.
Frontends
Both frontends and the webview read names through the trait; nothing visible changes. An open that does not fit the budget still names the setting to raise.
Bench
load_cost and remote_cost on the generated gate-level traces join the benchmark report: open time, wire bytes, client budget, client and server peak memory and the longest decode step, for VTR and FST, compared with the commit before.
Tests
Every existing hierarchy, sidebar, workspace and remote test, unchanged. A walk that compares the new model with the reader's hierarchy node by node on the fixtures. Over the in-process transport, a remote session equals a local one column for column, sizes included. A page larger than the remaining budget is refused before it is allocated, and a page with out-of-range ids is rejected.

Limits

What is estimated, and what it costs.

The gate-level traces are generated. They keep C910's real module tree and aliases, but give every net one three-pin cell. Real netlists have several cells per net, cells with more pins, and sometimes nets inside cells. Everything measured here is linear in scopes and variables, so real netlists should scale the same way; they were not measured.

The paged index is not measured. Its size, build time and page latency are estimates until stage 4. The design's claim rests on the linear costs above and on the reader being the floor for any design that loads the whole hierarchy.

Meters on a paged hierarchy need every variable. A frame of activity meters counts active signals in every scope, which needs each signal's scopes: the per-signal lists, 448 MiB at 53 million variables. On a paged trace they would be read from the index or built in one pass over it. Meters stay practical up to what those lists cost.

The webview is measured natively. remote_cost runs the production client as a native process. In the webview the same decoding runs as single-threaded wasm, which is slower by an unmeasured factor; its longest step was 25 ms for one core and 96 ms for four natively. Stage 2's pages bound each step by page size rather than by the design.

Search reads every name. Without a name index, a filter on a paged trace streams all name pages. It is progressive, not instant.

Signals, not bits. A size counts distinct signals, so a 64-bit bus is one. Gate-level traces have one-bit nets, so their counts are bits.

Research

No viewer shows sizes; the algorithm is old.

Viewers. wellen, which Surfer uses, loads the whole hierarchy eagerly into arenas: 40 bytes per scope and per variable, a first-child and next-sibling tree, and interned names, one String each. Aliases share a signal reference, and no per-scope sizes are stored. Surfer's scope rows show only names, and its tracker records slow UI with 80,000 variables in one scope (#550), scope and variable lists rebuilt every frame in post-synthesis traces (#376), and a regex filter taking 700 ms per frame (#205). GTKWave allocates a symbol and a node for every variable, aliases included, each with its full hierarchical name, and builds its tree from scope push and pop; its manual recommends the search filter for very large levels such as synthesized netlists. Neither shows sizes.

Formats. An FST hierarchy is one compressed stream of scope, upscope and variable records, where a variable either declares a handle or aliases one. The header stores totals only: scopes, variables and distinct handles. The stream is in preorder and can only be read in order. VCD is the same shape in text, with identifier codes as aliases. VTR stores its hierarchy in declaration order, in columns, as SPEC §5 describes.

Commercial tools. Verdi's smart load reads only the scopes first touched, reported as ten times less load time and memory, with the caveat that gate-level simulations with little hierarchy see no advantage. That is the flat-scope problem this design answers with groups and paging. We found no public documentation of per-scope signal counts in a commercial viewer. Synthesis tools report instance counts per hierarchy, for example Yosys stat -hierarchy.

Algorithms. Distinct colours per subtree is Hui's colour set size problem (CPM 1992), solved in linear time with one DFS and lowest common ancestors of consecutive same-colour leaves. Tarjan's offline LCA answers those in near-linear time with union-find, and Gabow and Tarjan made that special case linear. Bender and Farach-Colton give constant-time online LCA after linear preprocessing, which this design does not need, because preorder makes every query offline. Merging sets small into large solves the same problem in O(n log n) with more memory; a Fenwick tree over preorder answers distinct counts for arbitrary ranges. Succinct trees store a tree in about 2.4 bits per node; this design keeps 32-bit ids instead, since names and variables dominate, and leaves compressed string dictionaries for the name pages.
