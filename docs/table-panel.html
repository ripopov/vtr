Table panel specification

This document specifies the proposed table panel: how users inspect trace records, how rows and values are defined, and how the client prepares and queries them. The embedded prototype illustrates the interactions. It does not implement VTR decoding or demonstrate production performance.

1. Scope

The table is one panel kind for transaction records, sampled signal values and log records. These sources share navigation, filtering, sorting and selection, but use different rules to define a row. A generated source is also provided for testing the table independently of a trace reader.

The first version supports opening selected sources through Open in table, one selected row, typed column filters, sorting by one column, Find, column visibility and width, row/time navigation, record details, copying and a linked time cursor. Section 2 defines these interactions; sections 3–7 define the data and execution model that supports them.

Source editing, custom clock sampling, signal columns in transaction tables, range selection, automatic cursor following, a match-density overview and large exports are later extensions. They are described separately in section 8 and are not requirements for the first release.

Both local and remote sessions load complete selected signal histories and transaction tracks. The client performs table queries and presentation; the protocol carries raw trace data. Loading fails explicitly if the selected data exceeds the shared client memory limit. The table does not introduce server-side filtering or remote row paging.

2. UI and interaction

2.1 Open selected sources in a table

Select signals, a generator or a stream in the hierarchy, right-click, and choose Open in table. The command immediately opens a new table. It has no submenu or setup dialog. Shift+F10 provides the same context menu from the keyboard.

The command uses the current selection when the clicked item is already selected; otherwise it selects the clicked item alone. Existing Shift and Ctrl/Cmd selection gestures apply. A stream includes all its generators in catalog order, with duplicate references included once. Mixed signal and record selections disable the command with “Select signals or transaction sources separately.” Selecting a scope does not recursively add its signals.

Signals open with one row per distinct change timestamp across the selected histories and one value column per signal. Generators and streams open with one row per transaction, using the complete recording rather than just the visible time window. The initial record columns include ID, begin time, duration and available attributes; a source column identifies generators when more than one contributes records. Log sources use the same record route with log-oriented columns.

The same Open in table command is available in the Waves signal-row context menu and the Pipeline panel’s context menu. In Waves it uses the selected signal rows, or the clicked row alone. In Pipeline it opens the panel’s complete generator or stream; it does not introduce transaction-row selection. No rows are removed from the original panel.

The new table opens below the originating content panel and receives focus, following the existing Pipeline opening convention. For a hierarchy invocation, the origin is the focused content panel; a Start placeholder is replaced instead. Each invocation creates a new table. Existing docking controls handle moving, splitting, renaming and closing it. Opening does not move the shared time cursor or change the Waves/Pipeline time scale.

Enter, double-click and the sidebar “+” retain their existing Waves/Pipeline behavior even when a table is focused. The table keeps the source set captured when it was opened. To use another set in the first version, select it and open another table; there is no destination picker, source editor or add-to-existing-table operation.

The panel shows Loading while its data is prepared, then the completed rows. A failure shows the reason and Retry; closing the panel cancels pending work. Source references and loading decisions belong to the core, and histories already used by Waves or Pipeline are shared.

2.2 Interactive example

The example has three linked panels. Pipeline shows five bus transactions as rows of request, wait and response stages. Waves shows binary clk and valid, and 8-bit vectors addr and data. The transaction table lists the same records as Pipeline. Selecting a table row moves the cursor in both time-based panels to that transaction’s begin time.

Click either timeline to move the shared cursor without changing the selected table record. Drag to pan both timelines. Double-click a table row to fit its interval in both panels. The table marks the row with the latest begin time at or before the cursor; this is a time reference, not a list of all active transactions. Locate cursor reveals that row without changing selection.

The buttons below switch between two prepared examples, rather than changing a table’s sources in the product. The signal example lists values from the same histories shown in Waves. Table interactions are proposed; Waves retains signal rows and Pipeline retains transaction rows.

2.3 Filtering, sorting and Find

Filter opens an input beneath each column header. The input uses the column’s type: a status column offers values such as ERROR, while a duration column accepts a condition such as >=120. Conditions on different columns combine with AND. An active filter remains visible as a removable label even if its column is hidden. Only values for which the predicate is true pass the filter; missing values and logic states require explicit operators.

Clicking a sortable column header changes the row order. Sorting uses the complete typed values, not truncated cell text. Equal keys use a stable source-order tie-break. Find searches the displayed representations in enabled columns and moves between matches without removing rows. For example, filtering status to ERROR changes the result set; finding WRITE within that result only highlights and navigates between matching records.

While a new filter or sort is being calculated, the table keeps the last completed result. The status distinguishes the query currently displayed from the query being prepared. An invalid condition, cancellation or insufficient memory leaves the previous result available.

2.4 Selection, cursor and navigation

The selected row identifies a record. The shared cursor identifies a time in the recording. These are separate values: selecting transaction T42 does not mean that T42 is the only transaction active at the cursor time. When cursor linking is enabled, activating a row moves the cursor to its time anchor, normally the transaction’s begin time. Filtering and sorting do not move the cursor.

Selection is stored by stable row identity, so it survives a reorder. If a filter hides the selected record, the status reports that the record is filtered out. The cursor indicator uses the row with the latest time anchor at or before the cursor, regardless of the current display order. Equal timestamps use a stable source-order tie-break. If that row is filtered out, the panel reports this rather than marking an unrelated row.

Arrow keys move the selection; Page Up/Down, Home and End navigate the current result. Go to accepts a displayed row number or a time. Locate cursor reveals the cursor’s row without changing the waveform scale; if that row is absent from the result, it reports this. A command to find the nearest matching row is a separate operation. Enter opens record details. Show interval in waves explicitly fits the waveform view to the selected interval; merely selecting a row does not change the scale.

2.5 Columns

Columns controls which fields are visible; dragging a header divider changes the width. Hiding a column changes presentation, not the row source. A hidden column that still has an active filter continues to participate in the query.

2.6 Copying and keyboard access

Right-clicking a row selects it and opens Copy row and Copy with column headers. Ctrl/Cmd+C copies the selected row without headers. Both commands copy enabled columns in display order as tab-separated values, with quoting for embedded tabs, newlines and quotation marks. Copy is a row action and does not occupy a permanent toolbar button.

Shift+F10 opens the row menu from the keyboard; arrows choose an action and Escape closes the menu. Ctrl/Cmd+F opens Find. Row contents remain readable through a semantic accessibility representation; a canvas alone is insufficient. Long cell values open in record details instead of changing the fixed row height. Clipboard preparation is bounded by a byte limit, and the clipboard is replaced only after the complete copy is ready.

2.7 Saved state

Opening a table fixes the set of generators or signals used as its source. That set stays fixed in the first version; later selection changes in the sidebar do not replace it automatically. A saved workspace identifies the recording by its fingerprint and records source paths with enough information to distinguish repeated occurrences.

The workspace also stores the version of the rules used to form rows, column keys, typed filters, sort order, numeric formatting, units, cursor links and stable row anchors. It stores these settings rather than computed result buffers.

Restoring a source reports whether its saved reference resolves to exactly one source (Found), no source (Missing), or several candidates (Ambiguous). A changed schema must not silently bind to a similarly named field. Changes in saved-state semantics require a workspace format version change. Future MCP adapters use the same core commands and stable selection snapshots.

3. Rows, identity and time

A row recipe defines which source records create rows and how each row is identified. The resulting row domain has a canonical order before filtering or sorting. A source ordinal is a row’s position in that domain; a displayed rank is its position in a query result. Neither position replaces the stable row key used for selection and saved state.

3.1 Transactions

A transaction row is identified by recording, generator and transaction ID. Within a generator, canonical order is (begin, end, id). A table containing several generators either concatenates their domains using a directory of cumulative row counts or explicitly builds a global time-order permutation. These are different ordering choices and must not be switched implicitly.

The begin time is the navigation anchor; the closed interval [begin, end] is the transaction’s extent. “Begins within the selected interval” and “overlaps the selected interval” are different filters. Repeated attributes are addressed by phase, key and occurrence, so two attributes with the same name are not silently merged. Nested events, stages and relations appear in record details or in a separately defined event-row source.

3.2 Signal changes

The user explicitly chooses the signals whose recorded changes create rows. The row axis is the union of their distinct timestamps: changes recorded at the same time produce one row. Its key contains the recording, recipe and timestamp. Signals added only as value columns do not add timestamps to this axis.

At time t, an ordinary signal cell shows the last recorded value at or before t. A change mark means that an occurrence was retained at that timestamp, even if the recorded value repeats the previous value. Record details preserve the individual occurrences that were combined into the row.

3.3 Clock-edge sampling (later extension)

A clock-edge recipe creates one row per recorded edge occurrence. The strict rising-edge rule accepts 0→1 and rejects X→1. The row key includes the clock occurrence ordinal: two rising edges with the same timestamp remain two rows. An edge-index map locates the Nth edge; a timestamp lookup alone cannot distinguish these occurrences.

Sampling Before uses the last record with time < t; sampling At time uses the last record with time ≤ t. Repeated edges at the same time can therefore display identical sampled values. These rules describe recorded ordering only. They do not establish simulator scheduling regions, cross-signal delta-cycle order or the value actually sampled by a flip-flop. Event signals represent occurrences and must not be carried forward as persistent state.

3.4 Other sources and value types

A log row is identified by its recorded occurrence and retains the original log provenance. A derived source has a versioned recipe, stable keys, a finite row count or an explicit building state, and optional time anchors. Time-link controls are unavailable for sources without time anchors.

The value model distinguishes initial values, absent attributes, explicit nulls, unavailable or dump-off data, and logic states such as X and Z. Ticks and identities use u64. Conversion to physical units uses checked exact rational arithmetic; large integers cross the JavaScript boundary as decimal strings. Filters use typed raw values. Formatted-text search explicitly depends on the translator revision. VDB supplies client-side design semantics and presentation, without adding those fields to the raw trace protocol.

4. Architecture and data ownership

4.1 Component boundaries

All table behavior belongs in volna-core: source selection, row recipes, queries, navigation, layout and generation of the toolkit-neutral Scene. GPUI paints the prepared scene and hosts native controls. Integration adds PanelKind::Table, PanelLayout::Table and core commands while reusing PanelCanvas, NavState, themes and document load delivery. The egui frontend retains its existing minimal feature set and must continue to build.

A proposed OpenTable command carries the selected signal or track references, the originating PanelId and the document generation. The core captures that source set, expands streams, removes duplicate references and chooses the default row recipe from the source kind. It opens a new panel through the existing docking model and retains the required immutable data. The frontend only invokes the command from the context menu; it does not reinterpret selection after loading starts.

The session owns loading. Existing SignalHistory and LoadedGenerator objects own the immutable trace buffers. A table retains references to those objects and adds row indexes and query results; it does not copy every source record into a universal table store. When an adapter needs a missing operation, add it to the owning API instead of duplicating the owner’s data in a side table.

4.2 Snapshots and prepared cells

TableSnapshot binds a source, row domain, schema and source revision. QuerySnapshot retains that input and records which rows passed the filter and in what order they are displayed. ViewportTile contains prepared values for a small rectangle of visible rows and columns. Each result carries a ticket so delivery can reject work for an obsolete request.

These are proposed internal contracts, not a new public file format. project prepares cell previews, seek positions a source cursor, and advance reads the next row. An operation that exhausts its work budget returns a continuation and resumes later. Sequential cursor access is useful, but neither advancement nor arbitrary sampling is assumed to take constant time for every source.

4.3 Work outside the paint pass

Value lookup, decoding needed for access, and formatting run asynchronously before painting, with byte, operation and time limits. Paint consumes only ready previews and geometry. A jump to data that has not been prepared may show placeholders. Filtering and sorting can cause many noncontiguous reads, so their work must also be resumable.

The existing owned SignalHistory.value() may clone large values; the owner should provide borrowed or resumable access where needed. If transaction projection needs ordinal lookup, extend LoadedGenerator using its existing ID index. These operations must preserve immutable sharing across panels.

5. Indexes and viewport access

5.1 Membership and rank/select

Filtering produces a set of source ordinals. For example, if ordinals 2, 5 and 9 pass, the result contains three rows without copying their records. select(1) returns source ordinal 5 when ranks are zero-based; rank(9) counts the two members before ordinal 9. These operations map between source positions and positions in the filtered source order. Sorting adds the separate permutation described in section 5.3.

Partition the source domain into immutable shards of 65,536 rows. A shard uses All, Empty, sparse u16 local offsets or dense membership bits, according to its contents. Dense shards have local rank directories; the global directory stores u64 cardinalities. Padding in the last shard never represents a row. Begin with a flat immutable directory and publish complete results atomically. A persistent count tree is an optional optimization for workloads that justify shared versions or frequent partial publication.

5.2 Signal time axis

The initial multi-signal row axis stores the union of timestamps in chunks of u64 values. A compatible single driving signal can reuse its original axis. For K driving histories containing E input occurrences and U distinct timestamps, a heap merge takes O(E log(K+1)) work and the timestamp payload occupies 8U bytes. Memory is reserved before construction.

An edge-sampled source instead retains an index of qualifying clock occurrences. The index preserves repeated occurrences at the same time, in contrast to the timestamp union. Both representations provide an exact row count once construction finishes.

5.3 Column statistics and sorting order

Optional statistics summarize a chunk’s projected values: minimum, maximum and the presence of null, missing, unavailable or NaN values. They let a filter skip a chunk only when it can prove that no row matches. A dictionary-presence sketch may produce false positives, but never false negatives. Without statistics the chunk is scanned. Statistics are built only for requested columns and shared by source and expression revision.

Sorting stores a stable permutation of the M surviving source ordinals. The permutation changes display order without rearranging source records. u32 is valid only when the referenced ordinal domain fits in u32; filtering a large domain down to a small result does not make its original ordinals smaller. A separately budgeted indirection can assign compact indices to survivors. Sort keys keep their full types.

An inverse permutation can accelerate locating a selected record, but is not mandatory. When the full sort tuple is available, binary search may locate the record without another full-sized index. The initial sorting algorithm is interruptible stable merge sort; section 6 defines its execution and memory rules.

5.4 Mapping the viewport

Store vertical position as {top_rank: u64, subrow_px: f64}. Only local row differences are converted into pixel coordinates, avoiding a giant floating-point scroll position. Prefix sums of column widths locate the visible columns. Preparation and painting are limited to the visible rectangle plus a bounded margin.

For R visible rows, C visible columns and preview length capped at L, painting costs O(RCL). Rank mapping can add O(R log(B+1)) for B membership shards; source value lookup has its own cost and is excluded from the paint pass. Tile count, preview bytes, text-shaping cache and pinned-column width all have explicit limits. Releasing large results must also yield or run away from the UI thread.

6. Query execution

6.1 Building and publishing a result

A query starts by compiling the typed predicates and reserving its peak memory. It scans the source in bounded batches, builds membership, and finishes the requested ordering. Only after the result is complete and its delivery ticket still matches the current request does it replace the displayed snapshot. Publication is atomic: the grid never combines membership from one query with ordering from another.

The scan first visits the block containing the current source-row scroll anchor, then the cursor block, and then expands outward without revisiting blocks. This produces useful local evidence early. Progress reports exact inspected and matched counts, but the main grid retains its previous completed result. A later preview may expose local matches separately; it must not present unexamined rows as nonmatches or provisional positions as final ranks.

Sorting initially uses interruptible stable merge sort over the complete filtered set. Reservations include full-width keys and the merge scratch buffer as well as the output permutation. Cancellation checkpoints occur during key extraction and merging, not just between whole phases. An operation that cannot fit its reservation fails with a diagnostic while preserving the committed result.

6.2 Scheduling and cancellation

Native jobs run on a shared executor with bounded concurrency. Requests for visible cell tiles have priority over background scans. The current wasm host uses unshared memory, so work runs in cooperative steps scheduled through MessageChannel, initially targeting 2 ms slices. Long string comparisons, value formatting, allocations and releases need checkpoints as well. Declaring a CPU loop async does not make it interruptible; copying complete raw objects into workers is not the proposed solution.

A delivery ticket identifies the document, panel, input revisions and individual submission. Cancellation or retry increments the submission number. An identical recipe may reuse cached data, but must not make a cancelled submission current again. Query, tile, Find and export jobs have separate tickets, so changing a query does not accidentally cancel unrelated navigation.

QueryTicket = (document_generation, panel_id, source_revision,
               recipe_revision, predicate_revision, order_revision, submission)
TileTicket  = (QueryTicket, columns_revision, format_revision, request)

A mismatched ticket causes the delivered result to be discarded. A failed job leaves the committed snapshot available and reports the failure. A completed current job swaps in the new snapshot and restores the stable row anchor. Progress uses a mailbox that retains the latest update rather than an unbounded event queue; each job may have at most one unacknowledged snapshot. Old snapshots retained for display or export remain charged to the shared memory budget.

7. Memory limits

A small visible table can refer to a large dataset. Before starting an operation, account for the raw source objects, row domains, current and replacement query results, temporary query buffers, prepared tiles and snapshots retained by exports. Shared allocations are counted once at their owner. The table’s allowance is part of the existing client-wide budget, rather than an independent pool that can exceed it.

7.2 Limits of the current transaction owner

The current LoadedGenerator allocates 2 × next_power_of_two(N) u64 entries for its max-end tree. At 300 million records, that tree alone occupies 8 GiB, before transaction records, strings, attributes, relations and ID lookup. A procedural demo with that many logical rows therefore does not imply support for a resident generator of that size in default wasm32.

If real workloads require greater capacity, candidate changes belong in the source owner: borrowed columnar record views, a compact ID index or a block max-end tree. With 4,096 records per leaf, the tree payload at this scale is about 2 MiB, but exact overlap queries must scan candidate blocks and long overlapping intervals can remain expensive. The decoder must build the chosen representation directly rather than retaining two complete copies. Keep the current representation if the alternative regresses required operations.

These are capacity experiments, not prerequisites for the first table panel. Client-local disk spill for sorting is also a later feature; it requires quotas and failure handling and does not remove the requirement to load complete selected raw data. A persistent table cache or new storage format needs a measured use case before adoption.

8. Later extensions

The following capabilities build on the same source and query model. They are separated from the first-version interaction contract so that future work does not enlarge the initial toolbar or delay basic table navigation.

8.1 Scan coverage and match density

Scan coverage answers “which source rows have been examined?” Match density answers “how many examined rows matched in this region?” These are different quantities. For example, after scanning source rows 1–1,000, finding no matches says nothing about unexamined rows 1,001–2,000. An overview must distinguish unexamined regions, examined regions with no matches and examined regions containing matches.

For a complete result, a bin covering source positions [a,b) contains rank(b) − rank(a) matches. Every overview must state what its horizontal axis represents: canonical source positions, sorted result ranks or time. A table sorted by duration must not make its row-position overview look like a chronological timeline. Scan coverage is drawn from completed work, never inferred from the absence of matches.

8.2 Additional derived columns

Adding signals to an existing transaction table is a later extension. A sampled column reads the signal at each transaction’s start time, allowing the record to be compared with the hardware state at that moment.

For example, a transaction begins at 100 ns. The signal core.state changes to RUN at 90 ns and to WAIT at 110 ns. A column named core.state @ begin displays RUN for that transaction. It reads the signal history at the transaction’s begin time; it does not add rows for the signal’s changes. The column definition records the signal reference and whether it uses the last value strictly before the anchor or the last value at or before it.

This column therefore depends on both the transaction’s time anchor and the complete selected signal history. The client retains that history while the column is displayed or needed by an active query. Other panels reuse the same immutable history. Section 3 defines the behavior at repeated timestamps and for event signals.

An in-flight count reports how many transaction intervals contain the row’s time anchor. For closed intervals it is count(begin ≤ t) − count(end < t). Efficient evaluation requires sorted endpoint indexes or an equivalent source-owner query, with their memory and construction work explicitly budgeted. It is not the same operation as reading one stored cell.

A “difference from previous” column must define previous in source order or in displayed order. In the latter case its values change when the filter or sort changes, so those revisions are dependencies. Such a column cannot define its own sort order circularly. Each derived expression records the source objects and revisions it reads so that loading, reuse and invalidation follow its actual inputs.

8.3 Follow mode, ranges and export

Automatic Follow moves the table viewport as the shared cursor changes. Manual scrolling suspends Follow; an explicit resume action can use Locate. Follow does not change the selected record merely to keep the cursor visible.

Range selection pins its endpoints to a query snapshot. When a replacement query changes the result, the active row is preserved by key but obsolete ranges are cleared with a notice. Multi-row TSV export uses the pinned snapshot’s display order, quoting and byte limits. Large exports stream to a host-provided file sink rather than building one giant clipboard string. Cell/range keyboard navigation and an accessible paged reading mode extend the first version’s single-row access.

8.4 Progressive result publication

If the main grid later displays incomplete results, it needs an explicit partial-result mode. Only a contiguous completed prefix in canonical order can be published; out-of-order completed shards wait behind gaps. Counts are lower bounds, End reaches the known prefix, and full-result export is unavailable until completion. A viewport-first scan is biased toward the current location, so its match rate is not a statistically representative estimate of the full result.

8.5 Alternative indexing and sorting algorithms

A checkpointed signal merge may reduce memory compared with storing every union timestamp. Checkpoints retain source cursor positions and cumulative output ranks. Replay must be bounded by input records consumed, not merely by output rows produced: many repeated input timestamps can collapse into a single output row. Duplicate-run boundaries need an explicit representation or bounded lookup, and long seeks must yield. Compare memory, build time and cold random-access latency before choosing this design.

Bucket-based sorting is another experiment after the stable merge-sort baseline. Ordered buckets may be refined independently, but a bucket becomes visible in exact order only when refinement finishes. Navigating to an unfinished bucket shows a pending tile. Equal-key buckets can avoid comparisons; a skewed bucket containing many distinct keys still requires recursive partitioning, merge sorting or an explicit refusal. Refinement never runs inside paint, and two partition passes do not imply a universal responsiveness guarantee.

9. Implementation and verification

9.1 Implementation sequence

Start with source, domain and typed-value contracts in volna-core/table/{source,domain,value}. Add missing source-owner queries where necessary, then transaction, signal and synthetic adapters. Verify row identity and sampling against a simple reference implementation before optimizing access.

Next implement membership, queries, jobs and budget accounting in table/{rowset,query,jobs,budget}. Establish exact rank/select, filtering, stable merge sorting, cancellation and atomic publication. Then add the model, layout and painting in table/{model,layout,paint}, with App delivery and the GPUI canvas and controls. These module names describe proposed ownership boundaries.

Finish the initial integration with versioned workspace settings, unresolved-source handling, selected-row copying and accessibility. Keep egui compatible without adding the table feature there. Checkpoint axes, persistent directories, bucket refinement, compact source owners and local spill follow only if measurements justify them.

9.2 Correctness and interaction checks

Reference tests cover repeated timestamps, strict clock edges, initial and unavailable values, aliases, repeated attributes and inclusive interval overlap. Membership tests cover all, empty, sparse and dense shards, a partial final shard and source domains beyond 2³² rows. Filter and sort results must agree with the reference implementation.

Opening checks cover context-menu selection scope, stream expansion and deduplication, default signal/transaction rows, and preservation of existing Enter/double-click routing. Verify that the source set stays fixed after sidebar selection changes, opening leaves Waves/Pipeline navigation unchanged, closing cancels pending work, and loaded histories are shared.

Job tests cover cancellation, stale delivery and released memory reservations. UI checks cover exact last-row navigation, selection after filter/sort changes, filtered-out cursor rows, input during scans, keyboard copying and context menus, themes, enlarged text and accessibility. Local and remote loading must produce equivalent behavior, including saved-source restoration and disconnection. Count explicit resource refusals as outcomes rather than omitting them from results.

9.3 Performance measurements

Initial targets are p95 table-owned frame work below 8 ms, no table-owned UI task above 16 ms, and p95 cancellation acknowledgement below 50 ms on declared hardware. These are targets, not measured results. Report cell lookup, formatting, text shaping, Scene generation, GPU presentation and input-to-paint latency separately. A complete scan depends on data size and predicates; there is no universal subsecond target.

Exercise 10,000–300 million logical rows while distinguishing generated rows from resident datasets. Vary column count across 6, 64 and 1,024; navigate to the beginning, middle and end; and vary filter selectivity from 0% to 100%. Include clustered and adversarial sort keys, long strings and buses, duplicate timestamps, long intervals, concurrent panels and export during query replacement. Test native GPUI and the default single-threaded wasm/VS Code host.

For each optimization, compare the baseline and candidate on build time, random-seek latency, complete-query time and peak memory together. Retain the simpler design unless the measurements justify the additional mechanism. Run cargo test -p volna-core, volna/volna/check.sh and the GPUI verification workflow for implementation changes. Encoding or reader-decode changes also require the repository’s previous-commit A/B comparison and full benchmark suite; format changes require versioning, specification updates and round-trip coverage. This document itself changes neither runtime nor trace format.

10. Design references

The Astra proposal provides the ownership model, immutable query snapshots, prepared cell tiles, cancellation tickets and memory accounting. The Claude proposal contributes cross-source columns, viewport-first scanning and the checkpoint and density-overview ideas. This specification keeps those ideas but separates first-version requirements from experiments.

The Atlas prototype provides reference work on rank/select, two-axis culling, independent Find and filtering, and benchmark methodology. Its storage model and egui measurements are not Volna implementation results. Grid and analytics references discussed in the source proposals inform typed batches, late value projection, adaptive membership and block statistics; this document does not claim a new audit or comparative performance ranking of those projects.

The governing requirements remain GOAL.md, the Volna architecture and the client–server design. Consult the rationale before retrying previously measured alternatives, and update the architecture and rationale when the design is implemented.
