Debugging CHI coherence on the XiangShan ring, from one VTR file

A coherent read on the dual-core XiangShan system is not one bus handshake. It is a request, a directory lookup, snoops, data forwarded by another cache or sent by memory, and an acknowledgement, spread over five agents and an eleven-stop ring. This proposal records all of it as ordinary VTR transactions and relations. A VDB profile adds CHI meaning, and Volna gets five views over the same records: one transaction's flow, the ring, the history of one cache line, latency, and hangs.

Proposal with interactive demos, 27 September 2026. The system is the one in xiangshan-zhujiang-dualcore.html: its ring order, node IDs, friend ports, routes and its three guided flows are reused here unchanged. The panels build on tx-detail.html (the detail panel on the right of every mock), transaction-waveforms.html, table-panel.html and pipeline-view.html. All mocks read one trace, which a small cycle-level model of that system generates in this page ( records, flits, cycles). The model injects one fault near the end, so the run hangs the way a failing regression does. What the model is says what is modelled and what is not.

Recommendation: six decisions

  1. CHI goes into VTR as transactions and relations, with no format change. Each agent records what it sees locally. A requester records its requests, the home one entry per allocation in its point of serialization, the SN its memory accesses, and the ring every flit. The identifiers CHI already carries (TxnID, DBID, FwdTxnID, ReturnTxnID, HomeNID) resolve each record's parent and each flit's receiver while the simulation runs. VTR's streams, stages, parents and relations hold all of it, so no new section, value tag or version is needed.
  2. CHI meaning lives in a VDB profile. The profile holds channel and state colours, opcode classes, stage roles for latency accounting, and the ring's drawing. It also maps each producer's attribute names to CHI roles, so traces from CHIron, a VIP or another NoC work without renaming. The trace itself stays neutral, as the README's VTR/VDB boundary requires.
  3. The primary view is a flow: one transaction's records as a space-time diagram on the shared time axis. Lifelines are rows, messages are slanted arrows, and each record shows its stages. The critical path is marked, and other traffic on the same line stays visible as context. Proposal A.
  4. The network is shown as a map plus a Marey chart, both derived from flit transits. A flit on ZhuJiang's ring never stalls, so its inject time and route give every hop, and no per-hop record is needed. Proposal B.
  5. Lines, latency and hangs are analyses over loaded records, not new data. The history of one cache line, the latency heatmap with its breakdown, the wait-for chain of a hang and the protocol checks are all computed in volna-core from the same records. Their results are annotations and never go back into VTR. Proposals C, D and E.
  6. Every view is a query first. The flow tree, the critical path, a line's history and the wait chain are core functions with text results. An agent connected through MCP asks “why is still open?” and gets the same chain the Hang panel draws.

What a CHI debugger must answer

Waveforms of the CHI channels answer none of these questions directly. The flits are there, but one transaction's flits are spread over several ports and channels. Matching them requires the identifier rules of the specification, and some links, such as which request caused a snoop, are not in any flit at all. Every tool surveyed below starts by reconstructing transactions. They differ in what they draw afterwards.

What other tools do

The survey covered commercial protocol debuggers, Arm's CMN tooling, XiangShan's own tools, NoC visualizers, coherence and memory-model tools, and distributed tracing, which has solved causality across many agents at a much larger scale. The reference numbers in brackets point to the list at the end.

Protocol debuggers

Synopsys Verdi Protocol Analyzer shows a layered transfer, transaction, packet and handshake view in bus order. Selecting a parent highlights every linked child, and an error jumps to the matching transactions and signals. The CHI VIP adds system-level coherency and data-integrity checks, and Performance Analyzer flags min/max constraint violations [13–16]. Cadence Indago's protocol app has a channel viewer, a state-machine viewer, a “life story” of one object and a filtered smart log with saved sessions [17, 18]. Siemens QVIP has a cache-coherency monitor that links the originating request, its snoops and the subordinate access. The Avery CHI VIP writes cache-state trackers per home and requester [20, 21]. All of them are tied to their vendor's VIP and database, and little of their CHI-specific UI is documented publicly.

Arm CMN

CMN-700 puts a debug and trace monitor (DTM) in each crosspoint with four flit watchpoints. A watchpoint can count, trace or set the CHI TraceTag bit, which every response and spawned packet must copy [1, 6]. Arm's cmn_latency script uses that bit to sample one transaction's packets in latency order. cmn_diagram prints the mesh [11]. The ARCS 2024 study located nodes on a real mesh from counter heatmaps. It draws a hatched cell for “not observed”, which is different from zero, and it had to correct for mirrored columns [33]. On silicon only sampling is possible. A simulation trace has every flit, which is the advantage this design builds on.

XiangShan's own tools

XiangShan's ChiselDB writes probes into SQLite through DPI-C. Its TL-Log and CHILog tables are queried with SQL and printed as text [24]. In the pinned source, CHILogger is instantiated only for the OpenLLC configurations (Top.scala 492–537), not for the ZhuJiang connection that follows it, and it keeps TxnID-to-address tables in hardware so it can put addresses on responses. CHIron's CloganGUI reads those logs [25]. It has a flit table, a transaction view built from several candidate ID keys, a per-requester cache-line board, an address view, latency box plots by opcode and response, and an A/B latency diff between two traces. It is the closest existing tool to this proposal. ZhuJiang has a traffic board: a DPI-C FlitMonitor at every router's inject and eject port, a scoreboard keyed by target and channel, and a 500-cycle timeout (xijiang/tfb). XSTop turns it off (tfbParams = None). DongJiang's ReqPerf already classifies every request as HIT, DCT, DMT or non-DMT and measures its front-end and total latency.

NoC visualization

Loupe animates flits on a mesh from gem5 Garnet traces. It colours buffers and links by occupancy and marks the flits of a cyclic dependency in red. Its README warns that jumping back in time gives wrong state, a reminder that state must be random-access [35, 36]. NoCVision charts any per-router or per-link metric in interval, plot and event modes, with sum/max/min/average aggregation [37]. Vis4Mesh adds a transaction-versus-time overview with brushing and three sets of filters, and it scales to very large meshes through hierarchical packing [38]. BookSim's viewer is marked as not working in its own manual [39].

Coherence and memory models

gem5's ProtocolTrace writes one line per controller transition (tick, node, event, old>new, address) and warns that it grows very large [26]. The gem5 Sequencer keeps a latency split for every miss: issue to initial, initial to forward, forward to first response, first response to completion [28]. The Vivio MESI animation colours the lines of the current transaction and greys out stale memory [29]. herd7 draws execution graphs with po, rf, co and fr edges and has a “squished” mode for dense ones [31]. perf c2c ranks cache lines by remote HITM and breaks the hot ones down by offset, thread and code. It is the standard false-sharing table [32].

Distributed tracing and message diagrams

Lamport's space-time diagram, with processes as lines and messages as arrows between them, is the grammar of every CHI flow figure [40]. The CHI specification draws its own flows that way, with a lifetime bar per node, a marker where a request is blocked and inline state changes such as I→UC [1]. ShiViz links the diagram and the log both ways, collapses local events, hides hosts, searches for communication motifs and diffs two executions. It slows down beyond about 5,000 events [41]. Dapper goes from a table of patterns to a latency histogram, then to example traces, then to one trace, where each call is split into server time and network time [42]. Jaeger and Uber's CRISP compute the critical path by walking backwards through the last-returning child and aggregate it at P50, P95 and P99 [43, 44]. Perfetto draws flow arrows between slices and follows only direct flows by default, because following whole chains made dense traces unusable [46, 47]. The Wireshark flow graph and Mermaid sequence diagrams are the familiar ladder form [48, 49]. For many overlapping operations, Brendan Gregg's latency heatmap shows bimodal distributions that averages hide [50]. Brushing and linking connects the plots [52], and Little's law checks occupancy against latency and throughput [53].

Taken

  • Transactions as span trees with explicit causal IDs: Dapper, OpenTelemetry, and the CHI identifiers themselves.
  • Space-time diagrams with lifetime bars, inline state changes and blocked markers: the CHI specification and Lamport.
  • The critical path by last-arriving input, and its aggregation: Jaeger, CRISP and the gem5 Sequencer.
  • Distribution first, then examples: Dapper, Gregg, and CloganGUI's box plots.
  • A topology heatmap with a separate “no data” style: NoCVision and the ARCS figures.
  • A ranked hot-line table: perf c2c.
  • A per-line state board: CloganGUI and the Avery trackers.
  • Watchdogs over in-flight tables: ZhuJiang's traffic board and rocket-chip's TLMonitor.
  • Loupe's red cycle for deadlocks.

Rejected

  • A flit table as the main view (ChiselDB, CloganGUI): it is correct but you have to read it row by row, and it hides causality.
  • A ladder diagram as the default: its time axis runs down, so it cannot share the Waves panel's time axis. It stays available as a layout.
  • Forward-only animation (Loupe): state must be exact at any seek.
  • Transitive flow highlighting by default (Perfetto's original behaviour): dense traces become unreadable.
  • Heuristic stitching by time and address alone: it cannot tell which request caused a snoop without a fwd field. Only the home knows, so the home records it.
  • A separate database format such as SQLite beside the trace: VTR already holds transactions, relations and logs.

What the trace holds

The recording follows the rule VTR already has for pipelines: record what cannot be derived, name it stably, and link it. A CHI system has four kinds of agents, and each one records the part of a transaction that it alone can see. The hierarchy below is the model trace's, with record counts. It sits in a root scope TX outside the instance tree, like the C910 tracer's TX.core0. Each node scope carries its node ID, CHI node type, ring stop and RTL instance path as attributes.

Messages are relations. A flit's parent is the record that sent it, and a received_by relation names the record that consumed it. Every arrow in the Flow panel is therefore one flit between two records, and nothing is matched after the fact. Two more relation kinds carry causes that are not parenthood. blocked_by links a home entry to the entry it waited behind in the point of serialization. evicts links a fill to the write-back of its victim, in a requester or in the LLC.

Identifiers resolve the links while the simulation runs. Each monitor keeps small key spaces in vtr_track, as the C910 pipeline tracer does. It looks up the key a flit carries and gets the VTR record it belongs to. The rules are those of the specification (IHI0050 §B2.4–B2.5 [1]):

  • A request, CompData or a response to a request: (SrcID or TgtID, TxnID) in the requester's key space.
  • CompAck and write data: (TgtID, TxnID = DBID) in the home's or SN's DBID space.
  • DCT: the forwarded CompData carries TxnID = FwdTxnID for the requester, and DBID = the snoop's TxnID for the home's CompAck.
  • DMT: the SN's CompData carries TxnID = ReturnTxnID, DBID = the home's ReadNoSnp TxnID and HomeNID = the port that sent it. One flit therefore links parent and child.
  • Snoops: (home port, TxnID) in the home's snoop space. CHI snoop flits have no TgtID, so the capture port is the target. ZhuJiang's ring adds a target for routing anyway.

One link cannot come from identifiers: which request made the home snoop. Forwarding snoops name the requester in FwdNID, but invalidating snoops and snoop-filter back-invalidations name nobody [1]. The home monitor therefore records the parent itself, at the moment SnoopCM issues the snoop. This is why the design records at the agents and does not stitch a flit log afterwards.

Attributes. Keys with the chi. prefix hold the flit fields: opcode as an enum, TxnID, DBID, SrcID, TgtID, HomeNID, FwdNID, ReturnNID, Resp, FwdState, address, DataID, and optionally a 64-bit fold of the data. Requester records add chi.state_before and chi.state_after, read from the L2 directory. Home entries add DongJiang's own view under dj.: the snoop filter and LLC state before and after, the decoded path, and the block reason. Addresses are line addresses. A real capture must also key on the physical address space (NS), because two lines with the same address in different spaces are different lines [1]. Link flits (opcode 0) are not transactions and are not recorded. Keys are data, not presentation, and VTR reserves none of them.

Capture points in the pinned XiangShan

  1. Ring: ZhuJiang already instantiates FlitMonitor at every router's inject and eject port when tfbParams is set. It calls tfb_flit_monitor through DPI-C with the node, the channel and the whole flit. A VTR-backed implementation of that one function records the transits, and XSTop only needs to stop setting tfbParams = None.
  2. Requesters: a bound monitor on CoupledL2's CHI port, the same point CHILogger wraps in the OpenLLC configurations. The L2 directory read gives the state before and after.
  3. Homes: DongJiang's PoS allocation and release, the block reasons in Block.scala (pos, dir, resp), the directory read and write, the SnoopCM and ReadCM issue points, and Commit. ReqPerf already derives the path, so the monitor copies it.
  4. SN: the AxiBridge's AR/R and AW/W/B handshakes, keyed by the ERQ TxnID.

As with the C910 tracer, these are SystemVerilog modules from the vtr_trace package, bound to unchanged RTL and writing through the keyed tracker. The model in this page writes records for cycles of two harts. Size and write-time cost on a real XiangShan run must be measured before any claim is made, which is the first step of the plan.

The CHI profile in VDB

VTR says what happened, and the profile says what it means and how it looks. Like the pipeline profile in VDB_APPNOTE.md, it is a list of selectors over stable names with semantics attached. It has four parts. Roles tell the core analyses which streams are requesters, homes, subordinates and flits, and which attribute keys hold the CHI fields. Another producer writes a new role table and reuses everything else. Stage roles assign each stage to a latency category, which gives the critical-path colours. Palette covers channels, cache states, paths and stages. Topology places ring stops or mesh crosspoints on the map. Ring order and node IDs are runtime facts in VTR, but the drawing is presentation.

Proposal A · Flow panel

One transaction, every agent, one time axis

The Flow panel draws the record tree of one transaction as a space-time diagram. Rows are the agents. Each record is a bar on its agent's row, coloured by its stages. Each flit is an arrow from the sender's bar at its inject time to the receiver's bar at its arrival, and a dashed lead-in marks any wait to inject. The panel shares the document's time axis and cursor with Waves, so the handshakes that carried a flit line up under its arrow. The steps below are the three flows of the XiangShan diagram, as they occur in the trace, followed by three cases it does not animate.

How it works

The tree comes from parents, the arrows from relations. Selecting any record (a flit, a snoop or a home entry) climbs parents to the requester's record and then collects the records below it. The panel draws exactly those, with the flits whose sender or receiver is among them. No timing heuristics are involved, so a DCT arrow from CC1 to CC0 is drawn because the forwarded CompData's received_by says so.

The critical path is walked backwards. It starts at the requester's end, goes to the last input that arrived before it, then to the record that sent that input, and repeats until it reaches the request. This is CRISP's rule. Each segment is either time inside a record, split by its stages, or time on the ring. The profile's stage roles turn the segments into the categories in the detail panel's bar, and they always add up to the latency.

Context is explicit. Same line adds the other records on this address in the window, faintly, and all adds every record. Double-clicking one opens its flow. Nothing is chosen automatically. The same record always opens the same diagram.

Why a swimlane and not a ladder

The specification, Wireshark and Mermaid draw ladders, with time running down. One transaction reads well that way, which is why the layout is offered. But Volna's panels share a horizontal time axis. A Flow panel docked under Waves then shows, for example, that the second CompData beat is the one that stretched rxdat's valid high. That alignment is worth more than a familiar form.

Inline state changes such as I→SC and SF cc1→cc0+cc1 come from the records' state_before/state_after and dj.sf_* attributes. They follow the specification's figures, which print state transitions next to the lifetime bars.

Scale. A tree is 3–12 records and 4–20 flits, so the panel does no bounded-work tricks for its own records. Context uses the window query that transaction lanes already use and caps what it draws.

Proposal B · Ring panel

Where the ring is busy, and who waits for it

A ring or mesh needs a map, but a map shows one instant or one sum. The Ring panel pairs the map with a Marey chart, the train-timetable diagram. Stops go down in ring order and time goes across, and every flit is a line through the stops it passes, one stop per cycle. A flit going index-increasing runs downward and one going index-decreasing runs upward. A dashed start is a wait to inject, and bundles of parallel lines show congestion. Dragging across the chart picks the window the map sums over, clicking places the cursor, and the dots on the map are the flits on the ring at the cursor.

Derived, not recorded

ZhuJiang's routers pass ring flits through one register per stop, and a flit already on the ring always has priority over injection. Once injected, a flit is therefore at stop path[k] at cycle inject + k. The panel builds per-link prefix sums from the flit records once, and any window's utilization is then two lookups. Recording each hop would multiply the flit data by the hop count and add nothing. A fabric whose flits can stall in flight, such as a mesh with credit-based buffers, would record hop events as stages of the flit record, and the chart would draw them unchanged.

Random access by construction. Loupe could only step forward, because it replayed state. Here the state at any cycle is a query over records, so seeking backwards is as exact as playing forwards.

What the map encodes

Each link has an outer arc for the index-increasing ring and an inner arc for the index-decreasing ring. Each arc has one lane per channel ring (REQ, RSP, DAT and HRQ, which carries SNP and ERQ), coloured by the fraction of cycles in the window that a flit occupied it. The scale's maximum is printed. An orange ring around a stop is proportional to the cycles that flits waited there to inject. Stops that carry no traffic in this build (RNI, MN and the pipeline stop) are drawn dim, as the XiangShan diagram marks them.

For a mesh, the same panel places crosspoints on a grid from VDB coordinates and draws the Marey rows per crosspoint in XY order. The chart then shows turns as bends. That is the case for CMN, where Arm's tools print the grid from discovery data.

Proposal C · Line history

Who held this line, and what happened to its data

Coherence bugs are about one address: two writers, a reader that got stale data, a snoop filter that no longer matches the caches, or two cores fighting over a line. The line view gathers every record of one address. It rebuilds each cache's state over time from the requester and snoop records, and the snoop filter and LLC from the home's records. Below that it shows the data values as they moved between caches, and at the bottom the transactions and home entries. The table on the left ranks lines by how often ownership moved between cores, like perf c2c's shared-data table.

States from messages, and what they cannot show

A cache's state changes when its request completes, when it answers a snoop, or when its write-back leaves. Requester and snoop records carry the state before and after, so the rows need no protocol table. Some changes are silent: CHI lets a UC line become UD on a store without any message. The row then shows the last known state until a later record reveals the change. When a snoop or write-back reports a dirty line the view believed clean, the interval since the last message is drawn hatched in both colours. The view does not guess when the store happened.

Invariants are checked on the rebuilt rows, not by the simulator. There is at most one unique owner, or any number of sharers, and at every home lookup the snoop filter must match the caches. A violation would be drawn red at the cycle where it happens. On this trace both rules hold for all lines.

Data provenance

When data flits carry a fold of their payload (chi.data), the data row shows each transfer as a chip coloured by value. A chip's colour changes only where a store happened, and a reader that receives an older colour than the last one written has read stale data. That is the question behind most coherence failures that difftest reports. Recording the fold costs 8 bytes per data flit and is optional.

Where it lives in Volna

The rows are derived rows in the Waves panel. An analysis that takes (address, agent) produces a state track, which the enum painter draws like any other value row. The table is a Table panel over a derived source, the same kind of synthetic source table-panel.html reserves. No new panel kind is needed. The mock puts both in one frame.

Proposal D · Latency panel

Distribution first, then the transaction

Every request is a dot, placed by issue time and latency on a log scale and coloured by where its data came from. Bands form at once: LLC hits, DCT and memory, and whatever sits above its band has a story. Dragging a rectangle selects a group. The panel on the right then shows its percentiles and the mean critical-path breakdown of the group. Below the plot, occupancy rows show how many requests each L2, home and the SN held at every moment, so a latency rise can be checked against queueing with Little's law. Clicking a dot selects that request, and the Flow panel above shows it.

The breakdown is the critical path, summed

The bar on the right is the average of the selected requests' critical paths from Proposal A, by category: requester, ring, inject wait, home pipeline, same-line wait, peer cache and memory. Averaging critical paths, not stage durations, is what makes the parts add up to the mean latency. Time spent waiting for something that was not on the path does not count. CRISP aggregates the same way, and the gem5 Sequencer's four-part split is a fixed special case of it.

Heatmap or dots. Dots show individual outliers but saturate in dense regions. The heatmap counts requests per cell and keeps a bimodal distribution visible at any density. Both use the same axes and the same brush.

Not CHI-specific

Latency against time works for any generator whose records have a duration: AXI bursts, TileLink transactions, OpenTelemetry spans. The breakdown needs parents or relations plus stage roles, so it works wherever a VDB profile names them. It is proposed as a general panel that CHI is the first user of.

Occupancy is the number of open records per generator, averaged per pixel column. Little's law (mean occupancy = throughput × mean latency) is printed for the brushed window, so a queue that the latency blames can be checked against the queue itself.

Proposal E · Hang and checks

Why the run stopped

The trace ends with difftest's watchdog. The Hang panel starts where a debugging session does, at the end. It lists every record still open, grouped by what it waits for. It follows those waits (blocked_by relations, home entries waiting for a CompAck, requesters waiting for their home entry) to the record at the end of the chain, and it runs the protocol checks over the whole trace. Each finding selects the records involved, so the other panels open on them.

Wait edges come from records

An open home entry whose last stage is blocked waits for the entry its blocked_by relation names. An open entry in wait CompAck waits for its parent, the requester. An open requester waits for its home entry. The chain ends at a record that is not waiting on anything open. Here that is a requester record that closed normally, which is a contradiction the checker also reports: it received its data and never sent CompAck.

Cycles. A true deadlock is a cycle in this graph. It is drawn red, as Loupe marks deadlocked flits. Credit waits would add edges from records to link resources, once the link layer's L-credits are recorded (see open questions).

Checks are analyses, results are annotations

The rules run in volna-core over loaded records and produce findings with record IDs and times. They are never written into the trace, because they are one tool's opinion, and a checker that runs in the simulation writes its messages as LOG records like any other log. The first set covers what this trace needs: CompAck after data when ExpCompAck is set, home entries finishing within the traffic board's 500 cycles, every flit having a receiver, TxnID reuse only after all responses, one unique owner per line, and the snoop filter matching the caches.

The injected fault is in the model, not in XiangShan. After cycle 6760, CC0's L2 drops a CompAck that loses its TXRSP port to a snoop response in the same cycle. The page uses it because it hangs the run the way a real lost acknowledgement does.

How it lands in Volna

The five views need two new panel kinds (Flow and Topology), one general panel that is not CHI-specific (Latency), derived rows in Waves, and a set of core queries. Everything else already exists: the document selection, the transaction detail panel, window queries over loaded generators, and workspaces.

Loading. The CHI views need several generators together. One command, Open CHI views on the TX.chi scope, loads the generators the profile names. Locally that means mapped blocks. Alternatives considered

Rejected for the trace

  • Flits only, stitched afterwards. This is simplest for the producer, and it is how CHILog and CHIron work. It cannot know which request caused a non-forwarding snoop or an LLC victim write, and it must guess retry chains. The home monitor records those links at no extra cost.
  • Reconstructed transactions only, without flits. Smaller, but the ring views and message arrows need transit times, and checks such as “every flit has a receiver” need the flits.
  • Cache states as signals, one per line and agent. Unbounded in count. States are properties of messages, and a derived row rebuilds them for the one line being viewed.
  • A CHI section in the format. It would put protocol semantics into VTR. Stages, parents and relations already express everything, and the README reserves semantics for VDB.
  • Per-hop records on the ring. They are derivable (see Proposal B) and would multiply flit volume by the hop count.

Rejected for the views

  • An animated block diagram as the main debug view (the XiangShan page's player, Vivio). It is excellent for teaching one flow and poor for finding one. It stays a documentation device.
  • A Sankey or chord diagram of traffic between nodes. It shows volume and loses time, which is the dimension every question above needs.
  • One giant sequence diagram of all traffic. ShiViz shows where that stops scaling. Context in the Flow panel is bounded and optional.
  • 3D mesh views. Occlusion and no shared axis. The Marey chart shows the same flits flat.
  • Automatic panel layouts for CHI traces. Volna opens every trace the same way, and Open CHI views is an explicit command.
  • Averaged stage durations as the breakdown. They overlap and do not add up. The critical path does.

  1. Record a real run and measure it. A VTR sink for ZhuJiang's tfb_flit_monitor, plus requester, home and SN monitors in the vtr_trace package, bound to the pinned XiangShan with tfbParams enabled. Run the dual-core CoreMark and a coherence stress test, then report size, write time and read time against the same run without CHI recording, as AGENTS.md requires. Done when vtr tx shows the three guided flows of the XiangShan diagram in the recorded file, and a headless test compares their flit sequences with that page's steps.
  2.   3. Flow panel in GPUI with display-list tests: arrows between the right bars, critical-path marks, both layouts, workspace round trip.
  4. Latency panel and derived rows, general first, then with the CHI profile.
  5. Topology panel with ring and mesh layouts.
  6. MCP adapter exposing the queries as text.

The self-test line at the bottom of the page reports the same invariants.

What the model is

The trace is generated when the page loads, by about 600 lines of JavaScript, and nothing is precomputed. Taken from the XiangShan source (through the XiangShan diagram's literal port):

  • the ring of 11 stops;
  • node IDs as index × 8;
  • friend ports and routing direction;
  • bank selection by PA[12] and directory bank by PA[6];
  • DongJiang's decisions: DCT through forwarding snoops, LLC hits that invalidate the LLC copy, DMT with ReturnNID, the LLC filled only by write-backs of lines no other L2 holds, and SC_PD snoop data written to memory;
  • CompAck to HomeNID;
  • L2 TxnIDs as MSHR indexes.

Simplified or invented:

  • all latencies (home pipeline 6 cycles, snoop service 7–12, memory 36–54 plus a 4-cycle return per line);
  • capacities (16 MSHRs, 40 L2 lines and 256 LLC lines, scaled down so that evictions happen in a short run);
  • two data beats per line;
  • no L1 and no TileLink;
  • no retries: DongJiang blocks in its PoS and sends no RetryAck; ZhuJiang's source only defines the opcode;
  • no link-layer credits;
  • the workload;
  • the fault.

The panels do not depend on any of these. They read records.

Open questions

  • Link credits. Recording L-credit grants as events on a per-link record would make credit starvation visible as wait edges. Is it worth the volume, or should credit counters be analog signals (c910-perf-counters.html) sampled per cycle?
  • Retries. CHI allows a retried request to use a new TxnID, and nothing links the attempts [1]. For homes that retry (CMN, OpenLLC), should the monitor record a retry_of relation from the home's point of view, where P-credit allocation makes the link certain?
  • TileLink below CHI. Linking the L1's AcquireBlock to the L2 request would make the core's view the true root. That is a CoupledL2 monitor on the TileLink side with a parent link. It is out of scope here but it uses the same rules.
  • Two runs. CloganGUI's A/B latency diff and Konata's overlay suggest a comparison mode for the Latency panel. Which identity pairs requests across runs: address plus order, or a core-side instruction ID?
  • Physical address space. Should the address index key on (PAS, address) always, or only when the profile says the system has more than one PAS?
