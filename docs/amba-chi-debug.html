Debugging CHI coherence on the XiangShan ring, from one VTR file

A coherent read on the dual-core XiangShan system is not one bus handshake. It is a request, a directory lookup, snoops, data from another cache or from memory, and an acknowledgement, spread over five agents and an eleven-stop ring. This proposal records each agent's part as ordinary VTR transactions linked by parents and relations. volna-core reads them through a causal model that is not tied to any protocol, and one VDB profile supplies the CHI meaning. Five Volna views follow from that: one transaction's flow, the ring, the history of a cache line, latency, and hangs. A second pack, for a UCIe link between two chiplets carrying CXL.mem, runs the same views on a second trace to show that nothing in them is CHI.

Proposal with interactive demos, 27 September 2026. The system is the one in xiangshan-zhujiang-dualcore.html, and its ring order, node IDs, friend ports and routes are reused here unchanged. The panels build on tx-detail.html (the detail panel on the right of every mock), transaction-waveforms.html, table-panel.html and pipeline panel. Every mock reads one trace, which a small cycle-level model of that system generates when the page loads: records, flits, cycles. The model injects one fault near the end, so the run hangs the way a failing regression does. The mocks follow the page's theme, drawing with Volna's One Dark and GitHub Light palettes.

The proposal in seven decisions

  1. Record causes where they happen, with no format change. Each agent records only what it alone can see: a requester its requests, a home one entry per allocation in its point of serialization, the SN its memory accesses, and the ring every flit. CHI's own identifiers (TxnID, DBID, FwdTxnID, ReturnTxnID, HomeNID) resolve each record's parent and each flit's receiver while the simulation runs. VTR's streams, stages, parents and relations already hold all of it.
  2. Analyse a causal model that knows no protocol. Six concepts cover the analyses: agent, work, cause, message, wait and subject. They map onto VTR scopes, transactions, parents and relations. volna-core indexes them once and answers every question the views ask, and none of its code names a CHI stream, opcode or state. The model in this page proves it: a test renames every stream, key and relation, and all results stay the same.
  3. Put CHI in a protocol pack: one VDB profile. The pack binds the six concepts to CHI names. It also holds the classes of reads, the latency categories, the parameters of the protocol rules, the ring's drawing and the colours, which are given as hues. A TileLink, AXI or OpenTelemetry pack is another document, not another code path. The UCIe section runs a second pack, for a die-to-die link with retry and credits, on the same code.
  4. The primary view is a flow: one transaction as a space-time diagram on the shared time axis. Lifelines are rows, messages are slanted arrows, and each record shows its stages. The critical path is marked, and other traffic on the same line can stay visible as context. Proposal A.
  5. The network is a map and a Marey chart, both drawn from message transits. A flit on ZhuJiang's ring never stalls once injected, so its inject time and route give every hop, and no per-hop record is needed. Where a message can stall or be dropped, as on a UCIe link, its record carries one stage per hop instead. Proposal B.
  6. Lines, latency and hangs are analyses, and their results are derived sources. A cache line's history, the latency distribution with its breakdown, the wait-for chain of a hang and the rule findings are computed from the same records. Panels show them like loaded data. Workspaces save the recipe, never the result, and nothing is written back into VTR. Proposals C, D and E.
  7. Every view is a query first. The flow tree, the critical path, a line's history and the wait chain each have a text form. An agent connected through MCP asks “why is still open?” and gets the chain the Hang panel draws.

Background

CHI in ten minutes

AMBA CHI is Arm's protocol for coherent interconnects [1, 3]. Components are nodes that exchange packets called flits over four channels. The protocol lets several caches hold copies of memory and keeps every copy correct while they read and write. To debug it you need four ideas: who the nodes are, what the channels carry, which states a cache line can be in, and how identifiers tie the flits of one transaction together.

States

A cache line in an RN-F is in one of five states, named along two axes [1]. Unique means no other cache holds it, so the owner may write without asking. Shared means others may hold it. Dirty means memory is out of date, and this cache must write the line back or pass it on.

CleanDirty
UniqueUC write without askingUD the only valid copy
SharedSC read onlySD read only, must pass it on
InvalidI no copy

The invariant every coherence check comes down to is single writer or many readers. At any time a line is Unique in at most one cache, or Shared in any number. A store to a UC line makes it UD with no message at all. The debugger has to show changes like that honestly: the line history marks them as a hatched interval (Proposal C).

Three ways to serve a read

A read that misses in CC0's L2 goes to the line's home. The home looks it up in its snoop filter and LLC and serves it in one of three ways, and each is a guided step in Proposal A:

  • Direct cache transfer (DCT). CC1 holds the line. The home snoops it with a forwarding snoop, and CC1 sends the data straight to CC0. Three nodes and five messages are involved, and the data never passes the home.
  • LLC hit. No cache holds it, but the home's LLC does. The home sends the data itself.
  • Direct memory transfer (DMT). Nobody has it. The home asks the SN, which sends the data straight to CC0.

In all three, CC0 finishes with a CompAck to the home, which lets the home release the line to the next request. The hang at the end of this page is one CompAck that was never sent.

Identifiers stitch a transaction together

No flit says which transaction it belongs to. Each carries a few identifiers, and each receiver matches the ones it expects: TxnID, which every requester and home allocates for its own requests, and DBID, which a node hands out to be addressed by later. A forwarding snoop copies the requester's node ID and TxnID into FwdNID and FwdTxnID, and a home asking memory copies them into ReturnNID and ReturnTxnID [1, §B2.4–B2.5]. Only the home knows, so the home's monitor records it as the snoop's parent at the moment it issues the snoop. That is the reason for recording at the agents, not stitching a flit log afterwards.

Waveforms of the CHI channels answer none of these questions directly. The flits are there, but one transaction's flits are spread over several ports and channels. What other tools do

The survey covered commercial protocol debuggers, Arm's CMN tooling, XiangShan's own tools, NoC visualizers, coherence and memory-model tools, and distributed tracing, which has solved causality across many agents at a much larger scale. The numbers in brackets point to the list at the end.

Protocol debuggers

Synopsys Verdi Protocol Analyzer shows transfers, transactions, packets and handshakes as layers, in bus order. Selecting a parent highlights every linked child, and an error jumps to the matching transactions and signals. The CHI VIP adds system-level coherency and data-integrity checks, and Performance Analyzer flags min/max constraint violations [13–16]. Cadence Indago's protocol app has a channel viewer, a state-machine viewer, a “life story” of one object and a filtered smart log with saved sessions [17, 18]. Siemens QVIP has a cache-coherency monitor that links the originating request, its snoops and the subordinate access. The Avery CHI VIP writes cache-state trackers per home and requester [20, 21]. All of them are tied to their vendor's VIP and database, and little of their CHI-specific UI is documented publicly.

Arm CMN

CMN-700 puts a debug and trace monitor (DTM) in each crosspoint with four flit watchpoints. A watchpoint can count, trace or set the CHI TraceTag bit, which every response and spawned packet must copy [1, 6]. Arm's cmn_latency script uses that bit to sample one transaction's packets in latency order. cmn_diagram prints the mesh [11]. The ARCS 2024 study located nodes on a real mesh from counter heatmaps. It draws a hatched cell for “not observed”, which is different from zero, and it had to correct for mirrored columns [33]. On silicon only sampling is possible. A simulation trace has every flit, which is the advantage this design builds on.

XiangShan's own tools

XiangShan's ChiselDB writes probes into SQLite through DPI-C. Its TL-Log and CHILog tables are queried with SQL and printed as text [24]. In the pinned source, CHILogger is instantiated only for the OpenLLC configurations (Top.scala 492–537), not for the ZhuJiang connection that follows them. It keeps TxnID-to-address tables in hardware so it can put addresses on responses. CHIron's CloganGUI reads those logs [25]. It has a flit table, a transaction view built from several candidate ID keys, a per-requester cache-line board, an address view, latency box plots by opcode and response, and an A/B latency diff between two traces. It is the closest existing tool to this proposal. ZhuJiang has a traffic board: a DPI-C FlitMonitor at every router's inject and eject port, a scoreboard keyed by target and channel, and a 500-cycle timeout (xijiang/tfb). XSTop turns it off (tfbParams = None). DongJiang's ReqPerf already classifies every request as HIT, DCT, DMT or non-DMT and measures its front-end and total latency.

NoC visualization

Loupe animates flits on a mesh from gem5 Garnet traces. It colours buffers and links by occupancy and marks the flits of a cyclic dependency in red. Its README warns that jumping back in time gives wrong state, a reminder that state must be random-access [35, 36]. NoCVision charts any per-router or per-link metric in interval, plot and event modes, with sum/max/min/average aggregation [37]. Vis4Mesh adds a transaction-versus-time overview with brushing and three sets of filters, and it scales to very large meshes through hierarchical packing [38]. BookSim's viewer is marked as not working in its own manual [39]. The oldest tool on the list is the time–distance diagram, which Charles Ibry drew for the Paris–Le Havre railway in the 1840s. Marey published it later, and it keeps his name [62].

Coherence and memory models

gem5's ProtocolTrace writes one line per controller transition (tick, node, event, old>new, address) and warns that it grows very large [26]. The gem5 Sequencer keeps a latency split for every miss: issue to initial, initial to forward, forward to first response, and first response to completion [28]. The Vivio MESI animation colours the lines of the current transaction and greys out stale memory [29]. herd7 draws execution graphs with po, rf, co and fr edges and has a “squished” mode for dense ones [31]. perf c2c ranks cache lines by remote HITM and breaks the hot ones down by offset, thread and code. It is the standard false-sharing table [32].

Distributed tracing and message diagrams

Lamport's space-time diagram, with processes as lines and messages as arrows between them, is the grammar of every CHI flow figure [40]. The CHI specification draws its own flows that way, with a lifetime bar per node, a marker where a request is blocked and inline state changes such as I→UC [1]. ShiViz links the diagram and the log both ways, collapses local events, hides hosts, searches for communication motifs and diffs two executions. It slows down beyond about 5,000 events [41]. Dapper goes from a table of patterns to a latency histogram, then to example traces, then to one trace, where each call is split into server time and network time [42]. Jaeger and Uber's CRISP compute the critical path by walking backwards through the last-returning child and aggregate it at P50, P95 and P99 [43, 44]. OpenTelemetry models a message as a producer span and a consumer span joined by a link, which is the shape of a flit here [45, 58]. Perfetto draws flow arrows between slices and follows only direct flows by default, because following whole chains made dense traces unusable [46, 47]. The Wireshark flow graph and Mermaid sequence diagrams are the familiar ladder form [48, 49]. For many overlapping operations, Brendan Gregg's latency heatmap shows bimodal distributions that averages hide [50]. Brushing and linking connects the plots [52], and Little's law checks occupancy against latency and throughput [53].

Taken

  • Transactions as span trees with explicit causal IDs, and messages as linked producer and consumer records: Dapper, OpenTelemetry, and the CHI identifiers themselves.
  • Space-time diagrams with lifetime bars, inline state changes and blocked markers: the CHI specification and Lamport.
  • The critical path by last-arriving input, and its aggregation: Jaeger, CRISP and the gem5 Sequencer.
  • Distribution first, then examples: Dapper, Gregg, and CloganGUI's box plots.
  • A topology heatmap with a separate “no data” style: NoCVision and the ARCS figures. A time–distance chart for movement: Ibry and Marey.
  • A ranked hot-line table: perf c2c. A per-line state board: CloganGUI and the Avery trackers.
  • Watchdogs over in-flight tables: ZhuJiang's traffic board and rocket-chip's TLMonitor. Loupe's red cycle for deadlocks.

Rejected

  • A flit table as the main view (ChiselDB, CloganGUI): it is correct but you have to read it row by row, and it hides causality.
  • A ladder diagram as the default: its time axis runs down, so it cannot share the Waves panel's time axis. It stays available as a layout.
  • Forward-only animation (Loupe): state must be exact at any seek.
  • Transitive flow highlighting by default (Perfetto's original behaviour): dense traces become unreadable.
  • Heuristic stitching by time and address alone: it cannot tell which request caused a snoop that names nobody.
  • A separate database format such as SQLite beside the trace: VTR already holds transactions, relations and logs.

Design

Architecture: a causal model, protocol packs, derived sources

CHI is the first coherent protocol Volna will show, but it will not be the last. XiangShan alone speaks TileLink between its L1 and L2, CHI above the L2, and AXI to memory. A debugger built around a CHI model would need a second model for each of them, and another for every link between chiplets. This design keeps one model, which describes causality and not protocols, and puts each protocol into data. The UCIe section tests that on a protocol with no coherence at all.

Principles

  1. Record causes where they are known. A parent or a relation is written by the monitor that knows it, at the moment it knows it. Nothing is inferred from timing afterwards.
  2. Derive everything else, exactly. Hops, cache states between messages, occupancy, critical paths and wait chains are computed from records by rules that are stated and tested. A derived value is never approximated. Where the records cannot decide, the view says so (the hatched silent upgrade).
  3. Attach meaning by name. The profile selects streams, generators, attribute keys, stage names and relation kinds by name, as VDB_APPNOTE.md requires. Selectors that match nothing are reported, and the rest keep working.
  4. One model, many protocols. volna-core knows six concepts. A protocol pack is a document that binds them. A new protocol needs a pack and, perhaps, a template or a parameter, never a new model. The UCIe section lists what its pack needed.
  5. Save recipes, not results. A line history, a latency selection or a rule run is saved in the workspace as the analysis, its arguments and the profile version. It is recomputed on load, so it follows the trace when the simulation is rerun.
  6. Text first. Every analysis has a text result before it has a picture. Panels draw it, and MCP and the CLI return it.

Queries and what they cost

Each view asks the core for a few results. Most are local: they read the records around one id or one time window through the reader's existing indexes (SPEC §7.3). A few are folds: one pass over the bound streams, run in the background, cancellable, with a progress bar like the table panel's bake store. Only folds touch the whole run.

Finding a record's children is the one lookup VTR has no index for. The parent field is stored in the child. The design uses the fact that a child begins inside its parent's lifetime in every binding so far, and looks up children with a window query over that lifetime. If a measured run shows this is too slow, the fix belongs in VTR: a parent-id range in the TX_BLOCK header, next to the existing relation ranges. That is a format change, and it would go through SPEC.md, the reader, a round-trip test and RATIONALE.md, as AGENTS.md requires.

Where results live

An analysis result is a derived source, the same kind of object as a loaded track. A state track is drawn by the Waves enum painter. Hot lines, open records and rule findings are Table panel sources, as table-panel.html reserves. A critical path is an overlay on the Flow panel and a bar in the detail panel. Findings are annotations: one tool's opinion, kept beside the trace and never inside it. A checker that runs in the simulation writes LOG records like any other log.

Scale and remote sessions

Local queries cost what they read. Folds read the bound streams once, and their results are small: a row per line, a count per bin, a finding per violation. Remotely, the server returns raw records only, as the client/server design requires, and profiles, analyses and presentation stay in the client. The model trace here is records. A long XiangShan run will be two to four orders of magnitude larger, so the plan measures before it promises.

Messages are relations. A flit's parent is the record that sent it, and a received_by relation names the record that consumed it. Every arrow in the Flow panel is therefore one flit between two records, and nothing is matched after the fact. Two more relation kinds carry causes that are not parenthood. blocked_by links a home entry to the entry it waited behind in the point of serialization. evicts links a fill to the write-back of its victim, in a requester or in the LLC.

Identifiers resolve the links while the simulation runs. Each monitor keeps small key spaces in vtr_track, as the C910 pipeline tracer does. It looks up the key a flit carries and gets the VTR record it belongs to, by the rules the primer's figure shows: (SrcID or TgtID, TxnID) in the requester's space, (TgtID, TxnID = DBID) in a home's or SN's DBID space, FwdTxnID and ReturnTxnID for data that skips the home, and the capture port for snoops, which have no TgtID.

Attributes. Keys with the chi. prefix hold the flit fields: opcode as an enum, TxnID, DBID, SrcID, TgtID, HomeNID, FwdNID, ReturnNID, Resp, FwdState, address, DataID, and optionally a 64-bit fold of the data. Requester records add chi.state_before and chi.state_after, read from the L2 directory. Home entries add DongJiang's own view under dj.: the snoop filter and LLC state before and after, the decoded path and the block reason. Addresses are line addresses. A real capture must also key on the physical address space (NS), because two lines with the same address in different spaces are different lines [1]. Link flits (opcode 0) are not transactions and are not recorded. Keys are data, not presentation, and VTR reserves none of them.

Capture points in the pinned XiangShan

  1. Ring: ZhuJiang already instantiates FlitMonitor at every router's inject and eject port when tfbParams is set. It calls tfb_flit_monitor through DPI-C with the node, the channel and the whole flit. A VTR-backed implementation of that one function records the transits, and XSTop only needs to stop setting tfbParams = None.
  2. Requesters: a bound monitor on CoupledL2's CHI port, the same point CHILogger wraps in the OpenLLC configurations. The L2 directory read gives the state before and after.
  3. Homes: DongJiang's PoS allocation and release, the block reasons in Block.scala (pos, dir, resp), the directory read and write, the SnoopCM and ReadCM issue points, and Commit. ReqPerf already derives the path, so the monitor copies it.
  4. SN: the AxiBridge's AR/R and AW/W/B handshakes, keyed by the ERQ TxnID.

As with the C910 tracer, these are SystemVerilog modules from the vtr_trace package, bound to unchanged RTL and writing through the keyed tracker. The model in this page writes records for cycles of two harts. The size and write-time cost on a real XiangShan run must be measured before any claim is made, and that is the first step of the plan.

VTR says what happened, and the profile says what it means and how it looks. Below is the whole profile the page runs on, printed from the same object the analyses read, with each hue shown as a swatch in the current theme. It has six parts. The binding maps the six concepts to CHI names. Classes name the paths a read can take. Latency assigns every stage to a category of the critical path. Rules give the parameters for the templates in volna-core. Topology says what the network is and whether hops are derived or recorded, and present says how to draw it: hues, captions, nouns, and the panels' rows and toggles. The UCIe pack has the same six parts.


  

    

      
Colours are hues, not hex values

      
Volna has One Dark, Dracula, Catppuccin, GitHub and VS Code themes, and users can install their own. A profile that fixed #6ea0ff for REQ would be right in one of them. Here the profile gives a hue per category, and the theme gives each tone a lightness and chroma in the perceptually even OKLCH space [61]: a line tone for arrows and dots, a fill tone for stage bars, and quiet and tint tones for backgrounds. This is the rule Volna's stage palette already follows, with one lightness per appearance. Switch the page's theme to see the same profile in both.

    

    

      
Binding is checked, and it is the only CHI knowledge

      
The analyses and the panels in this page read the trace only through this object. The page's test renames every stream (TX.chi becomes sys.fab), every attribute key, every relation kind and two stage names, both in the trace and in the profile. It then checks that every tree, critical path, history, wait chain and rule result is unchanged. It does the same for the UCIe pack, and it checks that the source of the causal module and of the panels names no CHI or UCIe term. When a profile loads in Volna, a selector that matches nothing is listed, the views that need it say what is missing, and the rest keep working.

How it works

      
The tree comes from parents, the arrows from relations. Selecting any record (a flit, a snoop or a home entry) climbs parents to the requester's record and then collects the records below it. The panel draws exactly those, with the flits whose sender or receiver is among them. No timing heuristics are involved, so a DCT arrow from CC1 to CC0 is drawn because the forwarded CompData's received_by says so.

      
The critical path is walked backwards. It starts at the requester's end, goes to the last input that arrived before it, then to the record that sent that input, and repeats until it reaches the request. This is CRISP's rule. Each segment is either time inside a record, split by its stages, or time on the ring. The profile's stage roles turn the segments into the categories in the detail panel's bar, and they always add up to the latency.

      
Context is explicit. Same line adds the other records on this address in the window, faintly, and all adds every record. Double-clicking one opens its flow. Nothing is chosen automatically. The same record always opens the same diagram.

    

    

      
Why a swimlane and not a ladder

      
The specification, Wireshark and Mermaid draw ladders, with time running down. One transaction reads well that way, which is why the layout is offered. But Volna's panels share a horizontal time axis. A Flow panel docked under Waves then shows, for example, that the second CompData beat is the one that stretched rxdat's valid high. That alignment is worth more than a familiar form.

      
Inline state changes such as I→SC and SF cc1→cc0+cc1 come from the records' state_before/state_after and dj.sf_* attributes. They follow the specification's figures, which print state transitions next to the lifetime bars.

      
Scale. A tree is 3–12 records and 4–20 flits, so the panel does no bounded-work tricks for its own records. Context uses the window query that transaction lanes already use and caps what it draws.

      
Not CHI-specific. The panel draws agents, work, stages and messages. The UCIe flow below is this panel on a second trace, with a flit that is cancelled, a Nak and a replay. An AXI interconnect trace with parent links, or an OpenTelemetry trace with producer and consumer spans, opens the same way under its own profile.

    

  






  
Proposal B · Ring panel

  
Where the ring is busy, and who waits for it

  

    
A ring or mesh needs a map, but a map shows one instant or one sum. The Ring panel pairs the map with a Marey chart, the railway time–distance diagram [62]. Stops go down in ring order and time goes across, and every flit is a line through the stops it passes, one stop per cycle. A flit going index-increasing runs downward and one going index-decreasing runs upward. A dashed start is a wait to inject, and bundles of parallel lines show congestion. Dragging across the chart picks the window the map sums over, clicking places the cursor, and the dots on the map are the flits on the ring at the cursor.

Derived, not recorded

      
ZhuJiang's routers pass ring flits through one register per stop, and a flit already on the ring always has priority over injection. Once injected, a flit is therefore at stop path[k] at cycle inject + k. The panel builds per-link prefix sums from the flit records once, and any window's utilization is then two lookups. Recording each hop would multiply the flit data by the hop count and add nothing. Where the ring runs on its own clock, cycle means that clock: stop path[k] is reached at the k-th edge after injection, read from the ring's CLOCK stream (SPEC §7.4). A fabric whose flits can stall in flight, such as a mesh with credit-based buffers, records each hop as a stage of the flit record instead, and the pack says hops: recorded. The chart draws both the same way. The UCIe stack is such a case.

      
Random access by construction. Loupe could only step forward, because it replayed state. Here the state at any cycle is a query over records, so seeking backwards is as exact as playing forwards.

    

    

      
What the map encodes

      
Each link has an outer arc for the index-increasing ring and an inner arc for the index-decreasing ring. Each arc has one lane per channel ring (REQ, RSP, DAT and HRQ, which carries SNP and ERQ), coloured by the fraction of cycles in the window that a flit occupied it. The scale's maximum is printed. An orange ring around a stop is proportional to the cycles that flits waited there to inject. Stops that carry no traffic in this build (RNI, MN and the pipeline stop) are drawn dim, as the XiangShan diagram marks them.

      
The map's drawing follows topology.kind. A ring is drawn as here. A chain, such as a die-to-die link's layers, is drawn as a row, as in the UCIe section. For a mesh, the panel would place crosspoints on a grid from VDB coordinates and draw the Marey rows per crosspoint in XY order, so turns show as bends. That is the case for CMN, where Arm's tools print the grid from discovery data. The link sums, the chart and the playback are shared by all three.

States from messages, and what they cannot show

      
A cache's state changes when its request completes, when it answers a snoop, or when its write-back leaves. Requester and snoop records carry the state before and after, so the rows need no protocol table. Some changes are silent: CHI lets a UC line become UD on a store without any message. The row then shows the last known state until a later record reveals the change. When a snoop or write-back reports a dirty line the view believed clean, the interval since the last message is drawn hatched in both colours. The view does not guess when the store happened.

      
Invariants are checked on the rebuilt rows, not by the simulator. There is at most one unique owner, or any number of sharers, and at every home lookup the snoop filter must match the caches. A violation would be drawn red at the cycle where it happens. On this trace both rules hold for all  lines.

    

    

      
Data provenance

      
When data flits carry a fold of their payload (chi.data), the data row shows each transfer as a chip coloured by value. A chip's colour changes only where a store happened, and a reader that receives an older colour than the last one written has read stale data. That is the question behind most coherence failures that difftest reports. Recording the fold costs 8 bytes per data flit and is optional.

      
Where it lives in Volna

      
The rows are derived rows in the Waves panel. An analysis that takes (address, agent) produces a state track, which the enum painter draws like any other value row. The table is a Table panel over a derived source, the same kind of synthetic source table-panel.html reserves. No new panel kind is needed. The mock puts both in one frame.

Rules are templates, findings are annotations

      
The rules are the six templates of the architecture, run in volna-core with the parameters in the profile. They produce findings with record IDs and times, and the same run works headless in CI. Findings are never written into the trace, because they are one tool's opinion. A checker that runs in the simulation writes its messages as LOG records like any other log. The CHI set covers what this trace needs: CompAck after data when ExpCompAck is set, home entries finishing within the traffic board's 500 cycles, every flit having a receiver, TxnID reuse only after all responses, one unique owner per line, and the snoop filter matching the caches.

      
The injected fault is in the model, not in XiangShan. After cycle 6760, CC0's L2 drops a CompAck that loses its TXRSP port to a snoop response in the same cycle. The page uses it because it hangs the run the way a real lost acknowledgement does.

    

  






  
Proof of generality · a second protocol pack

  
The same panels on a UCIe die-to-die link

  

    
The design claims that CHI lives in two places only: the monitors bound to the RTL, and one VDB pack. This section tests that claim on a protocol that shares almost nothing with CHI: a UCIe link between two chiplets, carrying CXL.mem. It has no coherence, no ring and no home. It has a layered stack, a link that loses flits and replays them, and credits that gate every request. The model, the pack and the guided steps below are new. The causal module, the Flow, Topology, Latency and Hang panels, the detail panel and the legends are the code the CHI mocks run, instantiated a second time on a second trace in the same page:  records,  flits,  ns. The page's test checks that none of that code names a CHI or a UCIe term.

UCIe also makes the case for trace-based debug more strongly than CHI does. Its micro-bumps cannot be probed, and there is no analyzer or scope for them in the lab. None of them links a replayed flit, the credit it held and the request that starved into one causal record, which is what the questions below need. The pack also answers the two open questions the CHI design left: how credits appear as waits, and how retries appear as causes.

  


  
UCIe and CXL.mem in five minutes

  
  

    

      
Layers, flits and retry

      
UCIe has three layers on each die. The protocol layer (PCIe, CXL or a streaming protocol) talks to the die-to-die Adapter over FDI, and the Adapter talks to the physical layer over RDI. The Adapter does CRC, retry, arbitration between protocol stacks, and link state [64]. At the data rates used here the raw bit error rate is 10−15, so CRC and retry are required [66, 67]. A 16-bit CRC covers each 128 bytes of a flit [65, 67].

      
Retry is PCIe flit-mode retry, simplified. The flit header carries a sequence number and Ack/Nak [65], and there is neither a selective Nak nor a receive-side retry buffer [68]. The model therefore treats a Nak as go-back-N: the receiver drops every flit after the bad one until the replay arrives, and the sender replays from the bad one on. To save latency, the Adapter may pass a flit to the protocol layer before its CRC check has finished, and cancel it afterwards with pl_flit_cancel [69].

    

    

      
CXL.mem and credits

      
CXL.mem has two channels from host to device, Req (MemRd) and RwD (MemWr with data). It has two back: DRS (MemData) and NDR (Cmp). A 16-bit Tag names the host's request-table entry, and the response echoes it [70, 72].

      
Every channel is credit-controlled. The sender spends a credit per message. The receiver gives credits back as its buffers free, in a CRD field of any flit header or in an LLCRD flit [70, 71]. A credit that is never given back is gone for the rest of the run. Enough of them lost, and the host can send nothing: a hang with no cycle and no lost message on the link.

What the UCIe model is

      
Taken from the specifications: the three layers with FDI and RDI; a 16-bit CRC, sequence numbers and go-back-N replay with no selective Nak; forwarding before the CRC check, with pl_flit_cancel; the CXL.mem channels and Tags; credits returned as buffers free, in LLCRD flits.

      
Simplified or invented: every latency (a 4 ns flit, 2 to 3 ns per layer, 30 to 62 ns of DRAM);  request credits and 8 RwD credits granted at link-up and not drawn; one message per flit and one LLCRD per freed entry; errors in the die 0 → die 1 direction only, injected  times at a rising rate, as a margin test does through the Adapter's error-injection register [66]; the workload; and the fault, a cancel path that takes back a request credit.

Alternatives considered

  

    
Rejected for the trace
    
      
  • Flits only, stitched afterwards. This is simplest for the producer, and it is how CHILog and CHIron work. It cannot know which request caused a non-forwarding snoop or an LLC victim write, and it must guess retry chains. The home monitor records those links at no extra cost.
    • 
      
  • Reconstructed transactions only, without flits. Smaller, but the ring views and message arrows need transit times, and checks such as “every flit has a receiver” need the flits.
    • 
      
  • Cache states as signals, one per line and agent. Unbounded in count. States are properties of messages, and a derived row rebuilds them for the one line being viewed.
    • 
      
  • A CHI section in the format. It would put protocol semantics into VTR. Stages, parents and relations already express everything, and the README reserves semantics for VDB.
    • 
      
  • Per-hop records on the ring. They are derivable (see Proposal B) and would multiply flit volume by the hop count.
    • 
    

    
Rejected for the design
    
      
  • A CHI model in volna-core. It is quicker to write, but TileLink, AXI, the next NoC and every chiplet link would each need another one. The causal model with packs costs one binding step and is tested once. The UCIe pack in this page took seven generic additions and no protocol code.
    • 
      
  • A panel set per protocol (a CHI flow, a UCIe flow). Each would fork the painters, the hit testing and the tests. Here the pack supplies nouns, rows and toggles, and one panel serves both.
    • 
      
  • Colours as hex values in the profile. They are right in one theme only. Hues with per-appearance tones follow any palette.
    • 
      
  • A rule language. Deferred. Six templates with parameters cover every rule so far. A language is worth its cost only when packs need rules the templates cannot express.
    • 
      
  • An animated block diagram as the main debug view (the XiangShan page's player, Vivio). It is excellent for teaching one flow and poor for finding one.
    • 
      
  • A Sankey or chord diagram of traffic between nodes. It shows volume and loses time, which is the dimension every question above needs.
    • 
      
  • One giant sequence diagram of all traffic. ShiViz shows where that stops scaling. Context in the Flow panel is bounded and optional.
    • 
      
  • 3D mesh views. Occlusion and no shared axis. The Marey chart shows the same flits flat.
    • 
      
  • Automatic panel layouts for CHI traces. Volna opens every trace the same way, and opening a pack's views is an explicit command.
    • 
      
  • Averaged stage durations as the breakdown. They overlap and do not add up. The critical path does.
    •

What the CHI model is

  

    

      
The trace is generated when the page loads, by about 600 lines of JavaScript, and nothing is precomputed. It emits exactly what the monitors would write: hierarchy, records, relations and one log record. The analyses read those, never the model's state. Taken from the XiangShan source (through the XiangShan diagram's literal port):

      
    
        
  • the ring of 11 stops, node IDs as index × 8, friend ports and routing direction;
    • 
        
  • bank selection by PA[12] and directory bank by PA[6];
    • 
        
  • DongJiang's decisions: DCT through forwarding snoops, LLC hits that invalidate the LLC copy, DMT with ReturnNID, the LLC filled only by write-backs of lines no other L2 holds, and SC_PD snoop data written to memory;
    • 
        
  • CompAck to HomeNID, and L2 TxnIDs as MSHR indexes.
    • 
      

    

    

      
Simplified or invented:

      
    
        
  • all latencies (home pipeline 6 cycles, snoop service 7–12, memory 36–54 plus a 4-cycle return per line);
    • 
        
  • capacities (16 MSHRs, 40 L2 lines and 256 LLC lines, scaled down so that evictions happen in a short run);
    • 
        
  • two data beats per line, no L1 and no TileLink;
    • 
        
  • no retries: DongJiang blocks in its PoS and sends no RetryAck, and ZhuJiang's source only defines the opcode;
    • 
        
  • no link-layer credits, the workload, and the fault.
    • 
      

      
The panels depend on none of these. They read records through the profile.

    

  






  
Open questions

  
    
    
  • Link credits. The model now has pool waits, and the UCIe pack uses them for CXL.mem credits. For CHI's L-credits the question is volume: record grants and returns as messages per link, or keep credit counters as analog signals (c910-perf-counters.html) sampled per cycle and bind a pool to the counter?
    • 
    
  • Retries. CHI allows a retried request to use a new TxnID, and nothing links the attempts [1]. For homes that retry (CMN, OpenLLC), should the monitor record a retry_of relation from the home's point of view, where P-credit allocation makes the link certain? The causal model takes it as a cause without change, as the UCIe pack's replays relation shows.
    • 
    
  • Children lookup. Is the window over a parent's lifetime fast enough on a real run, or does VTR need a parent-id range per TX_BLOCK? The plan's step 2 measures it.
    • 
    
  • Two runs. CloganGUI's A/B latency diff and Konata's overlay suggest a comparison mode for the Latency panel. Which identity pairs requests across runs: address plus order, or a core-side instruction ID from the TileLink pack?
    • 
    
  • Physical address space. Should the subject key be (PAS, address) always, or only when the profile says the system has more than one PAS?
    • 
    
  • Where packs live. Bundled with Volna like its themes, beside the trace, or both, with the trace's copy taking precedence?

Glossary

  

    
Adapter (D2D)
UCIe's middle layer on each die: CRC, retry, arbitration between protocols and link state.

    
CompAck
The requester's acknowledgement to the home that a transaction completed, which lets the home release the line.

    
Credit
Permission to send one message on a channel. The receiver gives it back when its buffer frees, in CXL in a CRD field or an LLCRD flit.

    
Critical path
The chain of work and messages that decided when a transaction finished, found by walking back through the last input to arrive.

    
DBID
An identifier a node hands out so that a later message (write data, CompAck) can find it.

    
DCT, DMT
Direct cache transfer and direct memory transfer: data goes from a peer cache or from memory straight to the requester, skipping the home.

    
Derived source
An analysis result that panels show like loaded data, saved in workspaces as its recipe.

    
FDI, RDI
UCIe's interfaces between the protocol layer and the Adapter (flit-aware) and between the Adapter and the physical layer (raw).

    
Flit
The unit a CHI channel carries, one packet or one data beat. On a UCIe link, one 68- or 256-byte unit with its own CRC and sequence number.

    
Go-back-N
Retry in which a Nak makes the sender replay from the bad flit on, and the receiver drop everything until then.

    
HN-F, RN-F, SN-F
Home, requester and subordinate node types. The F means fully coherent (for SN: normal memory).

    
LLC
Last-level cache. In DongJiang it is filled only by write-backs of lines that no L2 holds.

    
LLCRD
CXL's link-layer credit flit, which returns credits when no other flit carries them.

    
Little's law
Mean occupancy = throughput × mean latency, for any stable queue.

    
Marey chart
A time–distance diagram: stops down, time across, and one line per vehicle or flit.

    
pl_flit_cancel
The UCIe Adapter's signal that a flit it already passed to the protocol layer failed its check and must be dropped.

    
Pool wait
A wait on a shared resource, such as credits. It points at every record that holds part of the pool.

    
PoS
Point of serialization: the place where the home orders all requests to one line. A second request waits there, blocked.

    
Protocol pack
A VDB profile that binds the causal model to one protocol's names, with its classes, rules, topology and hues.

    
Replay
A retransmission. Its record carries a relation to the transmission it supersedes.

    
Snoop filter
The home's record of which caches hold each line, so it snoops only those.

    
Subject
What a piece of work is about, such as a cache line. Its state at each holder is rebuilt from the records.

    
Tag
CXL.mem's 16-bit name for a host request-table entry, echoed by the response.

    
TxnID
The identifier a requester or home allocates for each of its outstanding requests.

    
UC, UD, SC, SD, I
Unique Clean, Unique Dirty, Shared Clean, Shared Dirty and Invalid, the five cache states used here.
