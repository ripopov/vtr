01 / RELEASE CONTRACTOne useful vertical slice.

This proposal defines a smaller replacement for the initial scope in the full table specification. It is a design baseline, not a description of features already shipped. The broad prototype is preserved on archive/table-full-prototype at ea26c9b; implementation of this reduced version starts from the existing viewer.

The central invariant: a table is a view over sources that are already complete, immutable and indexed before the table opens. Display rank is the source ordinal. Opening and scrolling create no table-owned array proportional to the row count — with one declared exception: a signal table over more than one signal materializes a merged timestamp axis of 8 bytes per distinct change time. That axis is admitted, accounted and refusable like any other allocation, and it is the only structure the table owns that grows with N.

Included in the baseline

  • Open one transaction generator from the hierarchy or an existing single-generator Pipeline panel, or any set of signals selected in the hierarchy’s variables list or in a Waves panel. Both routes use the same right-click Open in table command and reuse the document’s loaded owner, or request it through the existing loader.
  • Signal tables: one row per distinct change timestamp across the selected signals, so simultaneous changes collapse into one row. Columns are Time plus one per selected signal, showing the last value recorded at or before the row’s time. The signal set is fixed when the table opens; changing it means opening another table.
  • Columns from a fixed catalogue per source kind. Transactions: Label, Begin, Duration, End, ID, Status and a bounded Attributes preview, with Label, Begin, Duration, Status and Attributes visible by default; End and ID are hidden until asked for. Signals: Time plus the selected signals, all visible by default. A row-number gutter is always present.
  • A Columns menu in the table toolbar shows or hides catalogue columns. Display order is the catalogue order; visibility is panel state, never a change to the row source.
  • Virtualized rows, horizontal overflow, exact Go to row, wheel/scrollbar navigation, Home/End and Page Up/Down.
  • One selected record. Selection moves the linked time cursor, and linked timelines follow it automatically, exactly as the existing timed panels do: pan only when the cursor leaves the window, keep the current zoom, and animate through the shared navigation path.
  • Record details for the selected row, toggled from the panel header or with Enter: the complete attribute list, events and stages of a transaction, or the per-signal values behind a signal row. Read for one row on demand, bounded and cancellable, and never part of the viewport window. Each list shows 20 items by default; one global setting changes that number.
  • Copy the selected record’s standard fields as complete TSV with Ctrl/Cmd+C, with a selectable-text fallback. Copy is a row action, not a permanent toolbar button.
  • Loading, empty, admission failure, retry, cancellation, keyboard operation and basic row accessibility.
  • Existing docking and workspace persistence save the generator reference and panel settings. Restore at the first row.

Explicitly deferred

  • Multiple generators or whole streams in one table; global time merging.
  • Editing a table’s signal set in place, mixing signals and transactions in one table, and clock-sampled or otherwise derived row domains.
  • Filters, sorting, Find, row-set indexes, permutations, and background query jobs.
  • Attribute columns beyond vtr.label, schema discovery, log-specific layouts and expanded log-message formatting. The catalogue is fixed at compile time; it is not derived from the data.
  • Relations between records, navigation from a detail field to another row, and promoting detail fields to columns or filters. Details render values, they do not become a second row domain.
  • Column reordering, resizing and derived columns; custom numeric formats, range selection and large export.
  • Restoring selected/top records across sessions, recording fingerprints added for that purpose, reverse cursor lookup, and fitting a record’s interval or otherwise changing the timeline’s zoom from the table.

A log site is eligible when represented as a transaction generator; it uses the same column catalogue. A stream, a mixed signal/generator selection or several generators shows “Choose one generator, or only signals.” Signals keep their existing Waves behavior as well; opening them in a table neither moves nor copies them. These boundaries keep the release to two row domains — source ordinals and change times — and no query engine.

02 / INTERACTIVE WORKSPACERead a record. Keep its context.

The demo follows the same hierarchy, panel, cursor and dense-grid language as the full proposal. Click a row, use the navigation controls, scroll, or jump to the final record. Toggle signals in the variables list or on a Waves lane label, then right-click either one and choose Open in table to replace the transaction table with the union of their change times. The time cursor and selected record remain distinct: clicking Waves moves only the cursor. The Columns menu in the toolbar shows or hides catalogue columns; ID is available there, hidden by default, while the selected-record strip keeps showing it as the record’s identity.

03 / DATA MODELThe source is the row store.

The current LoadedGenerator already owns records ordered by (begin, end, id) and provides identity lookup; SignalHistory already owns each signal’s changes with time(i), value(i) and the hinted index_at_hint search that Waves uses to paint. The baseline borrows both directly. Existing native and remote sessions deliver the same immutable types; the table introduces no presentation data into VTR or the raw protocol.

RowSource {
    Generator { source: TrackRef, loaded: Arc<LoadedGenerator> },
    Signals   { keys: Vec<SignalRef>,    // captured at open, then immutable
                histories: Vec<Arc<dyn SignalHistory>>, // shared with Waves
                axis: Option<Arc<[u64]>> },  // merged change times; None for one signal
}

TableModel {
    source: RowSource,                   // one generator, or a fixed signal set
    top: u64,                            // zero-based source ordinal
    subrow_px: f32,                       // bounded fractional offset
    selected: Option<TransactionRef>,   // identity, not a displayed row number
    cursor_linked: bool,
    columns: ColumnSet,                  // visible keys from the fixed catalogue
    window: PreparedWindow,              // bounded; replace as the viewport moves
    request: u64,                        // rejects an obsolete preparation result
}

row_count()       = transactions: loaded.transactions().len() as u64
                    signals:      axis.len()  (one signal: history.len())
row_at(ordinal)   = transactions: loaded.transactions().get(checked_usize(ordinal))
                    signals:      axis[ordinal]  (one signal: history.time(ordinal))
cell(t, signal)   = signal.index_at_hint(t, cursor)  → value, plus "changed here" when time(i) == t
row_key(row)      = transactions: (document_generation, generator, record.id)
                    signals:      (document_generation, signal_set, timestamp)

This is an ownership sketch, not a new public trait hierarchy. Use existing model/load state types where they fit. Add a source query at its owning layer if needed. Synthetic large-ordinal sources belong to tests; they are not a second production source type.

Workspace boundary

Persist only the panel kind/version, the row source’s declaration references — one generator, or the ordered signal set — the visible column keys and the link preference inside the existing workspace. A restored signal table rebuilds its axis through the same admission path; an unresolvable signal leaves the table in “Source unavailable” rather than silently opening a smaller set. Read-time IDs, selection, top row, requests and previews are session state. A future release can add durable navigation after its recording-identity cost is measured. A new baseline panel payload must use a distinct version from incompatible prototype payloads; unsupported versions receive the existing explicit restoration error.

04 / BOUNDED WORK & MEMORYNo surprise work in a scroll event.

Prepare a small window

  1. Compute the visible ordinal interval with checked integer arithmetic. Add at most two overscan rows on each side.
  2. For signals, read the row times from the axis (or the single history) and keep one monotone search hint per column so the window costs O(rows × columns × log gap), never a scan from the recording’s start.
  3. Read those records by ordinal. Reuse overlap from the previous window. Prepare only the visible columns.
  4. Stop at 256 prepared rows, 256 preview bytes per Attributes cell, and the panel’s admitted byte limit. Huge viewports still honor the cap.
  5. Publish one completed window only if its document, source and request are still current. Missing cells show placeholders; old rows are never relabelled as new ones.

Reuse the existing scheduling path

  • Resident, bounded work may complete synchronously only while measured UI work remains within the frame budget.
  • When yielding is needed, keep one pending viewport continuation per panel, with a 2 ms slice target and checks between bounded value fragments.
  • New scroll requests supersede obsolete work. No query scheduler, worker copy, unbounded queue, tile LRU, or speculative whole-source warming is required.
  • Record details are read only while the panel is open and only for the selected row: one bounded request, replaced when the selection moves, released when the panel closes. A viewport scroll that does not change the selection performs no detail work.
  • The signal axis is built once at open, not during scrolling: admit its bytes first, merge in bounded slices through the same yielding path, and publish it only when complete. Cancelling or closing discards it; no partial axis is ever shown as a row domain.
  • Native loading uses the existing background executor; default wasm yields through host tasks. Closing or replacing the panel invalidates all deliveries.

One memory ledger

The document/session accounts for raw data, decoding workspace and existing indexes. The table shares that budget and reserves its incremental prepared text, shaping/Scene storage and clipboard output before allocation. Native raw owners must participate in the same accounting as remote owners. A separate table-only cap is insufficient. Extend admission at the data owner if this is missing; preserve the same ownership path for native and remote use.

Peak admission=shared source + load workspace+bounded panel buffers

Set an initial 4 MiB incremental cap per table for prepared windows, including old/new windows while a replacement is in flight. The open details panel’s admitted bytes are part of the same cap, so a record with large values reduces what the windows may hold rather than escaping the ledger. A multi-signal table additionally reserves its merged axis — 8 bytes per distinct change time, sized from the selected histories’ change counts before the merge starts — and is refused with the required/available sizes when it does not fit. The signals’ histories themselves stay charged once to the document and are shared with Waves. Shared renderer caches are reported separately; this is a cap on admitted table-owned buffers, not on process RSS. Count shared raw owners once across panels. Keep the existing global and per-object limits. If the owner cannot fit, refuse the load with the required/available sizes; do not substitute a sampled subset. Closing a table drops its references, not a source still used by another panel.

Illustrative lower bound: source bytes + 4 MiB for one table. Add metadata, source indexes, in-flight decode/transfer peaks and other panels before admission. Bytes/record is an assumption until measured on the selected trace.

Loading and cancellation

Distinguish a load from a viewport preparation. A cold load can scale with the complete selected source; repeated scrolling over a ready source must perform no reader or network I/O. Show indeterminate loading until genuine progress is available. Releasing the last owner can be expensive: measure close/drop separately and keep large destruction work off the UI event path, using the existing ownership/scheduling layer.

On memory failure or disconnect, show the reason and Retry. Retry creates a new request identity. Document replacement and panel closure cancel pending table work; late native or browser messages cannot revive the old panel. A rejected copy leaves the prior clipboard intact and retains at most its admitted 64 KiB payload for recovery.

A small, representative matrix

  • Real resident data: 10,000, 100,000 and one million transactions when admitted. Use scalar attributes, long strings, nested values, duplicate timestamps, zero-length records and long overlapping intervals. Publish source size and measured bytes/record. Refusals stay in the results.
  • Generated ordinal stress: 10,000 → 300 million logical rows, plus exact positions above 2⁵³. This validates navigation and bounded work without pretending the full recording is resident. Only the default columns are needed; repeat the widest catalogue selection once.
  • Signal fixtures: one signal (no axis), 8 and 64 signals with clustered, coincident and sparse change times; a signal with no changes; rows before a signal’s first change; and a selection whose axis exceeds the budget.
  • Interaction: wheel bursts, first/middle/last/random Go, keyboard selection, cursor updates, copying during scroll, panel close during preparation and reopen with a missing source.
  • Ownership: one table, two tables sharing a generator, table + Pipeline, and different generators approaching admission limits. Verify release after success, failure and cancellation.
  • Hosts: native offscreen GPUI, headless single-thread wasm, and an isolated real VS Code workspace host/webview. Software-rendered CI checks correctness; hardware presentation measurements retain their backend label.

Reproducible automation

Rust tests own the model, identity, borrowed projection, bounded work, admission and cancellation contracts. Checked-in JavaScript/TypeScript runners own browser/webview lifecycle, keyboard input, semantic assertions, clipboard failure and host messaging. Each runner provisions temporary fixtures and profiles, starts/stops its processes, enforces timeouts, and fails on missing prerequisites when explicitly requested.

Run three measurement repetitions after a documented warmup. Store raw samples, nearest-rank percentiles, maximums, build profile, revision, machine, viewport, source characteristics and rendering backend as CI artifacts. For an optimization claim, compare a baseline binary in the same session. Report cold runs separately. No manual browser operation, computer-use tools or screenshot review is a passing gate.

Check this document’s demo

node --test --test-concurrency=1 docs/tests/table-baseline.test.mjs

Requires Node 22+ and Chrome/Chromium; set VOLNA_CHROME for a nonstandard executable path. The self-contained runner verifies desktop/mobile layout, bounded row counts, exact u64 navigation, cursor following, column selection, signal-table construction (merged change times, coincident changes, values before a signal’s first change), record details, clipboard recovery, context menus and load/error/cancel states. .github/workflows/table-baseline.yml runs it on Ubuntu. These checks validate the prototype, not the future Rust implementation or its latency targets.

Release only when every boundary is covered. A fast core microbenchmark cannot stand in for UI latency. A generated row count cannot stand in for resident capacity. An isolated web page cannot stand in for a VS Code webview.

06 / DELIVERY & EXTENSION POINTSGrow from measured needs.

  1. Prove direct access in the core.

    One generator and one signal set, source ordinal lookup, the merged axis with its admission, exact identity, the fixed column catalogues and bounded borrowed previews. Assert no table-owned allocation proportional to N and no raw-buffer duplication.

  2. Deliver the complete interaction slice.

    Open, load/retry/refuse, virtualize, select, jump, follow the cursor, read details and copy. Wire the existing docking/workspace path and accessible rows. Keep behavior in volna-core; GPUI hosts controls, rendering and clipboard.

  3. Pass native, wasm and VS Code integration.

    Same immutable source semantics, same complete TSV, isolated persistence and reliable cancellation/cleanup. A host that does not pass is reported as unsupported for this release; no silent skip is counted as coverage.

  4. Establish and publish the baseline.

    Run the resident/generated workload matrix, reconcile memory admission with observed peaks, and attach all timing boundaries. Only then evaluate an extension against a concrete investigation workflow.

Keep the public surface small. Begin with a concrete model and a few core commands. Reuse source access, loaded ownership, admission, docking and formatting primitives. Add generic adapters only when a second implemented use case needs them. A new cache must address a measured cost and state its byte bound and invalidation rule.

There is no line-count acceptance gate: the aim is fewer behaviors and fewer independent representations. When the implementation needs a large new subsystem to satisfy this baseline, revisit the owning abstraction and the scope before expanding it.
