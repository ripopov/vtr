Growing the hierarchy during a run

UVM testbenches build their component tree in the build phase and create streams for objects while the simulation runs, and initial blocks may add scopes after the simulator has declared the design. VTR's format already allows the hierarchy to grow at any time. The writer mostly handles it. The reader does not: a signal added after the first block can crash it. This plan explains how hierarchy works in VTR, fixes the reader, replaces the writer's scope stack with a tree API in which every node names its parent, migrates every caller, and adds tests that pin the behaviour down.

Plan, 25 September 2026; implemented the same day. The findings in “What works today” and “The bug” describe core/vtr before the change; core/vtr/tests/dynamic_hierarchy.rs now covers them, and RATIONALE.md records the chunk-overhead measurement. Related: SPEC.md §2.4, §5 and §6, vtr_clocks.html and c910-verilator-tx-stream.html, whose SystemVerilog calls create streams while the simulation runs.

How hierarchy works in VTR

The hierarchy is a forest of nodes. There are five kinds: scope, var, stream, generator and enum table. Every node has a parent that was declared before it (or none, for a root), a name, and attributes. Node ids are dense numbers in file order. A var either declares a new signal or aliases an earlier one; signal ids are dense in the order their declaring vars appear.

Nodes are stored in HIERARCHY sections, each a chunk of consecutive nodes. The file is append-only, and SPEC §2.4 requires only that a node be declared by a chunk that precedes every section using it. Nothing says all chunks come first. A file can therefore interleave hierarchy chunks with signal, transaction and log blocks.

The writer keeps new nodes in a pending list. Before it hands any data to the encoder (a chunk of value changes, a transaction block, a log block, an explicit flush), it writes the pending nodes as one HIERARCHY chunk. Node attributes can be added until that happens. Today scopes are declared with begin_scope/end_scope, which push and pop a scope stack inside the writer; vars and enum tables go into the current scope, while streams and generators take an explicit parent. The Verilator fork declares the whole model this way inside VerilatedVtr::open, before the first dump. This plan removes the stack.

The reader collects every HIERARCHY chunk when it opens a file, including a crash-recovered file without a directory, so it always sees the complete forest. Viewers such as Volna open finished or recovered files and have no live-follow mode, so for them a late node is simply part of the hierarchy.

Signal values live in SIGNAL_BLOCK sections. A block covers a time range and partitions signals into groups of group_size consecutive ids (256 by default). Each block records n_signals, the number of signals known when it was written, and each stored group container records n_sigs, how many signals it holds. The container's frame gives each held signal's value at the block's start, and a prev-dirty table points to the last earlier block where each group changed. So the format already records exactly which signals existed in each block.

What works today

Throwaway tests declared nodes after emitting values, in foreground and background writer modes, with small blocks so that declarations fall before, inside and after block boundaries:

Added after the first valuesResult
Scope, stream, generatorWorks. The nodes are found by path, and a transaction on the late generator reads back.
Signal declared in the middle of a blockWorks in both writer modes. The block that holds the declaration covers the new signal; its history starts at its first emit.
Signal that starts a new groupWorks for every query (tested with group_size 1). Earlier blocks have no container for that group, which the reader already treats as "no data".
Signal that joins a group already stored in earlier blocksReader panics. load_signal, load_signals and changes fail whenever the signal's range includes such a block, and value_at fails for times inside it. With the default group size of 256 this is the normal case.

The tree API is the second problem. The scope stack is hidden state shared by every producer of one file: a node lands wherever the last begin_scope left the stack. A producer that adds nodes late, from a DPI call or a UVM callback, does not own that stack, and the fork has already emptied it at open. The API is also inconsistent. Rust has both add_var and add_var_in, and both add_alias and add_alias_in, but scopes and enum tables exist only in the stack form. The C API has only the stack form for vars and aliases. add_bits and add_log_stream are shorthands for other calls. No call checks that a parent exists or has the right kind.

The core crates have 35 tests and all pass, but none declares anything after values were emitted, and no CI workflow runs cargo test at all. That is how the panic went unnoticed.

Why late signals break the reader

To read signal s in block b, the reader finds the container of group s / group_size and then indexes its frame and its runs with the local position s − first_sig. It never compares that position with the container's n_sigs. For a signal that joined the group after block b was written, the position lies past the end of the container, and the frame lookup (Reader::frame, and the frame read inside load_signals) indexes out of bounds. The column lookup has the same flaw and could return another signal's data instead of panicking if run boundaries happened to line up.

Groups that did not exist yet are already safe: prev_dirty returns "none" for a group beyond the block's n_groups, and find_group finds no container. The whole-block walk behind for_each_change sizes its tables by each block's own n_signals and is also safe. Only the partially filled group is missing its check.

The writer side is sound. Tests with mid-block declarations and small chunks in background mode read back correctly whenever the group check was not involved. The writer re-snapshots the signal kinds after each declaration, grows its dirty-group tables on demand, writes the block's n_signals at the time of flushing, and emits the pending HIERARCHY chunk before the chunk of values that first uses a new signal.

Rules for a growing hierarchy

  1. Nodes can be added at any time. A producer may declare scopes, vars, aliases, enum tables, streams and generators before, between or after any value, transaction or log record. The writer places them in the next HIERARCHY chunk.
  2. Nodes are permanent. A node exists from the chunk that declares it to the end of the file. It is never removed, renamed or re-parented.
  3. A signal missing from a block has no data there. If s ≥ the block's n_signals, or its position in the group is ≥ the container's n_sigs, the block holds no changes of s. Its value there is the default from SPEC §6.3: all X for 4- and 9-state bits, 0 for 2-state bits and reals, the empty string for variable-length signals. This is the same value a signal has before its first change today.
  4. Every node names its parent. The writer keeps no current position. Each call that creates a node takes the parent's id, or none for a root, and checks it. A producer that walks a tree keeps its own path of ids.
  5. Attributes come with the node. Node attributes must still be set before the node's chunk is written, which in practice means right after creating it. Late producers do not need more than that.

Rules 1 to 3 describe what the format already means. They go into SPEC as clarifications; the layout does not change, so the format version stays. Files written today with late signals become readable, not reinterpreted.

What changes

SPEC

  • §2.4: HIERARCHY chunks may appear anywhere after META, interleaved with other sections; a node is valid from its chunk to the end of the file (rules 1 and 2).
  • §6.2 and §6.7: a signal outside a block's n_signals or outside its group container's n_sigs has no changes in that block, and a reader uses the default value for it (rule 3). The reading algorithm in §6.7 gains that check.
  • §5: which node kinds may be the parent of which (below). The format already implies it; SPEC states it so that writers and readers check the same thing.

Reader

  • GroupView gains holds(sig) -> bool, true when sig − first_sig < n_sigs.
  • value_at: when the last dirty block at or before the time does not hold the signal, return the default. The signal had no changes up to that block, because it did not exist yet.
  • changes, load_signal and load_signals: skip blocks that do not hold the signal, and seed its initial value with the default instead of reading a frame.
  • column: a dynamic alias whose target the block does not hold is reported as corrupt data, never followed.
  • The C reader API needs no change; it calls the same functions.

Writer: one tree API

The scope stack goes away entirely. One call per node kind remains, each taking its parent explicitly and returning an error for a bad one:

pub fn add_scope(&mut self, parent: Option<NodeId>, name: &str, scope_type: ScopeType, component: &str) -> Result<NodeId>;
pub fn add_var(&mut self, parent: Option<NodeId>, name: &str, var_type: VarType, direction: Direction,
               kind: SignalKind) -> Result<(NodeId, SignalId)>;
pub fn add_alias(&mut self, parent: Option<NodeId>, name: &str, var_type: VarType, direction: Direction,
                 signal: SignalId) -> Result<NodeId>;
pub fn add_enum_table(&mut self, parent: Option<NodeId>, name: &str, entries: &[(&str, &str)]) -> Result<NodeId>;
pub fn add_stream(&mut self, parent: Option<NodeId>, name: &str, kind: &str) -> Result<NodeId>;
pub fn add_generator(&mut self, stream: NodeId, name: &str) -> Result<NodeId>;
pub fn node_attr(&mut self, node: NodeId, key: &str, value: Value) -> Result<()>;

Removed: begin_scope, end_scope, current_scope, add_var_in, add_alias_in, add_bits (an add_var with fixed types) and add_log_stream (an add_stream of kind LOG; the kind stays available as the constant vtr::LOG_STREAM_KIND). add_log_site is unchanged, since it creates a generator with site data rather than duplicating another call.

The C API projects the same set one to one. Every id-returning function returns VTR_NONE on error, as the header already specifies; add_var returns two ids and therefore keeps its status code and output pointers:

uint32_t vtr_writer_add_scope(vtr_writer *w, uint32_t parent, const char *name, uint16_t scope_type, const char *component);
int      vtr_writer_add_var(vtr_writer *w, uint32_t parent, const char *name, uint16_t var_type, uint8_t direction,
                            uint8_t kind, uint32_t width, uint8_t states, uint32_t *node_out, uint32_t *signal_out);
uint32_t vtr_writer_add_alias(vtr_writer *w, uint32_t parent, const char *name, uint16_t var_type, uint8_t direction,
                              uint32_t signal);
uint32_t vtr_writer_add_enum_table(vtr_writer *w, uint32_t parent, const char *name, size_t n,
                                   const char *const *literals, const char *const *values);
uint32_t vtr_writer_add_stream(vtr_writer *w, uint32_t parent, const char *name, const char *kind);
uint32_t vtr_writer_add_generator(vtr_writer *w, uint32_t stream, const char *name);
int      vtr_writer_node_attr(vtr_writer *w, uint32_t node, const char *key, const vtr_value *v);

parent is VTR_NONE for a root. vtr_writer_begin_scope, vtr_writer_end_scope and vtr_writer_add_log_stream are removed; vtr_writer_add_alias now returns its node id like the other calls instead of a status code and an output pointer.

Parents are checked the same way everywhere. A scope, var, alias, enum table or stream goes under a scope or at the root; a generator goes under a stream. An unknown id, a wrong parent kind or an unknown aliased signal is an error, and nothing is added. Encoding does not change: a producer that declares the same nodes in the same order writes a byte-identical file.

Migration

Every caller moves to the new API in the same change, as AGENTS.md asks for breaking changes. Callers that walk a tree keep their own path of node ids; the fork already keeps such a path in m_prefixStack and only mirrors it into the writer today.

Simulators

Beyond the migration above, nothing in the fork changes for this plan, but two facts matter to the SystemVerilog producers built on it. First, initial blocks run during the first eval(). When the harness opens the file before that, as the C910 harness does, they run after open has declared the model and before the first dump, so hierarchy they add lands in the first chunks, ahead of any values. The tests cover that case explicitly. Second, a DPI call made before the harness opens the file has no writer to go to. The sink in vtr_clocks.html must therefore keep declarations made before open and replay them at open, and the UVM work will rely on that.

Tests

A new file, core/vtr/tests/dynamic_hierarchy.rs, lands together with the reader fix; its first test fails on today's reader. Each test compares against expectations the test computes itself, so no fixture files are needed.

  1. signals_declared_mid_run_read_back. For group_size 1, 3 and 256, and for foreground and background writers with 8-record blocks and 4-record chunks, it declares signals at five moments: before the first time step, at time 0 after the first values (the initial-block case), in the middle of a block, right after an explicit flush, and late in the run. The declarations fall both into partly filled groups and into new ones, and cover 1-bit 4-state, 8-bit 2-state and 4-state, real and variable-length signals. The test keeps the expected history of every signal and checks load_signal; load_signals mixed with early signals and repeated ids; changes over windows that start before the declaration; value_at at every time step, including the default before the declaration; and the merged order from for_each_change.
  2. nodes_added_mid_run. After values have been emitted, it adds a scope under an existing scope and one at the root, vars and an alias in both, an enum table, a stream and generator, and a log stream with a site, each with node attributes, interleaving the two subtrees. It writes a transaction and a log record on them, then checks paths with find_node, parents and children, attributes, the transaction and the log record.
  3. parents_are_validated. A scope, var or stream under a var, a generator under a scope, an alias of an unknown signal and an unknown parent id are all rejected with an error, and the file afterwards contains none of them.
  4. late_declarations_survive_recovery. It truncates a file with late nodes inside its last signal block, as recovery_without_directory does, and checks that nodes from chunks before the cut exist, that their signals read correctly up to the cut, and that nodes after the cut are simply absent.

The C smoke test core/vtr-capi/tests/c_smoke.c is rewritten on the new calls, adds a scope, var and stream after the first values, checks that a bad parent returns VTR_NONE, and reads everything back.

These tests only protect the feature if they run. A new workflow, .github/workflows/core-tests.yml, runs cargo test -p vtr -p vtr-capi on ubuntu-24.04 for every push and pull request. It is the first CI job for the core crates.

Out of scope

  • Node lifetimes. UVM objects are created and destroyed during the run, but a VTR node has no creation or end time; a viewer shows it for the whole run, and its data simply starts later. Recording lifetimes means reserved attributes set after the node's chunk was written, which the writer does not allow, or a new record kind. That design belongs in a UVM recording proposal, together with how viewers would show it.
  • Renaming, moving or deleting nodes. Rule 2 excludes them; nothing in the planned producers needs them.
  • Viewing a file while it is written. Volna and the CLI open finished or recovered files. A live mode would have to pick up new chunks as they appear; that is a separate feature.

Plan

  1. Reader fix and tests. GroupView::holds and its use in value_at, changes, load_signal, load_signals and alias resolution; tests 1 and 4; the SPEC §2.4, §6.2 and §6.7 clarifications; a RATIONALE entry recording that membership comes from the per-block counts rather than a stored creation time. The reader decode path changes, so read time is A/B-tested with bench/run.py against a worktree of HEAD. File sizes and write times are unaffected because the writer is unchanged in this step. Exit: test 1 fails before the fix and passes after, and read time is within noise.
  2. Tree API in the core. The new writer calls and parent checks in core/vtr, the C projection in core/vtr-capi, the SPEC §5 parent rules, a RATIONALE entry on removing the stack, and the migration of every caller inside this repository (core, tools, volna, bench, demos, documentation); tests 2 and 3 and the rewritten C smoke test. Exit: cargo test passes for the default members, volna/volna/check.sh passes, and the benchmark workloads written by vtr-bench are byte-identical to HEAD.
  3. Forks. verilated_vtr_c.cpp in the Verilator fork and the VTR callers in the Surfer fork, each committed upstream in its fork and bumped here in one commit. Exit: the fork's VTR regression tests and the Surfer fork's tests pass, and a C910 capture from the migrated fork is byte-identical to one from the previous build.
  4. CI. .github/workflows/core-tests.yml. Exit: the workflow is green on the branch, and it fails when the reader fix is reverted.
  5. Measure chunk overhead. A test-scale run that adds 10,000 nodes one at a time over a long run reports the number and total size of HIERARCHY sections next to a run that declares the same nodes up front. The writer emits at most one HIERARCHY chunk per flush of values, transactions or logs, so the overhead should be small, but the numbers go into RATIONALE either way.

The SystemVerilog calls that create streams while a simulation runs, in vtr_clocks.html and c910-verilator-tx-stream.html, need the ID-based tree API from steps 2 and 3 and the replay of declarations made before open. Steps 1 to 4 should land before either of those proposals starts.
