Volna / complete-object architecture

Load once.
Explore locally.

The server opens the trace and sends complete histories for requested signals and complete data for requested transaction tracks. The client does the rest.

Native and VS Code loading implement this boundary; see the current architecture and verification workflows and limits.

1. One loading model

Open the file beside the reader. Transfer the full hierarchy and track catalog once. When a user adds a signal or transaction track, load its data over the entire recording. Keep that data in shared immutable client storage while it is in use.

Client: exploration

Resident hierarchy and selected data
Search, cursor, pan, zoom, indexes
Transactions, VDB, annotations, painting

Pan, zoom, cursor movement, resizing, formatting and filtering loaded data issue zero data requests. Searching the hierarchy also stays local. An analysis that needs an unloaded signal or track explicitly loads that whole object first; its result must identify its loaded-data scope.

Changed requirement: transfer and client memory scale with the complete selected signals and tracks, plus all metadata. They do not scale with the visible time window. This deliberately replaces the viewport-scaling requirement in the repository’s previous remote direction. A very large selected history can be slow to load or too large for the client.

Keep the two existing deployment targets: native local and VS Code remote/local workspaces. Native calls the loader on background workers and shares buffers directly. In VS Code, the workspace extension owns one headless child per trace document and relays framed messages between its stdin/stdout and the webview. No separate HTTP service is needed for this first implementation.

Both paths use the same toolkit-independent Session backend to open recordings and load complete objects. Native executes LoadRequest in process; the remote client submits those same requests over the protocol, and the headless service calls the same backend methods. The document owns demand and completion handling. There is no separate local transaction-query interface. The existing standalone web file-opening path can remain available. The egui frontend needs only compatibility maintenance for its current features.

2. Borrow the proven boundary

The checked-out Surver server serializes its hierarchy, supplies a time table, and loads requested signals through a background loader. It deduplicates signal IDs and returns compressed complete signals. The Surfer client reconstructs those signals for local use. Borrow that division of work. Complete transaction-track loading is Volna’s extension of this approach.

Volna’s current session API already exposes resident metadata and full immutable signal histories. Its document loading path already coalesces signal requests, shares histories across rows and rejects stale generations. Preserve those behaviors. As described in the rationale, shared history storage avoids copies and a permanent history cache is unnecessary.

Remove remote time windows, summary queries, continuation tokens, coverage caches, viewport demand scheduling and server-side search from this proposal. Client indexes or drawing summaries may be derived from loaded data when useful; they have no wire representation.

3. Three complete payloads

ObjectContents and guarantee
MetadataTrace information, exact time units and range, capabilities, full hierarchy, signal declarations and aliases, and the full raw track catalog. Include raw availability/dump-off information needed to interpret histories. No signal histories or transaction records are loaded implicitly.
SignalCanonical signal ID, shape, initial-value/availability semantics, all timestamps and values for the recording. Preserve source ordering at equal timestamps, event occurrences, logic states, widths and supported value kinds. Each history is independently interpretable: transmit its timestamps, not a mandatory recording-wide time table.
Transaction trackAll member transactions for the recording, with complete typed attributes and phases, events, stages, raw lanes, status, kind, parent IDs, and all incoming/outgoing relations incident to those transactions. Include referenced strings/types so no backend table handle escapes.

A track is a raw stream or generator

Use the existing TrackRef catalog: a generator selects all its transactions; a stream selects all transactions of its generators. A VDB-defined grouping or visual lane is a client view, not a server load unit. Stream loads include member generators with no transactions.

Store loaded transaction records once per generator. A stream load fills those generator stores; selecting an already resident generator reuses them. Release a generator’s records when no loaded stream, generator view or active analysis retains them. Do not build a second transaction cache alongside this ownership.

Cross-track relations do not recursively load the graph

Each relation has a stable session-local ID, endpoint transaction IDs, endpoint generator IDs, raw kind and attributes. Repeated copies from different track loads share that identity; distinct parallel relations remain distinct. If the reader has no stable relation identity or endpoint-owner lookup, add that small API at the reader’s owning layer rather than deduplicating by content or scanning every track per relation.

A relation or parent may point into an unloaded generator. Retain the reference and show “track not loaded”; following it loads that generator in full. Parent references also include the owning generator ID. The server does not recursively transfer referenced transactions. An absent endpoint in a completed owner track is missing data, not another pending load.

Supported-but-empty is a successful complete object. Unsupported operations are explicit capability/error results. Data must never silently lose attributes or relations to satisfy a size limit. VDB, source interpretation, user comments, colors and visual row packing remain on the client and outside the raw trace protocol, following the VTR/VDB boundary.

4. A small protocol

One child owns one immutable opened recording. The host supplies its authorized path when launching it; the webview does not get an arbitrary server file API. Use these operations:

Open(protocol_version)          → Opened(session_id, Metadata)
LoadSignals(request_id, ids)     → one complete Signal or Error per unique ID
LoadTracks(request_id, ids)      → one complete Track or Error per unique ID
Close                           → release reader and exit

Every response carries the session ID and request ID. The client also associates requests with its document generation. The child assigns a fresh opaque session ID at open; a filename or design build ID is not a recording identity. Reject a mismatched protocol version before decoding payloads. No old-version compatibility or schema negotiation is required.

Use one versioned binary schema shared by the Rust server and client, with fixed-width IDs/timestamps and immutable packed history buffers. Use one established serializer and one compression codec: bincode with explicitly fixed options and LZ4 frames are the proposed starting point. Pin their versions and test their native/WASM round trips. Do not serialize trait objects or private reader structures.

Keep binary payloads opaque to JavaScript; represent envelope counters as strings if they pass through JSON. The VS Code adapter must test its actual message encoding rather than assume ArrayBuffer support. If byte arrays require base64 in this relay, encode only transport chunks and include that overhead in measurements.

Chunks are transport, not query pages

Send an object header with identity and expected decoded size, ordered bounded byte chunks, then an explicit end marker. Start with at most 1 MiB per transport chunk and one unacknowledged chunk across the relay. The client acknowledges after consuming it; this prevents the child and extension from filling queues with a whole large response. Compression/decompression is incremental across chunks, with output limits enforced.

The receiver builds the object privately, validates sizes, references and completion, then publishes it atomically. Never display half a history or call a truncated track complete. A stream track commits only after all its members and relations arrive. Transport chunks carry no time coverage, resume token or partially queryable result. A failed object is retried from the beginning.

Start with one active load batch per document and a deduplicated pending set. Preserve modest signal batching for VTR/FST decode efficiency; send tracks one at a time. Put batch limits in the executor rather than inventing a priority scheduler. Each requested ID must finish with exactly one success or error; a broken connection fails every remaining item.

5. Simple ownership and failure rules

Absent → Queued → Loading → Ready
                     └──→ Failed → Queued (explicit retry)

Last consumer removed → release data / remove queued demand
New recording         → new generation; reject old completions
  • One owner in the core. The document coordinates loads. Rows, panels and analyses retain shared immutable objects. Aliases use the canonical signal ID; failed retries update all consumers together.
  • No frame waits for loading. Native read/decode runs on workers. The web client must yield between bounded receive/decode/install steps or use a dedicated worker without requiring shared WASM memory. A single giant deserialize on the UI thread does not meet this requirement.
  • Removal needs no cancellation protocol. Remove queued demand immediately. An active batch may finish; discard objects with no consumers. Closing/replacing the document terminates its child and drops pending work. An explicit stop-and-reopen action can abandon an oversized active load.
  • Partial batch success is useful. Fully completed signals remain ready when another signal fails. An interrupted object is discarded. Errors name the object and reason and expose explicit retry.
  • Disconnect preserves completed data. Continue exploring resident objects offline; new loads fail visibly. Reconnect opens a new session and reloads selected objects. Do not merge old and new session data or attempt resumable transfers in the first version.
  • Immutable input only. No live-tail or in-place reload support. Producers must finish writing before open. On detected file change, invalidate the session and require reopen; a new recording never inherits old runtime IDs. Workspace restoration uses existing durable paths.

The server retains its reader and native reader caches, but adds no permanent copy of every sent history. Release response buffers after sending. Existing reader caches can still consume memory; this design does not claim that transport backpressure bounds reader memory.

6. Honest limits, predictable behavior

This design fits investigations that select a manageable subset of a large recording. Selecting every signal can approach or exceed the cost of transferring the file. A whole transaction stream can be much larger than its current visible region.

Client memory ≈ full metadata + unique loaded histories/tracks
              + client indexes + in-flight assembly/decode memory

Initial load  ≈ server decode + encode + transfer + client decode/install
Loaded pan / zoom / cursor: no network dependency

Configure a client memory budget and per-object transfer limit. Count decoded storage and temporary copies, not just compressed bytes. Reject an object before allocation when its declared size cannot fit; enforce checked lengths and decoded-byte limits while receiving it. Refuse additional loads with a clear “remove tracks or raise the limit” error. Never silently evict displayed data, truncate results or switch to a second window-query mode.

Metadata is subject to the same limits; if the complete hierarchy cannot fit, opening fails clearly. A byte limit alone cannot bound client index construction or native reader scratch, so measure peak memory and responsiveness with representative large objects before choosing defaults. The server may have to decode an object to learn its actual size; reject known oversize loads early and document this remaining server-side limitation.

Compression reduces transport bytes, not the resident data requirement. No speed or memory improvement is claimed without measurements. No new VTR encoding, file-format version or reader decode optimization is needed for this proposal.

7. Implement the seam, then the transport

  1. Complete local objects. Keep existing signal histories. Add whole-track loading and client-resident transaction queries to the core. Put server record extraction beside the existing session/backend adapters. Fix any missing reader relation identity/owner API there. Validate local semantics first.
  2. Asynchronous delivery. Retain the existing LoadRequest/LoadResult generation pattern and extend it for tracks and remote completions. The current blocking Session::load_signals cannot wait for browser RPC: use it inside the local executor; the remote executor sends requests and delivers results later. Both install the same objects. Drawing sees resident data only.
  3. Headless child and codec. Add the small server binary under tools/; share raw protocol types through a small toolkit-free module or crate under volna/. Keep native local execution free of serialization. Start with an in-memory transport harness, then framed stdin/stdout.
  4. VS Code relay. Replace whole-file delivery for workspace traces with child startup and opaque chunk forwarding. Add backpressure, load/error state and process cleanup. Keep UI policy in volna-core. Exercise real webview transport and decode scheduling before calling remote support complete.

When implementing this direction, update AGENTS.md’s remote intent, the architecture/session documentation and the old proposal links together so they no longer require viewport queries. Update API references and the rationale for any actual API changes. The VTR/VDB split remains binding; there is no reason to change the VTR file specification merely to add transport.
