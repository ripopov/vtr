Proposal · Multiple traces

Several traces. One workspace.

A system rarely fits in one recording, and a question rarely fits in one run. The CPU model dumps VTR while the DRAM model dumps FST; an optimisation needs its before and after side by side; a failing seed needs its passing twin. This proposal lets Volna open several traces in one session. It combines the parts of one system on one timeline, and compares runs of one design, for performance or to find where a regression starts.

Any mix of VTR, FST and remote recordings · two to eight traces per session · six layers, eight shippable stages · no change to the VTR format

Use cases

Why engineers open more than one trace.

Parts of one system

A simulation often writes several files. A CPU model built with Verilator dumps VTR, the DRAM model from a vendor dumps FST or VCD, the testbench logs to its own file, and a chiplet or a SystemC model may run in another simulator. Verilator can split one run into several FST files. The engineer wants all of them on one timeline: a request leaving the core and the same request arriving at the memory controller, with times that agree although one file counts nanoseconds and another picoseconds.

These traces are combined: nothing is paired and nothing is compared. They need a common time unit, a placement when their origins or clocks differ (a memory model may even count its own clock cycles), rows and panels from any file, and ways to follow one thing from file to file. The demo's first scenario is this case.

Runs of one design, compared for performance

An architect changes the branch predictor, the cache, the memory latency or the compiler flags, and runs the same program again. The question is where the time went, and the answer is in the pipeline. Konata's users load two logs and slide one over the other; Tracy and VTune compare profiles. The two runs execute the same instructions at different times, so they are paired in program order, not in time. What they need is slip over the run, cycles per stage, latency per transaction, and counters such as IPC overlaid. Here differences in timing are the point, not errors. The demo's second scenario is this case.

Runs of one design, compared to find a bug

A seed fails where another passes, a fix changes more than intended, a netlist disagrees with its RTL. The two runs should behave the same, so every difference is a lead, and the earliest is usually the cause. What they need is an exact compare with explicit rules for skew, X and tolerance, a ranking of the whole design by first difference, navigation between differences, and name mapping when the netlist renames the hierarchy. The demo's third and fourth scenarios are this case.

Many runs

Sweeps over seeds, corners or a parameter produce tens of runs. Nobody reads them one pair at a time: the engineer wants to see where the runs disagree, then pick a pair to study. This builds on the compare, with a summary per row across all traces and a headless check that runs in CI.

Principles

Eight rules for every layer.

  1. One session, several traces.Opening a file adds it to the session instead of replacing it. VTR, FST and remote recordings mix freely, because each trace is its own session behind the same interface, returning the same immutable data.
  2. Every trace keeps its identity.A trace gets a letter in opening order and a name taken from where its path differs from the others: runs/base/landing.vtr and runs/base/dram.fst become landing and dram. The letter tags its rows, panels, commands and saved state. Its format, unit and placement are one hover away on its chip.
  3. One timeline, placement in plain sight.Times are converted to one unit, and every trace reaches the timeline through a placement its chip shows: the same time, an offset, or a warp through matching events or clock edges. Volna never shifts a trace silently, and a second ruler shows a placed trace's own time.
  4. Combine or compare, decided per trace.Parts of one system are combined: their signals are separate rows. Runs of one design are compared: one row shows a path in every run. Volna proposes the relation from how many paths the traces share, and the chip's menu changes it.
  5. Pair things in their own terms.Signals pair by path, instructions by program order, transactions by key, and log messages by text. Each view compares in the units its reader thinks in: time, cycles per stage, latency per read, the words of a message.
  6. Every way of looking, one gesture each.Side by side, by opening a row into its traces. Superposed, for analog rows and the pipeline's outlines. Differences drawn explicitly, as bands and counts. Blinking, by holding Space.
  7. Layers, not modes.Each layer works without those above it. Combining needs only the trace set, placement and views. A performance comparison adds pairing. A bug hunt adds differences and rules. The plan ships them in the order that finishes one job at a time, so placement, a lower layer, reaches users after the compare that makes its effect visible.
  8. Edits are saved and undoable; navigation is not.Adding a trace, placing it, choosing the reference, mapping names and setting rules are workspace edits, saved with it and undone like any other. Focus, links, opened rows, blinking and moves between differences are navigation.

1 · Trace set

Opening. volna landing.vtr dram.fst opens a session with both. Ctrl+O still opens a new session, and Ctrl+Shift+O, or Add trace in the palette, adds to the current one. While a file is dragged over an open session, it offers two targets, Replace and Add as B. Close trace removes one trace and keeps the others and their rows.

Identity. Letters follow opening order and are kept for a trace's life, so rows and saved sessions stay stable. Names come from the first path segment that differs between the traces, and can be changed. The chip shows letter, name, format, unit and placement; the focus trace, the one a view draws first, has an accent chip.

Time units. Times are converted to the finest timescale among the open traces, exactly, because timescales are powers of ten. The demo's dram.fst is in picoseconds and landing.vtr in nanoseconds; both read in nanoseconds on the ruler. A trace in cycles (time.unit=cycle) has no common unit with the others and needs a clock placement, layer 2.

Hierarchy and rows. The sidebar shows one root per trace, labelled with its letter, file and format. A row added from a trace carries that trace's letter; rows of different traces mix freely in one panel and in groups.

Sessions. The workspace stores the traces with paths relative to it, their letters, names and roles, and every row names its trace. The recent list reopens a session as one entry.

2 · Placement

Every placement is one kind of object: a monotone, piecewise-linear map from the timeline to a trace's own time. It has one knot for an offset, two for a different clock period, and one per matched event for a warp. The painters, the compare and the cursor use only this map, so each new way of placing a trace only adds a way to find knots.

  1. Same time is the default. It is right for traces from one simulation, like the CPU and DRAM dumps, and for reruns of one test.
  2. Offset shifts the whole trace. It can be typed, or set by Alt-dragging an edge of one trace onto the matching edge of another. When a trace shares paths with the reference, Volna also looks for an offset. For the early edges of control signals, it takes the distance to the nearest edge with the same value in the reference, and the most common distance wins. For reset12 that is 16 ns, agreed by 59% of the edges. It is offered in the compare bar, never applied silently.
  3. Events match the n-th occurrence of an event in both traces and stretch time linearly between matches. The event can be the instructions of a pipeline stream, a counter's values, a named log message or a transaction key.
  4. Clock maps edges of a clock in one trace onto a clock in another, or a trace recorded in cycles onto a declared clock. A DRAM model that counts its own cycles lands on the timeline through the controller's clock, across its frequency change and gating.

We rejected dynamic time warping over values. Clocks and idle buses match almost anywhere, so the warp it finds would have no meaning; its cost grows with the square of the run length; and it would hide the timing differences a performance engineer is looking for. Placement on events you choose keeps every knot explainable.

3 · Views and links

Panels on any trace. A pipeline, table, transaction or transaction-lane view names the trace it shows in its header chip, and switching it is one click. The cursor, viewport and markers live on the shared timeline, so every panel follows them. A marker can be pinned to one trace's own time, and then it moves when that trace is placed again.

Value links. Click a bus or text value and every segment holding it is filled, in every row of every trace; N and Shift+N step through its occurrences in time. In the demo the L2's missing address, 0x10000900, is found in the controller's addr of dram.fst 4 ns later, and again when the L2 reads it much later.

Key links. Transactions carry attributes, and a VDB profile can declare which ones identify the same work across traces: an address, a transaction ID. The transaction panel then lists the matching records of the other traces, such as the DRAM burst behind an L2 read, and a click selects them.

One log timeline. The log panel merges the messages of every trace in time order, each tagged with its letter, and filters by trace.

4 · Pairing

The compare relation. A trace that shares at least half of its signal paths with the reference opens in compare; otherwise it is combined. In compare, a row names a path and shows it in every trace: opening a third run adds it to every row at once. A row opens like a group, with its chevron or Alt+→, into one sub-row per trace. The reference is A unless you choose another, so a comparison is always “B against A”, never a matrix.

Signals pair by path through a mapping. When the reference calls a design tb.dut and the netlist calls it top.u_dut, Volna finds the prefix pair that pairs the most leaf names and offers it. A bus rule gathers bit-blasted data[0] … data[31] into data[31:0], the obstacle GTKWave's maintainer names first. Unpaired signals are listed per trace.

Instructions pair in program order: a diff over each trace's sequence of program counters, with flushed instructions kept apart, so an interrupt taken at another point or an extra wrong-path fetch leaves only those instructions unpaired. Transactions pair by generator and key, or by address and issue order when no profile declares a key. Log messages pair by their text with the numbers removed.

5 · Differences

What counts as different. The default compare is continuous: at every change in either trace, the values must be equal, and only where both traces recorded. On the C910 benchmark, the converted recording and the simulator's own recording of the same run are identical from the first recorded time. Before it, every one of their 67,144 signals differs, X in one and 0 in the other, because a value before the first recorded time is a default, not data. Five rules loosen the compare, and the compare bar counts what they hide:

  1. Skew tolerance ignores a difference no longer than a set time (Questa's lead and trail tolerance).
  2. Clocked compare samples each trace only at a chosen edge of its own clock, the usual way to compare RTL with a netlist.
  3. X in the reference matches anything, bit by bit.
  4. Real tolerance treats analog and counter values within a relative band as equal.
  5. Ignore takes path patterns and time windows.

How a difference looks. A differing stretch of a row gets a violet tint and a 2px bar along its lower edge. The name column counts stretches per trace, B≠50 C=, and where the traces disagree at the cursor, the value column shows the focus trace's value and then the reference's, 0 ≠1. We measured the colour. The viewer's value colours already take most of the hue circle: under all three simulated colour-vision deficiencies, no hue gets further than ΔEOK 5.7 from all of them. So the shape carries the meaning, and an X keeps its hatch inside a difference. The violet, --viewer-diff, is oklch(.70 .16 285) in Volna Dark and oklch(.48 .18 280) in Volna Light. With typical vision it is at least ΔE 10 from every value colour, and it reaches 4.5:1 on the canvas.

Looking. D and Shift+D go to the next and previous difference on the selected row, or on any row. Holding Space shows the reference in place of the focus trace until you let go, in the waves and in the pipeline. Analog rows overlay the reference as a faint line under the focus trace.

6 · Tasks

Performance comparison

Aligned by instruction, each moment of A is compared with the moment B reached the same point in the program. In the pipeline, B's stages are filled and A's are outlines over them. Each row is aligned at its own retirement, so a stage that took longer sticks out to the left, and the Δ column gives the change in that instruction's latency. A slip curve over the whole run plots how far B retires behind A. Each step is a place where time was lost, and its tooltip names the refill that caused it. The header sums the cycles gained or lost per stage. The table view pairs transactions and adds a column per trace and a Δ column for latency and every numeric attribute. Counters such as IPC overlay.

Show

Regression debugging

A scan compares every signal the traces share, not only the rows on screen, and ranks them by first difference. The earliest is usually the cause and the rest are its consequences, so the list reads from the root down. A spread chart shows how many signals have differed by each moment, and the hierarchy browser marks every scope with its first difference. Go to first difference, Show only differing rows and Expected difference are in the palette. The last turns one difference into an ignore rule for that signal and time window. Log messages pair by text, so a message whose numbers changed stands out.

Many runs

Every compared trace is compared with the reference, so the work grows linearly. A row counts differences per trace, and its band marks where any of them differs. With more than four traces, the band becomes a consensus strip whose height in each pixel column is the share of traces that disagree with the reference.

Automation

The command catalogue gains traces (list, add, remove, place, rename), compare_rules and differences, and the proposed MCP tools wrap them with a letter as the trace argument. A headless volna compare a.vtr b.vtr --place offset|events:PATH|clock:PATH --rules FILE --json runs the same code and exits 1 when the traces differ, so a check made in the viewer can run in CI.

Research

What others do, and what nobody does.

We read the documentation of the commercial simulators and the source code of the open viewers, trace tools and diff tools, where they are public. Where only a secondary source was available, the table says so. Two families emerge. Profilers and system tracers merge: Perfetto 58 opens several trace files onto one timeline with per-file clock offsets, Nsight Systems stacks reports, and Trace Compass groups traces into an experiment. HDL viewers and Konata compare: Questa's datasets, compare rules and navigation are the most complete design we found, Verdi samples each side on its own clock, and Konata 1.2 overlays two pipelines. No tool does both, and the open-source HDL viewers do neither: GTKWave only syncs two windows' cursors, and Surfer's multi-file and compare requests are open issues.

Four things no tool does well, and this proposal addresses:

  1. Complementary and compared traces in one model, from any mix of formats.
  2. Placement beyond one offset: warps through events, and clocks for traces counted in cycles.
  3. Pairing pipelines and transactions as objects rather than as pixels.
  4. More than two runs at once, and a path from the first difference to its cause.

Architecture

Layered code, one layer per module.

Today one App holds one Document, which holds one Session. Every signal, track and transaction reference is an index into that session, and opening another trace wipes the document. The change keeps the Session interface and its immutable data objects, and builds six modules on it in volna-core, each depending only on the ones below. Headless tests cover each module. GPUI draws what the models decide, volna-egui keeps building with one trace, and MCP and the CLI call the same commands.

  1. trace: the trace set. TraceSet holds ordered TraceSlots of TraceId, letter, name, relation and session state, each with its own load generation. Document owns it instead of one TraceState. LoadRequest and LoadResult carry a TraceId, and session-local references are qualified as (TraceId, SignalRef) where they cross slots. TimeBase converts every slot's ticks to the session's unit. RowSource and TrackSource gain a trace, and the scope tree gets a root per trace. Remote servers open one recording per session, and the protocol still carries raw data only.
  2. align: placement. Warp is the monotone piecewise-linear map, with to_trace and to_ref in O(log knots). A trace's Placement, a whole scale since stage 1, becomes Same, Offset, Events or Clock over that scale; it resolves to a warp once its anchors are loaded, through a LoadRequest::Anchors, and applies where data arrives. detect_offset is a pure function. NavState and Viewport stay in timeline time.
  3. link: views across traces. Every panel model stores the TraceId it shows, and TxSelection gains one. ValueLink finds occurrences in the loaded histories of every trace; KeyLink runs a transaction query by key attributes in the other traces.
  4. pair: correspondence. SignalPairs by path through a Mapping of prefix rewrites and bus gathering, with suggest_prefix. InsnPairs is a Myers diff over program-order keys, O((N+M)·D), where D is small for runs of one program. RecordPairs pairs by key and LogPairs by template. Compare rows keep one path-based source and one history per trace.
  5. compare: differences. Rules and one function from two histories, a warp, the rules and a window to a list of differing stretches. It merges the two change lists, so its cost follows the changes in the window, like the painter's. Results are cached per row, trace, rules and warp, and painted per pixel column.
  6. Tasks. perf (slip, stage sums, latency pairs), diverge (the scan and the ranking) and sweep (consensus) read only the layers below. The divergence scan is a background LoadRequest that pairs signals by path and streams results earliest first. We measured a prototype on the C910 CoreMark benchmark, whose converted and simulator-direct recordings of one run have 204,905 variables and 67,144 distinct signals each. Opening both and pairing their paths takes 0.3 s; comparing all 1.19 billion changes takes 8.1 s on 16 threads and 46 s on one, with a 4.3 GiB peak. That is the worst case, because identical recordings force a full read.

Nothing changes the VTR format or the VTR/VDB boundary. A VDB profile may declare a pipeline's program-order key and a stream's transaction keys; without one, Volna uses the program counter, and the address with the issue order.

Plan

Eight stages, each shippable.

The design lands in eight stages. Every stage builds, passes cargo test -p volna-core and volna/volna/check.sh, and gives the user something useful on its own. It also updates the tests and documentation it touches. No stage adds a feature flag, or code that only a later stage calls. Each stage below says what the user sees, with numbers that match the red circles in its picture, and then what the commit contains. The pictures are painted by this page's demo code with only the features of their stage and the ones before.

Why this order. Each stage should finish a job or make the next one visible.

  • Stages 1–2 finish the complementary use case. Recordings of one simulation already share a time origin, so they need no placement: a trace set and links across files are enough.
  • Stage 3 lets two runs of one design be read side by side. This is useful before anything is computed.
  • Stage 4 computes differences.
  • Placement comes fifth. Offsets, detection and warps matter only for runs that are to be compared, and their effect is only visible once differences are counted: placing reset12 takes it from 16 differing signals to 2. The time map itself landed in stage 1 as Placement, a whole scale that joins nanoseconds and picoseconds. It applies where data arrives, so panels and painters only ever see session times; stage 5 widens it to offsets and warps without touching them.
  • Performance comparison comes sixth. Aligning by instruction is a kind of placement, and its paired pipeline builds on compare rows.
  • The bug-hunting ranking and the automation come last. They only read what the stages before them compute.

A trace recorded in its own cycles, such as a DRAM model that counts memory clocks, is the one complementary case that waits for stage 5.

Stage 1 Landed

Trace set

Today, opening a second file replaces the first. After this stage, both stay open. This alone serves recordings of one simulation, such as a CPU dump and a DRAM dump.

  1. Trace chips in the title bar: letter, name, format and unit for each open trace. A click selects the trace in the hierarchy; its menu renames or closes it. Roles arrive with compare rows in stage 3.
  2. Add, with Ctrl+Shift+O, the title bar's + and volna A.vtr B.fst, adds a trace instead of replacing one. A file dropped over open traces offers Add as B and Open instead.
  3. One hierarchy root per file, with its format, unit and signal count. Signals already on the waves are highlighted.
  4. A letter on every row and group, telling which file it comes from. Rows of different files mix in one panel.
  5. One ruler for all traces: the FST's picoseconds and the VTR's nanoseconds convert exactly to one unit.
  6. Panels name their trace. A pipeline, table or transaction tab carries its letter. The pipeline shows A's stream, because B has none.

Not in the picture: Close trace removes one trace with its rows, rulers and panels, and keeps the others. Trace A holds the workspace, so it closes only with everything.

Committed

Core
trace::{TraceSet, TraceSlot, TraceId, Traced}, trace::derive_names and trace::Placement. Document holds the set instead of one TraceState, with add_trace, remove_trace and rename_trace. Every identity above the session is Traced: LoadRequest, LoadResult, RowSource, TrackSource, ClockKey, TxSelection, table columns and the sidebar rows, so pipelines, tables, lanes, clocks and transaction panels work on any trace. The session unit is the finest among the traces; Placement scales each trace's times where its data arrives, and when a finer trace joins, every stored time refines exactly. ScopeTreeModel and MemberListModel take a root per trace, and App::trace_chips says what chips and trace rows show.
Frontends
GPUI: the chips and their menu, +, Add Trace… in the menu and palette, the drop menu, volna A.vtr B.fst, trace rows in the hierarchy, the letter gutter of the wave rows, letters on tabs and a mark on members already on the waves. egui keeps one trace.
Workspace
Version 5: traces: [{letter, path, name, rename}] replaces trace, timescale says which unit its times are in, and rows and panels of traces other than A name their letter. A restore converts the times to the unit of the traces it opens. Reopening A restores its workspace and opens the traces it names, so state.json needs no session entry.
Undo
Add trace B, Close trace B and Rename trace B are steps. Closing takes the trace's rows, rulers and panels in the same step, and the closed session stays in the journal, so undo is instant.
Tests
volna-core/tests/traces.rs: landing.vtr in ns with landing_dram.fst in ps, every DRAM burst on the controller's ACT; exact refinement, undo across it; rows per trace with letters; closing one trace with its panels; names and renames; the workspace round trip; a trace still opening while a workspace restores. Stage 2

Links across traces

With several files open, the next question is “where does this go?”. This stage follows one thing from file to file, and finishes the complementary use case.

  1. Click a value to link it. The L2's missing address, 0x10000900, is filled in A's request…
  2. …and everywhere else it occurs, here in B's DRAM controller 4 ns later. N and Shift+N step through its occurrences.
  3. The toolbar counts the occurrences per trace: 3 in A, 2 in B.

Not in the picture: a pipeline, table, transaction or lane panel can switch to another trace in its header. The transaction panel lists the records of other traces with the same key, such as the DRAM burst behind an L2 read. The log panel merges all traces in time order.

Committed

Core
link::{ValueLink, KeyLink} and the actions NextOccurrence and PrevOccurrence. Panels already name their trace (stage 1); the header chip switches it. The log source merges per-trace queries in time order.
Frontends
GPUI: the panel header's trace chip and the linked-value fill in the shared painter.
Workspace
Panels already save their track; the path gains the trace letter.
Undo
None: links are navigation. Switching a panel's trace is a layout edit through App::restructure.
Tests
Occurrences across two traces in time order; key links between the L2 reads and DRAM bursts of the generated pair; a selection that crosses traces; the merged log order.

Stage 3

Compare rows

Until now, two runs of one design would show every signal twice, once per file. After this stage, a run that shares most paths with the first opens as a compared trace: one row per path shows it in every run. Nothing is computed yet; this is side by side.

  1. Roles on the chips. A is the reference and B is compared at the same time. Make reference in the chip's menu changes the reference, and a click changes the focus the rows draw.
  2. One merged tree, “paired by path in 2 traces”, instead of one root per file. A path that only some traces have says so.
  3. A row opens into one sub-row per run, with its chevron or Alt+→. Here pc and resp_valid are open.

Not in the picture: when the netlist calls the design top.u_dut and the reference tb.dut, the chip offers the prefix mapping that pairs the most names. A bus rule gathers bit-blasted data[0] … data[31]. The chip's menu can switch a trace back to combined.

Committed

Core
pair::{SignalPairs, Mapping, suggest_prefix} and TraceSlot.relation, proposed from the share of paths in common. DisplayedSignal holds one history per trace, and opening a compare row reuses the group fold.
Frontends
GPUI: the chip menu's Make reference, Compare with A and Combine, and sub-rows through the shared painter.
Workspace
Adds the relation, the reference and the mapping.
Undo
Make B the reference, Map top.u_dut to tb.dut and Combine B are steps. Opening a row is navigation.
Tests
The relation proposed for the generated runs and for the CPU and DRAM pair; the suggested prefix on a copy with a renamed scope; bus gathering on a bit-blasted fixture; a third run appearing in every row.

Stage 4

Differences

The same rows, now with differences computed against the reference.

  1. The compare bar: the Exact and Tolerant rules, previous and next difference, Blink, and a summary, “15 of 16 differ · first at 177 ns”.
  2. Difference bands on each row: a violet tint with a bar along its lower edge.
  3. Counts per trace in the name column: B≠50.
  4. Both values at the cursor where they disagree: 0 ≠1.
  5. Analog overlays: the reference's IPC as a faint line under the focus run's.

Not in the picture: D and Shift+D move between differences, and holding Space blinks to the reference. Compare rules in the palette edits skew, clocked compare, X, real tolerance and ignore patterns.

Committed

Core
compare::{Rules, DiffRuns, diff}, the per-row cache, and the painter's difference pass. Actions NextDifference, PrevDifference and Blink. The theme gains diff and diff_fill from viewer.css.
Frontends
GPUI: the compare bar and the rules editor in the palette.
Workspace
Adds the rules.
Undo
A rules change is a step. Moving between differences and blinking are navigation.
Tests
The engine against a brute-force sampler on generated pairs, as this page's test does; each rule; the recorded-range rule; display lists in both themes; a frame_times A/B run, since the painter changes.

Stage 5

Placement

Runs rarely start together: reset12 holds reset 8 cycles longer, so at the same time all 16 of its signals differ. This stage places a trace on the timeline.

  1. Align B in the toolbar: Same time, or Offset +16 ns, which Volna detected by a majority vote over edges. While most signals differ at the same time, a bar under the toolbar offers the offset; it is never applied silently.
  2. The chip shows the placement: +16 ns.
  3. A second ruler shows the placed trace's own time, 16 ns more than the timeline's.
  4. The summary drops from 16 differing signals to 2: the X before reset and a monitor's warm-up.

Not in the picture: an offset can be typed, or set by Alt-dragging an edge onto the matching edge of another trace. Events placement warps through the n-th occurrences of a chosen event. Clock placement maps one trace's clock edges onto another's, which also places a trace recorded in cycles.

Committed

Core
align::{Placement, detect_offset} and Placement::resolve to a Warp with knots. LoadRequest::Anchors loads the events or clock edges an event or clock placement needs. Viewport::fit spans the placed ranges. Panels and painters are unchanged: they already see only placed times.
Frontends
GPUI: the Align control, the suggestion bar, an offset field, the Alt-drag gesture and the second ruler.
Workspace
Each trace saves its placement.
Undo
Place B by offset +16 ns is one step; an Alt-drag records one step on release.
Tests
Warp properties: monotone, round trip, extrapolation. The detected offset of the generated pair with a longer reset. A cycle-unit trace placed on a clock with a frequency change and gating. Display lists of the second ruler.

Stage 6

Performance comparison

The Konata-style job: the same program, before and after a change, compared in program order rather than in time.

  1. By instruction joins the Align control. It pairs the instructions of the two runs in program order and places B on them.
  2. The slip curve over the whole run shows how far B retires behind A. Each step is a place where time was lost; its tooltip names the refill, and a click goes there.
  3. A paired pipeline: B filled, A outlined, and each row aligned at its own retirement, so a stage that took longer sticks out to the left.
  4. A Δ column with each instruction's change in latency.
  5. Cycles per stage, summed over the run, in the pipeline header.

Not in the picture: the table view pairs transactions and adds a column per trace and a Δ column for latency, as in the table under Tasks.

Committed

Core
pair::InsnPairs (Myers diff over program-order keys), Placement::Events on instructions, and perf::{slip, stage_delta, latency_pairs}. PipelineModel gains a paired mode on one RowView, and TableSource gains paired generators.
Frontends
GPUI: the slip strip and the Δ columns through the shared painter and table model.
Workspace
A pipeline or table panel saves the pair it shows.
Undo
Aligning by instruction is a placement step. Everything else is navigation.
Tests
Pairing with an interrupt taken at different points and extra wrong-path fetches; slip steps equal to refills times the latency change on the generated pair; stage sums; per-row alignment geometry; display lists.

Stage 7

Regression debugging

The bug-hunting job: which signal went wrong first, across the whole design rather than the rows on screen.

  1. The Differences tab in the sidebar, beside Hierarchy.
  2. A spread chart of how many signals have differed by each moment.
  3. Every shared signal ranked by first difference, each with a strip of where it differs over the whole run. The earliest is usually the cause.
  4. Signals not on the waves are ranked too, and a click adds them.

Not in the picture: a background scan fills the list, with progress. The hierarchy browser marks each scope with its first difference. Go to first difference, Show only differing rows and Expected difference join the palette; the last turns one difference into an ignore rule. Log messages pair by text.

Committed

Core
diverge::{Scan, Ranking}, with the scan as a streaming LoadRequest::Diverge that can be cancelled. Rules.ignore holds expected differences. pair::LogPairs. Scope marks in ScopeTreeModel.
Frontends
GPUI: the Differences tab and its progress.
Workspace
Expected differences are saved with the rules.
Undo
Expected difference in soc.perf.ipc is a step.
Tests
The scan equals per-signal compares; cancellation; results arrive earliest first. A timed C910 compare joins the benchmark suite.

Stage 8

Many runs and automation

More than two runs, and the same compare without a window.

  1. Up to eight traces, all compared with one reference, each placed on its own.
  2. A count per trace in every row: B≠50 C=.
  3. A sub-row per trace when a row is open.

Not in the picture: with more than four traces, the bands become a consensus strip whose height is the share of traces that disagree. volna compare a.vtr b.vtr --place … --rules … --json runs headless and exits 1 on a difference. The command catalogue gains traces, compare_rules and differences for MCP.

Committed

Core
sweep::consensus per pixel column; the catalogue commands; a volna-compare binary on volna-core.
Frontends
GPUI paints the strip through the shared painter.
Workspace
Unchanged.
Undo
No new edits.
Tests
Consensus counts; golden JSON and exit codes of volna compare on the generated pairs; the MCP adapter's tests once it lands.

Open questions

  1. The compare threshold. Is “half of the paths shared” the right default, or should Volna ask once when a second run of one design is opened?
  2. A split pipeline. Konata shows two runs in one pane. Should the paired pipeline also offer two panes scrolled together by instruction, beside the overlay?
  3. Keys. Key links and transaction pairing need to know which attributes identify the same work. Should VDB profiles declare them, and what should the fallback be besides address and issue order?
  4. A run summary. Performance engineers also want totals: run length, retired instructions, IPC and latency percentiles per generator, one column per trace. Is that a table-view preset or its own panel?
