Design · VDB Fable

The trace says what happened. VDB says what it is.

A waveform is a million values without a noun. The design behind it has nouns: this register is a state machine, these six wires are an AXI channel, that bus at address 4 is the status register, this stage is “execute”. Verdi keeps them in KDB beside FSDB; today Volna keeps a fraction of them in an 809 MB JSON file that is three times the size of the trace it describes. This document is a fresh design for VDB, the design database beside a VTR trace: nine layers of design knowledge, from elaborated structure to human and agent findings, in one binary container stored per definition and addressed by content, read by the viewer and by AI agents through one query catalogue, and rolled out in twelve stages that each ship something an engineer can use.

No change to the VTR format · one container for RTL, gate level, pipelines, protocols and ESL · same queries for Volna, the CLI and MCP · every derived fact carries its provenance

Today

What VDB is now, and why it does not scale.

VDB began as an application note: a VTR file carries stable names, and any document that binds meaning to those names is a VDB. Three such documents exist in the repository, and they share nothing. The RTL VDB v2 (docs/VDB_RTL.md) is one JSON file per elaboration, written by the pinned Verilator at verilation and by the pyslang exporter, with instances, symbols, connections, process bodies as expression trees, a source index and a trace binding. It powers three real features: temporal driver tracing, module netlists with recorded values, and Surfer's source tile with values at the cursor. The pipeline profile (bench/workloads/c910/c910.pipeline.vdb.json, the schema of docs/VDB_APPNOTE.md) gives the C910 stages their roles and hues. The CHI protocol pack of the protocol proposal binds trace vocabularies to protocol concepts. Signal-group templates were postponed because nothing could hold them.

The RTL export is the only one with a reader, and measuring it on the largest design in the repository shows the shape of the problem. bench/vdb_size.py on the openC910 CoreMark model's Vtop.vdb.json:

Size is the visible symptom. The deeper limits are what the schema cannot say. The explorer above shows three of them on the small design. The DMA's state is declared as dma_state_t, and the trace keeps its enum table, but the export types it as logic[1:0] and compares it to 2'h1: the enum is lost between source and trace, so neither the netlist nor the driver tree can print REQ. The ctrl register is a packed struct; the export keeps the type text, but no consumer decodes irq_en from bit 6. And nothing in the schema can hold the fact that state, state_n and the always_comb at line 86 form a state machine, that CTRL_ADDR is a register address, or that a person concluded something about them last Tuesday. Each new view has invented its own document, and the trace binding, identity and discovery rules live only in the RTL one.

Verdi solved this in 2000 with KDB: one compiled design database beside FSDB that every window reads. Its shape is right; what has changed since is that the reader is as often an agent as a person, that the design may be a Chisel or SystemC model as well as RTL, and that a modern file can be small and random-access without a proprietary loader. That is what this document designs.

Use cases

What a design database must enable.

The list is deliberately broad. A database designed for one of these becomes an obstacle to the others, which is how three documents came to exist. Each use case names what it needs to know about the design, not about the run: the run is in VTR.

RTL debugging

The engineer at a wrong value asks why. The answer walks drivers backwards in time, through processes, ports and hierarchy, until it reaches an input or a decision. It needs the elaborated structure, the source of every symbol, the dataflow of every process, and a way to sample the trace at the right moment before or after an event. This exists today as temporal driver tracing; the design keeps its engine and gives it a smaller, faster store. The same facts feed the source tile with values at the cursor, jump-to-declaration, and the reverse: from a source line to the signals it drives.

Schematic views

A schematic is the design's structure drawn: cells, nets, pins, per module, with recorded values on the wires and drill-down into children. Verdi's nSchema and the Questa and Vivado schematic viewers all draw from a compiled database rather than from source. Volna already draws module netlists with elkrs from the RTL export; a schematic layer needs the graph per definition, with ports on the boundary, operators and processes as cells, and the cone of a selected net highlighted. At gate level the same layer must hold 53 million cells without expanding them per instance.

State machines

Every simulator's debugger has an FSM viewer, and every one derives it from the design: a register whose next value is chosen by a case or an if-chain over the register itself, with constant leaves, is a state machine. The database stores the states with their names, the transitions with their guards and source locations, and a link to the register. The viewer draws the diagram with the state at the cursor and, from the trace, how often each transition fired and which never did. An agent asks for the machine by name and gets its states as words, not bit patterns.

Registers, interfaces and protocols

Software talks to hardware through registers, and hardware talks to itself through interfaces. A register map, from SystemRDL, IP-XACT or a CMSIS-SVD file, or derived from a read multiplexer as the explorer does, turns wdata = 8'hc3 at addr 0 into “software started a burst of 3 with the interrupt enabled”. An interface binding turns six wires into one AXI channel that a lane in the wave panel can show as transfers, and a protocol pack turns transaction records into CHI or UCIe concepts. wavepeek ships AXI, AHB and APB extractors as code; here they are declarative rules over bound interfaces, so a new interface is a document.

Pipelines and typed values

The Konata-style view needs to know which stage is “execute” and how to colour it; the trace carries stage names only. A packed struct or an enum reaches the trace as flat bits in a two-state simulator, and only the design knows the field boundaries and the literal names. Both are presentation of design knowledge, and both belong in the same database so a pipeline profile can say “anchor the dependency arrow at the stage whose role is execute” and a wave row can say “show ctrl as start=1 irq_en=1 burst=3”.

Clocks, resets and domains

Which signals are clocks, which are resets and of which polarity, and which registers sit in which domain are static facts. They decide cycle rulers, edge snapping, what “before the edge” means to the driver engine, and where a crossing between domains deserves a warning. Declared clocks in VTR record the running clock; VDB records the clock tree.

Gate level, ESL and other producers

A synthesized netlist from Yosys, a Chisel design through CIRCT's debug info, a SystemC model's object tree, a gem5 configuration: each is a hierarchy of definitions with ports, and each has a source or a configuration behind it. The database must describe them with the same tables and the same identities, so that a SystemC transaction stream and an RTL waveform of the same SoC are one design to the viewer, and so that “trace driver” on a gate-level net walks cells instead of processes.

Smaller dumps

Whole-design tracing of the C910 costs 41 s and 243 MiB per CoreMark iteration. Verdi's Siloti records about a quarter of the signals and expands the rest from the design on demand, and emulators reconstruct combinational values from captured flip-flops. With the dataflow of every process in the database, a run may record registers and inputs only, and the viewer computes a combinational value when a row asks for it, marked as derived. The trace says what it left out; the database knows how to get it back.

Verification knowledge

Assertions and cover points are design facts with source locations; a failing property in a trace is a place to start. UVM testbenches have a component tree and a register model that mirrors the hardware's. Coverage databases (UCIS) hold results per point. VDB does not store results; it stores the points, so that a result in a trace or a coverage report can be shown against the design.

Several runs and several designs

Multiple traces in one session compare runs of one design and combine recordings of one system. The database must bind to several traces at once, tolerate a re-elaboration that changed a parameter, and let a fact derived once about a module definition, such as its state machine, apply to every run and every design that instantiates that definition unchanged.

Agents

An agent debugging a failure has a token budget and no eyes. It needs to find things by name and by kind, to be told what a thing is in one line, to walk cones and hierarchies to a bounded depth, to read the state of a machine or a register as words at a time, to get the source around a location, and to cite every answer with an identifier a person can open in Volna. It also needs to leave things behind: a finding with its evidence, an annotation on a module, a fact it derived. The database is the agent's memory of the design as much as the viewer's.

The design

Ten decisions.

  1. One container, nine layers. A VDB is a binary file with the section, directory and zstd discipline of VTR, holding any subset of nine layers: identity, structure, source, behaviour, idioms, interfaces, verification, presentation, knowledge. Layers are independent tables with their own versions. A build writes the first four; analysers, imports, people and agents add the rest, in the same file or in files that stack.
  2. Definitions, not instances. Every fact is stored once per module definition, that is per parameterisation, and the instance tree references definitions. Paths are computed, never stored. Facts that genuinely differ per instance (a hierarchical reference, an elaborated generate constant) are per-instance deltas. On C910 this is 373 records instead of 6,934, and 95,441 processes instead of 227,945.
  3. Three identities. A definition is identified by a content hash of its structure and behaviour, so it survives re-elaboration and is shared by every design that uses that IP unchanged. A symbol is a small integer inside its definition. An instance is a path of child indices. Every answer to a person or an agent carries these identities, and every identity resolves back to a name, a source location and a place in Volna.
  4. Facts are typed tables with provenance. Each layer is a set of columnar tables with row identifiers, so the same bytes serve the viewer through mmap, a query API through relational operators, and export to SQLite or Parquet for analytics. Every derived row says which producer wrote it, from which inputs, and with what confidence; a person's confirmation is itself a row.
  5. Source is a layer, not a link. Files with hashes, tokens with classes, declarations, macro expansions, inactive generate ranges, and the reverse map from a source range to the symbols, statements and processes it contains. “What does line 120 drive” and “show me the code behind this cone” are lookups, without a language server at debug time.
  6. Behaviour is one dataflow IR. Processes, expressions as compact directed acyclic graphs with interned types, assignments, sensitivity, ports and connections, per definition. From it the build precomputes bit-accurate driver and load summaries per symbol, so netlists, cones and “what drives x” need no evaluation, while the temporal engine that finds the triggering event keeps its evaluator. The same evaluator can reconstruct what a reduced dump left out: record registers and inputs, compute the rest.
  7. Idioms are extracted and cited. State machines, counters, FIFOs, memories, handshakes, pipeline registers, clock and reset domains, crossings. Each is a table whose rows point at the symbols and source they were recognised from. The build's analyser writes them, a Yosys or CIRCT producer may write them, an agent may propose one, and a person may confirm or reject it. Each of those is provenance, not a different schema.
  8. Interfaces, registers and protocols are bindings. A bus interface binds a role vocabulary to a set of symbols; a register map binds addresses, fields and enumerations to storage; a protocol pack binds trace vocabularies to protocol concepts; transaction extraction rules are declarative over bound interfaces. Imports from IP-XACT, SystemRDL and SVD, pattern rules, and extraction from read multiplexers all produce the same tables.
  9. Presentation is a cascade. Profiles are rules of selector and semantics: stage roles and hues, group templates, radices and formats, analog hints, row styles. They resolve like CSS, most specific first: an instance over a definition over a pattern over a default, a personal layer over a team layer over the build's. Colours are hues, and the theme gives them tone.
  10. One catalogue for the viewer, the CLI and agents. The queries that the Volna panels run are the queries an agent runs, served in-process by volna-core, by a stateless vtr-vdb CLI, and over MCP by the adapter of the agent control proposal. What an agent reads is what the user sees; what an agent writes is a labelled step in the knowledge layer.

Layers

Nine layers, from what the compiler knows to what people learned.

Each layer is a set of tables. The tables below are named as a spec would name them, with the key columns; the full column lists belong in the schema document that stage 1 of the plan writes. Every table row has an integer identifier local to its table, and every table that describes design objects is keyed by definition first, so that a definition's rows are contiguous and a viewer that opens one module touches one range. The column on the right names the features and the producers each layer serves.

  1. L0Identityidentity · sources · producers · bindings

    The design identity, one hash over structure and behaviour; the source manifest with content hashes and the elaboration record; the producers with versions and options; and the bindings: for each trace this VDB describes, the recorded root scope and the map from recorded paths to instances and symbols. A trace names its design by design.vdb_id; a binding is small because paths are derived from the instance tree, so it lists only exceptions.

The same tables describe an sc_module with sc_ports or a gem5 SimObject with its ports: the kind column says which.

Identity and binding

Three identities carry the design. The definition hash is computed over a definition's L1 and L3 rows with all identifiers replaced by their positions, so two builds of the same module with the same parameters produce the same hash on any producer that emits the same IR, and a change to one line changes the hash of that definition and of every definition that instantiates it. The design identity is the hash of the root definition, which therefore covers the whole tree, and it is what a trace records as design.vdb_id. The instance path is a sequence of child indices, printed as a name path on demand.

Because paths are derived, a binding is short: it names the recorded root (Verilator's TOP, a testbench wrapper) and lists only the recorded objects whose name is not the derived one, such as an unpacked array recorded element by element or a signal renamed by --protect-ids. A VDB may carry bindings for several traces, and a session with several traces of one design resolves them all against one structure. When identities differ, attachment is structural: the reader reports which definitions match by hash, which match by name and shape, and which do not, and every view says what it is standing on. This replaces today's all-or-nothing rejection.

Stacking

A session opens a stack of VDB files: the one the build wrote, an analysis file the team regenerates, a profile file from the IP vendor, the team's knowledge file in the repository, the engineer's own notes. Each file says which design identity or which definition hashes it applies to. Rows from later files override earlier ones in presentation and add to them elsewhere. Files that match no definition are listed and ignored. A knowledge file keyed by definition hash follows the IP into another design.

Format

Small on disk, mapped in memory, versioned per layer.

The container is VTR's, not by sharing a file but by sharing its code: a fixed header, sections with a kind and a version, a directory at the end for random access, zstd blobs, a string table with a hash index, varints and columnar frames. The reader in core/vtr-vdb memory-maps the file and decodes a table when a query touches it, as the VTR reader decodes a block. Nothing forces a whole-file parse; opening a VDB reads the header, the directory and the identity layer. A JSON projection of any table remains available from the CLI for scripts and for the tests that read it today.

Tables are stored per layer, one section per table, with the rows sorted by definition and then by local identifier, so that one definition's symbols, processes and expressions are contiguous. Indexes are sections too: symbol names hashed to identifiers, source positions to rows, definition hashes to definitions. A section carries its own version, and a reader that meets a newer version of one layer keeps every other layer usable and says which views it cannot serve. This is what “versioned per layer” means: the pipeline profile schema can change without re-exporting the design.

Size follows from folding. The measured C910 export has 17.5 MB of information at zstd -3 and 168 MB of definition-distinct text before any encoding, against 809 MB stored. The targets for stage 1 are stated as goals and then measured: a C910 VDB with structure, source and behaviour under 40 MB, opened in under 100 ms, a symbol resolved by name in microseconds, and a module's netlist assembled without touching another module's rows. The benchmark that reports them is bench/vdb_size.py extended to the binary file, run in the same session as the JSON baseline, and its numbers replace these targets in this page when the stage lands.

What the container is not

It is not SQLite. SQLite was the closest alternative: Perfetto's trace processor and UCIS both show that SQL over design or trace tables is a fine query surface, and an agent can write SQL. But a SQLite file cannot be shared by mapping without copying through its page cache, its schema migrations are the versioning story, and the WASM build carries the engine into the browser. The tables are designed so that a SQLite or Parquet export is a straight copy, and the CLI offers one; the query catalogue below is what Volna and agents use.

It is not a section of VTR. The boundary stands: a trace carries what happened and the names to bind to; many VDBs may describe one trace; a VDB describes many traces. It is not an object graph with pointers, as UHDM is, and not a text format: JSON stays as a projection.

Queries

One catalogue for panels, the CLI and agents.

The queries live in volna-core beside the trace queries, take identities or names, and return small typed results with identities in them. Volna's panels call them in-process. The vtr-vdb CLI runs one query and exits, printing text or JSON, in the shape of wavepeek, with a skill file an agent installs; for repeated calls it keeps a warm session in a named socket, as Perfetto's trace processor does, so a large design is opened once. The MCP adapter of the agent control proposal adds them as a design group beside its fifteen viewer tools, so an agent in a running session reads the same VDB stack the user attached, and its findings appear in the user's knowledge panel as labelled steps. Volna

What the viewer gains, layer by layer.

Volna attaches a VDB stack to a trace the way it opens a trace: a same-stem file is found, a --vdb argument or a workspace entry adds more, and the hierarchy sidebar shows a chip per file with what matched. Attachment never blocks the waveform; views that need a layer appear when it resolves. The panels below are the features the plan builds, each on the layer that makes it possible.

  • Hierarchy with definitions. The sidebar folds repeated instances under their definition, shows parameter values, and searches definitions and symbols alike (L1). The 9.2-million-scope gate-level hierarchy becomes 373 definitions with counts.
  • Typed rows. A packed struct is a row with fields, an enum prints its literal, a fixed-point type prints a number, and a whole interface is one foldable group (L1, L7). The translators exist; the types were missing.
  • Source tile. Surfer's tile ported to Volna: tokens, values at the cursor in a trailing column, declaration jumps, the inactive generate blocks dimmed, and the reverse: select lines, see the signals (L2).
  • Schematic panel. The elkrs netlist as a panel rather than an SVG: a definition's cells and nets with values at the cursor, drill-down into children, the cone of the selected net highlighted, and gate-level cells folded by type (L3).
  • Explain panel. Today's temporal driver tree as a panel at the cursor, each node opening its source and its wave row (L3 with VTR).
  • State machine panel. The diagram with the state at the cursor, transition counts and never-taken edges from the trace, and a decoded state row in the waves (L4).
  • Domains. Clock and reset roles colour the hierarchy and the rulers; crossings are listed (L4 with declared clocks).
  • Register panel. The map by address, a register decoded into fields at the cursor, and its write history as a table; a click on a write places the cursor (L5).
  • Interface lanes. A bound interface becomes a transaction lane of extracted transfers, using the lanes design without a tracer in the design (L5).
  • Pipeline and protocol profiles. The Konata-style panel and the CHI panels read their roles, hues and anchors from L7 instead of from files of their own.
  • Assertion rows. Properties as rows that show their evaluations from the trace, and cover points as a list with hit counts when a coverage database is attached (L6).
  • Knowledge panel. Annotations on the selected object, findings with evidence that jumps to the time, and the agent's proposals awaiting a decision (L8). Writes are undoable steps.

Every panel is a volna-core model painted by the frontends, tested headless, and driven through the command catalogue. The egui frontend keeps its minimal behaviour and gains nothing here.

Producers

Every frontend writes the same tables.

One writer in Rust with a C projection builds the container; producers fill the tables they know. The pinned Verilator remains the primary producer, writing L0 to L3 at verilation from its elaborated tree, before optimisation, as it does today; verilator_vdb_index writes L2 from slang. The pyslang exporter writes the same layers for standalone browsing. The analyser in vtr-vdb writes L4 from L3, so every producer gets state machines and domains without implementing them. Imports write L5 and L6 from IP-XACT, SystemRDL, CMSIS-SVD and UCIS. Volna and the CLI write L7 and L8.

Three producers extend the reach. Yosys, from RTLIL or its JSON, writes gate-level and synthesized designs: cells as L3 primitives, src attributes as L2 locations, and its own fsm_detect results as L4 rows with Yosys as provenance. CIRCT's HGLDD debug info writes L1 and L2 for Chisel designs, where the Verilog names are generated and the source is Scala. SystemC and gem5 write L1 from their object trees, with TLM sockets and ports as interfaces in L5, so that the ESL side of the SoC is a design and not just a set of transaction streams.

Boundaries

What stays out.

  • Trace data. No value, no transaction, no result of a run. Findings reference traces; they do not copy them.
  • Layout. Schematic coordinates are computed by the viewer and cached in its workspace; the VDB stores the graph.
  • Window state. What is open, selected and zoomed is the workspace's; a group template becomes workspace rows when inserted, as the groups design decided.
  • A language server. Code does not change during debugging; the index is written at build time.
  • Executable code. Rules and profiles are data with fixed vocabularies; a new protocol or idiom that needs code is a producer or an analyser, versioned in the repository.
  • The VTR format. It gains nothing; design.vdb_id and the enum tables it already carries are enough to bind.

Research

What the industry keeps beside a trace, and what nobody keeps.

We read the public documentation and datasheets of the three commercial debuggers, the manuals and source of the open tools, the debug-info formats of the compiler world, and the 2025–2026 papers and product announcements on agentic hardware debug. Cadence's site refuses direct fetches, so its material was read from archived copies and Cadence-authored slides; where only a search snippet was available the table says so. Three findings shape this design.

Every serious debugger has a compiled design database, and every one separates it from the waveform. Verdi's KDB beside FSDB, built by the same front end as the simulator (vcs -kdb) and loaded by scope on first touch. Questa's vopt -designfile design.bin beside qwave.db, with a wave-view mode that needs no design file at all. Cadence's .dsn beside .trn, the lightweight -lwdgen design file that loads incrementally instead of the simulator snapshot, and for emulation a new database, Sage, built by the emulator's own compiler so the hierarchy is identical. The join, however, is weak everywhere: FSDB embeds a path to the .daidir and matches by name with alias files; ModelSim's vsim.dbg must be regenerated after a structural change and the tool “does not automatically detect” one. Content-addressed definitions fix this, as build ids and debuginfod did for executables.

The semantic layers are the same in every tool, and they are all derived. KDB holds a language model over the parse tree and an inferred netlist model of instances, ports, instance ports and nets with cells classified as module, flip-flop or latch; on it run driver and load tracing, schematics, FSM extraction (nState), X tracing and assertion listing. Questa recognises state machines under three conditions (a finite state set, a clocked next-state assignment, and a next state that depends on the current one) and records the file, the state variable, the clock, the reset states, the state set and a transition table with source line ranges. Yosys's fsm_detect makes the same decision on a mux tree of constants and stores it as a $fsm cell with state and transition tables. DVT and Sigasi draw the same diagrams in an IDE from the same rule and mark dead states. Verdi keeps its behaviour analysis in a persistent side database, reused across sessions, and Siloti keeps an essential-signal database so that a 25% dump can be expanded on demand from the design. Nobody stores these as a per-instance JSON tree; UHDM's authors call the unfolded model “colossal” and keep a folded one.

Agents are arriving through the same door, and they need the same tables. In the first half of 2026 AMIQ's DVT, Sigasi and Siemens's Questa One each shipped an MCP server over their design model; Verdi Assistant exposes Verdi as an MCP server; Cadence's ChipStack grounds its agents in a “mental model” built by static analysis of the RTL and specifications. The research literature measures what helps: an AST-based driver back-trace with an agent-chosen depth raised VerilogCoder from 74.4% to 94.2%; VeriTrace's agents pass 0–33% of FSM problems without a trace inspector that takes signals and a window; FVDebug fits a causal graph of 169 (signal, cycle, value) nodes into a 50k-token prompt; BluesFL localises 24 of Ibex's bugs at top-1 from blocks with their input and output sets. Perfetto's warm-session RFC rejects MCP as the primary interface, since it “serves only LLM agents, not scripts, CI, or humans at a terminal”, and wraps it around a CLI session instead. The queries these need are precisely the layers above: resolve, describe, cone with values at a time, state machines by name, blocks with reads and targets.

What no tool does, and this design does

  1. Content-addressed definitions, so a fact about a module follows the module into another run, another design and another producer, and a stale companion is detected per definition rather than by a warning in a manual.
  2. One versioned container for RTL, gate level, generated HDL, ESL and profiles, open and mapped, instead of a database per vendor, per analysis and per view.
  3. The same bounded, cited queries for the viewer, the terminal and the agent, with what the agent learned stored as rows beside what the compiler knew.

Plan

Twelve stages, each one usable.

Each stage lands in one or a few commits on master, keeps every existing test green, and ships a feature an engineer can use that day. The order puts the container and the folding first because every measurement in this page says the JSON is the bottleneck; then the three layers the build already produces; then the layers that make the viewer richer; then agents, knowledge, producers and stacks. Each stage's picture is drawn by this page with only that stage's features, from the same recording as the explorer.

Stage 1

The container, identity and folded structure.

The .vdb binary container in core/vtr-vdb, sharing VTR's section, directory, string-table and zstd code; the identity and structure layers with definitions, instances, symbols and types stored per definition; definition hashes and the design identity; an importer that reads today's JSON v2 and writes the container; and the reader that memory-maps it and resolves names through a hash index. The JSON stays readable by the same crate until stage 3 moves the last consumer. This is the stage that turns 809 MB into a file that opens in milliseconds, and its first commit adds the measurement to the benchmark.

Core
vtr-vdb::container, layers::{identity, structure}, Vdb::open mapping the file, resolve and hierarchy; the schema document docs/VDB_SPEC.md with the tables and their versions.
Producers
The pinned Verilator and the pyslang exporter write the container through the C projection; the JSON importer covers older exports.
Volna
The hierarchy sidebar attaches a same-stem .vdb, shows a chip with what matched, and folds repeated instances under their definition with counts.
Agent
Nothing yet; the identities exist for stage 8 to return.
Tests
Round trips of the fixtures through import and export; identity stability across two builds; bench/vdb_size.py extended to the binary and run on C910 in one session with the JSON baseline.

Stage 2

The source layer and Volna's source tile.

The source index of today, folded per file, with macro expansions, inactive ranges per instance and the reverse map from ranges to symbols, statements and processes. On it, Surfer's source tile arrives in Volna as a volna-core model: tokens, declarations, values at the cursor in a trailing column, a jump from a wave row to its declaration and back, one active instance per definition chosen by the selection, and the inactive generate blocks dimmed. Sources may be embedded on request so a trace and its VDB travel together.

Core
layers::source; source query; volna-core::source panel model with cursor values through the existing translators.
Producers
verilator_vdb_index and the pyslang exporter write the folded index; an --embed-sources option.
Volna
The source panel in GPUI and VS Code; Go to source on rows and scopes; the panel in the workspace; no journaled edits.
Agent
None yet.
Tests
Headless panel tests on the fixtures and the four-state twin; a C910 open-time budget of 100 ms for the tile.

Stage 3

The behaviour layer, cones, and the schematic and explain panels.

Processes, expressions, statements and connections move into folded tables with interned types, and the build precomputes per-symbol driver and load summaries to the bit where the structure allows and marked imprecise otherwise. The temporal engine and the netlist builder read the tables instead of the JSON, with their goldens unchanged. Volna gains the schematic panel, laid out by elkrs per definition on demand with the selected net's cone highlighted and children opened by a click, and the explain panel that shows the temporal driver tree at the cursor.

Volna
Two panels; selection shared with the waves; drill-down as navigation, not an edit.
Agent
None yet.
Tests
All existing vtr-vdb netlist and trace tests pass on the container; panel tests; cone query time and the 2,000-descendant geometry test on C910's largest definition.

Stage 4

Types, and typed rows in the waves.

The types table gains what the exporters drop today: packed struct fields, enum literals, unpacked dimensions, interfaces and modports, fixed-point formats. Verilator writes them from its elaborated types before it flattens; the trace's own enum tables are joined to the same rows. Volna's translators decode a flat recording into fields and literals, so a row of state reads REQ and a row of ctrl reads its three fields, in the sidebar values, the source tile and the explain tree alike.

Core
Types in layers::structure; describe returns fields and literals; volna-core translators take a type.
Producers
Verilator and pyslang write struct, enum and array types; the importer maps FST enum tables.
Volna
Typed rows and folded struct groups; format chosen by type by default, overridable per row as today.
Agent
None yet.
Tests

Stage 5

A profile file is a VDB with only this layer, keyed by definition hashes or by design identity, and stacks on the build's.

Stage 6

The idiom analyser and the state machine panel.

The build runs it by default. Volna gains the state machine panel with the state at the cursor, transition counts and never-taken edges from the trace, state rows in the waves, and domain colouring in the hierarchy.

Stage 7

Interfaces, registers and extraction rules.

The interfaces layer: bus interfaces as role vocabularies bound to symbols, register maps with fields, enumerations, access and side effects, and extraction rules. Imports from SystemRDL, IP-XACT and CMSIS-SVD fill the tables; the analyser derives a map from a read multiplexer when there is no file, as the explorer does. Volna gains the register panel with decoded fields at the cursor and the write history, and interface lanes: a bound AXI or APB port becomes a transaction lane of extracted transfers without a tracer in the design.

Stage 8

The query catalogue, the CLI and the MCP design group.

The queries of the table above become one catalogue in volna-core with JSON schemas, bounded parameters and cited results, called in-process by the panels. vtr-vdb query runs one query and exits, or keeps a warm session in a named socket for repeated calls, prints text or JSON, and ships a skill file. The MCP adapter of the agent control proposal adds the design tool group, so an agent in a running Volna reads the attached stack and the user's cursor. Each result is measured in tokens on C910 and trimmed until a cone, a machine and a register card each fit a small budget.

Stage 9

The knowledge layer and the knowledge panel.

Annotations, findings with evidence, investigations and proposed facts as append-only rows written by people and agents, keyed by definition hash or design identity, in a personal file and in team files kept in the repository. Volna's knowledge panel shows the rows for the selection, jumps to evidence, and lets a person confirm or reject a proposal. A write is a journaled step labelled with its author; an agent's step never merges with a person's, as the agent control proposal decided.

Stage 12

Stacks, reuse across runs and designs, and reconstruction.

A session opens a stack of VDB files and resolves each by design identity or by definition hashes, so a team's idioms and knowledge for an IP apply in every design that instantiates it unchanged, and a multi-trace session binds every trace of one design to one structure with structural attachment where identities differ. Files are found beside the trace, in a cache directory by identity, or from a server that answers an identity with a file, as debuginfod does. Finally, the behaviour layer earns its keep on the trace side: a run that recorded only registers and inputs is expanded on demand, combinational values computed by the evaluator and shown as derived rows, with the tracer's own settings written into the trace so the viewer knows what was left out.
