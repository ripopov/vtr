Vision · VDB

VDB, rethought. What the design means, for people and agents.

VTR records what happened in a simulation. VDB should record what the design is and what it means, well enough that a person or an agent can ask why and get an answer that cites its evidence. Today VDB is two unrelated things under one name: an RTL export that takes 5.9 GiB of memory to open for openC910, and a few hand-written profiles that nothing loads. This page proposes one design knowledge base in four layers. Compiled facts come from the elaborated design and are stored once per module specialization. Derived facts name registers, clocks, state machines and interfaces. Packs add protocol, pipeline and register meaning. Notes hold what people and agents learn during an investigation. Every fact says where it came from, every answer cites its facts, and Volna, the CLI and MCP agents ask through one query catalogue.

Measured on openC910 CoreMark: 6,934 instances of 409 specializations · 809 MB of JSON today, about 14 MiB estimated in the proposed container · 95 state machines replayed against 1,181,073 recorded transitions, all of them predicted · research on Verdi, Indago and Verisium, Questa, CIRCT, hgdb, Glean, SCIP, Pernosco and agent debugging from 2024 to 2026

Today

Two things share one name.

The RTL export. Verilator and a pyslang script write vtr-rtl-vdb version 2: one JSON document with every instance, symbol, port connection and process of the elaborated design, a token index for rendering source, and a map from design paths to trace paths. The vtr-vdb CLI draws driver trees and module schematics from it, and Surfer uses it for source navigation and inline values. It works well on the test designs. On openC910 it does not:

The profiles. Separately, the application note describes hand-written documents that give trace names a meaning: stage roles and colours for a pipeline (c910.pipeline.vdb.json, 3.8 KB), counter units and row styles for C910's performance counters, CHI and UCIe protocol packs, clock roles, key attributes for pairing traces and signal-group templates. Each proposal defined its own schema. Volna loads none of them.

  1. Different data, one name. The export is compiled at build time, hundreds of megabytes and exact. A profile is written by a person, a few kilobytes and a judgement. They differ in producer, lifetime and trust, and should not share a schema. They should share identities and one way to ask.
  2. Stored per instance. 6,934 instances repeat 409 bodies. Stored once per specialization with names relative to the instance, the same content is 178.6 MiB of JSON, and 5.0 MiB when each specialization is compressed on its own. Nothing opens incrementally, and nothing can be paged to VS Code.
  3. Semantics stop at a subset. Partial and aggregate assignments (83,245 statements), case (3,493), complex port connections (4,115) and loops (138) are opaque. A quarter of the register targets can be explained, and no state machine can be recognized.
  4. Whole kinds of knowledge are missing. There are no registers with their clocks and resets, no clock domains, state machines, interfaces, memories, register maps, assertions or testbench objects, and no link from a transaction stream to the logic that produced it.
  5. No query layer. Debugger, NetlistIndex and Surfer each index the JSON their own way. An answer cannot cite a fact, because a fact has no identity beyond a path.
  6. No home for what is learned. An extracted machine, a transition count or an agent's finding has nowhere to live, and nothing records who asserted it or whether anyone checked.

What carries over. Much of today's work is right and stays: export from the simulator's own elaborated model before optimization; exact attachment by design id and an explicit binding, never by guessing suffixes; slang as the independent front end; the token index that lets Surfer render source without a language server; and the tracer's temporal rules, which search clock events rather than value changes, so enable holds and pre-edge sampling come out right. The trace-driver interface proposals remain the model for how a driver trace is shown.

Every debugger keeps a design database. Few make it a knowledge base.

Commercial debuggers all keep a design database beside the waveform database, usually built by the simulator's own front end. Three lessons. First, each vendor builds its design database with its simulator's front end and keeps it apart from the trace; the leaders differ in how much meaning they add on top, and Verdi adds an inferred netlist, state machines and power intent. Second, the stores that scale (Glean, SCIP, DWARF and BTF, OpenROAD) hold typed facts under stable, readable names, deduplicate by content, and name and version what they derive. Third, every measured gain for agents comes from structure joined with recorded values and served as causal graphs and small event tables, not from raw dumps. No open tool does all three, and none we found lets an agent write back what it learned, with its provenance, for people to review.

Rules

Ten rules.

  1. Facts, not documents. VDB is a set of typed facts about entities: a declaration, a process, a register, a state machine, a protocol binding, a note. Every fact has a kind, a readable key that stays the same across builds while its module does not change, and provenance: its layer, its producer and version, its inputs, and whether it is exact, recognized, asserted or a hypothesis.
  2. Four layers, by author. The simulator's front end writes compiled facts; named analyses write derived facts; people and generators write packs; an investigation writes notes. A layer adds facts about the entities below it and never changes them.
  3. Store once per specialization. A module body with its parameter values is stored once, under a hash of its content. Instances are a tree of references. Derived facts are computed per specialization and shared by every instance, and by every build in which the module did not change.
  4. Open in milliseconds, page the rest. A reader maps the file and reads the directory, the instance tree and the name index, and nothing more until asked. The same pages travel to VS Code.
  5. Complete, or explicitly partial. The IR covers synthesizable SystemVerilog: case, loops, functions, partial and aggregate assignments, memories, structs and any width. Anything else becomes an opaque fact with its reads, writes and reason. The exact share is measured on C910 at every stage.
  6. Time stays in VTR. VDB never copies values. Facts computed from a trace, such as coverage, derived transactions and reconstructed signals, are cached in that trace's .index sidecar under both identities, and can always be rebuilt.
  7. Answers carry evidence. A query result names the facts, source spans and recorded samples it used, as links that a person opens in Volna and an agent quotes. Ambiguity is a result, not an error.
  8. Recordings check claims. Whatever can be checked against a recording is: an extracted machine is replayed on its recorded inputs, a handshake binding is tested on the trace, a reconstructed net is compared with a full dump. A disagreement is a finding, never silently resolved. The demo's replay is this rule at work.
  9. One catalogue. The Rust query API is the catalogue and the C API projects it. The CLI, Volna's panels and the MCP tools are thin adapters, so anything an agent can ask, a person can see, and the other way round.
  10. Many producers, one schema. Verilator writes VDB natively and slang covers other simulators. Yosys brings gate-level netlists, CIRCT's debug information brings Chisel source, SystemRDL and IP-XACT bring register maps, and SystemC and gem5 bring their structure through runtime reflection.

Design

Four layers. Each lives beside what it describes.

The layers differ in who writes them and when, so they live in different places. The compiled and derived layers describe one build and travel with it. Facts derived from a run live beside that run. Packs are versioned with the design's sources, and notes with the investigation.

Notesworkspace

Findings, hypotheses, bookmarks and the steps of an investigation, written by people and agents, each with its evidence and a status: hypothesis until confirmed.

Packstext, in the design's repository

Protocol, pipeline, performance, register and specification meaning; key attributes; colours as hues and row styles; group templates. Written by people and generators, and proposed by agents for review. Packs resolve like CSS: an instance beats a module, which beats a pattern, and a personal pack beats a team pack, which beats the build's own.

Deriveddesign.vdb, and a stacked cache

Registers with clock, reset and enable; clock and reset domains, gates and crossings; state machines, counters, FIFOs, memories and pipeline registers; handshakes and interfaces; fan-in and fan-out indexes; module cards. Each written by a named, versioned extractor, exact or recognized by a rule it names. What the build derives goes into the file; what is derived later goes into a cache file stacked over it, keyed by specialization, so it survives rebuilds that leave the module alone.

Compileddesign.vdb, at build

Sources, tokens and a reverse index from source ranges to entities; specializations with declarations, types, ports, connectivity and statement IR; the instance tree; the binding to trace names. Written by Verilator, slang, Yosys for netlists, or a CIRCT import. Exact.

From a run<trace>.index

The derived layer applied to one recording: state coverage and transition causes, derived transaction streams, reconstructed signals, value-origin caches. Keyed by the design id and the trace's identity, and rebuilt when either changes, in the sidecar the activity index introduces.

One query catalogue

A Rust crate, projected to C, answers every question from these layers plus the VTR reader.

  • Volna panels: source, state machine, schematic, why, notes
  • vdb CLI and scripts
  • MCP tools for agents
  • Surfer and other viewers

Two views of behavior

Verdi keeps an elaborated language view and an inferred netlist side by side, and this design does too. The compiled layer keeps statements as written, with guards in priority order and source spans, because an explanation must quote the line that fired. The derived layer adds a bit-level dependency graph and, per register, a register-transfer form: clock, reset, enable and a next-state expression. Cones, schematics, state-machine recognition and reconstruction read the derived view; explanations walk the statements and cite them. Both are computed once per specialization.

Identity and citations

Design id. The SHA-256 of the elaboration record and the exported semantics, as design.vdb_id is today. A trace names the design it came from with that VTR attribute, so a trace finds its VDB and a stale VDB is refused.

Specialization key. The definition name and a hash of its parameter values and resolved content, such as ct_rtu_pst_preg_entry#9f2c1e. It does not change between builds while the module does not change, so derived facts are reused and two revisions can be compared module by module.

Entity key. A specialization key, a local path and a kind: ct_rtu_pst_preg_entry#9f2c1e/fsm/lifecycle_cur_state. Keys are readable, like SCIP symbols, and a file stores them once and refers to them by number.

Links. vdb: names an entity in an instance, src: a source span and vtr: a recorded signal at a time, for example vdb:…preg15/fsm/lifecycle, src:ct_rtu_pst_preg_entry.v:308-311 and vtr:…preg15.x_release_vld@4576. Volna opens all three, and agents quote them.

Fingerprints. Every answer carries the design id, the trace identity, the pack versions and the normalized query, as wave-mcp's answers do. The same fingerprint gives the same answer, byte for byte.

The boundary, restated

VTR stays as it is: trace data, runtime hierarchy and relations, with no design semantics and no presentation. VDB never writes into a trace. One refinement: compiled and derived facts are raw data about the recorded design, not presentation, so volna-server may serve their pages beside a remote trace, as it serves hierarchy pages. Packs and notes stay on the client.

Agents

Built for agents, checked by people.

An agent cannot read 14 MiB of design facts or 243 MiB of trace, and should not try. The research agrees: agents do well when a tool joins structure with recorded values and returns a small causal answer (VerilogCoder, FVDebug, VeriPilot), and badly on raw dumps (WaveformQA). So VDB gives agents verbs, not files. Each verb is a query of the catalogue; Volna's agent-control tools from the agent control proposal show the answer on screen.

The answer contract

  1. Bounded. A default budget of rows and bytes, the most important first, with a continuation token for the rest.
  2. Cited. Every claim carries a vdb:, src: or vtr: link. Volna opens each one, and the MCP server offers the three forms as resource templates, so a host can fetch a cited span or signal directly.
  3. Fingerprinted. The design id, trace identity, pack versions and normalized query come with every answer.
  4. Honest. "Ambiguous", "not computed" and "unsupported" are values with reasons, never silently dropped.
  5. Deterministic. Same inputs, same bytes, so tests can pin every tool's output.

An answer, as fsm_inspect would return it for the demo's machine. The numbers are the replay's; the budget kept four of the twelve transitions, the ones a person asks about first, and more continues.

Search and caching

design_search ranks by names, comments, module cards and structure. VDB stores no embeddings, because they would tie a design file to one model and go stale with it; an agent or an adapter can embed cards itself. Deterministic answers also make caching simple: an answer is reusable wherever its fingerprint matches, across agents and sessions.

Writing back

Agents write notes, never facts. A note starts as a hypothesis and becomes confirmed when a person, or a check the note names, confirms it. A recurring confirmed note can become a pack proposal. For example, an agent that sees a valid/ready pair proposes a handshake binding; the binding is checked against the recorded trace (valid never drops without ready) before a person accepts it into the pack. Nobody edits compiled or derived facts; they change only when the design or an extractor changes.

Measuring the benefit

The evaluation starts with the first agent tools. A task suite injects bugs with known root causes into picorv32 and C910 units and grades the answers. The same models answer once with raw waveform tools, as wavepeek offers, and once with VDB's tools. The report records success, tokens and tool calls, and every later stage reruns it. Tool outputs are deterministic and tested in CI; model runs are a benchmark with a checked-in command, like the performance suite.

Format

One container, one body per specialization.

The file reuses VTR's container, as the .index sidecar does: header, sections, directory and trailer, string tables and compressed blobs, with its own magic and version. A reader maps the file and at open reads only the directory, the instance tree and the name index.

Plan

Fifteen stages, each useful on its own.

Every stage builds, passes cargo test, cargo test -p volna-core and volna/volna/check.sh, and updates the specification, rationale, tests and documentation it touches. No stage adds a flag or code that only a later stage calls. Backward compatibility is not kept: the JSON export is replaced, not wrapped. Stages that change what Volna stores decide what is undoable, as the viewer architecture requires.

Why this order. The store comes first, because nothing scales without it, and the native producers retire the JSON right after. Agents come third, with the evaluation, so that every later stage is measured by what it adds for them. Volna and notes follow, so people see what agents cite. Then semantics in dependency order: the complete IR, then registers and clocks, then state machines. Explanations and schematics build on all three. Meaning (packs, interfaces, reconstruction, registers and software) comes after the structure it binds to, and comparing revisions comes last because it needs stable keys everywhere.

Foundation

Stage 1

The fact store

The container and a crate that writes and reads it, with a converter from today's JSON so that consumers move before producers do. The driver-tree and schematic commands keep their output and run on the new store.

Format
A new docs/VDB_SPEC.md: the container with its own magic and version 1; META, STRINGS, INSTANCES, NAMES, SPEC, SOURCES, TOKENS and BINDING; specialization and entity keys. A RATIONALE entry with the measured format decision.
Core
core/vtr-vdb becomes core/vdb: a writer and a memory-mapped reader over VTR's container code, specialization hashing, Vdb::open, instances, spec, find and resolve. Debugger and NetlistIndex read through it. vdb.h projects it to C one to one.
CLI
vdb info, find, check, convert (JSON to store), trace and netlist.
Tests
Round trip; every C910 entity equal between the JSON and the converted store; the driver-tree and SVG goldens unchanged.
Measure
C910 size, open time, peak memory and one driver tree, against the JSON's 13.3 s and 5.9 GiB, with vdb_census.py kept as the reference for the estimate.

Stage 2

Native producers

Verilator writes the store directly at --trace-vtr, and its source indexer adds the token pages. The pyslang exporter feeds vdb import, so standalone slang designs keep working. The v2 JSON and its reader are deleted.

Producers
V3EmitVdb writes through a small C++ writer in the fork, with no Rust in Verilator's build; verilator_vdb_index writes TOKENS; the runtime writes BINDING for each recording, as trace_binding does today.
Consumers
Surfer's source tile and schematic canvas read the store.
Tests
integrations/verilator/vdb/run.py on the store; Surfer's source snapshots unchanged; the slang fixtures through vdb import.
Measure
C910 verilation time with and without the export, and the store's size against stage 1's conversion.

Stage 3

Agent tools and the evaluation

An MCP server over the catalogue as it stands, and the task suite that tells whether it helps. Every later stage adds tools and reruns the suite.

Core
The answer contract as a library every tool uses: budgets, continuation tokens, links and fingerprints. Module cards built from compiled facts.
Agents
vdb mcp, a stdio server with design_search, design_describe, source_read, structure, read_values, explain_value (today's tracer) and find_events (conditions over recorded signals); vdb skill writes a skill file for agent harnesses.
Bench
Bugs injected into picorv32 and C910 units with known causes and graded answers; runs with raw waveform tools as the baseline; success, tokens and tool calls in the benchmark report.
Tests
Golden outputs of every tool on the fixtures and a C910 subset; budgets, continuation and fingerprints.

Stage 4

Volna attaches VDB

Volna finds a trace's VDB by its design id, locally and over the remote session, and gains a source panel: go to the declaration, values at the cursor inline, go to the driver. Links in agents' answers open the right place.

Core
A design attachment in the volna-core session, with load requests for SPEC, SOURCES and TOKENS pages; resolution of vdb:, src: and vtr: links; hierarchy rows that know their specialization.
Protocol
volna-server serves VDB pages beside the trace; a new protocol version.
Frontends
GPUI: the source panel. egui keeps its behavior.
Undo
None: opening sources is navigation. The workspace remembers open source tabs.
Tests
Attachment by id, and refusal of a stale VDB; remote pages equal local ones; inline values on the fixtures in both themes.

Stage 5

Notes

People and agents record what they find: a note on any entity, time range or selection, with evidence links and a status. An investigation keeps its steps as a tree, as Indago does, so a colleague can follow it.

Core
Note records in the workspace, written by one journaled writer: target, time range, text, evidence, author (person or agent), status (hypothesis, confirmed, rejected) and parent step.
Frontends
GPUI: a notes panel and note marks on rows and on the time axis.
Undo
Adding, editing, deleting and changing status are labelled steps; an agent's steps are labelled as the agent's and never merge with the user's.
Agents
The notes tool.
Tests
Note edits in the model-based history test; save and restore; export and import.

Semantics

Stage 6

The complete IR

The IR stops at nothing synthesizable: case, casez, unique and priority; loops unrolled at elaboration; functions and tasks inlined with their call sites; partial and aggregate assignments; memories; structs and unions; and a four-state evaluator of any width.

Producers
Verilator's export, still before width commitment, and slang's import, both extended to the new statements and bit-range targets.
Core
Opaque statements keep their reads, writes and reason; the evaluator works on arbitrary-width four-state values.
Tests
A corpus of statements and operators evaluated against values Verilator recorded; X and Z propagation.
Measure
The exact share of C910's register targets and combinational processes, and the rest by reason, against today's 25% and 47%. The target is above 99% of register bits.

Stage 7

Registers, clocks and resets

Every register gets its clock, edge, resets and enable from its process. Clock gates fold into the clocks they gate, and clock domains and the crossings between them are listed.

Core
The registers@1 and clocks@1 extractors, per specialization, in DERIVED sections at build and in the stacked cache otherwise; gates recognized by structure (a latch and an AND), not by cell name.
Frontends
GPUI: clock and reset in a signal's tooltip; cycle rulers from a register's clock, bound to VTR's declared clocks when the trace has them.
Agents
Module cards list clocks, resets and crossings.
Tests
Gated clocks, dividers, asynchronous and synchronous resets, and two domains with and without synchronizers.
Measure
C910's registers, gates (3,056 expected) and domains, and the extraction time.

Stage 8

State machines

The demo on this page, in Volna. State machines are recognized, named from their constants and comments, and drawn with counts; their state names replace raw values on wave rows.

Core
The fsm@1 extractor: Yosys's rules, extended to one-hot comparisons and part-selects; states named from enums and constants and described by adjacent comments; reset edges from the register. fsm_replay writes counts per source line, time in each state and ambiguous edges to the trace's sidecar.
Frontends
GPUI: a state-machine panel with the diagram, counts, never-taken transitions and time in each state, linked to the source panel and to wave rows; state names as a value format.
Undo
None; choosing an instance or a transition is navigation.
Agents
fsm_inspect; find_events gains state sequences.
Tests
The preg lifecycle on C910: 1,181,073 changes predicted and 62 ambiguous edges, as fsm_replay.py finds today; binary, one-hot and Gray machines; candidates correctly rejected.
Measure
Machines found in C910 against the 103 named candidates, with every difference reviewed; extraction and replay time.

Questions

Open questions and limits.

  1. The name. Synopsys calls its coverage database VDB (simv.vdb). The proposal keeps the name for the concept; the file is a single file with its own magic, not a directory.
  2. When to derive. Registers, clocks and state machines are cheap and useful at once, so the proposal derives them at build time; cones are derived on first use and cached. Verilation time on C910 decides.
  3. How expressive packs are. JSON with selectors and templates first. A rule language waits until two packs need more than templates, as the CHI design concluded.
  4. Generated RTL. C910's sources are themselves generated. Where a generator emits debug information, as CIRCT does with UHDI, VDB imports it as a second source view; otherwise the HDL is the source.
  5. Sources in the file. Embedding sources makes a VDB self-contained for remote and archived debugging, and also makes it carry the IP. It is a per-build choice.
  6. Gate-level designs. Standard cells repeat, so bodies are shared, and the instance tree is the paged scope index of the scope sizes design. Whether an inferred netlist of millions of cells stays within budget is measured, not assumed.
  7. Several designs in one session. A testbench model and a DUT from different front ends, or SystemC around RTL, need one binding per subtree of the trace.
  8. What leaves the machine. A remote model sees what the tools return. Budgets bound it, and a per-session policy can withhold source text and return structure only.
  9. Live simulation. The IR's statement guards are what source-level breakpoints need, as hgdb shows. Driving a live simulator is outside this plan; the store would serve it unchanged.
  10. A standard. No open debug-database format exists; a vendor-neutral debug data API presented at DVCon reached a 0.95 draft with no ratified standard we could find, and CIRCT's UHDI covers only generator debug information. Once stages 1 to 8 have landed, the store's specification could be offered as one.
  11. Model runs in CI. The evaluation needs model access. Tool outputs are gated in CI; model runs are a benchmark with a checked-in command.

Limits. VDB does not simulate. It cannot recover the order of events inside one time step, electrical resolution, or anything the trace did not record, and says so. Its inferred structure explains logic; it is not a synthesis result.
