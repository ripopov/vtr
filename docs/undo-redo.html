Undo and redo for the Volna cockpit

Volna never changes a trace, but people spend real effort on the cockpit they build around one: signals picked from a large hierarchy, formats, groups, markers and panels. ⌘Z should take back the last of those changes, wherever it happened, and ⇧⌘Z or Ctrl+Y should put it back.

Proposal with an interactive demo, 27 September 2026; implemented 28 September 2026. The demo runs the journal in JavaScript and checks it with a model-based self-test on every load. The Rust in this page is the implementation in volna-core (history.rs, app/undo.rs, wave/tree.rs): App::handle_at, the pre-order row tree of signal groups, Panels with App::created, the document's markers and the workspace codec. Where the implementation departed from the proposal, the text says so. Costs come from volna-core/examples/undo_cost.rs in release builds, on an Apple M5 laptop for the proposal and an Intel Core Ultra 7 265K for the implementation.

What it covers
What the cockpit contains and how it draws it: rows, formats, heights, groups, markers, rulers, panels and their layout.
What it leaves alone
Where you look: zoom, pan, cursor, scroll, folds, focus, selection, links and settings. Undo never moves the time axis.
How
Edits are data. Applying one returns its inverse, a step groups one command or gesture, and undo and redo are the same operation.

The design in eight decisions

  1. One linear history per open trace. Every panel, the markers and the layout share it, so ⌘Z takes back the last cockpit change wherever it happened. A new edit discards the redo list. The history is dropped when the trace or a workspace file is opened or closed, and it is not saved in workspace files.
  2. Undo covers what the cockpit holds, not where you look. Adding, removing, moving, grouping and formatting rows, markers, rulers and panels are undoable. Zoom, pan, cursor, scroll, folds, focus, selection and links are navigation and never make a step. Selection is restored with each step, so the restored rows come back selected.
  3. Edits are data, and applying one returns its inverse. A closed Edit enum has four variants: row splices, markers, panel properties (rulers among them) and layout. Every journaled field has exactly one writer, which keeps the value the field had before its first change; the app collects those inverses into the step after each command. Undo and redo are one function, flip, which applies a step's edits newest first and keeps what they return.
  4. Steps hold descriptions, never trace data. Removed rows are kept detached, like the row clipboard: format, height and path, but no history. A closed panel is kept after the app has released its data and its memory reservation. Undo attaches them again through the normal load path. The journal has one cap, 64 MiB, and always keeps the newest step.
  5. One command or one gesture is one step. App::handle_at opens a step and commits it when the command returns. A drag commits on release, and Esc rolls it back. Repeated adjustments to the same target within one second merge, as do a new group and its name. A gesture that ends where it started records nothing.
  6. Undo shows what it changed. It focuses the panel, raises its tab, restores the selection and scrolls the rows into view. Menus read “Undo Remove 3 rows”. The result is announced politely to assistive technology (“Undid Remove 3 rows”) and shown in the status bar. The time axis stays where you left it.
  7. Standard keys, owned by the focused element. On macOS, ⌘Z undoes and ⇧⌘Z redoes. On Windows and Linux, Ctrl+Z undoes and both Ctrl+Y and Ctrl+Shift+Z redo. Text fields keep their own text undo. In VS Code the extension forwards the keys and the page replays them through Volna's own focus chain, so it stays a read-only editor and never gets a dirty tab.
  8. Coverage is tested, not trusted. A model-based test drives random commands and checks two things after each one. Undo must reproduce every earlier state of the workspace projection exactly, and any change that leaves no step fails the test. Surfer shows why this matters: upstream forgot to save a snapshot for marker removal[1].

    What undo covers
    
  
    The rule is one question: would losing this change cost effort to rebuild? Choosing forty signals, a format for each and a group around them does. Scrolling back to where you were does not, and it should not use up undo steps. Viewers that keep the view out of undo put it in a separate history, like GTKWave's Undo Zoom, Questa's zoom last and Saleae's back and forward[5][7][8]. Blender and REAPER draw the same line[21][22]. In Volna's terms, the undoable state is what a workspace file stores minus its navigation fields. The tests use exactly that projection.

    Selection is restored, not recorded
    
      
    Blender and Figma make selection undoable. Figma users have asked for years for an option to leave it out, because undo spends steps on clicks[27]. Zed gives selection its own stack, REAPER makes it an opt-in bit, and Perfetto's history ignores it[13][22][9]. Volna records none of it. Each step stores the selection of the panels it touched, before and after, and restores it, so undoing a removal brings the rows back selected and ready to act on.
    
    
    
    
    
      
    Settings and the trace are other documents
    
      
    settings.json applies to every trace, and its JSON view is a text editor with its own text undo. Cockpit undo leaves it alone. The trace itself is immutable. Closing it drops the history; the autosaved workspace brings the cockpit back when the trace is opened again. Retry loading and every other data load are consequences of edits, not edits.

    Adopted
    
      
      
        
    • A linear history where a new edit clears redo. Every system above works this way; branching is opt-in in REAPER and an add-on in Emacs[28].
      • 
        
    • One step per command or gesture, as in Surfer, VaporView and QUndoStack.
      • 
        
    • Merging by identity and time: Qt's mergeWith, Zed's 300 ms and Yjs's 500 ms windows.
      • 
        
    • The view stays out of undo and has its own history: Surfer, GTKWave, Questa, Saleae, Blender, REAPER.
      • 
        
    • Records hold identities, not data, and undo reloads through the normal loader: Surfer's cache-free clones, and the fork's closed tiles.
      • 
        
    • Labels on every step and showing the result: Apple's HIG, Qt's “Undo %1”, Surfer's status bar[23].
      • 
        
    • A memory cap in bytes that keeps the newest step: REAPER, and Blender's memory limit.
      • 
      
    
    
    
    
    
      
    Avoided
    
      
      
        
    • Whole-state snapshots (Surfer, VaporView, redux-undo). A 100,000-row panel costs 200 ms and 8.3 MB to save through the workspace codec (measured).
      • 
        
    • Selection as steps (Blender, Figma, VaporView): it spends undo on clicks.
      • 
        
    • Undo reported to VS Code as document edits (VaporView): the read-only trace tab would turn dirty and prompt to save.
      • 
        
    • Opting in at each call site with nothing checking coverage: this is how Surfer missed marker removal. Here a test catches it.
      • 
        
    • A per-panel stack (QUndoGroup): closing a panel, markers and cross-panel paste do not belong to one panel.
      • 
        
    • A step limit: Apple's HIG says to “avoid placing unnecessary limits”, so the cap is in bytes instead.

    The design
    
  
    
    
    
      
    One history per trace
    
      
    The history belongs to App, beside the document and the panels it edits. A single stack for the whole cockpit matches how people think about undo: it takes back the last thing they did. It also handles what a per-panel stack cannot, such as closing a panel, the document's markers, a paste into another panel, and the start panel giving way to content. The history is linear. Undo moves a step to the redo list, and any new step empties that list.
    
      
    Opening or closing a trace, opening a workspace file and replacing the session all drop the history, because they replace the objects it names. Workspace files do not store it. The autosaved workspace already restores the cockpit across sessions, and Zed, Surfer and VaporView do not persist undo either.
    
    
    
    
    
      
    One command or one gesture is one step
    
      
    App::handle_at is already the single entry point for input, and it already compares workspace stamps around each command for autosave. It becomes the step boundary: edits made while a command runs join one step, which commits when the command returns. A pointer gesture keeps its step open until the release, so dragging rows or a marker is one step. Esc, or ⌘Z during the drag, rolls the open step back and records nothing.
    
      
    Two explicit rules merge steps. A merge key is the same kind of adjustment to the same targets, such as a format, a height step or a marker nudge. Such a step joins the previous one if that one was the last thing committed and less than one second has passed, so TTT is one step. A continuation lets a follow-up command join its origin with no time limit. G creates “Group 1” and opens its name field, and committing the name joins the group step, so one undo removes the named group.
    
      
    A gesture that ends where it started, such as a marker dragged away and back, records nothing. Commit drops every edit whose stored value equals the current state, compared by what a workspace stores (Entry::same), so a row height dragged out and back or a format cycled round within the window leaves no step. The demo's self-test found the first case, and the Rust model-based test found a second: a row moved past an identical copy of itself changes nothing, so tree::plan_move refuses it.
    
    
    
    
    
      
    What a step stores
    
      
    A step is a label, the inverse edits recorded while it ran, the context before and after (focus and the selections of touched panels), a merge key and a size. The inverse of a row splice holds the removed rows detached: source path, format, height, analog settings and group structure, with no SignalHistory. WaveModel::copy_selected detaches rows this way for the clipboard, and both use one helper, Entry::detached. A detached row costs about 320 bytes (measured).
    
      
    A closed panel is kept as a Panel value after App::release has detached it. Pipeline, table and transaction panels then no longer retain their tracks, tables and transaction panels return their memory reservation (park), and its wave rows are detached. Undo puts it back under its own PanelId, which is safe because the allocator is monotonic, and runs App::created again, which reserves the memory again and reattaches the rows. Because the journal holds no trace data, it is not charged to the session memory ledger. It has its own cap: 64 MiB, about 210,000 detached rows. The oldest steps go first, after a commit and after an undo (whose inverse may be larger than the step it replaces), and the newest step is always kept, even when it alone exceeds the cap.
    
    
    
    
    
      
    Showing the result
    
      
    Apple's guidelines ask apps to show the result, for example by scrolling a restored paragraph into view[23]. After undo or redo, Volna focuses the panel the step changed, activates its tab, restores the selection the step saved, and scrolls the first restored row into view. It never moves the time axis. A marker brought back off screen is announced, and the view stays put, because the time axis is where the investigation is.
    
      
    Every step has a label built by the core: “Add 3 signals”, “Remove 2 rows”, “Format hex”, “Add marker”, “Close Waves 2”. The Edit menu reads “Undo Remove 2 rows”: labels keep sentence case because they name signals, groups and panels, which title case would change. The palette lists “Undo: Remove 2 rows”, and the announcement says “Undid Remove 2 rows”. The announcement is its own event, Event::Announce, not a warning notice: the status bar shows it until the next edit, the web page passes it to document.ariaNotify where available, which is Baseline since September 2026[26], and falls back to a polite live region otherwise, and VS Code shows no popup for it. When there is nothing to undo, the announcement says so, and the menu item is disabled.
    
    
    
    
    
      
    Loads, failures and autosave
    
      
    Undo never waits for data. Re-inserted rows share a resident history for the same signal (App::resident_histories) or queue one load, exactly as Paste does, and show the loading state until it arrives. If an add is undone before its load finishes, the late delivery finds no row and does nothing, as it does today. Lanes, analog summaries and group summaries follow through the reconciliation that handle_at already runs after each command. VS Code's prepareUndoRedo suggests the alternative: load first, then apply synchronously. It was rejected because ⌘Z would then block on I/O.
    
      
    Journaled state changes only through edits, so when a step is flipped its targets are always there. If an apply fails anyway, that is a bug: debug builds panic, and release builds clear the history with a notice rather than leave a half-applied step. Undo and redo mark the workspace as changed, so autosave writes the result like any other edit.

    Architecture
    
  
    Everything lives in volna-core, in a new history module and app/undo.rs. Frontends only bind keys, host the Edit menu and show announcements. The core changes in one principle: every journaled field has one writer, and the writer keeps the inverse. Row edits are planned by the pure functions of wave::tree, which return splices; WaveModel performs them through its only row mutator and keeps their inverse. Markers, titles and table columns are Journaled<T> fields; rulers, pins and radixes keep their previous value in their owner. After each command, and before each change of the panel structure, App collects every inverse into the open step. App::apply performs edits only when a step is flipped.
    
  
    This departs from the proposal, which had every model return a planned Edit for App::apply to perform. Recording at the writer needs no edit plumbing through pointer handlers and command results, covers every caller of a field by construction, and a field that is changed without being collected fails the model-based test.
    
  

  
    Types
    

    // volna-core/src/history.rs
/// One change to cockpit state. Applying it returns the edit that undoes it,
/// so undo and redo are the same operation.
pub(crate) enum Edit {
    /// Replace runs of a wave panel's pre-order rows, applied in order. Rows
    /// kept in the journal are detached: no history, no load error.
    Rows { panel: PanelId, splices: Vec<Splice> },
    /// The document's markers, swapped whole (tens, not thousands).
    Markers(Vec<Marker>),
    /// One property of one panel, swapped whole.
    Prop { panel: PanelId, prop: Prop },
    /// The panel tree, the panels to close, and detached panels to put back.
    Layout(Box<Structure>),
}

pub struct Splice { pub at: usize, pub remove: usize, pub insert: Vec<Entry> }

pub(crate) enum Prop {
    Title(Option<String>),
    Clocks { rulers: Option<Vec<String>>, origin: Option<u64> },  // waves, pipelines
    Columns(ColumnSet),                                         // table
    Pin(bool, Option<ShownRecord>),                             // transaction: pinned, on what
    Radix(BTreeMap<String, Radix>),                             // transaction attributes
}

pub(crate) struct Structure {
    pub layout: Layout,          // as Panels::saved_view: the settings tab is chrome
    pub focused: PanelId,
    pub close: Vec<PanelId>,
    pub reopen: Vec<Panel>,      // released: no tracks, no reservation, rows detached
}

/// A field that changes only through set/update, which remember the value
/// before the first change since the app last collected edits.
pub struct Journaled<T> { value: T, before: Option<T> }   // Deref, no DerefMut

/// A labelled group of inverse edits: one command or one gesture.
pub struct Step {
    pub label: String,
    edits: Vec<Edit>,             // recorded order; flip applies them newest first
    pub before: Context,          // focus, and the selection of each touched panel
    pub after: Context,
    merge: Option<MergeKey>,      // same adjustment, same targets, within MERGE_WINDOW
    continues: Option<MergeKey>,  // a follow-up that may join with no time limit
    at: Instant,
    bytes: usize,
}

pub struct History {
    undo: VecDeque<Step>,
    redo: Vec<Step>,
    open: Option<Step>,
    last: Last,                   // Commit | Undo | Redo: merges only follow a commit
    bytes: usize,
    revision: u64,                // menus rebuild when it moves
}

pub const MERGE_WINDOW: Duration = Duration::from_secs(1);
pub const MAX_BYTES: usize = 64 << 20;   // the newest step is always kept
    

  
    App: collect, apply, flip
    

    // volna-core/src/app/undo.rs
impl App {
    /// Move the inverses the journaled fields keep into the open step. Called
    /// after each command and before every layout edit.
    fn collect_edits(&mut self) {
        if let Some(markers) = self.doc.take_markers_edit() { /* record Edit::Markers */ }
        for panel in self.panels.iter_mut() {
            // title, rulers and origin, the wave rows' journal (with the selection
            // before it and its merge keys), table columns, pin and radixes
        }
    }

    /// Perform one edit and return its inverse.
    pub(crate) fn apply(&mut self, edit: Edit) -> Result<Edit> {
        Ok(match edit {
            Edit::Rows { panel, mut splices } => {
                // detached rows share a resident history or queue one load
                let resident = self.resident_histories();
                attach_rows(splices.iter_mut().flat_map(|s| &mut s.insert), &mut self.doc, &resident);
                let waves = self.panels.waves_mut(panel).context("no wave panel")?;
                Edit::Rows { panel, splices: waves.splice(splices)? }    // the one row mutator
            }
            Edit::Markers(markers) => Edit::Markers(self.doc.swap_markers(markers)),
            Edit::Prop { panel, prop } => Edit::Prop { panel, prop: self.swap_prop(panel, prop)? },
            Edit::Layout(structure) => {
                let mut inverse = self.panels.install(*structure)?;
                inverse.reopen.iter_mut().for_each(|p| self.release(p));   // closed now
                inverse.close.iter().for_each(|&id| self.created(id));     // back now
                self.layout_changed();
                Edit::Layout(Box::new(inverse))
            }
        })
    }

    /// Undo and redo: apply the step's edits newest first and keep what comes
    /// back, which is the step that flips it again.
    fn flip(&mut self, step: &mut Step) -> Result<()> {
        let mut out = Vec::with_capacity(step.edits.len());
        for edit in step.edits.drain(..).rev() {
            out.push(self.apply(edit)?);
        }
        step.edits = out;
        Ok(())
    }
}
    
  
    handle_at gains two calls. Before dispatch, begin_step notes the focus and time a step would start with. After dispatch, end_step collects every journaled field's inverse and commits the open step unless a panel still has pointer capture (Panel::dragging): the release commits it. Commit merges the step into the previous one when it repeats or continues it, prunes edits that cancelled out, empties the redo list, applies the cap and tells the workspace scheduler that the workspace changed. Every change of the panel structure goes through App::restructure, which collects first, so a panel's own edits are journaled while it still exists, and records nothing when only navigation changed (focus, active tabs, sash sizes, the settings tab). ClearSelection or Command::Undo during a drag drops pointer capture and flips the open step back (cancel_gesture). Command::Undo and Command::Redo flip a step, restore its context, scroll to the restored rows, announce the result and mark the workspace changed. Command::named has "undo" and "redo" for hosts, and App::undo_label, App::redo_label and History::revision feed the Edit menu and the palette.

    Why splices on the pre-order rows
    
      
    WaveModel::items is already a pre-order vector of Entry { depth, row }. Every row operation, from add to ungroup, is a sequence of splices on it: replace remove entries at at with insert. The inverse of a splice is a splice, and a list of them inverts in reverse order. A move of k rows across a 100,000-row panel stores k detached rows, not the range between the two places. One variant therefore covers the whole row tree. Its round trip is a few lines to test, and tree.rs keeps its pure planners, which now return splices instead of mutating.
    
      
    Indices are valid addresses because the history is linear, and nothing else reorders the rows. When a step is flipped, the rows it names are exactly as the step left them. Folding changes a group's collapsed flag, not the vector. The one asynchronous write to a row style today, a new lane taking the height its records need, only fills in an auto_height placeholder, and a restored or explicit height clears that placeholder.
    
    
    
    
    
      
    Rules that keep it correct
    
      
      
        
    • One writer per journaled field. The wave rows are private to WaveModel and change only through WaveModel::splice; markers, titles and table columns are Journaled<T>, which has no DerefMut; a timed panel's clock choices are private to NavState; a transaction panel's pin is private to it. Folds, loaded histories and a new lane's height change rows in place, because they are navigation or trace data.
      • 
        
    • Recording happens at the writer. WaveModel::pointer cannot reach App, and it need not: a release that moves rows keeps its inverse in the panel's journal, which the app collects when the command returns. Every inverse is held in a history::Before, and each owner hands its own over in take_edits (Panel::take_edits covers the title, the rulers and the kind's fields). Debug builds count the held Befores and assert after collecting that none is left, so a field whose owner forgets to hand it over fails the next command in any test, not only when the random test reaches it. Workspace restore and a new trace install values without recording (restore), and undo installs them with swap.
      • 
        
    • Swaps keep their earliest inverse. Within a step, a second swap of the same target (markers, or one property of one panel) is not recorded, and neither is an in-place rewrite of the same rows right after another, because the first inverse already restores the step's start. At commit, an edit equal to the current state is dropped.
      • 
        
    • Detaching has one implementation. The clipboard, removed rows and closed panels use Entry::detached and App::release, so the journal never holds a SignalHistory, a generator or a memory reservation.
      • 
        
    • The projection is the contract. The undoable state is Workspace::capture with the navigation fields cleared. The model-based test compares it byte for byte (tests).

    Frontends
    
  
    
    
    
      
    GPUI, native and web
    
      
    Two actions, Undo and Redo, dispatch Command::Undo and Command::Redo. Their bindings follow the existing pattern of binding both cmd- and ctrl-: cmd-z, ctrl-z, cmd-shift-z, ctrl-shift-z and ctrl-y, all in Workspace && !Embedded. GPUI matches bindings before key listeners, from the focused element outward, and the innermost context wins[15]. The sidebar filter and the group name editor (ui::TextInput) bind the same five keys in their TextInput context to their own text undo, where a run of typing or deleting undoes at once. The settings search and JSON editor are gpui-kit inputs, which bind text undo for the platform only; Volna binds the other keys in their Input context, so no undo key falls through to the cockpit while one has focus. The Edit menu (Undo, Redo, then the row clipboard) is rebuilt with set_menus when History::revision moves, and disables an item with nothing to take. The palette lists both commands with their labels. On the web, handled keys call preventDefault, so the browser's own Edit ▸ Undo does not act on the page.
    
    
    
    
    
      
    VS Code
    
      
    Volna stays a CustomReadonlyEditorProvider. Reporting cockpit steps as CustomDocumentEditEvents would give native undo, but VS Code would mark the trace tab dirty and ask to save a file that cannot change. VaporView accepts that, and Volna should not[18][4]. The webview host already swallows ⌘Z, posts it to the workbench and runs the custom editor's no-op undo[29]. The extension therefore contributes volna.undo and volna.redo keybindings with activeCustomEditorId == volna.waveform && !inputFocus, next to volna.saveWorkspace, and forwards them as {type: "command", name: "undo"}.
    
      
    The page does not run Command::named for these two directly. It replays the command as the key it stands for (Window::dispatch_keystroke): a focused Volna text field's binding takes it and undoes text, which VS Code's own webview inputs lack (issue #227849[30]); otherwise no binding of the embedded workspace matches, and the page runs Command::Undo or Command::Redo. VS Code's Edit ▸ Undo menu item cannot reach a read-only editor; the palette entries “Volna: Undo” and “Volna: Redo” stand in for it.
    
    
    
    
    
      
    egui and agents
    
      
    volna-egui keeps its minimal feature set and gets no undo bindings; the core does not need it to. Agent and MCP adapters stay thin: their edits are core commands, so they become labelled steps that a person can undo, and undo and redo are commands they can issue too.
    
    
    
    
    
      
    What the history is not
    
      
    It is not a navigation history. Going back to an earlier view is a separate feature with its own keys (Qt's standard Back is Alt+←, or ⌘[ on macOS[20]). It builds on the transaction panel's Back and Forward and the marker proposal's jump back, and it is out of scope here. It is also not a history panel: the list in the demo shows the journal to explain it. A Blender-style Undo History could later be a palette mode over History.

It then measures the size of a row and the time to detach every row. It also times a full save and restore of the workspace, which is what a snapshot-per-step journal would pay.     Alternatives considered
    
  
      
    
    • A workspace snapshot per step (redux-undo, VaporView). Always complete, but it costs 200 ms and 8.3 MB per step at 100,000 rows. Restoring also re-resolves every path and bumps the document generation, which breaks delayed pointer events.
      • 
    
    • Copy-on-write snapshots (Arc per panel, make_mut on change). Cheap to capture, but a format change on one row clones the whole row vector. The snapshots would also hold the history Arcs, so removed signals would stay resident and charged to the memory ledger for as long as the journal remembers them.
      • 
    
    • Recording by diffing the projection before and after every command. Coverage would be automatic, but capturing costs 200 ms at 100,000 rows. Instead, the same comparison runs as the test oracle.
      • 
    
    • Replaying commands from the opening state. Commands depend on focus, selection and loads that change between the action and the redo, and the fork's rationale rejects this for the same reason.
      • 
    
    • One stack per panel (QUndoGroup). Closing a panel, the document's markers and a paste into another panel have no owning panel.
      • 
    
    • An undo tree (Emacs undo-tree, REAPER's optional redo paths). It is more powerful, but people expect a linear list, and it would need a navigation UI of its own.
      • 
    
    • Selection as steps (Blender, Figma). It spends steps on clicks; restoring selection with each step gives the useful part.
      • 
    
    • VS Code document edits (CustomEditorProvider). Native undo and Edit-menu labels, at the price of a dirty, savable read-only trace.
      • 
    
    • Persisting the history in the workspace file. The file grows, and the format has to version edits. The autosaved workspace already restores the result.
      • 
    
    • A step limit (Surfer 50, Blender 32). Bytes are what actually runs out, and Apple advises against unnecessary limits.
      • 
    
    • Waiting for loads before applying (VS Code's prepareUndoRedo). Undo would block on I/O. Rows show a loading state instead, as a paste does.
      • 
  
    

    


    
  
    Tests
    
  
    
    
    
      
    volna-core (headless)
    
      
      
        
    • Model-based test (tests/history.rs). A seeded generator drives 400 inputs per seed over the landing trace, which has signals, generators, clocks, pipelines, tables and transaction records. The inputs add, remove, cut, paste, drag, format, plot, resize, group, name and ungroup rows; add and clear markers; toggle rulers and the cycle origin; split, close, close others, rearrange and rename panels; open pipelines, tables and transaction panels; toggle columns, pins and radixes; drag rows and row heights, some cancelled with Esc and some dragged back to the start. Undo, redo and navigation are interleaved, and quick repeats exercise merging. The projection is Workspace::capture with navigation cleared, kept for every undo depth. After each input the test checks that undo and redo reproduce the projection of their depth exactly; that an input that changes the projection made a step; that no step leaves the projection as it was; that navigation leaves the journal and the projection untouched; that a new step empties the redo list; and that the cap holds. At the end it unwinds everything and replays it. A second run uses a 12 KiB cap, which forces eviction; VOLNA_UNDO_SEEDS=n adds seeds.
      • 
        
    • Round trips. Every planner in wave::tree (removal, insertion, move, group, ungroup) is applied, undone and redone in unit tests, and the random tree test checks that each inverse restores the rows exactly. Invalid splices change nothing. history unit tests cover Journaled, merge windows, continuations, the cap and clearing.
      • 
        
    • Loads. Removed rows come back sharing a history another panel holds, without a request; with no copy left, undo queues one load and shows loading. An add undone before its load completes ignores the late delivery, and a redo during pending loads loads again.
      • 
        
    • Memory. Closing a table returns its 4 MiB reservation to the ledger, and the journal holds no ledger bytes. Undo puts the table back under its ID and reserves the memory again.
      • 
        
    • Grouping and gestures. TT within the window is one step; a pause of 1.5 s makes two; another selection is another target. G followed by a name 30 s later is one step. A row drag is one step on release; a height drag cancelled with Esc or ⌘Z restores the heights and keeps the redo list; a drag back to the start leaves none.
      • 
        
    • Context, labels and clearing. Undo refocuses the panel and restores the selection; redo of a split focuses it again; labels, announcements and the status line; navigation makes no step and undo keeps the time axis; the history is cleared on close, open and workspace restore, and a workspace file is byte-identical with or without history.
      • 
        
    • Cost. examples/undo_cost.rs times undo and redo of a 100,000-row removal and panel close (measured costs).

    Plan
    
  
    All nine steps are implemented, in this order. Where a step went differently, it says how.
    
  
      
    
    1. History module. Edit, Splice, Structure, Step, History, Journaled, byte accounting, merge and continuation rules, and unit tests.
      2. 
    
    2. Rows. WaveModel's rows are private behind splice. The mutators in tree.rs became planners that return splices; WaveModel performs them and keeps the inverse, so pointer outcomes carry nothing new. The detach helper is shared with the clipboard.
      3. 
    
    3. Markers and rulers. Document's markers are a private Journaled field, and NavState owns the journaled rulers and origin apart from the selected clock. The marker proposal's own journal is replaced by this one.
      4. 
    
    4. Panels. App::restructure records a Structure inverse for every open, split, close and rearrangement, and Panels::install applies one. Closed panels are released and parked in the journal and come back through App::created. Titles, table columns, pins and radixes are Prop edits; rulers joined them instead of having their own variant.
      5. 
    
    5. App. Command::Undo and Command::Redo and their named forms, step boundaries in handle_at, gesture commit and rollback, context restore and reveal, announcements, autosave, and clearing on open, close and restore.
      6. 
    
    6. Model-based test and the memory, async and grouping tests; undo_cost extended.
      7. 
    
    7. GPUI. Actions and bindings, text undo in TextInput, the Edit menu, palette entries, input precedence tests; the web platform prevents the default of handled keys.
      8. 
    
    8. VS Code. Keybindings, forwarding replayed as keys through the focus chain, and extension tests.

    Open questions
    
  
      
    
    • Is one second the right merge window for format and height presses? Zed uses 300 ms and Yjs 500 ms, both for typing, which is faster than choosing a format.
      • 
    
    • Should the journal cap be a setting (undo.memoryMiB) like memory.budgetMiB? It starts as a constant.
      • 
    
    • Should restoring a closed panel also restore its sash proportions exactly? The Layout swap restores the tree as it was at the step. Proportions changed since then are lost on undo, and people rarely notice.
      • 
    
    • Should a navigation history (back and forward over views) come next, with keys that stay clear of the marker proposal's jump back?

    Glossary
    
  
    
    
    Cockpit
    Everything a person builds around a trace: panels and their layout, rows and formats, groups, markers, rulers. A workspace file stores it.
    
    
    Navigation
    Where you look: viewport, cursor, scroll, folds, focus, selection, links. Never recorded.
    
    
    Edit
    One change to cockpit state, as data. Applying it returns its inverse.
    
    
    Splice
    Replace remove rows at at with insert in a panel's pre-order rows.
    
    
    Swap
    An edit that installs a whole value (markers, rulers, a property) and returns the old one.
    
    
    Step
    What one undo takes back: the inverse edits of one command or gesture, with a label and context.
    
    
    Flip
    Apply a step's edits newest first and keep their inverses: undo and redo.
    
    
    Detached
    A row or panel that keeps its description but holds no trace data or reservation.
    
    
    Gesture
    Pointer input from press to release; its step stays open until the release.
    
    
    Merge key
    The kind and targets of an adjustment; equal keys within one second merge.
    
    
    Continuation
    A follow-up command allowed to join the step that started it, such as naming a new group.
    
    
    Projection
    The workspace capture without navigation fields: the state undo must restore exactly.
