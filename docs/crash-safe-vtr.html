Design · VTR writer · Verilator fork

A crash should cost the process, not the trace.

Simulations die: a DPI model dereferences a null pointer, an assertion calls abort(), a job scheduler sends SIGTERM. Today a VTR file then keeps only its completed blocks. When SIGSEGV cut a 30-million-change run short, the file kept 56% of the value changes and none of the 396 log records, though the log is what explains a crash. This design makes the writer's accepted data survive every ending a process can observe. A tiny signal handler hands the work to a rescue thread that closes the file through the ordinary close path, within a hard deadline. It then ends the process with the original signal, so the exit status and core dump are unchanged. A prototype against today's libvtr.a kept 100% of the data in every catchable case, stack overflow included, in 0.21–0.69 s. Heap corruption was saved only once VTR allocated from its own heap.

Proposal · measured with bench/crashlab on a Core Ultra 7 265K, glibc 2.43 · stages 1–3 of 8 have landed

Basics

How programs end, for people who never had to care.

The rest of this page leans on a dozen ideas from operating systems. None is hard, but they are rarely taught together. This chapter explains each with the example that matters here: a simulator that records a trace on one thread and compresses it on another.

1A process and its threads

A running program is a process. It owns an address space, the memory only it can see. Inside it run one or more threads, each a sequence of instructions with its own position in the code and its own stack, a small region where function calls keep their local variables. All threads share everything else. That includes the heap, where long-lived objects such as buffers are allocated with malloc, new or Rust's Vec.

A Verilator simulation that records VTR has at least two threads. The simulation thread evaluates the model, and after every time step it hands the changed signal values to the VTR writer, which appends them to a buffer in memory. The writer's encoder thread takes full buffers, sorts them into columns, compresses them with zstd and writes finished sections to the file. With log records there are two more helper threads that encode log blocks. The design keeps compression off the simulation thread, so the simulator hardly waits. It also means that at any moment a lot of the trace exists only in memory.

When a process ends, for any reason, the kernel takes back all of its memory at once. Nothing in the heap, on any stack or in any thread survives. So whatever should outlive the process must be outside it before the end.

2Where the bytes are when the process dies

Data travels in three hops. The program collects bytes in its own buffers. The write() system call copies them into the kernel's page cache, a pool of memory the kernel uses for file contents. Other programs see them from that moment, even if they are not on the disk yet. Later the kernel writes them to the disk by itself, typically within 30 seconds, or at once when the program calls fsync().

One consequence runs through the whole design: a write() of a finished section is the commit point. Before it the section is at the mercy of the process; after it only the machine can lose it. One more detail matters. A single large write() is not atomic if the process is killed during it. The kernel stops copying at the kill, so the file can end in the middle of a section. On this machine SIGKILL during one 1 GiB write() left 98 to 438 MiB of it. A reader must therefore find the last complete section by itself, and VTR's sections carry a length and a CRC for exactly that.

3How a program ends

There are only a few ways out, and they differ in what code still runs.

  • Returning from main, or calling exit(n). The C library runs the functions registered with atexit and the destructors of static objects, flushes stdio buffers, then asks the kernel to end the process. Other threads are not stopped first. They keep running while destructors tear down objects they may still be using, which is the classic "logger destroyed while threads log" bug. Destructors of objects on the stack of main do not run when exit is called from deeper code, such as a DPI function.
  • _exit(n) and quick_exit(n). These end the process immediately, without destructors. quick_exit runs only its own short list of handlers.
  • abort(). This is what failed assertions, std::terminate (an exception nobody caught), a Rust panic across a C boundary and glibc's heap checks all call. It sends the signal SIGABRT to the calling thread. No atexit functions and no destructors run.
  • Death by a signal, described next. The exit status then encodes the signal: a shell prints 139 for SIGSEGV (128 + 11), 134 for SIGABRT and 143 for SIGTERM. CI systems, make and job schedulers read these numbers.

Verilator adds its own layer. $finish only sets a flag that the main loop checks. $fatal and internal errors call vl_fatal, which runs the registered exit callbacks, and the VTR trace closes in one of them. That path already works; the rest of this list does not close the trace today.

4Signals

A signal is the kernel interrupting a process to say that something happened. Each has a number and a default action, usually "end the process", often with a core dump, a snapshot of memory for the debugger. There are two kinds, and the difference matters.

  • Synchronous signals are caused by the instruction a thread just executed, and they are delivered to that very thread. SIGSEGV is an access to memory that is not mapped, such as a null pointer or a stack that ran out. SIGBUS is a bad access to a mapped file, SIGFPE an integer division by zero, SIGILL an illegal instruction. SIGABRT from abort() behaves the same way, because the thread sends it to itself.
  • Asynchronous signals come from outside, at an arbitrary moment, and are delivered to whichever thread does not block them. SIGINT is Ctrl-C. SIGTERM is the polite "please stop" from kill, timeout or a job scheduler. SLURM, for example, sends SIGTERM and then SIGKILL 30 s later by default. SIGXCPU means a CPU-time limit was reached.

A program may install a handler, a function the kernel runs instead of the default action, with sigaction(). Two signals can never be handled: SIGKILL and SIGSTOP. The Linux OOM killer, kill -9 and container runtimes use SIGKILL. Against it only data that is already outside the process helps.

5Why a signal handler may do almost nothing

A handler does not run in a fresh, orderly context. The kernel interrupts the thread wherever it is, between any two instructions, and runs the handler on top of it. The interrupted code may have been halfway through updating a data structure, or holding a lock.

So POSIX lists the functions that are safe to call from a handler, the async-signal-safe ones (signal-safety(7)). They are essentially plain system calls: write, read, poll, clock_gettime, sigaction, raise, pthread_kill, sem_post, _exit. Missing from the list: malloc and free, printf and all of stdio, mutexes, C++ streams, and anything that might use them, which includes zstd with a normal context and nearly all of the VTR writer. Operations on lock-free atomic variables are also allowed. Because a handler shares its thread with the interrupted code, it must also save and restore errno.

Most logging libraries break this rule on purpose and call it best effort (Quill says so in its header). Most of the time nothing is locked and it works. The failure mode, a hang instead of a crash, is worse than losing the log, which is why the good ones add a timeout.

6Handing work to another thread

The way out is to do nothing in the handler except ask another thread to do the work, then wait. The other thread is not interrupted. It runs ordinary code, may allocate, lock and compress, and can close the VTR file with the same code as a normal close. This design calls it the rescue thread. It is created when the guard is installed and sleeps until needed, because creating a thread during a crash would itself allocate.

Threads talk through memory, and two subtleties apply. First, processors and compilers reorder memory operations for speed. One thread's writes can reach another thread in a different order unless the code says otherwise with atomic variables and release/acquire ordering: everything written before a release store is visible to a thread that reads the stored value with an acquire load. The handler records the signal, then publishes "crash claimed" with such a store. Second, the waiting thread should sleep rather than spin, so the rescue thread blocks in read() on an eventfd, a kernel counter. The handler wakes it with one write(), which is async-signal-safe.

The rescue thread blocks every signal, which is how Quill protects its backend thread. An asynchronous signal is therefore never delivered to it, and it never runs a handler in the middle of a rescue. If it faults itself, the kernel cannot deliver a blocked synchronous signal and ends the process at once with the default action. That is the right outcome for a rescue that crashes.

Two threads can crash at nearly the same time. The handler therefore claims the crash with an atomic compare-and-swap: the first thread that changes the state from "idle" to "rescuing" proceeds, and the others wait for the first to end the process.

7Waiting with a deadline

The rescue can hang. A lock may be held by the dead thread, a disk may be full, the encoder may be stuck. A crash handler that never returns turns a crashed job into a hung job, which is worse: CI jobs time out after hours instead of failing in seconds, and cluster nodes stay occupied. So the handler waits with a hard deadline. It reads the clock with clock_gettime, sleeps a millisecond at a time with poll(), and stops waiting when the rescue reports done or the deadline passes, whichever comes first. (nanosleep is not on the async-signal-safe list; poll with no descriptors is.) After the deadline, whatever the encoder had already written stays in the file, and the reader recovers the rest of the file by scanning.

8Stack overflow and the alternate stack

Each thread's stack has a fixed size, 8 MiB for the main thread by default and often less for others. Below it lies a guard page that is not mapped, so running off the end faults instead of silently overwriting the heap. Deep or unbounded recursion, common in DPI code and in some generated models, ends there with SIGSEGV. The handler, however, normally runs on the same stack, which is full. The kernel cannot even start it and kills the process.

sigaltstack() sets up that separate stack, but only for the thread that calls it; each thread needs its own. The handler here is shallow, so 64 KiB with a guard page of its own is ample. Glibc's SIGSTKSZ constant is too small for processors with large vector registers, which the kernel saves on the signal stack. Measured: with an alternate stack a stack overflow was fully rescued; without one the process died before the handler ran.

9Ending the process the way it would have ended

After the rescue, the process must still die, and die of the same signal. The exit status then says SIGSEGV, the core dump is written, and a debugger or the crash reporter of the job system sees the real cause. The handler restores the action that was installed before it (the default, or a sanitizer's handler), and then does one of two things. For a hardware fault it simply returns: the faulting instruction runs again, faults again, and this time the default action ends the process, with the core dump pointing at the real culprit. For a signal that was sent (SIGABRT, SIGTERM) it sends the signal again to its own thread with tgkill. The signal is blocked while the handler runs, so it stays pending and ends the process the moment the handler returns. Quill, abseil, LLVM and Breakpad all end this way. g3log re-raises from its worker thread, so its core dump shows the wrong thread.

10Heaps and their locks

malloc in glibc keeps several arenas, pools of memory each protected by a lock, plus a small lock-free cache per thread (the tcache) for blocks up to about 1 KiB. The main thread allocates from the main arena. Memory corruption in the program under test, such as a buffer overrun or a double free, is often detected by glibc's own checks, which call abort(). Some checks run while the arena's lock is held, so the process can die with the main heap locked. Any other thread that then touches memory from that arena waits for ever, including a rescue thread closing a writer whose buffers were allocated there. The prototype hit exactly this. The remedy is for VTR to allocate from its own heap, so that the application's heap can be broken without VTR noticing.

11Compressed files that stop in the middle

zstd, like most compressors, turns a byte stream into frames, and each frame into blocks of up to 128 KiB. A decoder can emit a block as soon as it has all of it. A frame ends with an optional checksum, and a new frame starts with no memory of the previous one. The streaming API offers three verbs. ZSTD_e_continue lets the compressor buffer freely. ZSTD_e_flush emits everything so far as complete blocks, but the frame goes on and later data may refer back to earlier data. ZSTD_e_end also closes the frame. A file cut after a flush decodes up to the flush but carries no checksum yet. A file cut after an end decodes and verifies every closed frame. Section zstd measures what each choice costs and shows that VTR already sits on the safe side: every compressed piece of a VTR file is a closed, independent frame inside a section with its own CRC.

Today

The format survives a crash; the data in memory does not.

The file side is sound. A VTR file is a header followed by self-delimiting sections, each with its length and a CRC-32 of its payload. The directory and trailer come last. A file without a trailer is still readable: the reader walks section headers from the start, stops at the first one that does not fit in the file, and rebuilds the directory (SPEC.md section 2.3). Nothing is ever patched in place. Strings and hierarchy always precede the sections that use them, so every complete section is decodable. FST cannot say the same: it writes its header, geometry and hierarchy only at close, and keeps the hierarchy in a .hier side file until then.

The memory side is large. The writer batches aggressively because that is what makes it small and fast. When the process dies, the following exists only in memory:

  • On the simulation thread: the current chunk of up to 1.07 million changes on C910 (16 per declared signal), the block's time table and initial values, open transactions with their attributes, stages and events, up to 4 MiB of finished transaction and log rows (about 150,000 messages), running clock stretches, pending strings and hierarchy nodes, and blackout marks.
  • In the channel to the encoder: up to four more messages, each a chunk or a block.
  • On the encoder thread: the column fragments of every chunk of the current block. A block, 16,777,216 changes, is compressed and written only when it is complete. This is the largest item.
  • On the two log helper threads: log blocks being encoded.
  • In the file buffer: up to 1 MiB of finished sections that were not yet passed to write(). Writer::flush() only queues work and never empties this buffer.

On openC910 CoreMark, 596,626,011 changes in about 36 blocks, a block is about 1.5 s of simulation time on the clock and 7,100 cycles, so a crash loses up to that much waveform and every log record since the last 4 MiB log block. Nothing in the repository catches a signal: Verilator installs no handler, and the VTR crates and C API have none. vl_fatal closes the trace through Verilator's exit callbacks, and $finish ends with the user's trace->close(). Every other ending leaves a recovered file with its tail missing. A Rust panic inside the C API aborts the process, because the C API has no catch_unwind.

Survey

Quill (include/quill/backend/SignalHandler.h) is the reference most people know. SignalHandlerOptions has four fields: catchable_signals (SIGTERM, SIGINT, SIGABRT, SIGFPE, SIGILL, SIGSEGV; SIGBUS is not included), timeout_seconds (20), and a logger name with exclusions. The backend thread starts with every signal blocked, so asynchronous signals never land on it. The handler lets the first thread through with an atomic counter, parks the rest in pause(), and arms alarm(timeout). It then logs "Received signal" through an ordinary log call and waits in flush_log(), spinning on an atomic flag the backend sets once everything queued earlier has been written. If the alarm fires, the handler restores the default action for the original signal and raises it. Otherwise it re-raises the signal itself: SIGINT and SIGTERM exit with status 0, and fatal signals end with their default action. Quill installs with std::signal, uses no alternate stack, and documents its logging path as "not strictly async-signal-safe", intentionally.

g3log (src/crashhandler_unix.cpp) goes further in the wrong direction. The handler collects a backtrace with backtrace_symbols, formats it with ostringstream and pushes a fatal message through a mutex-protected queue to the worker. The worker flushes by destroying its sinks and then re-raises from the worker thread. There is no alternate stack and no timeout, so a crash with a lock held hangs for ever. glog separates the two halves explicitly. Its handler writes a minimal report with write(2) from a stack buffer, and a comment then marks the "transition" after which it flushes log files without taking their mutex. abseil's failure handler is the most careful of the in-process ones: an alternate stack of at least 64 KiB (on the installing thread only), SA_NODEFER, a 3 s alarm() watchdog, a compare-and-swap on the failing thread id, and re-raising to the previous or default handler.

reckless is the closest to this design. Its handler pushes a "panic" marker into the lock-free ring the writer thread drains, then waits on a raw futex until the writer has written everything before the marker. It uses no locks, but also no deadline and no alternate stack. Crashpad and Breakpad are the industrial crash reporters. They install per-thread alternate stacks, keep the handler to a socket message or a clone, wait on futexes with timeouts, and re-raise with tgkill for sent signals or return for hardware faults. LLVM runs up to eight registered callbacks claimed by compare-and-swap and removes temp files listed in a lock-free list. Rust's runtime gives every thread it starts an alternate stack sized from AT_MINSIGSTKSZ, to print "has overflowed its stack". A static library such as libvtr.a never runs that setup.

Outside the process. Perfetto's producers write into shared memory owned jointly with the tracing service, which scrapes a dead producer's buffers when that is enabled. LTTng keeps ring buffers in shared memory files, and lttng-crash reads them back after a crash. Chromium keeps histograms in a memory-mapped file, whose dirty pages the kernel writes back after the process is gone, and marks a clean exit in its header. JFR writes chunks to a disk repository as it goes and copies them next to the error report on a fatal error. These survive SIGKILL, and the cost is that every byte takes the slow path all the time. MCAP shows the file-format half of the same idea. Its chunks carry CRCs and it keeps a summary at the end, and mcap recover rebuilds a truncated file into a complete one.

zstd

Independent frames cost size; VTR already paid for them.

Flush versus end, measured. 64 MiB of three inputs was compressed with libzstd 1.5.7 as one frame, with ZSTD_e_flush every N bytes, and as a new frame every N bytes. A flush only ends a block early: 3 bytes of header and fresh entropy tables. A new frame also throws away the match history, and at level 3 the window is 2 MiB or more, so that is the expensive part.

A flushed frame is decodable but unverified. A streaming decoder given a file cut exactly at a flush returned the whole prefix, byte for byte. Cut 1,000 bytes into the next block, it returned the prefix up to that block and asked for more input, without an error. The frame checksum sits only at the frame's end, so nothing in a flushed-but-open frame is checked. Of 200 single-bit flips inside such a frame, 118 (Kanata text) and 139 (C910) decoded silently to wrong data. The same flips in a closed frame with a checksum were all detected. zstd -d writes every decodable byte and then fails with "premature end"; before issue #3602 it lost buffered output there.

Compressing in a handler is possible. A context made with ZSTD_initStaticCCtx in a preallocated buffer (1.3 MB for level 3) compressed a 1 MiB buffer inside a SIGSEGV handler with zero allocator calls, and the result passed zstd -t. Multi-threaded compression is refused on a static context. Even without a compressor, a valid zstd frame of raw blocks is a header and a copy.

What this means for VTR. VTR does not stream one long frame. Every compressed blob, a column run of at most 64 KiB, a string or hierarchy chunk, a transaction or log block, is its own closed zstd frame inside a section that carries a length and a CRC-32 over the stored bytes. This is the independent-frames design at a fine grain. Its size cost was accepted for random access long ago and is recovered by the per-run transforms. So the crash design needs no zstd change. Sealing a partial block is ordinary compression of a smaller block, and a torn tail is one section that fails its length or CRC check. Two rules follow. The section CRC must be checked while recovering: today recovery trusts the length alone and checks CRCs only on request, and the flip experiment shows zstd will not catch the damage. And compression stays out of the handler: the rescue thread does it with the normal code, so the static-context trick is not needed. The same facts explain the other formats. MCAP, SQLite's WAL and Perfetto's packets all frame their records with lengths and checksums and treat the last valid commit as the end, and FST alone depends on a header written at close.

Measured

A prototype against today's library.

bench/crashlab/crashlab.cpp is the design reduced to its core, about 150 lines of guard. It has the handler of rules 2 and 9 on a 64 KiB alternate stack, a rescue thread that appends a FATAL log record and calls the unchanged vtr_writer_close, a deadline, stop requests handled as a flag, and an atexit hook. It runs against libvtr.a as it is, and against a build whose Rust global allocator is mimalloc (private-heap.patch). run.py runs every case, checks each outcome and exits nonzero if one differs. Every catchable ending was saved in full except two. On the system heap, a double free detected under the main arena's lock hung the rescue until the 3 s deadline, as Basics 10 predicts. With VTR's allocations on mimalloc it was rescued in 220 ms, three runs out of three. The other is the stack overflow without an alternate stack. Write time with mimalloc was unchanged (0.54 s for 30M changes, both allocators).

How long a rescue takes depends on where in a block the crash lands. Best of three: 214 ms at 79% of a block, 250 ms at 99.9%, and 483–692 ms just after a block was handed off, when the previous block is still compressing. On C910 the encoder writes a block in about 0.25 s (36 blocks in the 9.0 s replay write), so the same range applies there. A 10 s deadline leaves a margin of fourteen times the worst case measured.

Knowing whether the owner is inside the writer is cheap. A relaxed atomic store plus a compiler fence at entry and exit cost +0.2% per time step, the granularity of a Verilator dump, and +0.9% around every emit call: 1.181 s, 1.183 s and 1.192 s for 60 million changes, best of five.

Design

Twelve rules for a guard that cannot make things worse.

The guard is a small crate, vtr-guard, beside the writer. Signal dispositions are global to a process, so this is the one piece of VTR with process-wide state. It is installed only by an explicit call and documented as such. The vtr crate keeps no global state; it gains the queries and the sealing path the guard needs.

  1. Two kinds of ending.Crashes (SIGSEGV, SIGBUS, SIGILL, SIGFPE, SIGABRT, SIGTRAP, SIGSYS) are rescued at once. Stop requests (SIGTERM, SIGINT, SIGHUP, SIGXCPU) are not crashes. The handler only sets a flag, the simulation finishes its time step and closes normally, and then the guard re-raises so the exit status still says SIGTERM. A second request, or a grace deadline, escalates to a rescue.
  2. The handler hands off and waits.It saves errno, claims the crash with a compare-and-swap (later crashers park in pause()), copies the signal number, code, fault address and thread id into static storage, and writes one word to the rescue thread's eventfd. It then waits with clock_gettime and poll until the rescue is done or the deadline passes. It calls nothing else.
  3. A rescue thread does the work.It is started at install with every signal blocked and sleeps in read(). On a crash it records the crash in each watched writer and closes it through the ordinary close path. The encoder threads keep running and finish the current block, the logs, the directory and the trailer. If the rescue itself faults, the kernel ends the process, and the file falls back to recovery by scanning.
  4. Only a writer at rest is closed.Each writer keeps a busy word, set on entry to every public call and cleared on exit (+0.9% measured). A writer at rest, which is the usual case because the fault is in model code, is closed in full. A writer interrupted mid-call, by a bug in VTR or an allocation failure inside it, is sealed instead (rule 5). Its half-updated state is never read.
  5. What reached the encoder can always be sealed.Today the simulation thread builds a block's time table and initial values only when the block ends. Instead it sends them with each chunk, so the encoder holds everything needed to write a block from the chunks it has. Sealing drops only the chunk still being filled, at most 16 changes per signal (about 0.1 s of C910), and only when the writer was busy.
  6. VTR allocates from its own heap.The C library's heap can die locked, and the rescue must never need it. libvtr sets mimalloc as its Rust global allocator and routes zstd's allocations there too. Measured: the lock-held double free became a full rescue, and write time did not change.
  7. Every writing thread gets an alternate stack.Registering a writer installs a 64 KiB alternate stack with a guard page on the calling thread, unless it has one. The Verilator fork does the same for its worker threads. Handlers use SA_ONSTACK, so a stack overflow is rescued like any other fault.
  8. A hard deadline, 10 s by default.That is fourteen times the slowest rescue measured, and below SLURM's 30 s kill wait. Afterwards the handler gives up on the rescue. Everything already written stays, and the reader recovers the rest. The value is an install option and the environment variable VTR_GUARD_DEADLINE_MS.
  9. Die of the same signal.The handler restores the disposition saved at install: the default, a sanitizer's or the program's. For a hardware fault (si_code > 0) it returns, so the instruction faults again and the core dump shows the real crash. For a sent signal it calls tgkill on its own thread. Exit statuses 134, 139 and 143 were preserved in every run.
  10. Every other way out closes too.An atexit hook closes watched writers when exit() is called from DPI or C code. The C API wraps every call in catch_unwind, so a Rust panic becomes an error code and a poisoned writer instead of an abort across the C boundary. vl_fatal keeps closing through Verilator's exit callbacks.
  11. Bound what nothing can save.SIGKILL runs no code. Each finished section is passed to write() at once instead of waiting in a 1 MiB buffer. A wall-clock commit interval (10 s by default) forces a block boundary in slow runs, whose blocks would otherwise stay in memory for minutes. SIGKILL then loses at most one block or one interval, whichever is shorter.
  12. The file says how the run ended.A rescue appends a FATAL record to a reserved vtr.run log stream: the signal, its code, the fault address, the thread and the simulation time, or "stopped by SIGTERM", or "exit(3)". vtr info prints it. A recovered file verifies section CRCs and drops a torn tail, and vtr recover rewrites it with a directory and trailer, as mcap recover does.

The guarantee

  • Crash on any thread, writer at rest: every change, transaction, clock stretch and log record the writer accepted, plus the crash record, in a complete file. Open transactions end with status Open at the crash time.
  • Crash while the writer is mid-call: everything handed to the encoder. At most the unfinished chunk is lost. The file is complete, and its crash record says it was sealed.
  • A stop request, or exit(): everything, through the normal close.
  • Crash of an encoder thread (a VTR bug), a rescue past its deadline, or a fault inside the rescue: every section written before, recovered by scanning.
  • SIGKILL or the OOM killer: all but the last block or commit interval. Power loss: what the kernel had written back; fsync stays optional and off.

When a thread other than the writer's owner crashes, the owner must not keep writing while the rescue closes its writer. The rescue sends the owner a park signal, a real-time signal chosen at install, as Tracy freezes threads with SIGPWR. At rest, the owner parks at once. Mid-call, it parks when the call returns, at the busy word's exit. The deadline covers an owner that never returns.

Coexistence. The guard saves and restores previous handlers rather than overwriting them, and never installs over a handler it did not expect without chaining to it. It runs its rescue first and then the previous handler, so an AddressSanitizer report still appears. VTR_GUARD=0 turns it off. Debuggers stop at the signal before any handler runs, so interactive debugging is unchanged.

Plan

Eight commits, each useful on its own.

Every commit builds, passes cargo test for the crates it touches and bench/crashlab/run.py, and updates its tests and documentation. Writer changes are A/B measured against the previous commit on the benchmark suite, reporting size, write time and read time together (AGENTS.md). The crash matrix moves into CI in stage 1 and tightens with every stage after it: each stage flips some expected outcomes from "blocks" to "full".

Why this order. The test harness comes first, so each later stage proves its effect. Durable sections and the termination record change the file, so they come before anything writes a crash into one. The sealable pipeline and the private heap make the rescue safe. The guard can then be simple, and the Verilator fork is a thin caller of it. vtr recover and the commit interval come last because they only bound what the guard cannot save.

Stage 1 Landed

The crash matrix in CI

Before anything changes, the endings of the demo are a test that runs on every push. It asserts today's outcomes, so every later stage shows its effect as a diff of expectations.

Core
None.
Tests
core/vtr-capi/tests/crash.rs compiles tests/crash_harness.cpp (the crashlab workload without its guard, plus mode switches) against the static library. It runs eleven endings in child processes with core dumps off and a 60 s timeout: a normal close, SIGSEGV, abort(), an uncaught exception, stack overflow, both double frees, SIGTERM, exit(3), SIGKILL, and a fault on a second thread while the owner writes. It checks the exit status and reads the file back: recovered or not, changes and log records. Today only the normal close keeps everything; every other ending leaves a recovered file of completed blocks and no log records. The run is small (2,000 signals, 3 million changes, 1 Mi-change blocks) and takes about 10 s in a debug build. bench/crashlab/run.py stays the full-size measurement.
CI
The crash-matrix job in core-tests.yml on ubuntu-24.04.

Stage 2 Landed

Durable sections, verified recovery

A finished section is passed to write() as soon as it is complete, so the file buffer never holds finished work. Sections are 100 KiB to several MiB, so this adds a few system calls per second. A recovering reader checks every section's CRC and stops at the first mismatch, so a torn or zero-filled tail is dropped instead of being decoded into wrong values.

Core
FileSink::write_section_parts flushes its BufWriter after each section. Container::parse verifies CRCs while scanning. Reader::recovered() returns Option<u64>, the bytes dropped after the last verified section; vtr_meta has recovered_dropped, and vtr info prints it.
Spec
SPEC.md 2.3 Recovery: "stopping at the first header that does not fit in the file, whose kind is 0, or whose CRC (when not 0) does not match". A RATIONALE.md entry records the torn-write measurement.
Tests
core/vtr/tests/recovery.rs cuts a file with every kind of section at every section boundary, inside every payload, and with a zero-filled payload or tail, and checks the rebuilt directory and that the data read is a prefix of the complete file's. A writer that is never closed has every finished section in the file. The crash matrix's kill-inline case expects every completed block after SIGKILL.
Measure
Write time A/B, best of five: within ±0.8% on every replay, transaction and log workload (C910 10.38 s both); sizes byte-identical; read time unchanged. The CRC check adds 22 ms to recovering the 243 MiB C910 file (27.6 to 50.0 ms for vtr info).

Stage 3 Landed

How the run ended

A file says whether its run closed normally, and if not, why. The record uses structures VTR already has: a log stream vtr.run under the root, with one FATAL site per kind of ending, whose typed arguments a tool can filter.

Core
Writer::close_with(Ending), where Ending is Closed, Stopped { signal }, Exited { status }, Crashed { signal, code, address, thread, sealed } or Recovered { dropped }, records the ending at the writer's current time; close() is close_with(Closed) and records nothing. Reader::ending() returns the record and its time, searching from the last log block, or Closed or Recovered for a file without one. Ending displays as "crashed by SIGSEGV (address 0x0, thread 41137)". A user stream named vtr.run at the root is rejected.
C API
vtr_writer_close_ending, vtr_reader_ending and vtr_ending_format over a vtr_ending struct.
CLI
vtr info prints "ended: crashed by SIGSEGV (address 0x0, thread 41137) at t=25360".
Spec
SPEC.md 8.5 Run ending: the reserved stream name and the four site formats, as a convention with no version change. RATIONALE.md: why a log record and not a new section, which is that every reader already shows it.
Tests
core/vtr/tests/ending.rs: a round trip for each ending with the inline and background encoders, each ending's text, no record for a normal close, Recovered for a cut file, and the reserved name. c_smoke.c checks the C projection.

Stage 4

A sealable writer

Whatever reached the encoder can be finished without the simulation thread, and the guard can tell whether the simulation thread was inside the writer.

Core
Each chunk carries the time-table slice and the initial values of the groups it dirtied first, so Msg::Signal only marks the end of a block. A busy word, an AtomicU32 set and cleared with relaxed stores and compiler fences, sits in every public Writer method. Writer::seal(Ending) is safe to call from another thread while the owner is stopped: it ignores simulation-thread buffers and tells the encoder to finish what it has, then write the ending, the directory and the trailer.
C API
Every extern "C" body is wrapped in catch_unwind. A panic returns VTR_ERR_STATE and poisons the writer, whose later calls fail fast and whose close seals it.
Tests
seal after random numbers of calls equals a close that dropped the unfinished chunk, for signals, transactions, logs and clocks. A panic injected in a C call returns an error.
Measure
The full suite A/B: write time with the busy word and per-chunk frames (the prototype measured +0.9%), size unchanged, read time unchanged.

Stage 5

VTR on its own heap

Heap corruption in the model can leave glibc's heap locked for ever. VTR's memory moves out of that heap, so the rescue never waits on it.

Core
vtr-capi declares mimalloc as its #[global_allocator] (without its override feature, so the application's malloc is untouched). zstd contexts are created with custom allocation functions that call the same heap. Rust users of the vtr crate choose their own allocator, as Rust programs do.
Tests
The crash matrix's lock-held double free flips from "blocks" to "full" once stage 6 lands.
Measure
The full suite A/B for write and read time and peak memory. The prototype measured no write-time change.

Stage 6

The guard

The rules of the design as a small crate, and its C projection.

Core
core/vtr-guard: install(Options) (deadline, signal sets, park signal, chaining), watch(&Writer) and unwatch, which register a writer in a fixed table of 64 atomic slots and install the calling thread's alternate stack, thread_init() for other threads, and stop_requested(). The handlers use only libc calls from the async-signal-safe list. The rescue thread, park signal, atexit hook and re-raise follow rules 1–10.
C API
vtr_guard_install(const vtr_guard_options*), vtr_guard_watch, vtr_guard_unwatch, vtr_guard_thread_init, vtr_guard_stop_requested, documented in vtr.h as the library's single piece of process-wide state.
Tests
The crash matrix runs with the guard. Expected "full": SIGSEGV, SIGABRT, uncaught exception, stack overflow, both double frees, SIGTERM, exit(), and a crash on a second thread while the owner writes. Expected "blocks": SIGKILL, a stalled rescue (deadline within ±20%), a fault inside the rescue. Every case keeps its exit status. An AddressSanitizer build checks that ASan's report still prints.
Measure
Rescue time at three points of a block; no change to write time when no crash happens.

Stage 7

The Verilator fork

A --trace-vtr model is guarded without any change to the user's main.

Fork
VerilatedVtr::open installs the guard once per process and watches its writer. It is on by default; VerilatedVtrC::guard(false) before open, or VTR_GUARD=0, turns it off. close unwatches first. The rescue works on the vtr_writer* alone and never takes m_mutex, which a crash inside dump() leaves locked. The busy word covers dump() as a whole. Worker threads call vtr_guard_thread_init when they start. A stop request sets gotFinish on the trace's context from the rescue thread, so a standard main loop ends and closes normally; after the grace period the guard escalates. The vtr_trace package's clocks and trackers end with the writer.
Tests
integrations/verilator/crash/: a model whose DPI function segfaults, aborts, recurses without bound or calls exit at a given cycle, plus $fatal and SIGTERM from the runner. Each file is compared with a run that finished: the same changes up to the crash cycle, the same log records, and the ending. It runs in the Verilator integration CI job.
Measure
C910 CoreMark with a forced SIGSEGV at cycle 200,000: rescue time and a check that the rescued file matches the complete run up to that cycle. No change to Verilator+VTR run time without a crash.

Stage 8

Bounded loss and vtr recover

What no handler can save is bounded, and a recovered file can be made whole.

Core
WriterOptions::commit_interval (10 s by default; 0 turns it off). set_time and log check a coarse monotonic clock every 1,024 calls and flush when the interval has passed. Fast runs fill blocks sooner and never see it.
CLI
vtr recover in.vtr out.vtr copies every verified section and appends a Recovered ending, a directory and a trailer. It exits 3 when data was dropped, as mcap recover does.
Tests
SIGKILL at random points of a slow run loses at most the interval; recover of every cut file of stage 2 round-trips.
Measure
Suite A/B with the default interval: fast workloads unchanged; file size of a slow log-only run over ten minutes.

Limits

What the guard cannot promise.

SIGKILL runs no code. The OOM killer, kill -9 and a scheduler's final kill leave what was written, bounded by stage 8. Surviving them in full needs the trace outside the process as it is produced, which is the Perfetto and LTTng approach. VTR's in-flight state is not a stream of raw records: initial values and time tables live on the simulation thread. Its raw record stream is 16 bytes per change, about 9.5 GB for one C910 CoreMark iteration against a 248 MiB file. A shared-memory ring could bound the resident part, but every change would still pass through it. That is deferred until a real workload needs it.

Memory corruption can reach VTR itself. A private heap stops a corrupt application heap from blocking the rescue. It does not stop a wild write from landing in VTR's buffers. Section CRCs protect what is written from damage after writing, not from damage before it.

A crash on an encoder thread is a VTR bug, and its writer cannot be rescued, because the thread that finishes blocks is the one that died. The guard records it on stderr, the handler re-raises, and recovery keeps the written sections.

Linux first. The design uses sigaltstack, eventfd and tgkill. macOS needs a pipe instead of eventfd and has the same signal model. Windows would use a vectored exception handler and SetConsoleCtrlHandler, as Quill does, and is out of scope.

The numbers are from a prototype. The crash lab measured the rescue with today's close path and a synthetic workload at C910's change rate. Stages 6 and 7 re-measure with the real guard and the real C910 model.
