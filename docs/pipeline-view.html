Design proposal · volna-core · GPUI · VS Code

A Konata-style pipeline panel for Volna, minimal by design

One new panel kind that draws the transactions of any VTR generator or stream as rows of stage cells, shares the waveform panels' viewport and cursor through the existing link flags, and zooms like a map: the point under the pointer stays put in both axes. Everything else is an extension point, not a feature.

existing already in the repository, reused as is proposed the first version described here later deliberately left out, with its seam named

Companion to VDB_KONATA_PLAN.html (how Kanata logs become VTR records and a VDB profile) and workspaces.html (panels, links, persistence). This document covers only the viewer panel. Status: proposal, nothing implemented yet.

Recommendation

Five decisions, then everything follows

1 · A panel kind, not a mode

PanelKind::Pipeline(Box<PipelineModel>) sits next to Waves and Settings. It docks, tabs, splits, focuses, saves and restores through the code that already exists for panels. Any generator can be shown in it; a PIPELINE stream is only recognized, with its own icon in the scope tree, never required.

2 · Time is the document's time

The Kanata importer writes cycles as VTR time units, so the pipeline's X axis is the shared Viewport. Synchronization with the waveform panels costs nothing: the same Link { viewport, cursor } flags, the same shared cursor, the same markers, the same animation.

3 · Rows are a second, local axis

A RowView { top, row_px } owns the vertical axis: which row is at the top edge and how tall rows are. Zooming applies one factor to both axes about the pointer. The X axis may be shared with other panels; the row axis never is.

4 · Data is a loaded track, nothing more

The panel retains a stream or a single generator through Document::retain_track and reads the resident LoadedGenerator objects: transactions in begin order, their stages, status and vtr.label. No new loader, no new index, no new wire format; remote sessions work unchanged.

5 · Painting is O(visible cells)

The painter iterates the visible row range and each row's dozen stages, skips what lies outside the time window, and collapses rows below two pixels into a density step. It emits ordinary Scene quads and text, so every frontend paints it with the code it already has.

What v1 deliberately lacks

Dependency arrows, VDB stage colours, split lanes, hide-flushed, search, tooltips, statistics, A/B comparison, gem5 specifics, clock mapping. Each has a named seam in Extension points. No new user settings are introduced.

What the mock implements versus what is proposed. The mock runs the same viewport math as wave/viewport.rs (ported line by line, including edge space and clamping), the proposed RowView and Tween, the link semantics of WaveModel::toggle_link, the density rule and the stage separation rule. It draws with the HTML canvas instead of a Scene; a browser cannot tell a mouse wheel from a trackpad scroll, so here every wheel zooms and ⇧+wheel pans, whereas the GPUI element receives precise trackpad deltas and pinch gestures and can pan on scroll. Stage colours are the v1 ladder by first appearance, not a VDB profile. The mock has no load states, no unresolved tracks and no workspace file.

Why the time axis needs no mapping in v1. The importer records Kanata cycles as VTR timestamps one-to-one and writes time.unit = cycle. A trace that carries both waveforms and a pipeline stream comes from one producer with one time base, so the shared viewport is already correct for both. A cycle-to-tick mapping between two differently timed recordings is a VDB binding concern (see the RTL bridge in VDB_KONATA_PLAN.html) and is not on the v1 path.

The two axes

X · time · Viewport existing

Shared with the document while link.viewport holds, local otherwise, exactly as a wave panel. Wheel zoom calls zoom_about(x, width, factor) on the state's target and animates to it, so consecutive wheel events accumulate instead of fighting the animation. Drag calls pan_px on the target and jumps.

Width used for the math is the cells column, not the panel: the label column is excluded, like the names and values columns of the wave panel.

Y · rows · RowView proposed

top: f64 is the fractional row index at the top edge of the cells area; row_px: f32 is the row height at interface zoom 1.0. row_at(y), y_of(row), zoom_about(y, factor, height) and pan_px(dy, height) mirror the time axis. clamp allows 20 % over-scroll at both ends and keeps row_px within [0.5, 48] design pixels.

One zoom gesture applies the same factor to both axes, so cells keep their aspect while the user zooms here. If another panel changes the shared X viewport, rows keep their height; the aspect is a default, not an invariant.

Tween replaces ViewportState. ViewportState is an animation over one Viewport. The row axis needs the same eased animation with the same explicit clock, so the animation becomes Tween<T: Lerp> in nav/tween.rs and ViewportState becomes Tween<Viewport>. The wave model does not change behaviour; its tests keep passing. App::tick advances the shared tween once plus every local tween, as it does today.

From records to pixels

  1. Rows. On Delivered::Track the model resolves its track to the loaded generators (one for a generator, all of them for a stream) and treats their concatenated transactions() slices as the row list, generator by generator in catalog order. Row i is a (generator index, transaction index) pair computed from prefix sums; no copy of the records is made. A Kanata stream has one generator, so rows are fetch order.
  2. Visible range. rows.value gives first = floor(top) and last = ceil(top + height / row_px). When row_px < 2 the painter uses a row step of ceil(2 / row_px) and paints every step-th row at the step's combined height, so the number of row quads never exceeds half the panel height in pixels.
  3. Cells. For each painted row, transactions whose [begin, end] misses the viewport are skipped outright. Each remaining stage on lane "0" becomes a quad from x_of(begin) to x_of(end), inset by half a gap on both sides, at least one pixel wide; an edge stroke in a darker shade separates consecutive stages when rows are six pixels or taller. A stage whose end is None extends to the transaction's end. Stages on any other lane are painted as a translucent grey band over the lower part of the row, on top of lane 0: the overlay reading of Konata, which needs no lane layout.
  4. Text. Stage names are centred in cells that are at least ten pixels tall and wider than the shaped name plus padding, measured through TextMeasure and cached per string. Label column rows show the index right-aligned and the vtr.label text (the record-phase attribute, joined), or the row index alone when the label is absent; below seven pixels the column shows only a flush tick.
  5. State colours. TxStatus::Aborted rows get a translucent error tint over the cells area and muted label text; Open rows draw their last stage with a dashed right edge. Hover adds the theme hover surface. Focus, cursor and markers use the wave tokens.
  6. Overlay. Header ticks come from wave::timeline::ticks; the cursor line, cursor chip and marker chips move from wave/paint.rs into a shared wave::overlay helper both painters call with a rectangle, a viewport, a cursor and the markers.

Cost per frame: O(painted rows × stages per row), with painted rows bounded by pixels. The LoadedGenerator interval tree is not consulted in v1 because rows index the records directly; it becomes useful when a feature needs time-to-rows queries (hide flushed, search, cursor follow).

Stage palette

v1 assigns each lane-0 stage name a hue from a ladder in order of first appearance across the loaded generators, the same idea as Konata's Unique scheme, with a fixed lightness so text stays readable in both appearances; the edge stroke is the same hue darkened. The mapping lives in StagePalette { by_name: HashMap<String, StageStyle> }, built once on delivery and consulted by the painter only through style(name). A VDB stage table later fills the same struct with authored colours and roles; nothing in the painter changes.

Routing

  • Pointer. Command::Pointer(id, ev) already names a panel; App::handle_at dispatches through Panel::pointer instead of panels.waves_mut(id), one match on the kind in one place.
  • Actions. Zoom, pan, go-to, marker and link actions resolve the focused panel's NavState and are implemented once against it; ZoomIn on a pipeline panel also scales rows, MoveSelectionUp/Down scroll rows. Row-selection, format and edge actions are no-ops for the kind. No new Action variants.
  • Open. OpenPipeline validates capabilities().transactions and that the track exists in the catalog, focuses an existing panel for that track, or creates one with Panels::create(focused, Some(Axis::Vertical)), link from panels.linkByDefault, and calls PipelineModel::open. Failures become Event::Notice.
  • Delivery. App::deliver already routes LoadResult::Track into the document; afterwards every pipeline panel refreshes its palette from doc.track(track). Close calls PipelineModel::close, which releases the consumer; the document drops the load and any queued request when the count reaches zero.
  • Sidebar. Command::ActivateMembers from hierarchy.html routes Member::Generator and Member::Stream to OpenPipeline { track }. The kind string is used for the icon and for the View ▸ Pipeline shortcut list, nowhere else.
  • Persistence. The codec gains a "pipeline" variant; restore resolves the saved path against session.tracks() and keeps Unresolved panels visible with an explanatory empty state, mirroring unresolved wave rows.

Synchronization rules

  • With link.viewport on, the pipeline reads and writes doc.shared.viewport: zooming in the pipeline zooms the linked wave panels and vice versa. Row height is untouched by other panels.
  • With link.cursor on, a click in either panel moves the one cursor; the wave panel's value column and the pipeline's cursor chip update in the same frame.
  • Unlinking snapshots the shared value into the panel; relinking adopts the shared value, discarding the local one, as WaveModel::toggle_link does today.
  • Markers belong to the document and are drawn by every panel at the marker's time.
  • The inactive-cursor colour marks a cursor drawn in an unfocused panel, so the focused panel is always evident.
Frontends

GPUI hosts it; egui keeps building

GPUI (native, web, VS Code)

  • PipelineCanvas is WaveTable with the wave-specific hitboxes swapped for the label divider and marker chips. The shared parts, the measurer, paint_prims, pointer forwarding and clip nesting, move to wave/canvas.rs so the two elements are thin.
  • dock.rs maps PanelKind::Pipeline to PanelView::Pipeline; the panel's header renders the title, the link buttons and, for an unresolved or failed stream, the notice.
  • The sidebar rows come from hierarchy.html (stream rows with the pipeline icon, generator rows in the member pane). The View menu gets a Pipeline submenu listing the recognized PIPELINE streams; the palette lists the same. All of them dispatch Command::OpenPipeline.
  • Trackpad handling: GPUI reports precise scroll deltas and pinch; the element maps them to Wheel with precise flag and to Pinch, exactly as the wave element does today.
  • Interface zoom flows through the theme metrics and LayoutInput::zoom; row_px and label_width are stored unzoomed and multiplied at layout.

volna-egui, remote, tests

  • The egui frontend must compile against the new kind and continue to show its single wave panel. It paints nothing for pipeline panels and never creates one; AGENTS.md forbids feature growth there.
  • Remote sessions need no protocol change: LoadRequest::Track already transfers a complete generator with its records, stages and relations under the client memory budget; oversized streams fail explicitly and the panel shows the failure with a retry.
  • Headless tests drive the panel with commands and assert on the Scene: see the plan below. The GPUI viewer harness adds one screenshot with a wave and a pipeline panel side by side.

Alternatives considered

What was rejected, and why

Embed Konata's renderer

The pinned Konata is a browser application; hosting it in a web view or wasm would put viewer logic outside the toolkit-free core, duplicate the time axis, and make the shared cursor a bridge protocol. It would also not run in the native GPUI window without a browser engine.

A separate time axis with cycle mapping in v1

The importer already writes cycles as time units; a mixed trace has one time base. A mapping would add a setting, a dialog and a second viewport to keep consistent, for no case the first version can exercise.

Lock both axes to square cells

Konata keeps cells square because it owns both axes. Here the X axis is shared with panels that have no rows, so a square-cell invariant would either break the link or resize rows behind the user's back. One factor per gesture, otherwise independent axes.

Wheel scrolls rows, Ctrl+wheel zooms

Konata's default. It conflicts with the wave panel, where wheel already zooms time, and with the map model the user asked for. Drag and ↑ ↓ cover vertical movement; trackpad scroll pans.

Require the PIPELINE stream kind

The panel needs stages and lifetimes, which every generator has. Gating on a kind string would refuse gem5 or SystemC generators that render perfectly well and would push a presentation decision into the loader. The kind stays a recognition hint: an icon in the tree and a shortcut list in the menu.

Rows as a second shared axis

No other panel has instruction rows, and two pipeline panels over the same stream are a legitimate way to look at two places at once. Rows stay local.

A generic "transaction panel" that also covers Gantt views

Tempting, but a Gantt view groups by generator and stacks overlapping transactions; a pipeline view is one row per transaction with stage cells. They share the loader and the overlay, which this design already factors out, and nothing else worth abstracting yet.

Plan and verification

Headless checks that define done

  • The scope tree of a Kanata trace lists cpu › thread0 with the pipeline icon and its member pane lists instruction; a non-PIPELINE stream gets the generic icon and still opens.
  • Opening a stream or a generator queues exactly one LoadRequest::Track; delivery paints one quad per visible lane-0 stage and one band per overlay stage; a second panel on the same stream queues nothing.
  • Zoom about a pointer position keeps the same (time, row) under it in both axes, at interface zoom 1.0 and 2.0.
  • With the viewport linked, a wheel event in the pipeline changes the wave panel's viewport to the same value; unlinked, the shared value is unchanged and the local one moves.
  • A click sets the shared cursor to the integer cycle under the pointer; the wave panel's value column shows the value at that cycle in the same frame.
  • At row_px = 0.5 over ten thousand rows, the scene holds at most height / 2 + 1 row quads and painting stays under the wave panel's frame budget in the ignored benchmark harness.
  • Workspace save and restore reproduce stream, links, viewport, cursor, rows and label width; an unknown track path restores as Unresolved and is written back unchanged.
  • Closing the last panel on a stream releases the track: doc.track(stream) is None and a late delivery is a no-op.
  • Flushed and open transactions are distinguishable in the scene by colour token, not by text.
