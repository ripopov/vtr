Clocks as time bases in VTR and Volna

Engineers count in cycles, but traces store time. This proposal adds one small record to VTR. For each clock that the design owner names, the file stores the stretches where the clock ran at a steady period: first edge, last edge and period, nothing more. A reader can then convert any time to a cycle number and back, across frequency changes and gated intervals, without loading the clock waveform. Volna uses this for cycle rulers, cycle readouts, snapping to clock edges and pipelines counted in cycles.

Proposal, revised 26 September 2026. Nothing here is implemented. It builds only on what exists today: VTR transactions (SPEC §7), the Verilator fork's --trace-vtr backend and Volna. It is the prerequisite of c910-verilator-tx-stream.html: it starts the vtr_trace SystemVerilog package and its sink in the fork, which pipeline tracing then extends, and it gives Volna the cycle counting that pipelines are shown in. Related: pipeline-view.html, VDB_RTL.md.

The problem

A VTR file has one time unit, and every timestamp uses it. Engineers ask questions in cycles: how many cycles a load took, what happened in cycle 150,231, how many bus cycles lie between a request and its response. Today a viewer can answer them in three ways, and each one fails somewhere:

  • Assume one time unit per cycle. Volna's Pipeline panel does this. It works for Kanata imports and fails for simulator traces: in the C910 harness one cycle is two time units.
  • Ask the user for a period. Questa and SimVision grids work this way. They are exact for one fixed clock, wrong after a frequency change, and unaware of a second clock.
  • Count the edges of a clock signal. Verdi's grid and Surfer's clock highlighting work this way. They are exact, but the whole clock history must be loaded first: 1.36 s and about 800 MB for 100 million changes in Volna. A pipeline-only run would also have to dump its clock just so it can be counted.

Performance tracing solved this long ago. Intel Processor Trace sends a frequency packet only when the frequency changes and counts cycles in between. gem5 keeps an (anchor tick, anchor cycle, period) triple per clock domain and starts a new one at each frequency change. The information that matters is small: where a clock runs steadily, and at what period.

The design in six rules

  1. The design owner names the clocks. Clocks are declared in the testbench, a few lines per clock, through the vtr_trace SystemVerilog package. Nothing is guessed from the netlist.
  2. The producer states the period. It says when a clock starts running at a period, in whole units, and when it stops or leaves that speed. That is one call per change and nothing per edge.
  3. A clock is a list of steady stretches. Each stretch stores its first edge, its last edge and its period. A fixed clock is one stretch for the whole run. Each frequency change or gated interval adds one more.
  4. Periods are whole time units. Simulators round every delay to the time precision, so recorded edges are always a whole number of units apart. The format needs no fractions and no rounding rule.
  5. Everything else is computed by the reader. Edge counts, cycle numbers, frequencies and "stopped" follow from the stretches. The first recorded edge is cycle 0, and numbering continues across stretches.
  6. VTR stores when a clock ticked; VDB and Volna store what it means. Which clock is "the core clock", how clocks relate, colours and a custom cycle origin are VDB or viewer data.

What the file stores

A clock follows the pattern that logs already use: a stream of a reserved kind whose records are transactions. It needs no new section, value tag or node kind. The SPEC additions are the stream kind CLOCK and two attribute keys under the existing reserved vtr. prefix.

ItemContent
clockA stream of kind CLOCK with one generator, edges. It is named after the clock net and placed in the net's scope, so a viewer pairs it with the net's waveform by path whenever that waveform was dumped.
stretchOne transaction of edges. begin is the first edge, end is the last edge, and vtr.period (time) is the spacing between them. A stretch of a single edge has no period.
linkvtr.clock (str) on a pipeline or protocol stream holds the path of the clock its stages are counted in.

Everything a reader needs follows from these three numbers per stretch:

edges in stretch s     n(s)     = (s.end − s.begin) / s.period + 1
first cycle of s       cycle(s) = sum of n over all earlier stretches
time of edge c         s.begin + (c − cycle(s)) · s.period      for the s that holds c
cycle at time t        the number of the last edge at or before t

Stretches never share an edge. The interval from the last edge of one stretch to the first edge of the next is one cycle, however long it is. After a frequency change it is an ordinary cycle. When a gated clock stops, it is one very long cycle. A reader shows it as stopped when it is longer than twice the periods on both sides; that is a display rule, not stored data.

In the demo, core_clk is three stretches: (400, 19772, 334), (20272, 49772, 500) and (50772, 99772, 1000). Together they describe 169 edges. On the C910 CoreMark harness, where the clock toggles every time unit, the whole run is one stretch with period 2.

The writer keeps stretches out of the large transaction blocks. It writes them into a small dedicated TX_BLOCK at each explicit flush and at close, so a reader loads a clock without decoding pipeline data, and a recovered file keeps every stretch up to its last flush. The stretch still running at close is written with status open.

Where clocks come from

Why the simulator cannot pick the clocks

The first draft of this proposal let the Verilator fork find "primary clocks" in the sensitivity lists by itself and derive stretches from the dumped values. Checked against the C910 RTL, that does not hold up:

  • Sensitivity does not separate clocks from resets. The C910 has 1,784 processes sensitive to negedge cpurst_b. That reset is a top-level input driven by the harness, which is exactly what a primary clock looks like.
  • There are too many candidates. The C910 RTL has 602 distinct nets in posedge sensitivity lists and 748 clock-gating cell instances. Which of them matter to the person reading the trace is a design decision.
  • Verilator itself dropped clock guessing. Since version 5 the /*verilator clocker*/ attribute and the --clk option are ignored.
  • Dumped values can miss edges. A harness that dumps once per cycle sees the clock at the same level every time. A run that records only transactions dumps no signals at all.
  • Frequency is not a simulator concept. In RTL, a frequency change is a testbench or PLL model changing a delay. The only observable fact is the spacing of edges.

So clocks are declared by the design owner, the same way pipeline tracing will later ask owners to report stages. The owner knows which clock matters and what to call it.

Declaring a clock

A clock is recorded from two calls, which fit testbench clock generators, gem5 clock domains and SystemC clocks, since all of them know their period:

  • Run at a rising edge: this edge begins a stretch, and edges follow every period.
  • Stop at any time: the clock has no more edges at its current speed after now. The stretch ends at its last edge at or before that time.

A gated clock is a stop when the gate closes and a run at the first edge after it opens. A change of speed is the same pair. The producer calls stop when it changes the generator's delay, and run at the next rising edge. From that edge on, the generator toggles at the new delay. The cycle between the two stretches may be irregular, because a delay already scheduled at the old value still completes. The file records it exactly as the one cycle between stretches, whatever its length. A run on a clock that is still running is misuse, because the writer cannot know where the old speed ended.

Clocks whose period nobody states are postponed: a gated clock after its gating cell, a divider inside the design, a PLL model or a clock multiplexer. They need an observed mode, in which the producer reports every rising edge; What was removed lists it.

The SystemVerilog API

This proposal starts vtr_trace, the one SystemVerilog package through which VTR is reached from a testbench or a design. It holds a common part and the clock functions. Pipeline tracing adds its trackers to the same package, and later parts are added the same way, for example scopes for UVM component trees or structured log sites. So that each addition fits without changing what came before, every part of the package follows these rules:

  • One package, one runtime. The declarations live in vtr_trace.sv, and every DPI function body lives in vtr_trace_dpi.hpp, written against a small sink interface. A new function changes those two files and nothing in any sink.
  • Names. Every exported name starts with vtr_ or VTR_, so import vtr_trace::* is safe in any testbench and the DPI-C symbols stay unique among C symbols. A handle type is vtr_kind_t, its constructor is vtr_kind(…), and an operation on it is vtr_kind_verb(handle, …).
  • Handles, not ids. SystemVerilog holds opaque int unsigned handles, 0 meaning none, and never sees a VTR node, stream or transaction id. The library tags each handle with its kind. Names are passed once, at construction.
  • Constructors set up; everything else is a direct call. A constructor is a context import, called once from an initial block. Every other function is a plain import with integer and string arguments, which Verilator compiles into a direct C call.
  • Time is the sink's. A call takes effect at the current simulation time in the file's unit, the time the waveform uses. Only _at forms take a time, which the caller saved earlier with vtr_now(). A duration, like a clock period, carries an explicit unit.
  • One scope rule. A constructor places what it creates by a scope path. "" is the calling instance. "^" is its parent, the instance that instantiates or binds it, and each further ^. goes one more level up. "a.b" is below the calling instance. "$root.top.a" is absolute, as in SystemVerilog. A path that names another object, such as a tracker's clock, is resolved the same way from the scope of the object being created.
  • The sink owns the file. No function opens, flushes or closes a file, sets the time scale or the time, or reads anything back. Those belong to the harness and the sink; that is what lets waveforms, the simulation log and package calls share one file safely.
  • Safe without a recording. Constructors always return a handle. The sink keeps what they declare before a file is open, together with each clock's latest run, and replays it at open, as dyn_hierarchy.html requires. Other calls return at once while no file is open, so no producer needs an enable flag.
  • Misuse is counted, not fatal. A handle of the wrong kind, a period that is not a whole number of file units, or a run on a clock that is still running skip the call and are counted per object and kind of misuse (a plain import has no call site to name). At close the counts go into the file's simulation log as warnings, where vtr log and Volna show them.

The package as this proposal creates it:

package vtr_trace;
  // ---- Common to every part of the package ---------------------------------------------------

  // Time units as powers of ten, the same values $timeunit returns.
  localparam int VTR_S = 0, VTR_MS = -3, VTR_US = -6, VTR_NS = -9, VTR_PS = -12, VTR_FS = -15;

  // The current simulation time in the file's unit; keep it to pass to an _at call later.
  import "DPI-C" function longint unsigned vtr_now();

  // ---- Clocks --------------------------------------------------------------------------------

  typedef int unsigned vtr_clock_t;   // a clock; 0 = none

  // Declare a clock: a CLOCK stream `name` in `scope`. Call once, from an initial block.
  import "DPI-C" context function vtr_clock_t vtr_clock(string scope, string name);

  // Now, which must be a rising edge, begins a stretch: one edge every `period` units of
  // 10^unit s, until vtr_clock_stop. The clock must not be running. Example: vtr_clock_run(c, 334, VTR_PS).
  import "DPI-C" function void vtr_clock_run(vtr_clock_t c, longint unsigned period, int unit);

  // No more edges at the current speed after now: call it when the clock is gated or when
  // its generator's delay changes. The stretch ends at its last edge at or before now.
  import "DPI-C" function void vtr_clock_stop(vtr_clock_t c);
endpackage

The period is an integer with an explicit unit, so the owner writes it in the units of their own testbench. The library converts it to the file's time unit with integer arithmetic only. A coarser unit is multiplied: 2 ns in a picosecond file is 2000. A finer unit is divided only when the result is whole: 334 ps in a nanosecond file is reported in the simulation log instead of being rounded.

A testbench generator whose half period can change stops the clock where it changes the delay, and runs it again at the next rising edge:

vtr_clock_t c;
bit         restart = 1;
initial c = vtr_clock("", "core_clk");
always #(half) core_clk = ~core_clk;

task automatic set_half(int unsigned h);   // called by the test to change speed
  vtr_clock_stop(c);                       // no more edges at the old speed after now
  half = h; restart = 1;
endtask

always @(posedge core_clk) if (restart) begin   // from this edge on, the new delay applies
  vtr_clock_run(c, 2 * half, VTR_PS);
  restart = 0;
end

In the C910 testbench, the core clock is toggled by the C++ harness every 100 ps time unit, so its period of 200 ps is known and declared once. The divided JTAG clock is unused by the benchmarks and is not recorded. The declaration sits under an `ifdef that only the VTR build of the model defines, so the FST build is unchanged:

`ifdef VTR_CLOCKS
import vtr_trace::*;
vtr_clock_t vtr_clk;
bit         vtr_clk_on;
initial vtr_clk = vtr_clock("", "clk");
always @(posedge clk) if (!vtr_clk_on) begin vtr_clock_run(vtr_clk, 200, VTR_PS); vtr_clk_on = 1; end
`endif

How the fork carries the package

A Verilator user should need nothing beyond --trace-vtr. The pieces below make that true, and pipeline tracing reuses every one of them:

  • Source. vtr_trace.sv and its DPI implementation vtr_trace_dpi.hpp are written once, in core/vtr-capi/include/. The implementation calls the C API through a small interface in two parts. A host, one per simulation context, gives the current time and what $root names. A sink, one per open file, gives the writer, the file's time unit, a map from instance path to hierarchy node that creates missing scopes, and a warning log. The runtime in the header keeps the handles, the declarations it replays at open and the misuse counts; the integration calls it when a file opens and just before it closes. An integration implements that interface and nothing else.
  • Install. integrations/verilator/build.sh copies both files into the installed include/vtr/, so every fork install carries the package of the VTR revision it was built from.
  • Parse. With --trace-vtr, Verilator parses include/vtr/vtr_trace.sv the way it parses verilated_std.sv for std::, and removes the package again when no module uses it. A design that uses nothing from the package generates the same model as before.
  • Sink. VerilatedVtr::open registers its writer, time source and scope map for the calling context, as it registers the simulation log sink today. Every --trace-vtr model compiles include/verilated_vtr_dpi.cpp, listed with the runtime sources for both Make and CMake; it includes vtr/vtr_trace_dpi.hpp, keeps one runtime per VerilatedContext and implements the sink over VerilatedVtr, whose trace prefixes give the scope map. $root is the model's name, which starts both DPI scope names and the trace hierarchy.
  • Signal-free runs. The harness can open the file without registering the model's signals. The file then holds clocks, the simulation log and, once pipeline tracing exists, transactions. This is the mode for long runs.
  • Harness time. A DPI call sees the context time at eval(). The C910 harness evaluates before it advances time, so its DPI calls would be dated one unit before the dump that shows the same edge. The harness is changed to advance time first. Its dumps stay byte-identical, and DPI times then equal waveform times.

Other simulators need a standalone sink that opens its own file and reads time through VPI. That sink belongs to the pipeline tracing proposal. It implements the same sink interface, so the package is plain DPI-C and needs no change for it.

The writer

The Rust writer gains three calls, projected one to one into the C API. All times and periods are u64 in the file's time unit, which the producer chose when it opened the writer, so no unit argument is needed here.

pub fn add_clock(&mut self, scope: Option<NodeId>, name: &str) -> Result<ClockId>;
/// From edge `first`, one edge every `period`, until clock_stop. The clock must not be running.
pub fn clock_run(&mut self, clock: ClockId, first: u64, period: u64) -> Result<()>;
/// No more edges at the current speed after `t`.
pub fn clock_stop(&mut self, clock: ClockId, t: u64) -> Result<()>;

The writer keeps the running stretch as (first, period). clock_stop ends it at its last edge at or before the stop time; stopping a clock that is not running does nothing. The file close ends a running stretch at its last edge at or before the writer's current time. A run on a running clock is an error, and so is a run whose first edge is not after the previous stretch's last edge. The C API adds the matching reader calls for clock timelines, and SPEC.md §7.4 holds the format rules.

Other producers

  • gem5. A clock domain's period is a whole number of ticks. It calls clock_run when the domain starts and at each change of performance level.
  • SystemC. An sc_clock is one clock_run from its start time; its period is a whole multiple of the time resolution.
  • Kanata import. The converter declares a clock named cycle with period 1 and sets vtr.clock on its pipeline streams. It is the first producer of vtr.clock; pipeline tracing adds the second.

Using clocks

The reader exposes clocks as a small query, so viewers and tools never scan stretches themselves. A timeline is immutable and shared, and loading it decodes only the clock's own block.

reader.clocks() -> &[ClockInfo]                   // name and path of each clock
reader.clock(id) -> Arc<ClockTimeline>           // its stretches, loaded once
timeline.cycle_at(t) -> Option<CycleAt>          // cycle, its edge, next edge, fraction, stopped
timeline.edge(cycle) -> Option<u64>
timeline.next_edge(t), timeline.prev_edge(t)

Every query is a binary search over the stretches and one multiplication. The CLI gains vtr clocks file.vtr, which lists each clock with its stretches, periods and stopped time.

Volna loads all clock timelines when a file opens, next to the hierarchy. It then offers:

  • Clock rulers. Under the time ruler, one row per chosen clock, with ticks at rising edges labelled by cycle number. Each stretch picks its own label spacing, a frequency change gets a small flag such as "→ 2.00 GHz", and a stopped interval is hatched. By default Volna shows the clocks that visible pipelines refer to.
  • A cycle axis. Any panel can count its main ruler in cycles of one clock. The cursor chip then reads 150231 + 0.42, and the status bar keeps the time.
  • Readouts and measurements. The status bar shows the cursor's cycle in each ruler clock, and the new cursor-to-marker delta reads, for example, "Δ 20.0 ns · 40 core · 10 bus".
  • Snapping and stepping. Clicks snap to the nearest edge of the selected clock, [ and ] step one cycle, and the palette gains "Go to cycle…".
  • Clock rows without waveforms. A clock can be shown as a wave row even when its net was never dumped, drawn from its stretches.
  • Pipelines in cycles. The Pipeline panel counts stages in its stream's vtr.clock instead of assuming one unit per cycle. A stream without vtr.clock keeps today's behaviour, one time unit per cycle.

Each piece has a natural home in volna-core: Document holds the timelines, loaded through a new LoadRequest::Clocks that local and remote sessions both serve; wave/timeline.rs gains clock ticks beside time ticks; NavState gains the axis choice; snapped_time gains a clock edge source; and cycle_at in the pipeline model asks the stream's clock. Which clocks a panel shows, its axis and any custom cycle origin are saved in the workspace, never in the VTR file.

VDB and VTR meet by path. A VDB profile can say that a clock stream is "the core clock" or that one clock is derived from another, without the trace saying so.

Cost and tests

A clock costs one call per change of speed and nothing per edge. It still goes through the benchmark gate like any writer change: a C910 capture with its clocks recorded must stay within measurement noise of today's write time and size. A stretch is one transaction with one attribute, a few dozen bytes; the file grows with frequency changes, not run length.

Tests, all headless:

  • Writer. Unit tests in core/vtr cover fixed, changing, gated and single-edge clocks and the misuse errors. For random run and stop sequences, the stretches must reproduce exactly the edges of a brute-force generator driven by the same sequence.
  • Round trip. A core/vtr/tests/ test writes clocks through every writer call and checks cycle_at, edge and stepping against brute-force edge counting, also on a crash-recovered file.
  • Fork. integrations/verilator/clocks/run.py, beside the log and VDB suites (the fork's own test_regress has no VTR library to run a model against), checks that the package resolves with --trace-vtr alone. It drives one testbench clock, which changes speed in both directions and is gated, through vtr_clock_run and vtr_clock_stop. It requires stretches whose edges equal the rising edges of the dumped clock waveform, in one and two thread modes. It also checks that a run on a running clock is reported. It also checks the unit conversion, including a period that is not a whole number of file units and its simulation log warning, the scope paths "", "^" and $root, a clock declared before the file opens, that a signal-free open still records the clock, and that a design that uses nothing from the package gets no package code, dependency or VDB source entry.
  • C910. With the clocks declared in the testbench, the capture holds one clk stretch of period 2 starting on the first rising edge of the recorded clk, with an edge count equal to the rising edges of that waveform.
  • Volna. Headless tests cover clock ruler ticks, the cycle axis, snapping, stepping, the delta readout, the Pipeline panel in cycles on a Kanata import, and the workspace round trip.
  • This page. node --test docs/tests/vtr_clocks.test.mjs drives the demo in headless Chrome, and a workflow runs it when the page changes.

What was removed, and what was rejected

The first draft carried more machinery. Each piece was dropped for a concrete reason:

  • Automatic clock detection in the Verilator fork, with --trace-vtr-clocks=primary|all|none. It mistakes resets for clocks, drowns in gated clocks, misses edges the harness does not dump, and cannot work in a run that dumps no signals. Explicit declaration replaces it.
  • Fractional periods with a rounding rule. They covered edges 333 and 334 ps apart. Simulators do not produce such clocks: SystemVerilog rounds each delay to the time precision, SystemC times are whole multiples of the resolution, gem5 periods are whole ticks, and a Verilator harness advances time in whole units.
  • Stored edge counts and cycle numbers. Both follow from begin, end and period, and a reader always loads all of a clock's stretches, so storing them only adds a way to be inconsistent.
  • Five further attributes. Duty cycle is visible in the waveform when it matters. Falling-edge or both-edge counting, if a design ever needs it, is a parameter of the producer's call; the file does not change. A "derived or declared" source flag changes nothing a reader does. A separate signal path is replaced by the naming convention. An "irregular" marker is not needed, because a clock is steady between its calls.
  • Only observed clocks. Reporting every edge of a clock whose period the producer already knows is wasted work, and gem5 has no edges to report. Declared clocks replace them.
  • A run that implicitly ends a running clock. The writer would have to guess where the old speed ended. After a slowdown from 334 to 500 ps it would place an edge at the old spacing that the simulator never produced. Stop, then run, is exact for any generator.
  • Finding stretches in SystemVerilog. $time and $realtime report in the module's time unit, rounded to it, so SystemVerilog cannot see edge times at the file's precision without calling out anyway. It would also duplicate the edge detection that observed clocks will add to the writer.
  • A realtime period in the caller's time unit. It hides a floating-point conversion and needs the library to look up the caller's time unit. An integer with an explicit unit is exact and visible at the call site.
  • Observed clocks, postponed. Some clocks have no owner who knows their period: a gated clock after its gating cell, a divider inside the design, a PLL model or a clock multiplexer. Recording them needs a writer call clock_edge(t) that finds stretches in reported edges; a vtr_clock_edge package function and a bindable observer module over it; and vtr convert trace.fst out.vtr --clock TOP.clk, which gives FST and VCD imports a clock from a dumped signal. None of it changes the file format or the reader, so it can be added when a user needs it. Until then, such a clock is not recorded, or its owner declares it.
  • Deferred to later work: a frequency plot row, a clk:N time syntax in the CLI, and deriving a clock from a loaded FST signal inside Volna.

Approaches rejected outright: a single period attribute, which is wrong after the first frequency change; counting clock edges at read time, whose cost grows with run length; Perfetto-style (time, cycle) snapshots, which do not say where a clock stopped; a floating-point frequency, which drifts over long runs; a new section or node kind, which adds format surface that the transaction encoding already covers; and inferring the period from transaction times, as Konata does, which cannot see frequency changes or tell two clocks apart. A pipeline stream without a clock is shown in time units, as today.

Plan

  1. Format and core. SPEC additions (CLOCK, vtr.period, vtr.clock), the three writer calls, the dedicated clock block, ClockTimeline, the C API, vtr clocks and the Kanata clock, with the writer, round-trip and recovery tests and a RATIONALE entry. Exit: the core tests pass.
  2. Package and fork. vtr_trace.sv with the common part and the clock functions; vtr_trace_dpi.hpp with the sink interface, scope paths, replay at open, misuse counts and the unit conversion; installation by build.sh, automatic parsing and pruning under --trace-vtr, the context sink in VerilatedVtr, verilated.mk plumbing and the signal-free open, with the integration test and a SPEC producer example next to the Verilator log example. Exit: the integration test passes in both thread modes.
  3. C910. The harness time order, the declared clk in the testbench, and the A/B benchmark. Exit: the C910 checks pass and write time and size stay within noise.
  4. Volna. Timelines in Document, clock rulers, the cycle axis, readouts, snapping and stepping, clock rows, pipelines in cycles and workspace support. Exit: the headless tests pass.
  5. Models. Clock stretches from the planned gem5 and SystemC integrations. Not needed by pipeline tracing.

Postponed, with no step yet: observed clocks, that is clock_edge, vtr_clock_edge, an observer module and vtr convert --clock. They are added to the writer and the package when a design needs a clock whose period nobody declares.

Steps 1 to 4 are the prerequisite of pipeline tracing. After them, that proposal adds only its tracker part to the package, following the package rules above, and its tracer to the C910 testbench.
