How busy is the C910, cycle by cycle

The pipeline trace shows what each instruction did. This proposal adds what the machine did around them: how full its queues were, which execution pipes were busy, how often caches and branch predictors missed, how much bus bandwidth was in use, and where every rename slot went. The values are integer and real signals under TX.core0.perf, in the same VTR file and on the same clock as the pipeline stream. Volna draws them as analog rows.

Proposal, 26 September 2026. It builds on c910-verilator-tx-stream.html, which added the tracer bound into openC910, the vtr_trace package and the TX.core0 root scope, and on analog-waves.html, which draws vectors and reals as plots. Nothing here changes the design. The demo data is not a mock. bench/workloads/c910/perf_metrics.py computed it from the signals in the full-design CoreMark recording, and that script is the reference model for the proposed monitor. Related: vtr_clocks.html, SPEC.md (real signals, code 3).

What to look for. list chases pointers through a linked list. It keeps the most in flight (17 ROB entries, the load/store queue at 7 of 12) and makes 58% of the run's bus reads, cold misses and the prefetches they trigger. matrix retires about two instructions a cycle, and its empty slots come from a full back end, not a starved front end. state is a switch statement driven by input data. The front end and mispredict recovery account for about three quarters of its slots, while the ROB holds only about six entries. crc is a serial dependency chain. The two ALU queues stay three-quarters full while their instructions wait on each other. The same row set shows each of these, which is the case for recording them all the time.

What the counters add to the pipeline trace

The pipeline stream answers questions about one instruction: when it was fetched, why it waited, what flushed it. It does not answer questions about time. Were loads missing everywhere or just here? Did the ROB ever fill? Was this phase starved by fetch or blocked in the back end? The answers are aggregates over thousands of instructions, and the Pipeline panel shows about a hundred at a time. A counter row answers them at a glance over the whole run. Where it spikes, the pipeline stream on the same timeline shows the instructions that caused it.

Three properties make this worth doing in the simulator rather than in a viewer script over a full dump.

  1. They are cheap to record and cheap to keep. A full-design dump of this run is 280 MB and slows the simulation about fourfold. The whole proposed set is a few dozen small integers per cycle, most of which change rarely. The pipeline-only build does not dump the design, so without in-simulator counters a nightly regression would have no utilization data at all.
  2. The RTL already computes most of them. The C910's PMU wires 42 event sources to ct_hpcp_top and evaluates them every cycle, whether or not software programs a counter. The issue queues and the ROB keep their own entry counts. A monitor mostly reads what exists.
  3. Exact beats sampled. Software reading mhpmcounter CSRs gets 16 counters, perturbs the program and sees only coarse intervals. A bound monitor sees all events at once, every cycle, and does not change the program.

Measuring techniques

Every metric in the catalogue is described along three independent axes: where its data comes from, how the value is encoded over time in the VTR file, and where it is computed. A fourth label says how far its meaning can be trusted. The axes are orthogonal. For example, D-cache read misses come from a PMU event wire (source), are stored as a per-cycle count plus a running total (encoding), are computed in the SV monitor (place), and are exact but one cycle late (reliability).

Source: where the value comes from

  1. PMU event wires. The 42 eventNN_adder inputs of ct_hpcp_top, each 0 to 4 per cycle. T-Head defines their meaning. Most are registered one cycle inside the unit.
  2. Structural state. Valid vectors (popcount), existing entry counters (aiq0_entry_cnt, rob_entry_num), free-register vectors and FSM states (refill_cur_state, div_cur_state).
  3. Handshakes. Valid and ready pairs on AXI and on internal request and grant ports. They give beats, bytes, requests in flight and latency.
  4. Slot accounting. Every cycle, each of the four rename slots is classified by rules over several signals (Yasin's top-down method). The result is a model, not a wire.
  5. Transaction attributes. Per-item quantities (bus read latency, load-to-use) belong on the existing TX.core0 streams and are aggregated from there, not re-derived.

Place: where it is computed

  1. SV monitor. A bound module samples each rising edge. It is exact and complete, and its cost is paid in simulation time. This is the default for anything a later step needs.
  2. DPI sink. C++ in vtr_trace_dpi.hpp owns windows, EMAs and running totals, fed by per-cycle values. This keeps SystemVerilog simple.
  3. Viewer. A ratio of two stored signals, derived at display time. Storage is cheapest this way, but Volna has no derived signals today, so this is a later step (plan).

Reliability

  1. exact Counts exactly what the RTL signal means, cross-checked where possible (retired instructions equal the tracer's count).
  2. exact, 1 cycle late A registered PMU source, shifted back by the monitor.
  3. proxy An exact count of a signal whose name promises more than it delivers (for example "back-end stall" also counts an empty decode stage).
  4. model A classification rule, such as top-down slots. It is consistent and useful, but it is an attribution, not a measurement.
  5. idle here or absent. The structure exists but CoreMark never uses it (TLBs with the MMU off), or this SoC does not have it (L2).

Encoding: what is stored in the file

The encoding decides what a plot can show and what can be computed from it later. Try the retire row's four encodings in the demo.

levelInstantaneous value
The occupancy of a structure after the edge: ROB entries, issue queue fill, reads in flight. It is written only when it changes, so a quiet queue costs nothing. Averaging a level over time gives mean occupancy, and Little's law turns mean occupancy into latency (see CoreMark).
countPer-cycle event count
How many events happened at this edge, 0 to N: instructions retired (0 to 9), issues (0 to 8), cache misses (0 or 1). This is the raw material. It is dense for busy events, since retire changes on 63% of cycles, and sparse for rare ones.
totalRunning total
A 64-bit accumulator, the way minstret works. The slope is the rate, and any window's count is the difference of two samples, so a viewer can derive every other encoding from it exactly. It changes as often as the count it sums. Plotted directly it is a ramp, which is readable only through its slope.
rateWindowed rate or ratio
A real updated once every W cycles: IPC, misses per kilo-instruction, bytes per cycle, top-down fractions. It is sparse (995 samples at W = 256 over this run) and plots directly, but it lags by up to W, and everything shorter than W is averaged away. gem5's periodic stat dumps, perf stat -I and XiangShan's --stat-cycles work this way. A window counted in instructions rather than cycles (ChampSim's heartbeat) aligns with program progress instead.
maxWindow extreme
The maximum (or minimum) of a level within each window, stored beside its mean. A mean of 0.3 reads in flight hides a burst of 9; the max keeps it. This is the lighter band in the demo, and the same argument that makes Volna's analog painter draw min and max per pixel column.
EMAExponential moving average
A real updated every cycle, with v ← v + α(x − v). It is smooth with no window edges, but it is biased toward the recent past, and it changes almost every cycle, so it costs as much as a count. None of the surveyed simulators store it. It belongs in the viewer.
histDistribution
How often each occupancy or latency value occurred over a phase or the whole run, as in XiangShan's XSPerfHistogram. It is not a waveform. It belongs in end-of-run attributes or in the viewer's summary of a selected range, as in the side panel of the demo.
attrPer-transaction sample
A quantity attached to the item it describes, such as a bus read's latency or a load's miss status. The TX.core0.lsu_bus stream already carries bus reads with their start and end times, so their latency is not re-recorded as a signal.

The recommendation that follows from this: record level and count signals as primitives. Record total for the handful of counts whose exact sum matters (cycles, instructions, mispredicts, misses). Add rate and max reals for the ratios people read directly, because Volna can plot a real today but cannot yet divide two signals. Leave EMAs and histograms to the viewer.

What CoreMark shows

The reference model computed these numbers from the full-design recording in 2.4 seconds, reading 61 probe signals. A program phase is the kernel of the function whose instruction retired last, taken from the retire PC and the program's disassembly. CoreMark runs its kernels in turn, so each phase spans many separate stretches.

PhaseCyclesIPCBranch MPKID$ read MPKIROB meanTop-down: retiring · bad spec · front end · back end core · back end mem

Four checks came out of computing them, and each one found a trap the monitor must avoid.

  • Retired instructions equal the pipeline tracer's count, 330,196. The sum of retire_inst{k}_num over valid retire slots is exact. The testbench's o_instret counts ROB entries instead (230,446), so the IPC it implies (0.90) is 30% low.
  • Mispredicts equal the tracer's within 0.3%: 5,117 against 5,104. The branch unit's mispredict wire is only meaningful when pipe 2 completes. Summed unqualified, it gives 18,185.
  • Rename counts need the dispatch stall. A stalled IS stage re-selects the instructions it holds. Counting ctrl_ir_pipedown_inst*_vld alone gives 554,301 renamed instructions, more than the core ever fetched on the wrong path. Qualified, the count is 398,557. That is 68,361 more than retired, the wrong-path work that top-down counts as bad speculation.
  • Little's law holds exactly. The mean of bus.rd_inflight times the cycle count, divided by the 1,562 reads, gives 42.3 cycles. The mean of the per-read latencies measured on the lsu_bus transactions is the same. A level signal and a transaction stream agree on the same quantity.

Design

  1. One more bound module, no design change. c910_perf.sv is bound like the pipeline tracer, but to ct_top, because the PMU, the MMU and the BIU are siblings of ct_core. The AXI ports come in as port expressions from the openC910 wrapper. Every probe is a hierarchical reference that already exists in the recording.
  2. Signals, not streams, in the same root scope. The values are ordinary VTR signals under TX.core0.perf, beside TX.core0.clk and the three transaction streams. They are declared by the DPI sink the way vtr_clock declares the clock (vtr_writer_add_var), so they exist in the pipeline-only build that does not dump the design. Integers use the narrowest width that holds the maximum (7 bits for the ROB). Rates are reals (SPEC.md signal code 3).
  3. Primitives in the monitor, arithmetic in the sink. SystemVerilog samples each rising edge, as the tracer does, and hands levels and counts to the sink. The sink writes a value only when it changes, keeps totals and closes windows. The monitor never divides.
  4. Time follows the tracer. Values are stamped at the edge that samples them. Registered PMU sources are back-dated one cycle with the tracer's t_prev rule, or tapped at their unregistered originals. Rates are stamped at the end of their window.
  5. Presentation stays in VDB. Units, ranges (0 to 64 for the ROB) and the analog, stacked or heat drawing style are presentation. They go in the VDB profile c910.perf.vdb.json, not in the VTR file, which carries only values (README's VTR/VDB boundary).
  6. Groups are opt-in at run time. +vtr_perf=core,lsu,bus selects groups and +vtr_perf_window=256 sets W. With nothing selected, the monitor costs one test per cycle.

The SystemVerilog side

Two functions join the vtr_trace package. A value handle is declared once. Per-cycle updates are cheap because the sink drops unchanged values. A window is a sink-side object that sums a count and emits the rate.

// vtr_trace.sv additions (proposal)
typedef int unsigned vtr_value_t;
import "DPI-C" context function vtr_value_t vtr_value(string scope, string name, int width); // width 0: real
import "DPI-C" function void vtr_value_set(vtr_value_t v, longint unsigned x);            // at vtr_now()
import "DPI-C" function vtr_value_t vtr_rate(string scope, string name, vtr_value_t num, vtr_value_t den,
                                             real scale, int window);                       // real = scale*Σnum/Σden

// c910_perf.sv, excerpt
vtr_value_t rob, retired, cycles, ipc, mpki;
initial begin
  rob     = vtr_value("/TX.core0/perf/rob", "entries", 7);
  retired = vtr_value("/TX.core0/perf/retire", "count", 4);
  cycles  = vtr_value("/TX.core0/perf", "cycle", 1);                                  // 1 per edge
  ipc     = vtr_rate ("/TX.core0/perf/retire", "ipc", retired, cycles, 1.0, window);
end
always @(posedge clk) begin
  vtr_value_set(rob, rob_entry_num);
  vtr_value_set(retired, (rt_vld[0] ? rt_num[0] : 0) + (rt_vld[1] ? rt_num[1] : 0)
                       + (rt_vld[2] ? rt_num[2] : 0));
  vtr_value_set(cycles, 1);
end

Open point: the fork's dump writes the design's changes for a time step after the DPI calls of that step have run. The sink therefore queues value changes and emits them in the dump callback at their time, as trackers already do for back-dated stages. That ordering needs a test in integrations/verilator/pipeline before the C910 work starts.

Verification

This follows the pipeline tracer's pattern: a replay of the rules over recorded probe signals, and an exact comparison.

  • Differential check. perf_metrics.py is the reference model. With capture.sh --pipeline --perf --check, it reads the probes from the full dump, computes every recorded perf signal per cycle and requires the recorded values to be identical. It covers level and count signals at every edge, and window rates to the last bit of the double.
  • Invariants. The top-down fractions sum to 1 in every window. retire.total at the end equals the tracer's retired count and the minstret CSR read by the program. cycles equals the declared clock's edge count. The mean of bus.rd_inflight reproduces the transactions' mean latency (Little's law). Each iq.* counter agrees with the popcount of its valid vector outside flush cycles.
  • The demo checks itself. The page's self-test re-checks the window sums, the per-cycle slot totals and the Little's law identity against the embedded data. docs/tests/c910-perf-counters.test.mjs drives the page headlessly at desktop and phone widths.

Cost

There is no measurement yet, so this is an estimate from the recording. Over the 254,773 cycles, the demo's per-cycle signals change 2.0 million times in total. The busiest are rob.entries (168k changes), preg.free (164k), retire.count (161k) and ibuf.halfwords (146k). Rare events such as dcache.read_miss (410) cost nearly nothing. Window rates add 995 samples per signal at W = 256.

For comparison, the pipeline tracer makes about 20 DPI calls per instruction, 6.6 million in this run, and costs 8.4% of simulation time. If the monitor checks for a change in SystemVerilog before calling out, the full demo set costs about a third of the tracer's calls, so a few percent of simulation time. The catalogue's other groups scale linearly with their change counts. The gate is the same as the tracer's (pipeline_cost.py): perf on top of the pipeline-only build must stay within 1.03× of it. The file cost is reported beside it.

Alternatives considered

  • Read the CSRs from software. This is what a user does on silicon. It is rejected for simulation: 16 counters at most, the program is changed, and intervals are as coarse as the reads. The pmu.mhpmcounterN signals keep this view available for comparison.
  • Compute everything from a full dump afterwards. This is how the demo was made, and perf_metrics.py stays useful for exploration. As the only path it is rejected: it needs the 280 MB dump and about four times the run time, and it leaves nightly pipeline-only runs with nothing.
  • Let Verilator trace the monitor's variables. This is the simplest to write. It is rejected because the signals would sit at the monitor's instance path deep in the design tree, not under TX.core0, and the pipeline-only build turns tracing off.
  • Periodic text dumps (gem5, XiangShan --stat-cycles). This only gives windowed rates, and not on the waveform timeline. It is rejected, but the idea of a fixed stat window becomes the rate encoding.
  • Store only running totals and derive the rest in the viewer. This is the cleanest storage. It is deferred until Volna has derived signals; until then a total plots as a ramp nobody can read.

Open questions

  • Whether top-down should use a stricter memory-bound rule (the ROB head is a load that missed) instead of "a fill is outstanding". The stricter rule needs the ROB head's type, which the tracer already knows.
  • Whether windows should be counted in cycles only, or also in retired instructions. Instruction windows align rates with program progress across runs of different speed.
  • Whether the program phase should be a signal. The retire PC is a design signal and function names belong to VDB, so the phase row in the demo is presentation that a viewer could derive.
