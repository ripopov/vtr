Design proposal · volna-core · GPUI · VS Code

One settings.json, a settings editor with fuzzy navigation, the same keys on every host

User settings for Volna that behave the way VS Code users expect: a human-edited JSON file with comments and schema-driven completion as the source of truth, a settings editor that searches every setting fuzzily and edits that file surgically, and one registry that generates the native editor, the JSON schema and the VS Code contribution block.

existing already in the repository proposed new design in this document library provided by gpui-kit 0.6.1

Written on 2026-09-17 after reviewing longbridge/gpui-kit at commit d604a2a (2026-09-16) against the pinned gpui-kit 0.6.1 that Volna builds with, plus the current preferences code in volna-core, the GPUI frontend and the VS Code extension. Implemented in the same month: volna-core::settings (registry, JSONC store with surgical edits, search, schema and VS Code emitters, migration), the native file path, the VS Code live-configuration path, the Settings tab, the JSON view and the command palette; see volna/volna/ARCHITECTURE.md for the state of the code. Two deliberate deviations: workspace.autosave applies on the next trace open on every host (the workspace candidates are read when a trace opens), and the palette reveals a setting by filling the search box with @id: rather than scrolling the page. The playground remains a browser mock of the design.

Recommendation

The simplest coherent design

The file is the truth

proposed A single settings.json (JSON with comments) holds only the keys the user changed. Defaults live in code. The editor writes into that file with surgical edits that keep comments and formatting, exactly as VS Code and Zed do, so hand edits and GUI edits never fight.

One registry, three outputs

proposed volna-core::settings declares every setting once: id, page, group, type, constraints, default, description, search keywords, apply mode. From it the core resolves values, emits diagnostics, generates the JSON Schema, and the build generates VS Code's contributes.configuration. The GPUI editor is built from the same table.

Reuse gpui-kit's Settings, own the search

library gpui-kit ships a Settings component (sidebar of pages, groups, typed fields, per-page reset, a search box) and a Command palette. proposed Their matching is plain substring; Volna runs its own ranked fuzzy search in the core and hands the component already-filtered, already-ordered pages.

Editor as a tab, JSON one click away

proposed ⌘, opens a Settings tab in the centre dock beside the waves, so appearance changes preview live. An "Open settings.json" button switches the same tab to gpui-kit's Editor with schema completion, hover docs and diagnostics from the core parser. ⌘K reaches any setting from the command palette.

Hosts move bytes, never parse

existing The workspace persistence pattern (byte store, save tickets, atomic rename, read-error write protection) is reused unchanged. Native watches the file; standalone web keeps the text in browser storage; VS Code supplies its own volna.* configuration and gets live updates through onDidChangeConfiguration.

State is not a setting

proposed Recent traces and recent workspaces leave the preferences file and move to state.json. Settings are what a user would sync to another machine; state is what the app remembers about this one. The two never share a file, as in VS Code.

Scope. Global user settings only: appearance, waveform behaviour, sidebar, workspace persistence, remote limits, logging. Per-trace state stays in the workspace file described in Panels and Workspaces. Key bindings are a natural second file (keymap.json) built on the same store and editor, but they are not designed here.

Gaps against the VS Code experience

  • Matching is substring, unranked. "folcur" finds nothing; "cursor follow" finds nothing because the whole query must occur contiguously. There is no scoring, no ordering by relevance, no match highlighting in results, and no filter syntax such as @modified.
  • Search filters instead of navigating. Non-matching items vanish; the reader loses the page context and there is no result count. VS Code shows a flattened result list with per-page counts in the table of contents.
  • No per-item modified indicator. Reset exists only per page. VS Code marks each changed setting with a bar and offers Reset, Copy Setting ID and Copy Setting as JSON on that item.
  • Search state is internal. Query and selection live in use_keyed_state keyed by element id. Deep links (open the editor at one setting from the palette) need the query to be owned outside the component.
  • No notion of a file. The component reads and writes app globals; persistence, defaults, validation and JSON are the application's job. That suits Volna, whose core already owns persistence.
  • No JSON toggle, no schema. The Editor and LSP hooks exist, but nothing connects a settings schema to completion or diagnostics.

Every gap is either a small wrapper around the component or work that belongs in volna-core anyway. Two items are worth offering upstream once they are proven in Volna: a Settings::matcher(...) hook that replaces the substring test with a scored matcher, and an externally owned query so a host can drive the search box.

Core

The settings model

The registry

proposed volna-core::settings::registry is a static table, one entry per setting, in the order the editor shows them. Titles, descriptions and keywords are English strings in code; the frontend never invents text.

// volna-core/src/settings/registry.rs (sketch)
pub struct Spec {
    pub id: &'static str,            // "waves.animation"
    pub page: Page,                  // Appearance | Waves | Sidebar | Workspace | Remote | Advanced
    pub group: &'static str,         // "Navigation"
    pub title: &'static str,         // "Animation"
    pub description: &'static str,   // Markdown allowed
    pub keywords: &'static [&'static str], // ["smooth", "motion", "reduce"]
    pub kind: Kind,                  // Bool | Integer{min,max,step} | Number{..} | Enum{values,labels} | Text | List
    pub default: Value,
    pub apply: Apply,                // Live | OnReopen | Restart
    pub hosts: Hosts,                // ALL | NATIVE | VSCODE | WEB bit set
    pub since: u32,                  // settings file version that introduced it
}

Ids are lowercase dotted paths with camelCase leaves, the VS Code convention, so waves.animation is volna.waves.animation in VS Code and nothing else changes. A test asserts that every id is unique, that every default satisfies its own constraints, and that the JSON emitted from the registry matches the contribution block committed in package.json.

Layers and resolution

proposed settings::Store holds three layers and one result:

  1. Defaults from the registry, always complete.
  2. The user document: the raw JSONC text plus the parsed map of top-level keys with their byte spans. Kept verbatim so edits can be surgical and so unknown keys survive round trips.
  3. Host overrides: values a host supplies and owns, such as VS Code's configuration or a command-line --set key=value. They win over the file but are never written into it.
  4. Resolved Settings: a plain typed struct (appearance.theme: String, waves.snapPixels: u32, …) rebuilt whenever a layer changes, plus a Vec<Diagnostic>. Invalid values fall back to the default and produce a diagnostic with the key's span; they never block start-up, matching the "missing metadata never gates startup" rule already used for themes.

The viewer reads only the resolved struct. App exposes settings() and a SettingsChanged { keys } event so frontends re-project the theme or re-layout only when a relevant key changed. Preferences is retired once the native file path lands: link_by_default, theme and autosave become registry entries, and the recent lists move to state.json (see below).

The file

// ~/.config/volna/settings.json — only what the user changed
{
  // Pick any palette JSON dropped into ~/.config/volna/themes/
  "appearance.theme": "gruvbox-dark",
  "appearance.uiFontSize": 14,
  "waves.animation": "reduced",
  "waves.snapPixels": 8,
  "panels.linkByDefault": false,
  "workspace.autosave": "off",
  "log.level": "debug",           // trailing comma tolerated
}

Parsing accepts comments and trailing commas (JSONC) with a small tolerant parser in the core; no new dependency is required, and the same parser records spans for edits. The file carries no version field: versioning is per key through since, and renamed keys are migrated by a table of old id → new id that rewrites the document once, keeping a comment with the old name. This is a deliberate exception to the GOAL.md rule that formats are versioned and incompatible files rejected: a hand-edited file must degrade key by key with a diagnostic, never fail as a whole, or one typo would reset every setting. The machine-written state.json below follows the rule. A file above 1 MiB is treated as unreadable, the same cap preferences.json has today, and an unreadable file disables writes until it is fixed.

state.json

proposed The machine state that leaves the preferences file. Plain JSON, written only by the app, so it is versioned and strict: { "version": 1, "recentTraces": [uri, …], "recentWorkspaces": [uri, …] }, newest first, each list trimmed to workspace.recentLimit on write. It is owned by volna-core::workspace::state (the code that keeps the recent lists today), read once at start, written through the same ticketed byte path as settings.json with the same 1 MiB cap and the same rule that a read or parse error makes the file non-writable. An unreadable or wrong-version file yields empty lists and a log line, never a failed start. The file is never synced, never edited by hand and never shown in the JSON view; it has no schema and no editor.

Surgical edits

proposed A GUI change becomes Command::Settings(Set { id, value }). The store answers with a text edit against the current document, not a re-serialisation:

  • Key present: replace the value span only. Comments on the line and elsewhere are untouched.
  • Key absent: insert "id": value before the closing brace using the document's indentation and quoting style, adding a comma to the previous property if needed. The new property carries no trailing comma: the parser tolerates trailing commas the user typed, but the editor never produces one, so the file stays valid for strict JSON tools that follow the $schema line.
  • Reset: remove the property and its comma; an empty document becomes {}.
  • Unparsable document: refuse the edit, keep the GUI read-only, and show the error position. The user fixes it in the JSON view.

The new text is applied to the store immediately (so the GUI and the waves update in the same frame), then handed to the host as Event::WriteSettings { ticket, bytes }. Writes follow the workspace scheduler: one in flight, acknowledged by ticket, coalesced after a short idle. When the host's file watcher reports a change, the store compares the SHA-256 of the bytes with the last write it issued and ignores its own echo, the same rule the workspace supersedes check uses.

GPUI frontend

The settings editor

Layout

proposed A centre-dock tab titled "Settings", opened by ⌘,, the App menu ("Settings…") or the command palette. The tab is a chrome panel: the core records that it exists (so focus and tab order work) but the workspace codec never saves it, and closing the trace leaves it open.

Inside the tab, gpui-kit's Settings component provides the table of contents on the left and the active page on the right. Volna hides the component's own search input through header_style and renders its search bar above the component: query box with the ⌘, hint, result count, an @modified chip, and the "Open settings.json" button on the right, as in VS Code.

Items

Each registry entry becomes a SettingItem whose title is a Label with match highlights, whose description is the registry Markdown, and whose field maps to a SettingField by kind: switch for booleans, number_input with the declared range and step, dropdown for enums, input for text, and render for lists and palette pickers. Get closures read the resolved struct; set closures dispatch Command::Settings(Set).

A changed item shows a coloured bar on its left edge and an actions button: Reset setting, Copy setting id, Copy as JSON. Items whose apply is OnReopen carry a small "reopen trace to apply" badge; Restart ones say so. Items not available on the current host are omitted, not disabled, so VS Code-only keys such as remote.memoryMiB never confuse a native user.

JSON view

proposed "Open settings.json" swaps the page area for gpui-kit's Editor in JSON mode with the file's text. Three providers, all backed by the registry: completion of key names when the caret is in a key position and of enum values in a value position; hover documentation for a key; diagnostics from the store's last parse (unknown key, wrong type, out of range, not an enum member) as squiggles with the message. A "Default settings" toggle shows the generated read-only document beside it. ⌘S writes the document through the same ticketed path as GUI edits; the GUI reflects the new values when the write is acknowledged.

On the web build highlighting is unavailable (the Tree-sitter stub), but completion, hover and diagnostics do not depend on it.

Command palette

proposed ⌘K opens gpui-kit's Command in a dialog with two groups: Commands (every registered action with its key hint) and Settings, filled by the same core matcher as the editor, capped at eight rows. Choosing a setting opens the Settings tab, selects its page, scrolls to the item and flashes it. Choosing a boolean toggles it in place without opening the editor, which is the fastest path for "turn animation off".

VS Code host. Fuzzy navigation

Search that finds "folcur"

proposed volna-core::settings::search ranks registry entries for a query and returns, for each hit, a score and the matched character ranges in the title and id. It is deterministic, allocation-light, and testable headless. The playground below runs the same algorithm in JavaScript.

  1. Filters first. Tokens starting with @ are constraints, not text: @modified keeps changed settings, @page:waves keeps one page, @id:waves.snap matches ids by prefix. Remaining tokens are lowercased search terms; every term must match (AND).
  2. Per term, best field wins. Title: whole word 100, word prefix 80, contiguous substring 60, fuzzy subsequence up to 50. Id segments: the same ladder at 0.8. Keywords: the same ladder at 0.7, with the fuzzy rule also allowed across the joined keyword list so one term can span two keywords. Description: whole word or substring only, at 0.4, because fuzzy matching prose is noise.
  3. Fuzzy scoring is fzf-like: characters must appear in order; each match earns 1, plus 3 at a word or camelCase boundary, plus 2 when adjacent to the previous match; each skipped character costs 0.3 with a cap. Fuzzy needs at least three query characters, and a fuzzy hit scoring under 15 is discarded so that a short term cannot collect stray letters across a long keyword list; below three characters only word, prefix and substring rules apply.
  4. Rank by total score, then modified items first, then registry order. The results view lists hits flat in that order with the page name as a secondary label; the table of contents shows a count per page and dims empty pages.
  5. Highlight the matched ranges in the title with Label::highlights; when the hit came from the id or a keyword, show that text under the title so the user sees why it matched.

Worked examples from the catalogue: folcur matches Link new panels through the fuzzy path over its keywords follow cursor (f-o-l at a word start, c-u-r at a word start); snap px matches Snap distance through the title and the id segment snapPixels; reduce matches Animation through a keyword; @modified snap lists only changed settings mentioning snap, which in the sample document is Snap distance alone.

Alternatives considered

  
Trade-offs

  

    
TOML like Surfer
Surfer keeps a TOML config resolved through ProjectDirs. Rejected: the VS Code host needs JSON anyway, gpui-kit's editor has a JSON grammar and no TOML one, and one format for settings, workspaces and palettes keeps the parsers and tests shared.

    
Nested objects like Zed
{"waves": {"animation": "off"}} reads well but the VS Code contribution is flat, surgical edits into nested objects need path-aware insertion, and search over ids becomes a join. Flat dotted keys are accepted as the only form; a nested form could be accepted later as input without changing the store.

    
GUI-only store, file as an export
Simplest to build, but it breaks the VS Code expectation that the file is authoritative, makes hand edits second class, and cannot preserve comments. Rejected.

    
Serialise the whole struct on every change
The current preferences path. It drops comments and unknown keys and rewrites formatting. The surgical editor is a few hundred lines with its tests, because it has to handle string escapes, block comments, duplicate keys, list values, CRLF line endings and a byte-order mark (the playground parser already covers all but the last two), and it removes an entire class of complaints; the store keeps serialisation only for the generated default document.

    
A modal sheet instead of a tab
gpui-kit's Sheet would take a day less. But a modal hides the waves, so appearance and navigation settings cannot be previewed, and it fights the dock's focus model. A tab is what VS Code and Zed do and what users expect from ⌘,.

    
Keep the component's own search
Zero code, but "folcur" and "cursor follow" find nothing, there is no ranking or highlighting, and the query cannot be driven from the palette. Replacing the match is the smallest change that makes the editor feel like VS Code's.

    
Adopt gpui-kit's theme JSON as Volna's theme format
It would give thirty ready themes for the chrome, but the waveform painter reads Volna's core tokens, and VS Code hosts already supply a palette snapshot in Volna's format. The registry's watch-a-directory idea is borrowed; the format is not.

    
Settings inside the workspace file
Would let a trace carry its own preferences, but workspace files are shared and copied with traces; user preferences in them leak between people. Per-workspace overrides can be added as a fourth store layer later without touching the file format.

  






  
Verification

  
Behaviour and regression checks

  
Each statement is a headless test in volna-core unless marked otherwise.

  
    
    
  • Parsing accepts comments, trailing commas and unknown keys; the resolved struct equals defaults for an empty or missing document.
    • 
    
  • A document with a wrong type, an out-of-range integer and an unknown enum member resolves to the defaults for those keys and reports three diagnostics with the correct line numbers.
    • 
    
  • Set on a present key changes only that value's byte span; the rest of the text, including every comment, is byte-identical. Set on an absent key inserts one property with the document's indentation and no trailing comma; the result parses under strict JSON when the rest of the document does. Reset removes exactly one property and leaves valid JSONC. Repeating a hundred random set/reset operations keeps the document parsable and equal to the resolved values.
    • 
    
  • A syntax error makes Set return an error, keeps the last good resolution, and the diagnostic names the line; fixing the text restores writes.
    • 
    
  • The echo of the store's own write, delivered as a watcher change with identical bytes, produces no SettingsChanged; a different external write produces one with the changed keys only.
    • 
    
  • Search: folcur ranks Follow cursor first; snap ranks Snap distance above any description-only hit; @modified lists exactly the keys present in the document; ranking is stable across runs and independent of page order except as a tie-break.
    • 
    
  • The registry has unique ids, defaults within constraints, and its VS Code emission equals the committed package.json block.
    • 
    
  • Migration of a version 1 preferences.json produces the expected settings.json and state.json, and a second run is a no-op.
    • 
    
  • GPUI (macOS harness): ⌘, opens the tab, typing a query shows the results view with highlighted titles, toggling a switch updates the JSON view text without reformatting, and the tab is absent from a saved workspace.
    • 
    
  • VS Code (extension tests): changing volna.waves.animation in VS Code settings reaches the webview without reopening the trace; the generated contribution block validates as a VS Code manifest.
    •
