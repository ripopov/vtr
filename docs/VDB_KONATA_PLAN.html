Format explanation + implementation proposal

How Kanata works.
How VTR + VDB replaces it.

Kanata is a sequence of commands describing instructions over time. VTR stores the resulting instructions, stages and dependencies as structured trace data. VDB supplies the rules that turn those records into a Konata-like pipeline view.

Kanata is the file format. Konata is the viewer. Replacing the file format is only half the job: we must also move the viewer’s assumptions—stage colors, dependency anchors, flush styling and row labels—into VDB.

1 / understand the input

A Kanata file is a little state machine.

The file is tab-separated text. Its first line is Kanata<TAB>0004. The remaining commands update a current cycle and a collection of instructions. Every command uses the current cycle until a C or C= changes it. Time moves forward; commands for different instructions can be interleaved.

Each instruction owns its stages

An instruction has a file-local ID, a simulator ID and a hardware thread. It can occupy multiple lanes at once. A lane is a layer of activity within that instruction: lane 0 conventionally holds normal pipeline stages; lane 1 can show a simultaneous stall.

A stage has a name and a start/end cycle. Names such as F, X and stl are strings, not a fixed set of opcodes.

Do not confuse the IDs

I 10 700 0 creates file operation 10, whose simulator ID is 700, in thread 0. Later commands refer to 10.

R 10 5 0 later records retirement ID 5. It does not rename the instruction. Speculatively assigned retirement IDs can overlap on flushed instructions.

The file records facts; Konata supplies conventions. S 10 0 X records the string “X”. Konata recognizes names containing “X” as execute stages for dependency anchors. The file does not contain an RGB color, a drawing coordinate, or a “show this as an execute stage” command.

Reference: Kanata format and the pinned parser. Malformed-input recovery is a separate compatibility policy; the examples here use valid input.

No “C 1” records are necessary in VTR. Their effect is already present in absolute event times and interval boundaries. The original file’s exact whitespace and choice of C versus C= are not preserved; its instruction behavior is. An importer keeps source/version/origin metadata for interpretation and diagnostics.


Why labels become events in the proposed mapping
A Kanata L line occurs at a cycle, even though Konata normally displays accumulated text. The current converter folds type 0/1 labels into transaction attributes and type 2 into stage attributes. This retains final text, but transaction attributes have only begin/record/end phases; they cannot say exactly when a fragment arrived.
Proposed canonical representation: write one TxEvent named kanata.label per L line, with attributes type, text and, for type 2, stage_index. Preserve order for events at the same timestamp. The stage index is a run-local ordinal in the ordered stage list, so repeated stage names and multiple lanes are unambiguous.
The session derives final row/tooltip text by joining type 0/1 fragments and inserting line separators between type-2 fragments. A cursor-aware view can instead join only events up to the cursor. This avoids storing the same text twice. A legacy profile can still read the existing converter’s aggregate label/detail attributes, but it cannot recover fragment timing that was discarded.




3 / reconstruct the view
VTR has the facts. VDB tells the viewer what they mean.
After reading the example, a generic VTR reader knows that a transaction has a stage named X and a relation named wakeup. It does not know that X should be green, where the dependency arrow should touch, or which text belongs in the left-hand instruction column.

VDB rendering rules




Dependency anchors: a concrete example of semantics moving into VDB
W 20 10 0 says only that 20 depends on 10. It does not say “draw from pixel A to pixel B”. The pinned Konata parser treats stage names containing X as execute stages, using execute entry as the consumer anchor and the last execute cycle as the producer anchor.
Here, producer 10 executes on [101,103), so its last execute cycle is 102. Consumer 20 enters X at 102. The arrow anchors are therefore (10, 102) → (20, 102). The W occurrence is also 102 in this example, but it is a separate fact and need not equal either anchor.
A VDB compatibility rule encodes this policy. Preserve the pinned handling of repeated X stages and implicit closure. If an instruction has no suitable execute anchor, keep its relation inspectable without inventing an arrow. In physical waveform units, “end minus one cycle” requires the clock mapping; subtracting one trace tick is not equivalent.


A minimal pipeline profile for this example
This is a proposed schema sketch. Its field names are illustrative; the semantics above are the contract the implementation must support.
{
  "version": 1,
  "profile_id": "kanata-v4",
  "select": {"generator_glob": "cpu.thread*.instruction"},
  "rows": {
    "identity_attribute": "insn_id_in_file",
    "order": "source_operation_order"
  },
  "labels": {
    "event": "kanata.label",
    "type_attribute": "type", "text_attribute": "text",
    "stage_reference_attribute": "stage_index",
    "targets": {"0": "row", "1": "instruction", "2": "stage"}
  },
  "stages": [
    {"name": "F", "role": "fetch", "color": "#d5e6f0"},
    {"name_contains": "X", "role": "execute", "color": "#dcedb5"},
    {"name": "stl", "role": "stall", "color": "#d5d5ce"}
  ],
  "lanes": [{"name": "0", "order": 0}, {"name": "1", "order": 1}],
  "lifecycle": {"retired": "Unset", "flushed": "Aborted", "incomplete": "Open"},
  "dependencies": {"kind": "wakeup", "anchors": "kanata-execute-v1"}
}
Reusable names, not run-local IDs. The profile selects generator paths, keys, stage names and relation kinds. On attachment, the session resolves them to the IDs in this particular VTR. TxId 501 is not written into a reusable VDB profile. Paths must be canonical and matches unambiguous; changing a color does not change the design’s identity.




4 / implement the replacement
Translate once. Query records. Apply a profile.

→
Replacement path
Simulator or Kanata importer → VTR records → VTR reader + VDB profile → the same pipeline behaviors.


A simulator can keep producing Kanata while we build the importer. A native producer can later call the same VTR writer APIs directly, avoiding text serialization and re-parsing. This is an architectural option, not a measured speedup claim.


1. Implement the command-to-record contract
The importer tracks current_cycle, file_id → TxId, thread generators, live instructions, open stages per lane and the latest stage ordinal for each instruction. Keep producer ID mappings after retirement so a later consumer can still depend on an older producer.
For L, emit the label event described above. For R, close still-open stages at the retirement/flush time, attach retire_id and end the transaction. For EOF without R, preserve Open and the observed horizon; do not turn it into a successful retirement.
2. Add the pipeline domain to VDB
The current Database::open accepts only vtr-rtl-vdb version 2. Introduce a domain-neutral package with an optional typed rtl payload and an optional pipeline profile. The pipeline profile above belongs inside that package; it is not appended to VTR.
{
  "format": "vtr-vdb", "version": 1,
  "domains": {
    "rtl": "<complete current RTL v2 payload, when present>",
    "pipeline": "<pipeline profile shown above>"
  },
  "bindings": "<optional pipeline-to-RTL rules>"
}
This shape is illustrative: payloads will be objects, not these placeholder strings. Version the envelope and domains separately. Reject unsupported required versions; tolerate additive metadata. A pipeline-only package needs no RTL export. A loader adapter can wrap legacy RTL v2 documents without changing their semantics.
3. Resolve and query in an attached session
Resolve generator and attribute names once. Use visit_transactions(TxQuery) for generator/time selection and relations_from/to for dependencies. Reconstruct row labels from events and stage bars from TxStage lists; apply the VDB’s styles and lifecycle rules.
The current reader has no row-page or retirement-ID query. Add session-level indexes for original operation order, committed RID lookup and filtered row positions; keep page data immutable and share cached storage. A time filter alone is insufficient: panning the X axis should not reorder the instruction rows. Search/statistics may need cancellable scans.
4. Connect a Konata-compatible viewer
Use a data-provider adapter in the pinned Konata viewer to retain its navigation, comparison and analysis behavior. Its current OpStore getters are synchronous: add asynchronous page prefetch and read only ready pages during rendering. A local Rust host can reuse the existing VTR reader and RTL engines; browser-only WASM needs a separate file-access adaptation because the reader currently uses mmap.
VDB provides semantics and default styles. The viewer/session retains pan, zoom, open tabs, bookmarks, user overrides and comparison offsets. These controls do not belong in the trace. Reload an immutable VTR snapshot; do not tail a concurrently changing mmap file.

5 / keep RTL and add a bridge
A pipeline profile sits beside the RTL database.
The existing RTL VDB still describes instances, ports, specialized types, source locations, connections and processes. Netlist rendering and temporal driver tracing continue to consume that typed RTL payload. Pipeline support adds another domain and an explicit navigation binding.

Use the existing debugger
Open that instance’s annotated netlist at tick 25. Select result to invoke temporal driver tracing at the same mapped moment.


The binding proves where to navigate, not what caused the value. The VTR wakeup edge links two instructions. The RTL driver tree explains assignments, guards and clock/reset events. These are distinct relationships; retain both rather than replacing one with the other.


Conditions for a correct pipeline ↔ RTL jump
  • Same design: preserve the RTL design_id and check existing VTR design.vdb_id. Keep exact path/prefix, width, type and ambiguity validation. Missing design identity remains explicitly “structural matching only”.
  • Same execution: combined waveforms/transactions in one VTR share the trace timeline. Separate pipeline and waveform files need matching run identity or explicit verified pairing; the same RTL design hash is not enough.
  • Same time: use an explicit clock origin and scale with integer/rational arithmetic. Gated or changing clocks require observed edge mapping, not a constant multiplier. Dump gaps or ambiguous edges make the jump unavailable.
  • Same RTL semantics: retain netlist hierarchy boundaries, aliases, X/Z and wide-value display. Preserve driver tracing’s pre-event sampling, unchanged writes, enable holds, resets, source-order evaluation and explicit unsupported/missing results. Do not replace assignment history with the last value change.
Keep slang as the standalone RTL exporter. The planned pre-optimization Verilator exporter can target the same RTL domain and provide explicit original-symbol → traced-signal mapping and a shared build identity. Pipeline-only browsing does not depend on that exporter.




6 / finish the Konata replacement
The other features reuse the same foundation.
Understanding Kanata’s commands explains the data model. Full Konata parity also includes input adapters and viewer behavior. These are follow-on acceptance requirements, not additional fields to embed in VTR.

Implementation order
  1. Lock down this translation: make the worked example and edge cases executable converter fixtures.
  2. Implement the VDB profile and resolver: demonstrate two renderings of the same VTR, plus pipeline-only and combined packages.
  3. Add queries and the viewer provider: preserve the pinned controls, gem5 handling, comparison and analysis.
  4. Add the RTL bridge: verify identity/time mapping and run all existing netlist/driver regressions.
  5. Declare parity after evidence: finish the inventory above, document final schema/API conventions in the application note and references, and run applicable correctness/benchmark suites.
