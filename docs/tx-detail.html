Design proposal · volna-core · GPUI · VS Code

One Transaction panel for the table, the pipeline, and whatever selects next

A dockable panel that shows the transaction selected in any Table or Pipeline panel: what it is, when it ran, its stages and events on a lifeline, its attributes as typed values, and every related transaction one click away. Selection becomes a document concept, so the same panel serves the transaction lanes proposed for the wave panel and any command that arrives from the palette or an agent.

existing already in the repository, reused as is proposed the first version described here later deliberately left out, with its seam named

Companion to pipeline-view.html (the rows this panel explains), table-baseline.html (whose record details this replaces), transaction-waveforms.html (a third selecting panel) and the UX prototype in demos/pipeline-viewer/, whose instruction inspector is the standard this design is measured against. Status: implemented in volna-core/src/transaction and the GPUI transaction_panel.rs, except the agent adapter (no MCP adapter exists yet); see docs/RATIONALE.md. The mock-up below runs on recorded data from volna/volna/examples/pipeline_showcase.vtr and feature_showcase.vtr.

Recommendation

Five decisions, then everything follows

1 · A panel kind, not an inspector strip

PanelKind::Transaction sits next to Waves, Pipeline and Table. It docks beside or below whichever panel the user is reading, tabs, splits, saves and restores through the panel code that exists. It outlives the panel that selected its record, because it retains the track itself. The 360 px strip inside today's table panel goes away.

2 · Selection is the document's

A single TxSelection { track, id, origin } on the document. Table rows and pipeline rows write it; the transaction panel reads it; every panel that shows the record highlights it. A pinned transaction panel ignores changes, so two panels side by side compare two records with no extra feature.

3 · Content follows the record, not the panel

Identity, timing, lifeline, attributes, stages, events, related: always in that order, whether the record is a Konata instruction, an AXI burst or an OpenTelemetry span. Empty sections collapse to a heading with a zero. There is nothing to configure per stream kind.

4 · Every time is a link, every reference is a jump

Begin, end, a stage cell, an event tick: clicking moves the shared cursor, and linked panels follow. Parent, child, a wakeup producer, a causes request: clicking makes that record the selection, with Back to return. A reference on a track that is not loaded loads it, the same way opening a pipeline does.

5 · Bounded exactly as the table is today

The panel reads one resident record, never scans a source, and lists at most transaction.detailItems entries per section (today's table.detailItems, renamed because it no longer belongs to the table). Cuts are stated as “showing the first 20 of 300”. Values are complete, not the 256-byte previews of a table cell.

What v1 deliberately lacks

Notes, source context, VDB stage roles and authored colours, cause analysis (“waiting to retire”), a diff between two records, a relation graph, search across records by attribute value, multi-selection. Each has a named seam in Model and Alternatives. No new settings beyond the rename.

Today

What the viewer shows now

The table panel's Details toggle opens a strip on the right of the grid: a title line, eight fixed fields, then Attributes · n, Events · n and Stages · n as name/value text, each stage flattened into one string. It is correct, bounded and hard to read: raw decimals (pc = 2147483656), no unit, no colour, no link to time, no way to reach the producer that the wakeup relation names, and it disappears with the table. The pipeline panel has no selection at all: a click sets the cursor, and the status bar names the hovered row and stage. To read an instruction's attributes the user opens a table of the same generator, finds the row, and opens the strip there. The prototype in demos/pipeline-viewer shows the standard: a persistent inspector with a headline, a status badge, timing tiles, a stage breakdown and dependency links that navigate.

The table strip as implemented in volna/volna/src/table_panel.rs, drawn from the same record (#4 of pipeline_showcase.vtr) the mock-up opens first. The width, order and wording are those of the code; the figure is static.

Interactive mock-up

Try the panel

Three panels over one document, laid out as the core would model them: a Pipeline panel and a Table panel on the left, sharing the document's viewport and cursor, and the proposed Transaction panel on the right. The pipeline shows the soc.cpu0.pipeline stream of the pipeline showcase (a five-stage in-order core: 109 instructions in the first 200 cycles, cache misses, operand stalls, one mispredicted branch); the table shows the soc.l2.bus/read generator, whose records are the memory requests those instructions cause. The second file, feature_showcase.vtr, has a three-stage core with retire events, DMA transfers with 18 attribute types and one event each, and firmware spans as their parents. Both are the checked-in example traces, read with vtr tx; nothing is synthesized for the page.

What the mock implements versus what is proposed. The mock has the proposed selection model, panel content, history, pinning, cursor links, cross-track jumps and the stage ladder colours of pipeline/palette.rs. Its pipeline and table are reduced re-implementations, not ports: no follow-activity, no density mode, no link toggles, no load or refusal states, no workspace file. The browser cannot tell a mouse wheel from a trackpad, so every unmodified wheel zooms both axes and ⇧+wheel pans. Copy only reports what it would copy. The mock keeps at most two Transaction panels; the product has no such limit.

Anatomy

Seven regions, top to bottom

The order answers the questions in the order an engineer asks them: which record is this, when did it run, what shape did it have, what does it carry, what happened inside, what is it connected to. Everything above the fold is fixed-height so that the same region is in the same place for every record; the sections below it collapse and remember their state per panel.

1Header

The panel's title, a chip that says whose selection it follows (follows Pipeline 1) or that it is pinned, Back and Forward through the records it has shown, the pin, and close. Back and Forward exist because relations are the main way to navigate here; without a history every jump is a one-way door.

2Identity

Breadcrumb stream › generator with the sidebar's icons and the record's row ordinal in that track; the ID as a chip; the vtr.label as the headline in the monospace face; a status badge (ended, ok, error, aborted, dashed open) with the raw TxStatus name as its tooltip; the span kind when it is set; child of #n when there is a parent. The label is presentation, so it is not repeated among the attributes.

3Timing

Three tiles: Begin, End, Duration, in the producer's time.unit (cycles here, nanoseconds in the feature showcase). Begin and End are buttons: the cursor goes there. An open record shows open and a duration with a ≥ sign, never a fabricated end.

4Lifeline

The record's own Gantt: one row per lane, the primary lane first, cells in the same ladder colours as the pipeline panel, overlay lanes in grey, events as amber ticks, the shared cursor as a dashed line when it falls inside the lifetime. Hovering a cell highlights that stage in the list and in the pipeline row; clicking sets the cursor to the stage's begin. This is the region the table strip could never have: shape at a glance, for a record that may be off screen.

5Actions

Reveal in Pipeline n scrolls the pipeline to the row and fits the time axis to the lifetime; when no open panel shows the record's track it becomes Open in Pipeline, the existing OpenPipeline { track }. Fit lifetime moves only the shared viewport, so a Waves panel above shows the signals during exactly this record. Copy writes the complete record as TSV, with the table's byte limit and refusal.

6Attributes · Stages · Events

Attributes are a key/value table with typed rendering: integers in tabular figures with a per-key radix that a click cycles (dec → hex → bin: pc reads 0x80000008 after one click, and every later record keeps it), strings plain, booleans and null distinct, vectors, fixed-point, pointers and enums as VTR prints them, long values folded with a click to expand, a filter box above eight entries, and the phase (record, end) as a small tag when it is not begin. Stages are grouped by lane and drawn as rows: swatch, name, interval, a share bar over the lifetime, duration, and the stage's own attributes as chips (miss true, reason operand). Events are a time-ordered list with their attributes as chips. Every time is a cursor link.

7Related

The parent, the children, then relations grouped by kind and direction (wakeup · from · 2, wakeup · to · 2, causes · to · 1). Each entry is a button with the other record's ID, label and, when it lives on another track, that track's path; the relation's own label is the second line. Clicking selects it, so the pipeline and table highlight it, and the panel shows it with Back enabled. A target whose track is not loaded reads not loaded and loads it on click.

Rules that keep it readable

  • Selection outlines, arrows on demand. The selected row gets a one-pixel outline in the pipeline, and only the selected record's relations are drawn as arrows (blue into it, teal out of it). Arrows for every row would be the Konata wall of lines; arrows for one row are a fact about that row.
  • Escape does not blank the panel. Clearing the selection in a pipeline or table removes the highlight and the arrows; the transaction panel keeps its record until another is selected, so a reader who cleared the highlight to see the rows does not lose the page they were reading.
  • Counts are always true. A section heading says Attributes 18 even when the list is cut at 5; the cut is a sentence below the list, naming the setting.
  • No presentation from the file. Status names, the word ended for Unset, the ladder colours, the radix memory and the collapsed sections are client state; a VDB profile may later supply stage roles and colours through the same StagePalette.
Selection

One selection, three writers, any number of readers

Writers

existing The table's row selection already exists (selection.rs, one row for details). proposed The pipeline gains one: a click on a row or a cell selects that transaction and sets the cursor to the cycle under the pointer, as Konata and the prototype do; a click on empty rows only sets the cursor. later The transaction lanes of transaction-waveforms.html write the same selection from a bar click.

Readers

Every panel that shows the selected track highlights the record if it has a row for it, and does nothing otherwise: selecting a bus request in the transaction panel highlights it in a table of soc.l2.bus/read while the cpu0 pipeline shows nothing. A non-pinned transaction panel shows the record. The status bar names it. Nothing scrolls unless the user asked to reveal.

Opening the panel

Enter, a double-click, the panel header's Details button, the context menu and the palette all issue ShowTransaction: focus the first transaction panel that is not pinned, or open one split to the right of the originating panel. With every open panel pinned, a new one opens, which is how a comparison starts.

Lifetime of the data

The transaction panel retains the track of the record it shows through Document::retain_track, exactly as a pipeline panel does, and releases the previous one when the record changes. Closing the pipeline that selected it therefore does not empty it, and a workspace restores a pinned panel by track path and ID, an unpinned one as empty.

Accessibility

The panel is ordinary list and table content, so the GPUI accessibility projection carries every value, and a screen reader hears “Attributes, 4 items”. Colour never carries meaning alone: stage rows have names, status badges have words, arrows have the Related section. Targets are at least 22 px tall at zoom 1.0; the lifeline's cells are duplicated by the stage rows for anyone who cannot hit a 3 px cell.

Model

Where it lives in the core

All behaviour is in volna-core with headless tests; the GPUI element only renders a prepared view and forwards commands. The table's Details, DetailList, ToggleDetails and CloseDetails are removed rather than kept beside the new panel: one owner of record presentation, per the ground rule on missing abstractions.

// document.rs
pub struct TxSelection { pub track: TrackRef, pub id: TransactionRef, pub origin: PanelId }
impl Document { pub fn select(&mut self, sel: Option<TxSelection>); pub fn selection(&self) -> Option<&TxSelection>; }

// transaction/view.rs — pure function of resident data and limits, tested headless
pub struct TxView {
    pub identity: Identity,          // stream path, generator, ordinal, id, label, status, kind, parent
    pub timing: Timing,              // begin, end: Option<u64>, unit: TimeUnit
    pub lifeline: Vec<LaneRow>,      // primary lane first; cells carry StageStyle; events as ticks
    pub attributes: Section<AttrRow>,// key, phase, Value (typed), display with radix
    pub stages: Section<StageRow>,   // name, lane, [begin, end), attrs, share of lifetime
    pub events: Section<EventRow>,
    pub related: Section<RefRow>,    // parent, children, relations by (kind, direction); resolved or NotLoaded
}
pub struct Section<T> { pub total: usize, pub rows: Vec<T> }   // rows.len() ≤ detail_items
pub fn view(doc: &Document, track: TrackRef, id: TransactionRef, prefs: &ViewPrefs) -> Option<TxView>;

// panels — PanelKind::Transaction(TransactionModel)
pub struct TransactionModel {
    shown: Option<(TrackLocator, TransactionRef)>, pinned: bool,
    history: Vec<(TrackLocator, TransactionRef)>, cursor: usize,
    prefs: ViewPrefs,                // radix per key, collapsed sections, filter text
    retained: Option<TrackRef>,      // Document::retain_track / release_track
}
pub enum TransactionCommand { Jump(TrackLocator, TransactionRef), Back, Forward, Pin(bool), Cursor(u64), FitLifetime, Reveal, Copy, Radix(String), Collapse(SectionKey, bool), Filter(String) }

Frontends

What each host draws

GPUI (native, web, VS Code)

A TransactionElement built from gpui-kit lists and the existing icon set (circle-dot for the panel, the sidebar's stream and generator icons in the breadcrumb, locate, link, table-details). The lifeline is a small custom paint over the same Scene primitives as the pipeline cells. The VS Code adapter changes nothing: it hosts the same web build.

volna-egui

Keeps building and ignores the new panel kind, as AGENTS.md prescribes. Its minimal waveform behaviour is unaffected because the wave panel does not change.

Theme

Status badge colours and the arrow colours are theme tokens next to wave_row_hover; stage colours come from StagePalette, so a VDB stage table recolours the pipeline and the panel together.

Alternatives

Shapes considered and rejected

Keep a strip inside each panel. The table has one today; the pipeline would grow another. Two implementations of the same content, each squeezed beside the thing it explains, neither able to show a record from another track, neither surviving its panel. Rejected: the panel must be shared to pay for its content.

Tooltip or popover on hover. Cheap and familiar, but it cannot hold a list of relations, cannot be scrolled, and vanishes when the pointer moves to click the producer. Retained as the later hover tooltip in pipeline-view.html, showing the identity line only.

A modal record dialog. Blocks the panels the record should be read against; a cursor link that closes the dialog is a contradiction. Rejected.

A single properties sidebar tab, like an IDE's. One per window, on the far side from the pipeline, unable to dock below a table or sit beside a second copy for comparison. Rejected in favour of a panel; a sidebar tab could host the same element later if wanted.

Cause analysis in the panel. The prototype's “L1 data-cache miss: memory response arrives at cycle 41” is the most useful line on its screen, and it is synthesized from a model the prototype owns. VTR records only what the producer wrote; here that is a stage attribute miss = true and a stall reason, shown as chips. A VDB rule that turns such attributes into a sentence is the right seam, later.

Plan

Order of work

  1. Selection in the document. TxSelection, SelectTransaction, the pipeline click and arrow keys, the selection outline and relation arrows in the pipeline painter; the table writes the same selection. Headless tests on the scene and the model.
  2. The view function. transaction::view over resident records with typed value rendering, lane grouping, related resolution and limits; tests over the feature showcase, which has every value tag, status and kind, an open record and cross-stream relations.
  3. The panel. TransactionModel, history, pin, retain/release, commands, workspace entry, the setting rename; the GPUI element and the accessibility projection; removal of the table strip and its types.
  4. Jumps that load. Not-loaded references, the loading state, remote delivery; Open in Pipeline through the existing command.
  5. Agent adapter. The two MCP wrappers; then the transaction lanes proposal can write the same selection without touching this panel.
References

What was borrowed

  • demos/pipeline-viewer (this repository): the persistent inspector with headline, status badge, timing tiles, stage breakdown bars and dependency buttons that navigate; its RESEARCH.md records the Konata and Perfetto lessons behind it. Borrowed: the region order, the breakdown bars, the jump buttons, the “selection is stable” rule. Not borrowed: the cause card and the notes, for the reasons in Alternatives.
  • Perfetto UI: a details panel that follows the current selection, shows arguments and flows, and clears on Escape. Borrowed: selection as a document concept, flows as jump buttons. Rejected: blanking on Escape.
  • Jaeger's span detail: tags, process and logs as collapsible sections under a span header with timing. Borrowed: sections with counts, events as a timestamped list, the parent link.
  • Konata (ext/Konata): tooltips are its only detail view; its dependency arrows for every visible instruction are the wall of lines this design avoids by drawing arrows for the selection only.
  • table-baseline.html: the bounded, superseded-by-identity record read and the byte ledger, kept unchanged.
