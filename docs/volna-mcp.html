Proposal · volna-core · MCP · Codex · voice

Let an agent work in Volna beside you

A hardware engineer asks an agent such as Codex to show the signals that matter, find an event, mark it and explain what went wrong. The agent sees what the engineer sees and acts on the same Volna window. The engineer keeps clicking, and one ⌘Z takes back whatever the agent did.

Research proposal, 28 September 2026. Nothing here is implemented. The demo below simulates the proposed tools in JavaScript on a small trace generated in the page; the conversation is scripted, and every number in it comes from a simulated tool result. Sources were accessed on 28 September 2026. Statements about Volna's code refer to commit 12d303b.

Recommendation
One catalogue of semantic commands and queries in volna-core, served as an MCP server by a thin adapter. There is no separate Volna control protocol.
What it reuses
App::handle, the undo journal, workspace paths as identities, complete-object loading, the VS Code message bridge.
What stays with others
Speech, turn-taking, reasoning and approvals belong to the conversation host. Codex, Claude Code and ChatGPT voice already ship them.

The recommendation in eight decisions

  1. MCP over Volna's own command bus, not a new protocol. Every shipped agent host speaks MCP: Codex, Claude Code, VS Code, JetBrains, Zed. Volna already funnels every user action through App::handle(Command). A thin adapter that turns MCP tool calls into core commands and queries gives any host full control. Adding a Volna-specific protocol first would add a second contract with no client.
  2. A catalogue in volna-core is the single source. Each operation has a stable id, a JSON Schema for its arguments, a description, a kind (read, view or edit) and an undo decision. The palette, the VS Code commands, Command::named and the MCP tools all derive from it. Today these are four hand-kept lists.
  3. Read what the user sees, by identity. get_view returns a compact text snapshot plus structured data: panels, rows with their values at the cursor, cursor, view, markers, selection, the newest undo step and a revision number. Rows, markers, panels and transactions are addressed by the identities the workspace codec already uses (hierarchy paths, marker ids, panel ids, track and record ids), never by pixels or list positions.
  4. An agent edit is one labelled undo step. Each edit call runs as one core command inside App::handle_at, so it becomes one step labelled “Agent: Add 3 signals”. It never merges with the user's steps, and the user undoes it with the usual key. The agent may undo only its own newest step.
  5. The user wins every race. Calls run on the UI thread between frames, so each is atomic. While the user holds a gesture, edits return busy and the agent waits for the activity feed. A status-bar control pauses the agent: reads keep working and edits are refused.
  6. Answers come from the viewer's own data. Values, edges and searches come from the same resident histories and translators that paint the panel, loaded through the same session, local or remote. What the agent says therefore matches what the user sees. VTR, VDB and the remote protocol do not change.
  7. Speech belongs to the host. ChatGPT voice, the Codex app's dictation, Claude Code's /voice and the Realtime API each own whichever of microphone, transcription, turn-taking and spoken replies they offer. Volna adds no speech stack. It keeps tool calls fast, results short enough to speak, and “this” and “here” resolvable from the selection and the cursor.
  8. Some things stay with the user. Quitting, closing the trace, global settings, file dialogs, the OS clipboard, arbitrary paths and raw pointer or key input are not tools. Opening a trace or workspace is allowed only under roots the user configured.

The problem

The workflow

A verification engineer has a failing test and a trace. They open it in Volna and say, or type, to an agent: “show me the handshake of the transaction I selected”, “why is this stuck at eight?”, “find the next time the FIFO drops a write and mark it”, “make the counters decimal”, “put the pipeline beside the waves”. The agent reads the view, acts on it and says what it did and found. Meanwhile the engineer keeps scrolling, selecting and removing rows; sometimes they point at something first and then ask about “this”.

Voice is the motivating case. Both hands stay on the mouse and keyboard while the conversation happens. That raises the bar for latency, for short answers, and for resolving references such as “this signal” or “here” without the user reading anything aloud.

What the solution must satisfy

The comparison criteria follow from that workflow and from the ground rules in AGENTS.md:

  • Coverage of every meaningful viewer function, not only open and move the cursor.
  • Live state: the agent must know what the user is looking at and has selected.
  • Reliability and feedback: deterministic effects, results that say what changed, loud failures.
  • Shared control: concurrent human input, ambiguity, long operations and reversal.
  • Effort and maintainability: thin adapters over volna-core, no duplicated logic, headless tests.
  • Responsiveness suitable for spoken turns.
  • Deployments: native GPUI, the wasm page, the VS Code webview with local or remote data.

What Volna has today

Volna has the right core and no outside door. Everything a user does is already a Command handled by App::handle in volna-core: 48 command variants, 45 keyboard Actions, 17 outgoing Events. Each command runs inside one undo step, and loads go through a pull-based session that works the same locally and remotely. What is missing is an external transport, a structured read API and a registry that names commands with their arguments. Several operations exist only as pointer gestures.

The repository already states the direction. README.md asks for MCP adapters that stay “thin over toolkit-independent core commands and query APIs”, and for a feedback path carrying “a stable selection snapshot and readable trace, signal, and time references”. The undo design expects agent edits to become labelled steps. The marker and transaction panel proposals sketch marker and transaction tools.

Semantic tools, screen automation and scripting

Measured evidence favours semantic tools where they exist. On WebArena, API-calling agents reached 29.2 % against about 14.8 % for browsing agents, and a hybrid reached 38.9 % [50]. OSWorld-MCP found that adding MCP tools raised o3 from 8.3 % to 20.4 % and Claude 4 Sonnet from 40.1 % to 43.3 %, though models chose a tool in at most about 36 % of tasks, so discoverability matters [51]. Microsoft's UFO2 gained 6–8 points by adding application APIs to UI automation [52]. Screen agents have improved quickly, but computer use is documented as slow, asks for a VM and human confirmation, and a canvas such as Volna's waves exposes nothing to accessibility trees [53][54]. Arbitrary code execution (Blender, Figma writes, LLDB's generic command) gives the widest coverage for the least server code, and in every case the vendor warns about safety or adds scaffolding to make results checkable.

What the survey settles

  1. MCP is the interoperable layer. Every host the user might talk to supports it, and most vendors that expose a stateful application to agents do so through it (JetBrains, Chrome, Figma, Grafana, LLDB, Home Assistant; announced for Verdi and Questa). Unity's switch from its MCP server to a CLI is the counter-example, and a reminder to keep the adapter thin.
  2. WCP is not enough and is not needed as the agent contract. It is a sound editor-to-viewer channel, but it has no state reads or activity, no undo, one client and an unreleased version “0”. Its extension proposals are converging on what an agent needs, and every MCP bridge over it re-reads the trace to answer questions.
  3. Snapshots first, pixels as a last resort. Browsers, Figma, Grafana and tldraw all give the agent a compact semantic view, with ways to read a part of it, and return fresh state after every action.
  4. One registry of named commands with schemas. JupyterLab, Perfetto, Zed and Blender expose one registry to both UI and automation, and Jupyter shows what goes wrong without schemas. KiCad keeps its internal action names out of the API.
  5. Agent edits belong in the application's undo as named groups: KiCad commits, Ghidra transactions, Blender operators, Figma's commitUndo, Neovim buffers.
  6. The user's selection and cursor are the hand-off (DevTools, Figma desktop, IDE bridges, Ghidra, tldraw), and the application reveals what the agent did (Zed's follow, KiCad's FocusOnItems, Grafana's deep links).
  7. Busy is an answer. KiCad returns AS_BUSY rather than fight the user; LLDB refuses to close a session the user owns.
  8. Speech is solved in the hosts. Microphone capture, transcription, voice-activity detection, barge-in and spoken replies live in ChatGPT, the Codex app, Claude Code and the Realtime API. MCP carries no audio.

Chosen: MCP over a core catalogue

  • It is the only option that is both interoperable with the hosts engineers use today and able to cover the whole viewer with shared-control semantics.
  • It fits the repository rule that agent adapters are thin wrappers over volna-core commands and queries.
  • The same adapter serves a headless core, so trace questions work without a window, as the Blender Lab server and wavepeek show is useful.
  • What it costs is mostly work Volna needs anyway: set cursor and view by time, select and move rows, find, values at a time, one command registry.

Not chosen, and what is borrowed

  • WCP as the agent contract. Borrowed: the greeting's capability list, server-minted item references, the wasm message entry point. A WCP facade over the catalogue stays a deferred option for language servers (slang-server's go-to-declaration flow), not for agents.
  • A Volna protocol with an MCP bridge (the Blender, Vivado and Xcelium shape). The relay between the MCP process and the viewer forwards MCP messages unchanged instead.
  • Embedded scripting. Rejected for the first stages: coverage comes from the catalogue, and generated code is where vendors warn about safety. Reconsider only if agents repeatedly need batches the catalogue cannot express.
  • Screen automation is the fallback hosts already have; Volna does nothing for it.
  • Trace-only tools stay, complementing the viewer: the vtr CLI and a future wavepeek adapter answer questions without any Volna state.

The design

How it feels to the user

The user turns on Allow agents in the status bar or with volna --agent; it is off by default. On the first connection Volna asks “Codex wants to use this window” with Allow and Deny, as Unity and Chrome do. While connected, a chip in the status bar shows the agent's latest action (“Agent: Add 3 signals”). Rows the agent adds flash in the agent colour, markers it places carry a small agent badge in their tooltip, and its steps show in the Undo menu with the “Agent:” prefix. A click on the chip pauses the agent: reads keep working, edits return paused.

When the agent moves the view to show something, the previous view is pushed onto the go-back list from the marker proposal, so one key returns the user to where they were. The agent never changes focus, theme, zoom, sidebar or settings.

The README's first feedback path is a command, Copy reference for agent. It puts a stable, readable reference on the clipboard, for example volna://fifo_stall.vtr?panel=1&rows=top.dut.fifo.count&t=1420ns, for pasting into any chat, even one with no MCP connection.

The catalogue

A new control module in volna-core lists every operation once: a stable dotted id (rows.add, view.set, markers.rename), a JSON Schema for the arguments, a one-line description, a kind, an undo decision and the core command it builds. Reads are pure functions of &App. Edits build ordinary Commands, so the undo journal, autosave and repaint work unchanged. The palette, Command::named and the VS Code command list are generated from it, which removes today's four lists.

Operations that are missing today are added as core commands, because users need them as much as agents do: set cursor, set view, select rows, move rows, set format, height and analog on given rows, add a marker at a time, rename a marker, find. Commands that currently act on “the focused panel” gain an explicit panel argument; the keyboard path keeps passing the focused one.

MCP tools are grouped views of the catalogue: 15 tools with an op argument where one object has several verbs. Tool schemas are generated from the catalogue, so a new command appears in the palette and in MCP together, and a test fails if an operation is reachable from neither.

Identities, not positions

The workspace codec already names rows by hierarchy path plus an occurrence number, panels by stable ids, markers by number, and transactions by track path and record id. The agent API uses exactly those. A row is {panel: 1, row: "top.dut.fifo.count"}, or with #2 for the second copy of the same signal. Such identities survive reordering and the user's own edits, unlike Playwright's snapshot refs, so no per-snapshot handle table is needed. An identity that no longer resolves fails with unknown_row and lists what is shown.

Every result carries the document revision, a counter bumped by any change from anyone. An edit may pass if_revision to say “only if nothing changed since I looked”, as PanelsCommand::SetLayout already does with the layout revision. Otherwise edits apply to current state, and the result returns the state they produced.

What the agent reads

get_view returns a text form of about 1–2 KB for a typical panel and the same data as structured content. The text is for the model and for speaking; the data is for exact follow-up calls. Parts can be requested (detail: "panels" | "rows" | "markers" | "selection"), as Grafana's summary and JSONPath reads do for large dashboards. Row values come from a new core query, WaveModel::value_at(row, t), which the painter uses too, so the text always equals the value column on screen.

wait is the activity feed. It returns everything since a revision, each entry tagged user or agent: cursor moved, selection changed, step committed, panel opened, load finished. Where a host supports MCP subscriptions, the same feed is the resource volna://activity. Codex currently pulls, so the feed must work without push.

Concurrency, reversal and failures

  1. One call is one command on the UI thread. The relay hands each request to the frontend's executor, which calls App::handle_at between frames, like any key press. Nothing interleaves inside a call.
  2. Author on every step. history::Step gains an origin (user or agent client). An agent step never joins a user step: the merge window compares origins, and an agent call never commits into a step a user gesture holds open.
  3. Busy instead of interference. While a pointer gesture is open, edit calls return busy with retry_after: "activity", and the agent calls wait. Reads are always served. An agent undo never cancels the user's drag, as a user undo does today.
  4. The agent undoes only itself. history.undo succeeds only when the newest step is the agent's; otherwise it returns not_agent_step with the label, and the host asks the user. The user's ⌘Z undoes anything, as now.
  5. Navigation is not journaled. Cursor, view, selection and focus stay out of undo, as the undo design decided. Agent navigation is reversible through go-back instead.
  6. Loud, structured errors. invalid_arguments (schema), unknown_signal with near matches, ambiguous with candidates, unknown_row, stale_revision, busy, paused, not_allowed, over_budget (the memory ledger refused a load) and not_agent_step. All are MCP tool results with isError, so the model can correct itself.
  7. Ambiguity goes back to the person. Hierarchy::find_* already distinguishes found, missing and ambiguous. The adapter returns candidates rather than guessing; the host asks, by voice if the user spoke. MCP's multi round-trip input requests can carry the choice where hosts support them.
  8. Long work becomes a task. A call that needs data not yet resident (a find over a signal that is not loaded, a transaction track, an open) waits up to 2 s for the load, then returns {task, status: "working", progress}. wait polls it, and MCP progress notifications and the tasks extension are used where the host supports them. Loads keep their current limits, generations and cancellation; a newer open makes an old task fail with superseded.

Voice

The host owns the microphone, transcription, turn detection, barge-in and any spoken reply; Volna never sees audio. Volna's part is to keep a spoken turn fast and unambiguous. Reads on resident data answer in milliseconds; every result begins with one sentence that can be read aloud; “this” resolves to the selection and “here” or “now” to the cursor, both in get_view. When the user interrupts, the host cancels the request, and a cancelled call that has not reached App::handle has no effect. Hosts that stream audio to a model (the Realtime API) reach Volna only through a local MCP connection or a tunnel; that route is deferred until a user needs it.

The tools

Fifteen tools cover the catalogue. A small set matters: VS Code caps a request at 128 tools, and OSWorld-MCP shows models fail to pick among many. Grouping by object keeps each schema readable. Annotations follow the kind: reads are readOnlyHint, view changes are idempotent, and nothing is destructiveHint because every edit is undoable. That lets Codex users choose default_tools_approval_mode = "writes" and approve edits while reads run freely. The demo implements the tools marked “demo”.

Deployment environments

Native (macOS, Linux, Windows)

With agents allowed, Volna listens on a Unix socket in a user-only runtime directory (a named pipe with an owner-only ACL on Windows) and writes a discovery record volna-agent-<pid>.json: trace path, window title, socket path and a random token. This is the LLDB registry and IDE lock-file pattern. volna-mcp is the stdio server a host starts. It reads the records, attaches to the viewer with the requested trace (or the most recently focused one), and relays MCP messages unchanged, since both sides speak the same JSON-RPC. With no viewer running, open starts volna --agent FILE.

Headless

volna-mcp --headless trace.vtr runs App without a frontend and serves the same tools. It answers trace questions in CI or in a terminal-only session, and it is the test harness for everything above.

VS Code

The extension registers the server with vscode.lm.registerMcpServerDefinitionProvider, so Copilot agent mode finds it with no configuration. Codex or Claude Code in the integrated terminal use the same discovery record, which the extension host writes. The extension host owns the socket (the webview's content security policy forbids connections) and forwards each message to the webview over the existing postMessage channel. The wasm side adds one export, control_message(json) → json, like Surfer's handle_wcp_cs_message. With a remote workspace, the data still comes from volna-server beside the file; control stays with the webview's core.

Web page

A browser page cannot listen. Automated tests drive control_message through the DevTools protocol. A standalone page connecting out to a local volna-mcp is deferred until someone needs it.

Verification, all headless

Every check below runs unattended in GitHub Actions, provisions its own trace, processes and browser, and asserts rather than inspects. No test needs a desktop, a signed-in host or a model.

  1. Catalogue coverage (volna-core/tests/control.rs). Every Command and Action variant is either built by a catalogue entry or listed in an exclusion table with its reason, so a new command cannot silently miss the agent surface. Every entry's schema accepts its examples and rejects wrong types.
  2. Shared-control model test. The seeded random-command generator of tests/history.rs interleaves user commands, open and closed gestures and agent calls on examples/landing.vtr. After each step it asserts that agent steps carry the agent origin and never merge with user steps, that an edit during a gesture returns busy and changes nothing, that history.undo refuses user steps, that undo restores the workspace projection, and that reads never change the revision.
  3. Read fidelity. For random rows and times, get_view values equal the text the painter draws in the value column (from the Scene), and read_values and find agree with vtr value and vtr changes on the same file.
  4. MCP conformance (volna-mcp tests). A scripted client speaks both revisions: initialize for 2025-11-25 and server/discover with per-request metadata for 2026-07-28. It checks tool lists against the catalogue, schemas, isError results, progress, cancellation before dispatch, and tasks.
  5. End to end, native. A Node test starts volna-mcp --headless over stdio and runs the scenarios above as tool sequences with assertions on results. A GPUI TestAppContext test attaches through the socket relay and injects simulated user input between agent calls (Linux CI, like the existing undo_ tests).
  6. End to end, web and VS Code. The headless-Chrome harness (volna/volna/tools/browser-test.mjs) loads the wasm build, sends control_message calls and synthetic mouse and key events through the DevTools protocol, and asserts the shared result. The extension's Node tests cover the socket-to-postMessage relay with a fake webview.
  7. Latency. The headless end-to-end test measures each read and edit on landing.vtr and fails above the budgets in the plan.
  8. Hosts, as smoke tests only. A job may run codex exec or claude -p against the headless server where credentials exist. It is informative, never a gate, because model output is not deterministic.

This page's demo has its own self-test (the line under the demo) and a headless test, docs/tests/volna-mcp.test.mjs, run by .github/workflows/volna-mcp.yml.

Risks and open questions

Risks

  • MCP churn. The 2026-07-28 revision removed the handshake and sessions, and Claude Code's channels do not yet accept servers that negotiate it. Keeping the adapter thin and testing both revisions contains the cost; the catalogue does not depend on either.
  • Surprising the user. An agent that moves the view while the user reads is disruptive. Go-back, the status chip and pause are the mitigations; whether navigation should wait for a quiet moment needs trying with users.
  • Local security. Any local process that can read the discovery record can drive the viewer. User-only permissions, a token, agents off by default and a per-connection prompt follow Unity and Chrome, but the trust model is only as good as the user account.
  • Tool choice. Fifteen grouped tools may still be picked poorly. The server's instructions text and schema descriptions carry the guidance; tool-choice logs from the smoke tests should inform the grouping.
  • Result size. Large panels and long change lists can exceed host limits (Claude Code's 25k tokens, Codex's per-tool output limit). Caps with counts (“first 20 of 3,112 changes”) are part of every schema.

Open questions

  • Should the agent get its own panel by default (the UFO2 picture-in-picture idea) or act in the user's focused panel? This proposal acts in the user's panel and makes a separate panel one panels call away.
  • How long should an edit wait for a gesture before it returns busy: immediately, as proposed, or for a short grace period?
  • Can the undo design's merge rules stay unchanged when two agents are attached, or does each client need its own origin in the merge key? The proposal gives each client its own origin.
  • Where does the VS Code extension host run in remote workspaces, and does the discovery record reach a Codex process on the other side?
  • Will Codex consume progress notifications or the tasks extension? Until it does, wait polling is the portable path.
  • Which of the marker proposal's verbs (reference, measure) should be tools in the first stage?
